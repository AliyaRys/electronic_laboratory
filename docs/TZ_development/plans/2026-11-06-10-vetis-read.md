# ВетИС: получение входящих Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Последним блоком подключить разрешённое read-only получение входящих транспортных эВСД непосредственно из production через профиль ВУ.

**Architecture:** Изолированный Zeep adapter реализует ports DATA-06; PostgreSQL outbox и arq worker того же backend image. Кнопка «Обновить» запускает чтение от личного initiator врача/заведующего.

**Tech Stack:** Zeep4.3.3, SOAP ВУ, arq/Redis, PostgreSQL.

**Spec:** API-04/10, DATA-02/05/06, INPUT-01, ADR-018. Зависит O01–03 и локальных модулей.

## Global Constraints

- «Только ветеринарные управления, mercury-vu.service; нет fallback на сервис ХС».
- Production-подключение проекта строго read-only: `VETIS_WRITE_ENABLED=false` не временный этап, а обязательный release-gate O-11.
- Неработающий read-метод тестового контура не разрешает использовать production для проверки гашения/возврата.
- «Автономный опрос от общего аккаунта не вводится».
- Production WSDL/serviceId/endpoint/namespace неизвестны до получения зарегистрированного профиля; не конструировать по URL wiki и не переносить значения тестового контура.
- Manifest ВУ для `mercury-vu.service` и локальное зеркало ProductService — разные контракты. Таблица `mercury_product_guid_lvl_2` уже содержит исходный pilot-снимок 28 продуктов второго уровня; перед production-чтением он не считается автоматически production-справочником и публикуется раздельно по contour.
