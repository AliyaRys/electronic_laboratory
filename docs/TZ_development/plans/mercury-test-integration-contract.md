# Контракт интеграции с тестовым Меркурием

Дата фиксации: 09.11.2026. Основание: решение владельца O-12, локальные
успешные примеры `API REQUESTS.txt`, официальный справочник Россельхознадзора
для [GetVetDocumentListOperation v2](https://help.vetrf.ru/wiki/GetVetDocumentListOperation_v2)
и [ProcessIncomingConsignment v2](https://help.vetrf.ru/wiki/ProcessIncomingConsignment_v2).

Сырой файл примеров и файл credentials не входят в Git. В код и тесты попадают
только обезличенные fixtures без apiKey, issuerId, логинов, паролей, реальных
UUID/GUID участников и персональных данных.

## 1. Закреплённый профиль ВУ

| Параметр | Значение/правило |
| --- | --- |
| Контур | Тестовый ВетИС |
| Семейство | Профиль ветеринарных управлений |
| Endpoint | `https://api2.vetrf.ru:8002/platform/services/2.0/ApplicationManagementService` |
| WSDL-кандидат | тот же адрес с `?wsdl`; V01 загружает, проверяет и фиксирует checksum вместе со всеми XSD imports |
| `serviceId` | `mercury-vu.service:2.0` |
| business namespace | `http://api.vetrf.ru/schema/cdm/mercury/vu/applications/v2` |
| SOAP | SOAP 1.1, `Content-Type: text/xml; charset=utf-8` |
| submit action | `submitApplicationRequest` |
| result action | `receiveApplicationResultRequest` по `applicationId` |

Реквизиты `gateway login/password`, `user_login`, `issuer_id`, `apiKey` и scope
площадки загружаются из server-side secret-файла установки. Они не являются
полями manifest и никогда не возвращаются frontend. Логин базовой
аутентификации, инициатор бизнес-операции и issuer — разные значения.

## 2. Получение входящих эВСД

Запрос задаёт текущую площадку Агропромышленного парка,
`vetDocumentType=INCOMING`, `vetDocumentStatus=CONFIRMED`, `count<=1000` и
`offset`. Система обходит страницы до `offset + count >= total`. При
использовании `issueDateInterval` один интервал не превышает 31 день.

Операция не предоставляет фильтр `productType` на уровне запроса. Поэтому
после получения и до создания локальной партии применяется обязательный
предикат:

```text
получатель = закреплённая площадка
AND vetDType = TRANSPORT
AND vetDStatus = CONFIRMED
AND certifiedConsignment.batch.productType = 1
```

Документы с иным `productType` не попадают в мясной MVP. Проход при этом не
считается ошибочным: сохраняются обезличенные счётчики отфильтрованных записей
и причина фильтра, но не создаётся поступление. Отсутствующее/неразбираемое
значение не приравнивается к `1`.

Для каждого принятого в MVP документа сохраняются raw XML, UUID эВСД,
`lastUpdateDate`/доступная внешняя версия, checksum и нормализованный снимок.
Повторный UUID обновляет источник без дубликата. Ошибка или неполная страница
не превращается в пустой успешный проход и не двигает checkpoint.

### Имена и идентификаторы

Каждый объект сохраняется со своим `guid`, `uuid` и `name`, если они пришли в
этом эВСД. В частности, отдельно сохраняются:

- `batch.product` — второй уровень;
- `batch.subProduct` — третий уровень;
- `batch.productItem` — номенклатура производителя;
- единица, упаковка, участники и площадки — их собственные `name`.

Frontend показывает `name` соответствующего объекта из закреплённого снимка.
Он не подменяет имя второго уровня именем номенклатуры и не выполняет SOAP
вызов справочника при каждом чтении. Отсутствие общего локального справочника
или неизвестный там GUID не блокирует импорт, если source `name` присутствует.
Если обязательное имя отсутствует и его нельзя получить из самого ответа,
пользователь видит «Название не получено», а технический ID доступен только в
защищённой диагностике.

Таблица `mercury_product_guid_lvl_2`, уже созданная предыдущими задачами,
перестаёт быть источником UI-названия. До отдельной миграции она может
оставаться compatibility-хранилищем четырёх policy-флагов обязательной
трихинеллоскопии. V01 обязан обновить нормализатор и тесты так, чтобы новый
входящий source `name` сохранялся, а промах общего справочника не отклонял
документ.

## 3. Гашение: вход пользователя → XML

Гашение реализуется как полноценная пользовательская функция: preview,
подтверждение, реальный submit, poll и reconcile. Этот раздел запрещает
ИИ-агенту выполнять живой вызов для проверки, но не разрешает заменить
функцию заглушкой.

До построения preview система закрепляет UUID и checksum версии входящего
эВСД, проверяет текущий статус, получателя, единицы и права инициатора. Из
интерфейса требуются три независимых результата:

| Действие пользователя | XML |
| --- | --- |
| Данные документа соответствуют факту | `docInspection/result=CORRESPONDS` |
| Есть допустимое расхождение | `docInspection/result=MISMATCH`, плюс `info` и для принятия всей/части — `discrepancyReport` |
| Документарная проверка не проводилась, если сценарий это допускает | `docInspection/result=UNSUPERVISED` |
| Ветосмотр проведён, груз соответствует | `vetInspection/result=CORRESPONDS` |
| Ветосмотр проведён, груз не соответствует | `vetInspection/result=MISMATCH` |
| Ветосмотр не проводился | `vetInspection/result=UNSUPERVISED` |
| Принять всё фактически прибывшее | `decision=ACCEPT_ALL` |
| Принять часть и немедленно вернуть часть | `decision=PARTIALLY` |
| Вернуть всю прибывшую партию | `decision=RETURN_ALL` |

`responsible/login` берётся из проверенной привязки текущего уполномоченного
пользователя Меркурия, а не из gateway login и не из редактируемого поля UI.
`vetCertificatePresence=ELECTRONIC`. Для электронного сертификата в
`delivery/accompanyingForms/vetCertificate` достаточно UUID исходного эВСД;
остальные сведения Меркурий читает из документа.

### Матрица шести сценариев

| Сценарий | `docInspection` | `decision` | Принятая `delivery/consignment` | `discrepancyReport` | `returnedDelivery` |
| --- | --- | --- | --- | --- | --- |
| 1.1.1 соответствует, принять всё | `CORRESPONDS` | `ACCEPT_ALL` | фактически принятое | нет | нет |
| 1.1.2 соответствует, принять часть | `CORRESPONDS` | `PARTIALLY` | принятая часть | нет | возвращаемая часть |
| 1.1.3 соответствует, вернуть всё | `CORRESPONDS` | `RETURN_ALL` | не передаётся | нет | вся прибывшая партия |
| 1.2.1 расхождение, принять всё | `MISMATCH` | `ACCEPT_ALL` | фактически принятое | обязателен | нет |
| 1.2.2 расхождение, принять часть | `MISMATCH` | `PARTIALLY` | принятая часть | обязателен | возвращаемая часть |
| 1.2.3 расхождение, вернуть всё | `MISMATCH` | `RETURN_ALL` | не передаётся | не передаётся | вся прибывшая партия |

`vetInspection` во всех шести строках определяется фактическим действием
пользователя и не выводится автоматически из `docInspection` или решения.

Допустимые для принятия расхождения по официальному описанию: номер/дата ТТН,
номер транспортного средства, объём, срок годности, маркировка и
`productItem`. Иное критическое расхождение не превращается автоматически в
акт: принятие блокируется до получения подтверждённого правила API.

При отсутствии расхождений допустима погрешность объёма до 5% включительно.
Для `PARTIALLY` принятая и возвращаемая части положительны; их сумма описывает
фактически прибывшую партию. Недоставленный объём не становится возвратом.
При расхождении более 5% и принятии всей/части нужен акт. В
`discrepancyReport` должно присутствовать хотя бы `reason` или `description`.

Возврат в этой операции — немедленная отправка исходному отправителю тем же
транспортным средством. Другой транспорт или более позднее перемещение —
отдельный транспортный эВСД и не реализуется этой кнопкой.

## 4. Асинхронность и доказательство результата

`submitApplicationRequest` возвращает принятие заявки и `applicationId`, а не
успешное гашение. Завершение определяется только результатом
`receiveApplicationResultRequest` и проверкой бизнес-ответа. При таймауте или
потере ответа submit не повторяется вслепую; состояние остаётся `UNKNOWN` до
reconcile. Только подтверждённый `CONFIRMED` открывает дальнейший маршрут.

## 5. Реализация и безопасная проверка

- V01/V02 могут выполнять согласованное чтение тестового контура и повторный
  read-проход, не изменяющий внешние данные.
- W01/W02/W03 обязаны реализовать production-код реального transport и UI
  enabled-state. Для проверки используются обезличенные копии шести сценариев,
  XSD validation, snapshot/contract tests и transport spy с
  `external write calls = 0`.
- Ни одна автоматическая проверка не вызывает `ProcessIncomingConsignment`.
- `VETIS_WRITE_ENABLED=false` является безопасным значением установки и
  остаётся неизменным во время работы агентов. При false API отказывает до
  outbox/сети; при true рабочий маршрут отправляет запрос только после явного
  подтверждения уполномоченного пользователя.
- Оператор включает capability после решения владельца. Агент не выполняет
  первый живой submit и не использует текущие credentials/эВСД для проверки.
