# Проверка пакета ТЗ

Дата: 06.11.2026. Проверяется документация для разработки, а не промышленное приложение.

## Состав и воспроизводимая проверка

11 последовательных планов, 31 задача с файлами/интерфейсами/пятью шагами проверки и сдачи. Общие приложения задают модель данных, REST, все поля, права, входные параметры, UI-сопоставления и трассировку. Команда из C:\journal:

```powershell
python docs/superpowers/plans/validate_docs.py
```

Проверка требует 11 планов, уникальные задачи, обязательные секции writing-plans, Files/Interfaces и пять checkboxes на задачу; проверяет локальные Markdown-ссылки/якоря, ровно 81 FT,82 поля,101 SC,25 AT без пропусков/дубликатов, checksum исходного baseline. При изменении источников проверка требует повторно сверить ТЗ, а не автоматически переписать manifest.

`sources-manifest.json` содержит SHA-256 всех 32 файлов ADR, актуальных верхнеуровневых документов ФТ v2.0 и UI-контрактов/инструкций/архива. Все 21 верхнеуровневых файла распакованной ФТ v2.0 побайтно совпали с соответствующими файлами архива ФТ-v2.0.zip. Старая ФТ v1 не использована как действующее требование по совпадающему номеру.

## Самопроверка содержания

Проверено соответствие:

- ADR1.1/ФТ v2/O/R → SPEC-01; scope исключений сохранён.
- ADR001–014/024 → I/F/O; новый React-клиент отделён от старых HTML и API компонентов.
- ADR015–017 → DATA/SPEC/A/S/E; независимые UUID, UNIQUE партии/номера, снимки, отсутствие draft/history, блокировки/revision/key, полночь после lock.
- ADR018/019 и O-12 → V/W; 15-минутный test read ВУ, подтверждённый endpoint плюс pinned WSDL/XSD manifest, `productType=1`, source `name`, выделенная read identity, шесть write-сценариев на офлайн-адаптере, UNKNOWN без слепого submit; внешний transport блокирует write, будущий submit требует нового указания владельца и owner authorization.
- ADR020 → C/E; Decimal, ROUND_HALF_UP, прежние price/norm, ярмарочный 0 без скрытого обычного тарифа.
- ADR021/022 → R/D; точные строки 5-вет, signed session payload, snapshot не пересчитывается, два основания заключения, одинаковый вывод/печать.
- ADR023 → E03/O02; DELETE remote WAL flush,503 до commit/UNKNOWN при разрыве, restore без возвращения удалённых карточек; обычный save local commit.
- Каждый FT имеет задачи и исходный критерий, каждый CHK/VSE имеет DTO/хранилище/проверку/владельца. Все SC/AT назначены адресно; O приоритетнее старой формулировки SC.

Проверка типов и зависимостей: внутренние сервисы используют один UoW без commit; координатор ВСЭ вызывает готовые pricing/sample contracts; SOAP-типы не выходят из adapter; mutations не получают readonly server-поля. SampleSelection NEW/REUSE/EDIT совпадает в API/DATA/E/S. ReceiptEvidence принимает только служебная confirm-команда, production fixture endpoints нет. HMAC привязан к session/actor/lab/period, form/rule/mapping версии сохраняются в отчёте.

При самопроверке уточнены: отдельная таблица прав по действиям; идентификация участников в field mapping включает группу и название; нулевая доставка не возвращает отсутствующий груз; неполные сохранённые данные отчёта не подменяются новым расчётом; совместимость baseline проверяется при реализации, версии не обновляются молча.

## Граница результата

Реализация приложения, миграции, Compose/CI и production-конфиги не созданы. Документы описывают будущие файлы. Код validate_docs.py проверяет только документацию. Чужие изменения, исходные ADR/ФТ, макеты и каталог компонентов не изменены. Коммиты не создавались.

Storybook, UI/сценарные тесты приложения, frozen-install, живой read ВетИС, нагрузка и restore этой документационной правкой не выполнялись. Test credentials и успешные XML предоставлены локально, но не использовались для сетевых запросов и не входят в Git. Живое гашение не является тестом действующего плана: оно запрещено O-12. W03 доказывает только test-read UI, отсутствие write-вызовов и офлайн-корректность контракта; fixtures не разрешают внешнюю приёмку.
