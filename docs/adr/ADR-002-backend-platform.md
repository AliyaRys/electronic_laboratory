# ADR-002: Backend развивается от закреплённого форка FastAPI

- **Статус:** Accepted — архитектурное решение принято автором по прямому поручению владельца продукта 06.11.2026.
- **Дата:** 2026-11-06
- **Ответственность:** агент-разработчик реализует и проверяет решение; аналитик отвечает за изменение продуктовых правил. Дополнительное согласование архитектуры не требуется.
- **Связанные:** [ADR-001](ADR-001-postgresql.md); [трассировка](traceability.md).
- **Основание:** ФТ v2.0: FT-COM-05/08; adr_request §4–6; [исходные требования](../../%D0%A4%D1%83%D0%BD%D0%BA%D1%86%D0%B8%D0%BE%D0%BD%D0%B0%D0%BB%D1%8C%D0%BD%D1%8B%D0%B5%20%D1%82%D1%80%D0%B5%D0%B1%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F/v2.0/README.md).

## Контекст
Новая система разрабатывается командой Python/TypeScript. Фактический форк проверен через git, а не по описанию upstream.

## Решение
**Accepted:** источник https://gitverse.ru/a9v/FastAPI-boilerplate.git; uv, FastAPI, SQLAlchemy и Alembic сохраняются. Установка uv sync --frozen; образы по SHA/digest, non-root.

**Принятое решение:** исходная точка 4deb9c45f4298d4a84f005126f6ee8ccd823acf8 (HEAD/main проверен 06.11.2026). LICENSE.md — MIT, copyright и текст лицензии сохраняются. Это лицензия исходника, не заключение по всем транзитивным зависимостям.

Сохраняются uv.lock, Alembic, async SQLAlchemy, crudauth для аутентификации, инфраструктура тестов/pre-commit. require_permissions заменяется единым делегированием авторизации в Casbin: независимого второго разрешающего механизма нет. Удаляются демонстрационные tier/публичная регистрация, Faker-данные, SQLAdmin с обходом предметных правил, Memcached/SQLite, неиспользуемые брокеры. Форк фактически содержит Taskiq, не arq: переход на arq принят в ADR-005. Python 3.15.2 выбран для новой среды. Установка и тесты закреплённых зависимостей — обязательный критерий первого платформенного этапа; это проверка реализации, не ожидание согласования архитектуры. Изменять baseline lock без отдельного upgrade-коммита запрещено.

Раз в месяц назначенная задача сопровождения для агента-разработчика проверяет diff upstream benavlabs; агент переносит исправления cherry-pick с тестами и журналом происхождения. Массовый merge и автоматическое обновление uv.lock запрещены. Версии форка и свежие версии реестров разделены в README.

## Рассмотренные альтернативы
1. Переписать backend с нуля: меньше наследуемого кода; нарушает исходное решение и добавляет собственную инфраструктуру — отклонено.
2. Автоматически следовать main upstream: быстро получать исправления; непредсказуемо меняет API и безопасность — отклонено.

## Последствия
- Решение сохраняет указанные продуктовые ограничения и задаёт проверяемую границу реализации.
- **Риск/цена:** Форк несёт функциональность вне MVP; совместимость Python 3.15.2 с закреплённым набором пока не проверена.
- Изменение архитектуры оформляется замещающим ADR с причиной и проверкой; изменение продуктового правила согласуется с аналитиком и отражается в ФТ.

## Проверка
Перед реализацией сохранить baseline SHA и license inventory; после удаления демонстрационных модулей выполнить auth smoke и все backend gates; обновление lock — самостоятельный PR.

## Открытые вопросы
Незакрытых архитектурных решений нет. Применимые значения настройки и внешние данные перечислены в [контракте входных данных](deployment-and-input-contracts.md); их заполнение не требует повторного выбора архитектуры.
