# ADR-003: Async SQLAlchemy и Alembic управляют данными

- **Статус:** Accepted — архитектурное решение принято автором по прямому поручению владельца продукта 06.11.2026.
- **Дата:** 2026-11-06
- **Ответственность:** агент-разработчик реализует и проверяет решение; аналитик отвечает за изменение продуктовых правил. Дополнительное согласование архитектуры не требуется.
- **Связанные:** [ADR-002](ADR-002-backend-platform.md); [трассировка](traceability.md).
- **Основание:** ФТ v2.0: FT-COM-05/06, FT-SMP-07; [исходные требования](../../%D0%A4%D1%83%D0%BD%D0%BA%D1%86%D0%B8%D0%BE%D0%BD%D0%B0%D0%BB%D1%8C%D0%BD%D1%8B%D0%B5%20%D1%82%D1%80%D0%B5%D0%B1%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F/v2.0/README.md).

## Контекст
Форк использует async SQLAlchemy/asyncpg; рабочие операции связаны транзакциями. Миграции нескольких реплик не должны конкурировать.

## Решение
**Accepted:** SQLAlchemy 2.x, Alembic — единственный путь изменения схемы; alembic upgrade head запускается one-shot сервисом с profiles: ["migrate"] до обновления API, не в entrypoint.

**Принятое решение:** AsyncSession на единицу работы; сессии не разделяются между конкурентными задачами. Версии SQLAlchemy/asyncpg/Alembic первоначально остаются из uv.lock. Commit выполняет прикладная операция, не каждый repository. Изоляция READ COMMITTED с явными блокировками агрегатов; REPEATABLE READ для формирования отчёта. CAS-ревизия защищает пользовательскую правку. Долгая сеть не выполняется внутри транзакции. Отдельный ограниченный sync-пул адаптера Casbin не используется для предметных записей.

DDL выполняется по expand/contract: сначала совместимая схема, затем приложение, удаление старых полей отдельным релизом. create_all в production запрещён. Необратимая миграция требует проверенной копии и плана roll-forward.

## Рассмотренные альтернативы
1. Sync ORM для всего API: проще адаптер Casbin; блокирующий I/O усложняет конкурентные запросы и расходится с форком — отклонено.
2. Автоматическое create_all при старте: удобно локально; нет контролируемой истории изменения данных — отклонено.

## Последствия
- Решение сохраняет указанные продуктовые ограничения и задаёт проверяемую границу реализации.
- **Риск/цена:** Явные блокировки требуют единого порядка и контроля deadlock; downgrade не обещает восстановление утраченных данных.
- Изменение архитектуры оформляется замещающим ADR с причиной и проверкой; изменение продуктового правила согласуется с аналитиком и отражается в ФТ.

## Проверка
На эфемерном PostgreSQL выполнить upgrade head с нуля и с предыдущей схемы; проверить две конкурентные записи и rollback всех зависимых изменений.

## Открытые вопросы
Незакрытых архитектурных решений нет. Применимые значения настройки и внешние данные перечислены в [контракте входных данных](deployment-and-input-contracts.md); их заполнение не требует повторного выбора архитектуры.
