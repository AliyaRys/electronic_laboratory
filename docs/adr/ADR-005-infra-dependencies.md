# ADR-005: Redis и arq обслуживают фоновые задачи без хранения бизнес-истины

- **Статус:** Accepted — архитектурное решение принято автором по прямому поручению владельца продукта 06.11.2026.
- **Дата:** 2026-11-06
- **Ответственность:** агент-разработчик реализует и проверяет решение; аналитик отвечает за изменение продуктовых правил. Дополнительное согласование архитектуры не требуется.
- **Связанные:** [ADR-004](ADR-004-authn-authz.md); [трассировка](traceability.md).
- **Основание:** ФТ v2.0: FT-ARR-01/14, FT-COM-05/07; [исходные требования](../../%D0%A4%D1%83%D0%BD%D0%BA%D1%86%D0%B8%D0%BE%D0%BD%D0%B0%D0%BB%D1%8C%D0%BD%D1%8B%D0%B5%20%D1%82%D1%80%D0%B5%D0%B1%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F/v2.0/README.md).

## Контекст
Заявки ВетИС завершаются отдельно от HTTP запроса. Очередь может повторить задачу и потерять сообщение. Фактический форк содержит Taskiq.

## Решение
**Принятое решение о замене технологии:** сохраняем Redis как инфраструктурную зависимость; заменяем Taskiq на arq 0.28.0, уже предусмотренный adr_request. Для сервера Redis выбран 8.10.3-alpine3.23, digest в README. Python redis первоначально из uv.lock; совместимость Redis/arq проверяется установкой и интеграционным smoke на платформенном этапе. Taskiq, RabbitMQ-адаптеры и их конфигурация удаляются после проверки отсутствия использований.

До подключения ВетИС Redis хранит сеансы crudauth и общий rate-limit входа; при его отказе вход и защищённые запросы закрываются ошибкой 503. Для очереди, сеансов и лимитов используются отдельные key-prefix; настроены AOF appendfsync everysec и noeviction. Потеря Redis требует повторного входа; задания восстанавливаются из PostgreSQL outbox. На последнем этапе добавляется worker из того же backend-образа. PostgreSQL outbox хранит задания и состояние операций; Redis содержит транспорт сеансов, доставку задач и технический лимит; роли и предметные факты всегда читаются из PostgreSQL. Периодический dispatcher повторно ставит незавершённые записи; worker берёт lease и сверяет БД перед действием. Восстановление Redis не доказывает повторяемость SOAP-команды. Кеш медицинских данных и кеш разрешений не вводятся.

## Рассмотренные альтернативы
1. Сохранить Taskiq: меньше изменений форка; сохраняет второй брокерный стек сверх выбранного arq — отклонено этой записью.
2. Выполнять SOAP в web-request: меньше сервисов; разрыв соединения теряет управляемое ожидание результата — отклонено.

## Последствия
- Решение сохраняет указанные продуктовые ограничения и задаёт проверяемую границу реализации.
- **Риск/цена:** Добавляются Redis/worker и миграция Taskiq; Для установки Redis 8 выбран по ветке AGPLv3 [доступного лицензирования Redis](https://redis.io/legal/licenses/), без модификации Redis и без предоставления внешнего Redis-сервиса. Текст выбранной лицензии и notices включаются в поставку. Предоставление модифицированного Redis или публичного managed-сервиса вне принятого способа использования потребует отдельного ADR.
- Изменение архитектуры оформляется замещающим ADR с причиной и проверкой; изменение продуктового правила согласуется с аналитиком и отражается в ФТ.

## Проверка
Остановить Redis/worker до и после фиксации outbox: команда не теряется; повтор доставки не повторяет подтверждённое действие; отказ лимитера не открывает неограниченный вход.

Незакрытых архитектурных решений нет. Применимые значения настройки и внешние данные перечислены в [контракте входных данных](deployment-and-input-contracts.md); их заполнение не требует повторного выбора архитектуры.
