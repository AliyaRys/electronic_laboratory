# ADR-006: OpenAPI задаёт REST-контракт и единый формат ошибок

- **Статус:** Accepted — архитектурное решение принято автором по прямому поручению владельца продукта 06.11.2026.
- **Дата:** 2026-11-06
- **Ответственность:** агент-разработчик реализует и проверяет решение; аналитик отвечает за изменение продуктовых правил. Дополнительное согласование архитектуры не требуется.
- **Связанные:** [ADR-005](ADR-005-infra-dependencies.md); [трассировка](traceability.md).
- **Основание:** ФТ v2.0: FT-COM-01–08, FT-ARR-14; [исходные требования](../../%D0%A4%D1%83%D0%BD%D0%BA%D1%86%D0%B8%D0%BE%D0%BD%D0%B0%D0%BB%D1%8C%D0%BD%D1%8B%D0%B5%20%D1%82%D1%80%D0%B5%D0%B1%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F/v2.0/README.md).

## Контекст
Фронтенд не должен угадывать поля, числовую точность и неизвестный внешний исход.

## Решение
**Accepted:** backend отдаёт /openapi.json; маршруты /api/v1; openapi-typescript генерирует типы; CI перегенерирует контракт и выполняет git diff --exit-code. Префикс одинаков в backend, nginx и Vite.

**Принятое решение:** JSON REST; явные команды complete, complete-waiting, delete, receipt и disposal вместо универсального обновления статуса. Спецификация содержит запросы, ответы, ошибки, авторизацию, идемпотентность и ревизию. paths включают полный /api/v1/…, servers содержит /; сгенерированные типы сохраняют эти пути, клиент использует пустой baseUrl без дублирования префикса. День — ISO date, момент — ISO 8601 с timezone, Decimal — строка, идентификаторы/коды/номера — строки. Списки page/page_size=20, устойчивый порядок created_at DESC, id DESC.

Ошибки application/problem+json: type/title/status/detail/instance, code, trace_id, errors с путём поля; локализованное сообщение не заменяет стабильный code. 401 — нет сеанса; 403 — известный запрет; 404 — отсутствующий/чужой объект без раскрытия; 409 — конфликт ревизии, дубль, неопределённая незавершённая команда; 422 — валидация; 503 — недоступность зависимости. Принятая фоновая операция отвечает 202 с operation_id, не успешной приёмкой. Актуальные права проверяются и при повторе. Версия v1 меняется совместимо; breaking change получает v2 с отдельным сроком перехода.

## Рассмотренные альтернативы
1. Ручные TS-интерфейсы: быстро начать; дрейфуют от backend — отклонено.
2. HTTP 200 с success=false: единая оболочка; скрывает отказ и ломает сетевое поведение клиента — отклонено.

## Последствия
- Решение сохраняет указанные продуктовые ограничения и задаёт проверяемую границу реализации.
- **Риск/цена:** OpenAPI не доказывает предметные инварианты; необходимы контрактные и сценарные проверки.
- Изменение архитектуры оформляется замещающим ADR с причиной и проверкой; изменение продуктового правила согласуется с аналитиком и отражается в ФТ.

## Проверка
Намеренно изменить поле API без генерации: drift-gate падает; клиент различает 202, 409 и 503; недопустимый pH получает errors с путём VSE-F25.

## Открытые вопросы
Незакрытых архитектурных решений нет. Применимые значения настройки и внешние данные перечислены в [контракте входных данных](deployment-and-input-contracts.md); их заполнение не требует повторного выбора архитектуры.
