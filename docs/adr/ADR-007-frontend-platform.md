# ADR-007: Новый клиент реализуется как TypeScript React Vite SPA

- **Статус:** Accepted — архитектурное решение принято автором по прямому поручению владельца продукта 06.11.2026.
- **Дата:** 2026-11-06
- **Ответственность:** агент-разработчик реализует и проверяет решение; аналитик отвечает за изменение продуктовых правил. Дополнительное согласование архитектуры не требуется.
- **Связанные:** [ADR-006](ADR-006-api-contract.md); [трассировка](traceability.md).
- **Основание:** ФТ v2.0: FT-COM-02/03/09/10; adr_request §4–5; [исходные требования](../../%D0%A4%D1%83%D0%BD%D0%BA%D1%86%D0%B8%D0%BE%D0%BD%D0%B0%D0%BB%D1%8C%D0%BD%D1%8B%D0%B5%20%D1%82%D1%80%D0%B5%D0%B1%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F/v2.0/README.md).

## Контекст
Рабочая папка содержит HTML/обычный JS и общие компоненты. Новое промышленное приложение задано как React SPA; перенос одного компонента не разрешает менять runtime макетов.

## Решение
**Accepted:** TypeScript React, Vite SPA, монорепозиторий backend/ frontend/ docs/; без SSR/Next.js. Один frontend-образ для сред, VITE_API_BASE_URL=/api/v1 без запечённых хостов.

**Принятое решение:** Node 26.13.0 LTS, npm 12.2.2, TypeScript 7.0.2, React/react-dom 19.3.1, Vite 8.3.6 (источники/дата — README). package-lock.json обязателен, установка npm ci, TS strict=true. Структура frontend/src: app, pages, features, entities, shared; импорты направлены к shared, предметные операции не размещаются в UI-kit. Сгенерированный API-клиент в shared/api.

Существующие макеты и globalThis API остаются в текущем виде. Новый frontend создаётся отдельной задачей после ревью ADR; соответствие экранов сверяется с FT v2, затем с действующими DESIGN/UX/STORYBOOK. Старые HTML-маршруты получают явную таблицу соответствия и совместимые переходы; молочная демонстрация не становится частью MVP. Граница переноса принята: промышленная React SPA создаётся в frontend/; HTML/JS остаются эталонными макетами. FT-COM-10 трактуется как сохранение компонентов/поведения макетов, а не запрет на заданную React-платформу нового приложения. Компоненты React и их stories используют одну новую каноническую реализацию; общий SVG-реестр импортируется через адаптер, без перерисовки. Таблица старый HTML URL → SPA route входит в frontend-ТЗ; ранее доступные адреса получают совместимые переходы на соответствующую сущность.

## Рассмотренные альтернативы
1. Переписать макеты на React в этой задаче: быстро унифицировать; нарушает документационный объём и AGENTS — отклонено.
2. Сделать production на старом JS: легче переносить экран; не соответствует обязательному стеку новой системы — отклонено.

## Последствия
- Решение сохраняет указанные продуктовые ограничения и задаёт проверяемую границу реализации.
- **Риск/цена:** Нужно отдельно согласовать перенос API компонентов и маршрутов; совместимость новых npm-пакетов ещё не доказана сборкой.
- Изменение архитектуры оформляется замещающим ADR с причиной и проверкой; изменение продуктового правила согласуется с аналитиком и отражается в ФТ.

## Проверка
При реализации npm ci и production build из чистого checkout; прямой URL/обновление страницы работают; один образ запускается с разными backend host.

## Открытые вопросы
Незакрытых архитектурных решений нет. Применимые значения настройки и внешние данные перечислены в [контракте входных данных](deployment-and-input-contracts.md); их заполнение не требует повторного выбора архитектуры.
