# ADR-014: Версии закрепляются с отдельным контролем обновлений

- **Статус:** Accepted — архитектурное решение принято автором по прямому поручению владельца продукта 06.11.2026.
- **Дата:** 2026-11-06
- **Ответственность:** агент-разработчик реализует и проверяет решение; аналитик отвечает за изменение продуктовых правил. Дополнительное согласование архитектуры не требуется.
- **Связанные:** [ADR-013](ADR-013-compose-and-environments.md); [трассировка](traceability.md).
- **Основание:** ФТ v2.0: adr_request §5–6; FT-COM-08; [исходные требования](../../%D0%A4%D1%83%D0%BD%D0%BA%D1%86%D0%B8%D0%BE%D0%BD%D0%B0%D0%BB%D1%8C%D0%BD%D1%8B%D0%B5%20%D1%82%D1%80%D0%B5%D0%B1%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F/v2.0/README.md).

## Контекст
Свежая версия реестра не доказывает совместимость с закреплённым форком. Продуктовые данные должны переживать обновление.

## Решение
**Accepted:** версии только из проверенных первоисточников; неизвестное помечается unverified. Lock форка не обновляется молча; uv sync --frozen, npm ci, image SHA/digest обязательны.

**Принятое решение:** таблица README различает проверенный свежий выпуск, выбранную исходную версию lock и выбранную версию нового пакета. Backend начинает с uv.lock указанного SHA; выравнивание на свежие версии — отдельный PR с compatibility matrix, миграцией и полным CI. Frontend новые версии из README закрепляет package-lock.json после проверки peer dependencies. Python 3.15.2 и Node 26.13.0 — выбранные runtimes. Совместимость доказывается frozen-install и CI на этапе реализации. Найденная несовместимость исправляется в отдельном upgrade-коммите с доказательством причины; автоматического перехода на произвольные версии нет.

Обновления проверяет агент сопровождения раз в месяц; критическая уязвимость получает внеочередной PR и оценку в течение 1 рабочего дня. Renovate/Dependabot не внедряются: они добавили бы отдельную поддерживаемую службу без необходимости для MVP. Проверка выполняется по первоисточникам при запуске задачи сопровождения; календарная задача задаётся эксплуатацией как часть поставки, автоматического merge нет. Major upgrade, новый брокер/ORM/UI-kit и изменение семантики API получают отдельный ADR. ADR устарел при EOL, несовместимом API, изменении продуктового инварианта, замене инфраструктуры. Старый ADR сохраняется со ссылкой на замену.

Перед релизом повторно проверяются актуальность digest, лицензии, уязвимости и поддержка runtime; восстановление после отката схемы не предполагается автоматически.

## Рассмотренные альтернативы
1. Обновлять всё автоматически: быстрые исправления; неконтролируемая совместимость — отклонено.
2. Навсегда оставить baseline: воспроизводимость; накапливает уязвимости и EOL — отклонено.

## Последствия
- Решение сохраняет указанные продуктовые ограничения и задаёт проверяемую границу реализации.
- **Риск/цена:** Таблица 06.11.2026 со временем устареет; наличие версии не означает успешную установку или готовый релиз.
- Изменение архитектуры оформляется замещающим ADR с причиной и проверкой; изменение продуктового правила согласуется с аналитиком и отражается в ФТ.

## Проверка
Чистый frozen-install, CI и миграционный прогон на каждом upgrade PR; версия образа восстанавливается по digest, не по плавающему тегу.

## Открытые вопросы
Незакрытых архитектурных решений нет. Применимые значения настройки и внешние данные перечислены в [контракте входных данных](deployment-and-input-contracts.md); их заполнение не требует повторного выбора архитектуры.
