# ADR-015: Модульный монолит изолирует предметные процессы и ВетИС

- **Статус:** Accepted — архитектурное решение принято автором по прямому поручению владельца продукта 06.11.2026.
- **Дата:** 2026-11-06
- **Ответственность:** агент-разработчик реализует и проверяет решение; аналитик отвечает за изменение продуктовых правил. Дополнительное согласование архитектуры не требуется.
- **Связанные:** [ADR-015](ADR-015-module-boundaries.md), [трассировка](traceability.md).
- **Основание:** ФТ v2.0: 00-specification, FT-ACC-03, FT-ARR-14, FT-COM-05.

## Контекст
Небольшая команда и единый рабочий цикл требуют транзакций без распределённой инфраструктуры. ВетИС должен развиваться и включаться отдельно.

## Решение
Backend — модульный монолит с PostgreSQL и отдельным процессом worker того же приложения. Предлагаемые модули backend/src/modules: identity (пользователи, сеансы, назначения), arrivals (партии, сверки, локальные факты приёмки), examinations (ВСЭ, исследования, итог), samples (отборы и утилизация), catalog_pricing (методики/нормы/тарифы), reporting (операционные показатели и снимки), documents (рендер заключения/отчёта), integrations/vetis (SOAP, внешний журнал операций, синхронизация). Общий инфраструктурный слой даёт БД, авторизацию, часы, логирование.

Модуль владеет изменением своих данных. Чтение для общего отчёта выполняет reporting через согласованные read-model/query; запись в чужой repository из маршрута запрещена. Сквозная прикладная команда координирует изменения в одной SQL-транзакции. VetIS предоставляет внутренние порты list_incoming, submit_receipt, get_operation, reconcile_receipt и нормализованные DTO; предметные модули не видят XML, credential и SOAP-типы. Отдельный модуль означает границу кода/контракта, не новый сетевой микросервис. Если позже понадобится независимое размещение, новый ADR определит извлечение.

Направление: браузер → frontend nginx → REST API → прикладная команда → предметные модули → PostgreSQL. Внешнее исполнение: outbox PostgreSQL → dispatcher/arq → VetIS adapter → SOAP ВетИС; результат через adapter возвращается в прикладную команду подтверждения. Права проверяются в API и повторно перед исполнением отложенной команды.

## Рассмотренные альтернативы
1. Микросервисы по каждому процессу: независимые релизы; распределяют сохранение ВСЭ/пробы/стоимости — отклонено для MVP.
2. Единый CRUD без модулей: быстро начать; XML и предметные правила расползаются по экранам — отклонено.

## Последствия
- Определена ответственность за данные и проверяемая граница операции.
- **Риск/цена:** Границы не обеспечиваются отдельными БД, поэтому требуются ревью импортов и запрет обхода прикладных команд.
- Реализация и ТЗ обязаны сохранить указанные инварианты и обработку отказов.

## Проверка
Архитектурная проверка импортов; замена VetIS adapter на контрактную модель не меняет код ВСЭ; API-процессы не выполняют SOAP напрямую.

## Открытые вопросы
Незакрытых архитектурных решений нет. Применимые значения настройки и внешние данные перечислены в [контракте входных данных](deployment-and-input-contracts.md); их заполнение не требует повторного выбора архитектуры.
