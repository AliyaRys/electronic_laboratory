# ADR-018: Модуль ВетИС использует SOAP-профиль ветеринарных управлений

- **Статус:** Accepted — архитектурное решение принято автором по прямому поручению владельца продукта 06.11.2026.
- **Дата:** 2026-11-06
- **Ответственность:** агент-разработчик реализует и проверяет решение; аналитик отвечает за изменение продуктовых правил. Дополнительное согласование архитектуры не требуется.
- **Связанные:** [ADR-015](ADR-015-module-boundaries.md), [трассировка](traceability.md).
- **Основание:** ФТ v2.0: FT-ARR-01/14, FT-ACC-11; INPUT-01; указания пользователя 06.11.2026.

## Контекст
Пользователь требует отдельную интеграцию для ВУ и откладывает её до завершения локальных модулей. Ссылки v2 описывают бизнес-операции, но не подтверждают точный доступный профиль ВУ.

## Решение
Интеграция реализуется последней, в два последовательных этапа: сначала только GetVetDocumentListOperation, затем отдельное включение ProcessIncomingConsignment. На первом этапе VETIS_WRITE_ENABLED=false; read-функция не посылает гашение/возврат. Отсутствие продуктивных credentials не задерживает разработку локальных модулей через внутренний контракт. В промышленном режиме без подключения показывается «Интеграция не настроена»; фиктивные поступления/подтверждения не создаются.

Профиль — ветеринарные управления: семейство mercury-vu.service, не mercury-g2b.service. Официальное описание различий подтверждает отдельные пространства имён и возможность фильтра ВУ businessMember; это историческое описание, не доказательство точной версии v2 ВУ. URL бизнес-операции с _v2 не используется как SOAP endpoint. Принятое правило подключения — versioned contract manifest ВУ: endpoint, serviceId, business schema version, WSDL и полный набор импортируемых XSD с SHA-256. Их значения берутся из зарегистрированного профиля подключения ВУ. Получение такого manifest — обязательная задача адаптера в ТЗ интеграции; это внешний параметр подключения, а не нерешённый выбор транспорта. Неподтверждённые сейчас строковые значения честно отмечены unverified в контракте входов; адрес и namespace из примера ХС не подставляются. Поддерживается только явно закреплённый manifest, его смена проходит контрактные тесты. Автоматического fallback на профиль ХС нет.

Выбран transport Zeep 4.3.3, отдельная новая зависимость этого ADR. SOAP/XML изолирован адаптером; ограничены размеры/таймаут, DTD/external entities выключены, TLS проверяется; WSDL/XSD закрепляются по checksum, внешние schema imports ограничиваются утверждённым набором. Credentials (gateway login/password, apiKey, issuerId по профилю) доступны только серверу; initiator — отдельный личный логин, связанный с локальным сотрудником. На первом интеграционном этапе синхронизацию запускает врач/заведующий кнопкой «Обновить» в своей лаборатории; job продолжает чтение от имени этого сотрудника с его личным внешним initiator. Автономный опрос от общего аккаунта не вводится. Перед каждой SOAP-заявкой повторно проверяются активность сотрудника и его область. Нет личного initiator — 422 INTEGRATION_INITIATOR_MISSING, нет связи лаборатория→ХС/площадка — 422 INTEGRATION_SCOPE_MISSING; ввод сверки сохраняется.

Получение списка выполняется с явной областью ХС/площадки лаборатории, входящим транспортным назначением и допустимыми статусами. Бизнес-фильтр — входящий документ, получатель текущей площадки, транспортное происхождение, поддержанная мясная классификация; значения enum и возможности серверной фильтрации берутся из закреплённого manifest. Условия, которые профиль не умеет сочетать, дополнительно проверяются локально до записи партии. Нельзя заменять этот предикат одним enum INCOMING и считать его транспортным происхождением. Все страницы обрабатываются с дедупликацией и повторной сверкой изменений; отсутствие строки не считается аннулированием. Checkpoint обновляется только после согласованного сохранения полного прохода, неуспешный проход помечается неполным; врач видит время последней успешной синхронизации. Нормализованный снимок хранит внешние идентификаторы, статус, участников, классификацию, единицы и прежнюю ВСЭ; местные факты не затираются.

Источники: [получение v2](https://help.vetrf.ru/wiki/GetVetDocumentListOperation_v2), [гашение v2](https://help.vetrf.ru/wiki/ProcessIncomingConsignment_v2), [различия ВУ/ХС](https://help.vetrf.ru/wiki/Различия_в_запросах_от_хозяйствующих_субъектов_и_ветеринарных_управлений), проверены 06.11.2026. Конкретные XML-элементы из примеров ХС не переносятся в ВУ автоматически.

## Рассмотренные альтернативы
1. SOAP из браузера: быстрее прототип; раскрывает секреты и обходит централизованное подтверждение — отклонено.
2. Сразу сервис ХС из примера v2: есть готовые XML; не отвечает требуемому профилю ВУ — отклонено.

## Последствия
- Определена ответственность за данные и проверяемая граница операции.
- **Риск/цена:** Без зарегистрированного manifest/секретов адаптер остаётся выключен; архитектура задаёт их проверку, но не выдумывает выданный оператором endpoint. Совместимость Zeep подтверждается контрактными проверками реализации.
- Реализация и ТЗ обязаны сохранить указанные инварианты и обработку отказов.

## Проверка
Контрактная проверка пагинации, повторов, namespace и доступа площадки; обновление одного документа без дубликата; этап чтения технически не имеет доступной write-команды.

## Открытые вопросы
Незакрытых архитектурных решений нет. Применимые значения настройки и внешние данные перечислены в [контракте входных данных](deployment-and-input-contracts.md); их заполнение не требует повторного выбора архитектуры.
