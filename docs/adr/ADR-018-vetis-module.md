# ADR-018: Модуль ВетИС использует SOAP-профиль ветеринарных управлений

- **Статус:** Accepted — архитектурное решение принято автором по прямому поручению владельца продукта 06.11.2026.
- **Дата:** 2026-11-06; уточнено решением владельца O-12 от 2026-11-09
- **Ответственность:** агент-разработчик реализует и проверяет решение; аналитик отвечает за изменение продуктовых правил. Дополнительное согласование архитектуры не требуется.
- **Связанные:** [ADR-015](ADR-015-module-boundaries.md), [трассировка](traceability.md).
- **Основание:** ФТ v2.0: FT-ARR-01/14, FT-ACC-11; INPUT-01; указания пользователя 06.11.2026.

## Контекст
Пользователь требует отдельную интеграцию для ВУ и откладывает её до завершения локальных модулей. Ссылки v2 описывают бизнес-операции, но не подтверждают точный доступный профиль ВУ.

## Решение
Интеграция подключается к выданному тестовому профилю ВУ. Полный контракт ProcessIncomingConsignment, включая реальный transport, preview/submit/poll/reconcile и UI enabled-state, обязателен по O-13. `VETIS_WRITE_ENABLED=false` — безопасное значение установки во время разработки, а не постоянный запрет функции. Агенты/CI не включают его и проверяют enabled-state на spy без живого вызова. После решения владельца оператор включает capability; уполномоченный пользователь явно подтверждает конкретное действие. Без проверенного read-подключения показывается «Интеграция не настроена»; фиктивные поступления/подтверждения не создаются.

Профиль — ветеринарные управления: семейство mercury-vu.service, не mercury-g2b.service. Успешный пример подтверждает endpoint `https://api2.vetrf.ru:8002/platform/services/2.0/ApplicationManagementService`, `serviceId=mercury-vu.service:2.0` и namespace `http://api.vetrf.ru/schema/cdm/mercury/vu/applications/v2`. Принятое правило подключения — versioned contract manifest ВУ с endpoint, serviceId, business schema version, WSDL и полным набором XSD SHA-256. V01 обязан загрузить и закрепить фактические WSDL/XSD: успешный XML не заменяет schema pinning. Поддерживается только manifest тестового профиля; автоматического fallback на ХС/production нет.

Выбран transport Zeep 4.3.3, отдельная новая зависимость этого ADR. SOAP/XML изолирован адаптером; ограничены размеры/таймаут, DTD/external entities выключены, TLS проверяется; WSDL/XSD закрепляются по checksum, внешние schema imports ограничиваются утверждённым набором. Credentials (gateway login/password, apiKey, issuerId по профилю) доступны только серверу. Планировщик каждые 15 минут запускает чтение всех страниц для закреплённых ХС/площадок Агропромышленного парка от выделенной read-only интеграционной идентичности; ручная кнопка врача/заведующего ставит тот же идемпотентный job вне очередного интервала. Перед каждой SOAP-заявкой повторно проверяются активность binding, read-capability и область лаборатории. Нет read-идентичности — 422 INTEGRATION_INITIATOR_MISSING, нет связи лаборатория→ХС/площадка — 422 INTEGRATION_SCOPE_MISSING; ввод сверки сохраняется. Эта служебная read-идентичность не имеет write-capability и не может использоваться receipt transport.

Получение списка выполняется с явной областью площадки, `INCOMING`, `CONFIRMED` и локальной проверкой транспортного происхождения. Поскольку операция не имеет server-side фильтра первого уровня, до записи партии обязательно проверяется `certifiedConsignment/batch/productType=1`. Все страницы обрабатываются с дедупликацией и повторной сверкой изменений; отсутствие строки не считается аннулированием. Checkpoint обновляется только после полного прохода. Для каждого внешнего UUID сохраняются raw XML, внешняя версия/дата изменения, checksum и нормализованный снимок. Для `product`, `subProduct`, `productItem`, единиц и участников сохраняются их собственные GUID/UUID и source `name`; UI показывает source `name` без общего dictionary lookup. Изменение источника не затирает местные факты, но инвалидирует сверку прежнего checksum. Отсутствующее имя показывается честно, технический ID доступен только в диагностике.

Источники: [получение v2](https://help.vetrf.ru/wiki/GetVetDocumentListOperation_v2), [гашение v2](https://help.vetrf.ru/wiki/ProcessIncomingConsignment_v2), [различия ВУ/ХС](https://help.vetrf.ru/wiki/Различия_в_запросах_от_хозяйствующих_субъектов_и_ветеринарных_управлений), повторно проверены 09.11.2026. XML-карта ВУ сверяется с предоставленными успешными примерами. Ссылка на гашение описывает только офлайн-моделируемый контракт и не разрешает живой вызов.

## Рассмотренные альтернативы
1. SOAP из браузера: быстрее прототип; раскрывает секреты и обходит централизованное подтверждение — отклонено.
2. Сразу сервис ХС из примера v2: есть готовые XML; не отвечает требуемому профилю ВУ — отклонено.

## Последствия
- Определена ответственность за данные и проверяемая граница операции.
- **Риск/цена:** Без зарегистрированного manifest/секретов адаптер остаётся выключен; архитектура задаёт их проверку, но не выдумывает выданный оператором endpoint. Совместимость Zeep подтверждается контрактными проверками реализации.
- Реализация и ТЗ обязаны сохранить указанные инварианты и обработку отказов.

## Проверка
Контрактная проверка пагинации, повторов, namespace, `productType=1`, source names и доступа площадки выполняется на тестовом read-профиле. Write-проверки доказывают наличие production transport boundary и enabled-state через spy при нуле настоящих вызовов ProcessIncomingConsignment; фактический `VETIS_WRITE_ENABLED` агент не меняет.

## Открытые вопросы
Незакрытых архитектурных решений нет. Применимые значения настройки и внешние данные перечислены в [контракте входных данных](deployment-and-input-contracts.md); их заполнение не требует повторного выбора архитектуры.
