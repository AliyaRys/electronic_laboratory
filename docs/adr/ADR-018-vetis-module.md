# ADR-018: Модуль ВетИС использует SOAP-профиль ветеринарных управлений

- **Статус:** Accepted — архитектурное решение принято автором по прямому поручению владельца продукта 06.11.2026.
- **Дата:** 2026-11-06; уточнено решением владельца O-11 от 2026-11-08
- **Ответственность:** агент-разработчик реализует и проверяет решение; аналитик отвечает за изменение продуктовых правил. Дополнительное согласование архитектуры не требуется.
- **Связанные:** [ADR-015](ADR-015-module-boundaries.md), [трассировка](traceability.md).
- **Основание:** ФТ v2.0: FT-ARR-01/14, FT-ACC-11; INPUT-01; указания пользователя 06.11.2026.

## Контекст
Пользователь требует отдельную интеграцию для ВУ и откладывает её до завершения локальных модулей. Ссылки v2 описывают бизнес-операции, но не подтверждают точный доступный профиль ВУ.

## Решение
Интеграция подключается к промышленному профилю ВУ только для разрешённых операций чтения, начиная с GetVetDocumentListOperation: тестовый контур не используется как доказательство этого метода, поскольку он там не отрабатывает. `VETIS_WRITE_ENABLED=false` является обязательным release-gate, а не временным состоянием первого этапа. Production read-функция не имеет доступной команды, credentials или сетевого маршрута гашения/возврата. Полный контракт ProcessIncomingConsignment, включая preview/submit/poll/reconcile, реализуется, но проверяется офлайн на детерминированном адаптере/fixtures; его живое включение не входит в действующее решение. В промышленном режиме без read-подключения показывается «Интеграция не настроена»; фиктивные поступления/подтверждения не создаются.

Профиль — ветеринарные управления: семейство mercury-vu.service, не mercury-g2b.service. Официальное описание различий подтверждает отдельные пространства имён и возможность фильтра ВУ businessMember; это историческое описание, не доказательство точной версии v2 ВУ. URL бизнес-операции с _v2 не используется как SOAP endpoint. Принятое правило подключения — versioned contract manifest ВУ: endpoint, serviceId, business schema version, WSDL и полный набор импортируемых XSD с SHA-256. Их значения берутся из зарегистрированного профиля подключения ВУ. Получение такого manifest — обязательная задача адаптера в ТЗ интеграции; это внешний параметр подключения, а не нерешённый выбор транспорта. Неподтверждённые сейчас строковые значения честно отмечены unverified в контракте входов; адрес и namespace из примера ХС не подставляются. Поддерживается только явно закреплённый manifest, его смена проходит контрактные тесты. Автоматического fallback на профиль ХС нет.

Выбран transport Zeep 4.3.3, отдельная новая зависимость этого ADR. SOAP/XML изолирован адаптером; ограничены размеры/таймаут, DTD/external entities выключены, TLS проверяется; WSDL/XSD закрепляются по checksum, внешние schema imports ограничиваются утверждённым набором. Credentials (gateway login/password, apiKey, issuerId по профилю) доступны только серверу. Планировщик каждые 15 минут запускает чтение всех страниц для закреплённых ХС/площадок Агропромышленного парка от выделенной read-only интеграционной идентичности; ручная кнопка врача/заведующего ставит тот же идемпотентный job вне очередного интервала. Перед каждой SOAP-заявкой повторно проверяются активность binding, read-capability и область лаборатории. Нет read-идентичности — 422 INTEGRATION_INITIATOR_MISSING, нет связи лаборатория→ХС/площадка — 422 INTEGRATION_SCOPE_MISSING; ввод сверки сохраняется. Эта служебная read-идентичность не имеет write-capability и не может использоваться receipt transport.

Получение списка выполняется с явной областью ХС/площадки лаборатории, входящим транспортным назначением и допустимыми статусами. Бизнес-фильтр — входящий документ, получатель текущей площадки, транспортное происхождение, поддержанная мясная классификация; значения enum и возможности серверной фильтрации берутся из закреплённого manifest. Условия, которые профиль не умеет сочетать, дополнительно проверяются локально до записи партии. Нельзя заменять этот предикат одним enum INCOMING и считать его транспортным происхождением. Все страницы обрабатываются с дедупликацией и повторной сверкой изменений; отсутствие строки не считается аннулированием. Checkpoint обновляется только после согласованного сохранения полного прохода, неуспешный проход помечается неполным; врач видит время последней успешной синхронизации. Для каждого внешнего UUID сохраняются защищённый исходный XML, внешняя версия/дата изменения и checksum, а также нормализованный снимок идентификаторов, статуса, участников, классификации, единиц и прежней ВСЭ. Изменение источника не затирает местные факты, но инвалидирует сверку, построенную на прежнем checksum. Локальные контурные справочники разрешают GUID/UUID/коды в названия для UI; неизвестный код показывается как «Не найдено в справочнике» с техническим ID в диагностике, а не как понятное пользователю название.

Источники: [получение v2](https://help.vetrf.ru/wiki/GetVetDocumentListOperation_v2), [гашение v2](https://help.vetrf.ru/wiki/ProcessIncomingConsignment_v2), [различия ВУ/ХС](https://help.vetrf.ru/wiki/Различия_в_запросах_от_хозяйствующих_субъектов_и_ветеринарных_управлений), проверены 06.11.2026. Конкретные XML-элементы из примеров ХС не переносятся в ВУ автоматически. Ссылка на гашение описывает только офлайн-моделируемый контракт и не разрешает вызов production.

## Рассмотренные альтернативы
1. SOAP из браузера: быстрее прототип; раскрывает секреты и обходит централизованное подтверждение — отклонено.
2. Сразу сервис ХС из примера v2: есть готовые XML; не отвечает требуемому профилю ВУ — отклонено.

## Последствия
- Определена ответственность за данные и проверяемая граница операции.
- **Риск/цена:** Без зарегистрированного manifest/секретов адаптер остаётся выключен; архитектура задаёт их проверку, но не выдумывает выданный оператором endpoint. Совместимость Zeep подтверждается контрактными проверками реализации.
- Реализация и ТЗ обязаны сохранить указанные инварианты и обработку отказов.

## Проверка
Контрактная проверка пагинации, повторов, namespace и доступа площадки выполняется на production read-only профиле; обновление одного документа не создаёт дубликат. Transport spy и конфигурационная проверка доказывают ноль write-вызовов, отсутствие production write credentials/маршрута и `VETIS_WRITE_ENABLED=false`.

## Открытые вопросы
Незакрытых архитектурных решений нет. Применимые значения настройки и внешние данные перечислены в [контракте входных данных](deployment-and-input-contracts.md); их заполнение не требует повторного выбора архитектуры.
