# ADR-019: Приёмка подтверждается внешним результатом без слепого повтора

- **Статус:** Accepted — архитектурное решение принято автором по прямому поручению владельца продукта 06.11.2026.
- **Дата:** 2026-11-06; область применения ограничена решением владельца O-12 от 2026-11-09
- **Ответственность:** агент-разработчик реализует и проверяет решение; аналитик отвечает за изменение продуктовых правил. Дополнительное согласование архитектуры не требуется.
- **Связанные:** [ADR-015](ADR-015-module-boundaries.md), [трассировка](traceability.md).
- **Основание:** ФТ v2.0: FT-ARR-06–15, FT-DOC-02; INPUT-01.

## Контекст
Гашение/возврат меняют юридический документ. Успешная доставка SOAP и таймаут не доказывают итог бизнес-операции.

## Решение
Архитектура ProcessIncomingConsignment реализуется полностью, но до нового явного указания владельца работает без живого submit. Шесть сочетаний соответствие/несоответствие × полное/частичное принятие/полный возврат проверяются детерминированным офлайн-адаптером на обезличенных копиях предоставленных успешных XML. XML строится по закреплённой карте из raw XML/checksum конкретной версии эВСД и фактов сверки. `docInspection` следует документарной сверке, `vetInspection` независимо отражает осмотр (`CORRESPONDS/MISMATCH/UNSUPERVISED`), `decision` — выбор пользователя. При mismatch и ACCEPT_ALL/PARTIALLY передаётся discrepancyReport; при RETURN_ALL accepted consignment и акт не передаются. `returnedDelivery` существует только для PARTIALLY/RETURN_ALL. Перед intent повторно проверяются версия, получатель, объёмы, единицы, причины и коды. Недостача 120→100 при приёмке 100 не создаёт возврат 20; для partial обе части положительны и их сумма равна доставленному.

Гашение и возврат запрещены для smoke, e2e, приёмочных, нагрузочных и ручных тестов как в test, так и в production. External transport текущего выпуска отклоняет submit до сети; `VETIS_WRITE_ENABLED=false`. Живое включение требует нового явного указания владельца. Каждый реальный submit дополнительно требует внешнего одноразового `VetisWriteAuthorization{document_uuid,decision,expires_at,responsible,authorization_id}` и явного подтверждения уполномоченного пользователя; авторизация проверяется до outbox и повторно до сети и не создаётся через UI, API, seed, миграцию или тест. Успешные fixtures и test credentials не означают готовность живого гашения.

Команда фиксирует под блокировкой неизменяемое намерение, fingerprint состава, initiator, ревизию сверки и outbox. Локальные стадии: NOT_SENT → QUEUED → SUBMITTING → PROCESSING → CONFIRMED / REJECTED / UNKNOWN. Это технические стадии, не новые статусы пригодности. Один unresolved intent на входящий документ. До отправки повторно проверяются права сотрудника, внешняя область, статус документа и допустимость решения; изменённое намерение требует нового подтверждения.

Adapter использует асинхронный транспорт заявок: submitApplicationRequest, затем receiveApplicationResult по выданному applicationId; точный профиль закрепляется по WSDL. Сохраняются localTransactionId, applicationId и подтверждённые UUID гашения/возврата/акта. Ответ шлюза о приёме заявки не завершает приёмку. После успешного результата команда подтверждения атомарно фиксирует принятый состав и маршрут дальнейшей работы. Повторная доставка результата идемпотентна.

После сетевого разрыва в SUBMITTING не создаётся новая заявка: UNKNOWN → проверка результата известного applicationId и внешнего факта по исходному документу. Если applicationId не получен, повтор возможен лишь при доказанном отсутствии исполнения средствами утверждённого контракта. Возможность дедупликации по localTransactionId не предполагается. Пока доказательства нет, команда остаётся UNKNOWN с обращением к ответственному интегратору. Таймаут/HTTP 5xx сам по себе не разрешает повтор. Чтение результата повторяется через 2/5/10/30/60 секунд с jitter, затем раз в 60 секунд до 15 минут; после этого ставится UNKNOWN, дальнейшая проверка запускается явным действием «Проверить результат». Таймаут соединения 10 секунд, ответа 60 секунд, общий лимит одного job 120 секунд; ожидание poll не держит HTTP-запрос и SQL-транзакцию. Повтор необратимого submit автоматически запрещён. При потере worker lease в SUBMITTING следующий worker выполняет только reconcile, а не submit.

Ручное гашение подтверждается сверкой внешнего документа и связанных результатов: исходный UUID, площадка/получатель, принятый/возвращённый состав и доступные документы операции. Одного UTILIZED, введённого номера и кнопки «выполнено» недостаточно для доказательства частичного состава. Для восстановления приняты дополнительные служебные read-операции GetVetDocumentByUuidOperation и GetStockEntryByUuidOperation, плюс фильтрованный GetVetDocumentListOperation для связанных возвратных документов. Эти операции подключаются в выпуске гашения; они только читают и не расширяют исходящие процессы. Источники: [ВСД по UUID](https://help.vetrf.ru/wiki/GetVetDocumentByUuidOperation_v2), [версия stockEntry](https://help.vetrf.ru/wiki/GetStockEntryByUuidOperation_v2). Полный/частичный принятый состав доказывается подтверждённой записью приёмки и связанным возвратным документом; текущий складской остаток после последующих операций таким доказательством не считается. Если закреплённый ВУ-профиль не возвращает достаточно связей для доказательства, сервер оставляет UNKNOWN и выдаёт INTEGRATION_EVIDENCE_INCOMPLETE. Оператор получает диагностический пакет для проверки внешнего факта; ручная кнопка успешного подтверждения отсутствует. Это определённое поведение при недостатке доказательств, а не отложенный выбор дополнительных методов. CONFIRMED с положительным принятым объёмом открывает ВСЭ; RETURN_ALL — только возврат; удаление ВСЭ никогда не отправляет повторное гашение.

## Рассмотренные альтернативы
1. Повторять submit при каждом таймауте: повышает шанс ответа; может повторить юридически значимую команду — отклонено.
2. Считать локальную сверку подтверждением: позволяет продолжить без сети; нарушает FT-ARR-12/14 — отклонено.

## Последствия
- Определена ответственность за данные и проверяемая граница операции.
- **Риск/цена:** Неизвестный исход может потребовать ручного разбора; архитектура не обещает exactly-once внешнего API.
- Реализация и ТЗ обязаны сохранить указанные инварианты и обработку отказов.

## Проверка
AT-01–06 выполняются только на детерминированном офлайн-адаптере: обрыв до submit, после моделируемого принятия заявки, после моделируемого внешнего успеха до local commit; повтор worker; моделируемая ручная операция; полный возврат без ВСЭ. Любой сценарий с внешним write помечается «Не выполнялся — запрещено O-12», а не запускается для проверки.
