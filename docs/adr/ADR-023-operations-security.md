# ADR-023: Технический аудит и восстановление защищают данные без истории ВСЭ

- **Статус:** Accepted — архитектурное решение принято автором по прямому поручению владельца продукта 06.11.2026.
- **Дата:** 2026-11-06
- **Ответственность:** агент-разработчик реализует и проверяет решение; аналитик отвечает за изменение продуктовых правил. Дополнительное согласование архитектуры не требуется.
- **Связанные:** [ADR-015](ADR-015-module-boundaries.md), [трассировка](traceability.md).
- **Основание:** ФТ v2.0: FT-COM-08, FT-ACC-10, FT-VSE-12; OPS-01.

## Контекст
Нужна диагностика сбоев и внешних операций, но исключены история медицинских версий и восстановление удалённой карточки.

## Решение
Пишутся структурированные технические события: trace_id, actor UUID, область, действие, объект UUID, время, результат/code, ревизия, operation/applicationId и длительность. Пароли, cookie, токены, apiKey и полный медицинский payload в общие логи не попадают. История пользователя содержит реальные изменения назначений/статуса без секретов. Событие предметной команды фиксируется атомарно с изменением в БД; операционные логи дополняют его. Обычные роли не редактируют аудит. Аудит удаления содержит факт/UUID, не сохраняет полный протокол ВСЭ для восстановления.

Сырые SOAP для диагностики доступны только отдельному интеграционному хранилищу с маскированием секретов, доступом только служебной учётной записи установки и сроком 30 дней. Нормализованные доказательства приёмки и неразрешённые внешние операции автоматически не удаляются. Нормализованные доказательства внешнего результата сохраняются с операцией. Метрики: ошибки/задержка API, БД-пул/блокировки, размер/возраст outbox, UNKNOWN count/age, последняя успешная синхронизация, worker lag, успех backup/restore. Сигналы: UNKNOWN >0 — интеграционный инцидент; возраст UNKNOWN >15 минут — высокий приоритет; нет успешного полного backup за 26 часов, WAL lag >10 минут, outbox age >5 минут и свободный диск <20% — эксплуатационный инцидент. Получатели задаются контактами установки; отсутствие контакта не отменяет диагностический статус в служебной панели.

Восстановление всей установки из резервной копии — эксплуатационная аварийная процедура, не действие восстановления удалённой ВСЭ. После восстановления write ВетИС остаётся выключен до сверки незавершённых намерений и внешних фактов: состояние внешней системы не откатывается вместе с БД. Удалённые карточки, существовавшие в старой копии, не должны становиться доступными без применения доступного журнала удалений; при потере журнала выпуск после восстановления блокируется до разбирательства. Возврат к старому backup не используется как повседневный undo.

Приняты проверяемые цели разработки: RPO≤15 минут, RTO≤4 часов, технические логи 90 дней, security-события 365 дней, диагностические SOAP 30 дней. Юридически значимые подтверждения/нераспознанные операции, отборы/утилизации и сохранённые отчёты не удаляются технической очисткой логов. Это проектные правила хранения, не заявление о сроках по закону. При отказе сервиса/принтера нет автоматического офлайн-режима; подтверждённые данные сохраняются, повтор печати не меняет ВСЭ.

Принята проектная ёмкость: 100 лабораторий, 500 зарегистрированных сотрудников, 100 одновременно активных, 5 000 новых поступлений в сутки на установку, до 100 000 ВСЭ одной лаборатории за полугодие. Это нагрузочная цель для реализации, не утверждение о реальной численности заказчика. Первичная конфигурация app-хоста: 8 vCPU, 32 GiB RAM, 500 GiB SSD; отдельный backup-хост с 2 TiB шифрованного хранилища. При этой нагрузке p95 чтения страниц ≤2 секунд, локального сохранения ≤3 секунд без времени внешних систем; ошибки <1% при штатных зависимостях; формирование 5-вет до 60 секунд. Нагрузочный прогон длится 30 минут, поиск/списки/запись смешаны 80/20, проверяются корректность и отсутствие утечек между лабораториями.

Backup реализуется средствами той же версии PostgreSQL на отдельном backup-хосте: pg_basebackup ежедневно в 02:00 Europe/Moscow, pg_receivewal --synchronous непрерывно пишет WAL непосредственно на его зашифрованный диск. Для доступа выбран выделенный reverse SSH-туннель: non-root tunnel-процесс внутри закрытой Compose-сети инициирует соединение с backup-хостом и связывает только его loopback 127.0.0.1:6543 с postgres:5432 Compose-сети. GatewayPorts выключен, SSH-ключ ограничен этим forwarding, host-key закреплён. Порт PostgreSQL не публикуется на app-хосте; loopback-туннель доступен только backup-службе на backup-хосте. Туннель не даёт backup-службе административного доступа к ОС приложения. PostgreSQL выдаёт отдельную replication-role без предметных DML/DDL-прав и отдельный physical replication slot; pg_hba ограничивает эту роль replication-соединениями.

pg_receivewal подтверждает fsync сразу после записи, не ждёт закрытия WAL-сегмента; partial-WAL и восстановление до подтверждённого LSN проверяются restore-тестом. Receiver имеет отдельный application_name=vse_backup. synchronous_standby_names указывает этот receiver, но по умолчанию для прикладной роли synchronous_commit=local: обычные сохранения не ждут backup. Только команда удаления ВСЭ устанавливает SET LOCAL synchronous_commit=on; её COMMIT подтверждается после долговечной записи WAL на backup-хосте. remote_apply не используется: pg_receivewal не применяет WAL. archive_timeout не используется как управление pg_receivewal. max_slot_wal_keep_size=20GiB ограничивает накопление WAL; потеря непрерывной цепочки вызывает backup failure и новую base-copy. Хранятся 7 последних полных ежедневных копий, 4 еженедельных и необходимая цепочка WAL; удаление цепочки допускается только после проверки новой восстанавливаемой копии. Ёмкость backup-хранилища — минимум 2 TiB и одновременно не меньше объёма этих 11 копий + WAL +30% резерва по измеренному размеру, с оповещением до исчерпания. App-хост не хранит credentials для удаления backup-файлов. Контроль manifest/checksum — после каждой копии, полное восстановление — ежемесячно на изолированном восстановительном хосте. Секреты, key-ring и внешний append-only журнал удаления резервируются отдельно с тем же RPO. Redis не используется как источник восстановления предметных данных: сеансы отзываются, outbox переиздаёт только безопасную доставку.

Ключи snapshot/session/API не включаются в образ. Закрытый env-file на хосте доступен только служебной учётной записи; ключ snapshot 256 bit и key_id ротируются каждые 90 дней, предшествующий проверочный ключ хранится 9 часов. Факт удаления ВСЭ и его технический tombstone фиксируются в одной локальной транзакции и одном синхронно подтверждаемом WAL-потоке. Ответ об успешном удалении выдаётся только после remote flush; отдельного несогласованного зеркала tombstone с задержкой нет. Журнал не содержит медицинского протокола. Перед удалением проверяется backup readiness: есть проверенная восстанавливаемая base-copy, непрерывный WAL и активный receiver; при невыполнении перед удалением возвращается 503 BACKUP_DURABILITY_UNAVAILABLE без изменения данных. Если связь потеряна во время COMMIT и результат ещё неизвестен, клиент получает состояние операции UNKNOWN, а не утверждение «не удалено» и не успешное удаление. Повтор по тому же ключу сначала читает локальный факт и проверяет внешнюю долговечность. При локально завершённой транзакции повторный проверяющий запрос снимает текущий WAL LSN как безопасную верхнюю границу и не подтверждает успех, пока flush_lsn receiver не достиг её; сервер не делает повторный DELETE и не восстанавливает карточку. Если факт отсутствует, проверяются исходная ревизия/срок и состояние того же намерения до допуска повторной попытки. Автоматический TTL рабочих данных не вводится; технологический TTL не удаляет сохранённые отчёты, самостоятельные физические факты и подтверждения ВетИС. Восстановление включает всю доступную непрерывную цепочку WAL до последнего долговечно принятого LSN, включая подтверждённые удаления; произвольный PITR к более ранней дате не открывается пользователям как восстановленная текущая установка. Успешно подтверждённое удаление поэтому не теряется при потере app-хоста. Не подтверждённые операции имеют явный UNKNOWN и разбираются по восстановленному факту. RPO≤15 минут относится к обычным записям, для подтверждённых удалений принято RPO=0 относительно потери одного app-хоста. RTO≤4 часа проверяется для потери app-хоста при доступном исправном backup-хосте и ключах; одновременная потеря обоих хостов вне этой гарантии и требует аварийного разбора. Если непрерывность WAL/ключи повреждены, восстановление считается проваленным, публичный доступ не открывается и RTO не объявляется выполненным.

Источники backup-механизма: [pg_receivewal](https://www.postgresql.org/docs/18/app-pgreceivewal.html), [pg_basebackup](https://www.postgresql.org/docs/18/app-pgbasebackup.html). Обычные commit используют local, удаление — on с remote flush. Использование remote_apply запрещено. Цена усиленной сохранности удаления: при недоступности backup его нельзя успешно подтвердить; остальные локальные операции продолжаются.

## Рассмотренные альтернативы
1. Полный протокол каждой версии в логе: легче расследовать; создаёт историю ВСЭ и риск раскрытия — отклонено.
2. Не вести событий ради простоты: меньше хранения; невозможно безопасно разбирать UNKNOWN и изменения прав — отклонено.

## Последствия
- Определена ответственность за данные и проверяемая граница операции.
- **Риск/цена:** RPO/RTO требуют ресурсов и регулярной проверки; разрыв внешнего и локального состояния усложняет восстановление.
- Реализация и ТЗ обязаны сохранить указанные инварианты и обработку отказов.

## Проверка
Учебное восстановление с незавершённой внешней операцией, проверка отсутствия повторного submit; scan логов на секреты; подтверждение целостности проб/снимков/аудита. После успешного DELETE немедленно уничтожить app-хост и восстановить его: удалённый UUID недоступен. Оборвать receiver до DELETE: 503 без удаления; оборвать при COMMIT: UNKNOWN, безопасная проверка без второго удаления; обычное сохранение при недоступном backup продолжается с контролируемым RPO.

## Открытые вопросы
Незакрытых архитектурных решений нет. Применимые значения настройки и внешние данные перечислены в [контракте входных данных](deployment-and-input-contracts.md); их заполнение не требует повторного выбора архитектуры.
