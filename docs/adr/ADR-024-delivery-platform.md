# ADR-024: GitVerse CI/CD и частный OCI registry обеспечивают поставку

- **Статус:** Accepted — решение автора по поручению владельца продукта 06.11.2026.
- **Дата:** 2026-11-06
- **Ответственность:** агент-разработчик реализует поставку; отдельное согласование платформы не требуется.
- **Связанные:** [ADR-011](ADR-011-backend-quality.md), [ADR-012](ADR-012-frontend-quality.md), [ADR-013](ADR-013-compose-and-environments.md), [ADR-014](ADR-014-versions-and-upgrades.md).
- **Основание:** adr_request §4–6; FT-COM-05/08; отсутствие заданной CI-платформы.

## Контекст
Исходный форк находится в GitVerse, приложение размещается на собственных стендах через Compose. Вводить отдельный GitLab ради pipeline не требуется. Реестр должен хранить несколько релизов, не зависеть от небольшого публичного лимита пакетов.

## Решение
Выбраны GitVerse CI/CD и self-hosted Linux runner, привязанный только к закрытому репозиторию проекта. Будущие workflow размещаются в .gitverse/workflows/. Runner регистрируется на https://gitverse.ru, без устаревшего /sc. Jobs выполняются в контейнерах на отдельной машине, не на production-хосте. Для недоверенных pull request доступны только проверки без deploy/registry-секретов. Разрешённые actions закрепляются полным commit SHA; нет прямого запуска произвольного workflow с секретами установки.

Образы хранятся в частном CNCF Distribution registry 3.1.2 (официальный образ registry:3.1.2 с digest в README) на отдельной машине поставки. Registry закрыт TLS nginx, аутентификацией и сетью; контейнер запускается как UID 10001 на непривилегированном порту, данные в именованном volume с подготовленным при установке владельцем. Отдельные credentials для push pipeline и pull установки; их секретные значения задаются при размещении. Минимум 200 GiB SSD для registry/build cache; сохраняются используемый и пять предыдущих успешных релизов. Очистка не удаляет digest активных установок; registry и его конфигурация резервируются ежедневно. Готовые исходники/артефакты заказчика не публикуются в открытом репозитории.

Pipeline: frozen install → проверки ADR-011/012 → миграция на эфемерном PostgreSQL → сборка образов один раз → push под git SHA → запись digest в release manifest → развёртывание этих digest на собственный стенд → smoke. В production переносится тот же frontend-образ; адрес API не пересобирается. Миграция идёт отдельным one-shot до переключения API, через блокировку релизов одной установки. Runtime-процессы не имеют DDL-прав. Production deploy — явный запуск release-job агентом по поручению пользователя; автоматического развёртывания произвольного main-коммита нет. Внешнего архитектурного согласования release-job не требует.

Версия GitVerse как сервиса не закрепляется. Версия runner-image до получения доступа к registry оператора отмечается unverified; при реализации устанавливается точный официальный digest, который фиксируется в release manifest и проверяется smoke. Это воспроизводимый механизм пиннинга инфраструктурного инструмента, не выбор между CI-платформами. Docker Engine 29.9.3 и Compose 5.7.0 выбраны; версия registry проверена 06.11.2026.

Источники: [GitVerse self-hosted runners](https://gitverse.ru/docs/cicd/docs/runners/self-hosted/), [workflow](https://gitverse.ru/docs/cicd/introduction/), [Distribution 3.1.2](https://github.com/distribution/distribution/releases/tag/v3.1.2). Пакетные лимиты GitVerse проверены по [официальному описанию](https://gitverse.ru/docs/limits-lfs-cicd/limits-packages); их увеличение не требуется благодаря собственному registry.

## Рассмотренные альтернативы
1. GitLab Self-Managed: единая платформа и registry; требует новой крупной службы вне заданного контура — отклонено.
2. Только локальная ручная сборка: минимальная настройка; не обеспечивает обязательные исполняемые CI-gates и происхождение артефакта — отклонено.

## Последствия
- Поставка использует существующую платформу происхождения форка и собственное хранилище образов.
- **Риск/цена:** нужно сопровождать runner и registry; доступ к Docker-сборке требует изоляции от production и недоверенных jobs.
- Workflow, release manifest, registry и настройки хостов входят в ТЗ реализации, но не создаются в документационной задаче.

## Проверка
Сломанная миграция/тип/контракт блокируют push релиза; недоверенный PR не получает секреты. Два deploy одной установки сериализуются. Образ активного релиза переживает очистку. Восстановленный registry отдаёт прежний digest, frontend переносится между стендами без пересборки.

## Открытые вопросы
Незакрытых архитектурных решений нет. Адреса, namespace, токены и проверяемый digest runner — параметры установки по [контракту](deployment-and-input-contracts.md).
