# Задание агенту на подготовку ТЗ

Используй этот файл как точку входа вместе с папкой docs/adr. Дата 06.11.2026, пакет ADR 1.1. Задача следующего этапа — написать полное ТЗ на разработку, программный код пока не создавать.

## Полномочия и приоритет

Владелец продукта подтвердил ФТ v2.0 и R-01–R-09. Он поручил автору ADR самостоятельно выбрать технические решения; отдельного согласования руководителем, tech lead и эксплуатацией не требуется. ADR-001–024 имеют статус Accepted в рамках этого поручения. Не возвращай их в Proposed и не превращай назначение физических исполнителей в препятствие написанию ТЗ.

Продуктовые правила: ФТ v2.0 с приоритетом owner-decisions O-01–09 над foundation v1.9; архитектура: данный пакет. Исходные макеты/контракты UI сохраняют значение в непротиворечащей части. Прежняя редакция adr_request требовала согласования вариантов, но прямое уточнение владельца 06.11.2026 отменило этот этап. Изменять бизнес-правило нужно через вопрос аналитику; техническую детализацию в пределах принятых решений агент выполняет самостоятельно.

## Что должно быть в ТЗ

Для каждого модуля: границы, входы/выходы, модель данных и constraints, API, команды/переходы, права, источники данных, ошибки, конкуренция/идемпотентность, сценарии приёмки. Для каждой операции — что проверяется до фиксации, что фиксируется атомарно, как выглядит конфликт и как определяется факт после потерянного ответа. Не заменяй это общим «использовать транзакции».

Состав ТЗ: платформа/поставка и доступ; поступления/сверка; ВСЭ/ожидание/итог/удаление; физические пробы/полная утилизация; нормы/тарифы; заключения; отчётность/снимки; общие UX-состояния; эксплуатация/восстановление; интеграция ВУ двумя отдельными этапами. Приложения: полная матрица прав, CHK/VSE mapping, REST/OpenAPI-контракт, концептуальные связи/ограничения, manifest форм/каталогов/профиля ВУ и FT→пункт ТЗ→приёмка.

Детализируй DB-схему и API внутри ТЗ без создания миграций/конфигов приложения. Нельзя вводить сохранённый черновик ВСЭ, историю её медицинских версий, повторный ветосмотр, смешанный итог партии, новое автоматическое исходящее ВСД, электронную подпись и почтовое восстановление. Удаление ВСЭ не отменяет гашение, пробу, утилизацию и снимок отчёта.

## Как обращаться с пока отсутствующими значениями

Адрес/домен/секрет/контакт — параметр установки с типом, валидацией и местом хранения; не незакрытая архитектура. Реальные нормы/цены/классификация/официальная форма — конфигурационные данные с указанной схемой, этапом загрузки и отказом. В ТЗ включи реализацию и загрузку этих конфигураций; не останавливай написание документа и не подставляй данные макета как реальные.

Профиль ВУ и credentials выдаёт оператор; сейчас их нет. ТЗ должно содержать задачу получения/закрепления contract manifest перед реализацией последнего этапа, нужные поля и проверки ADR-018. Не объявляй неизвестный serviceId/WSDL проверенным. Не превращай это в предложение выбрать SOAP/REST или ВУ/ХС заново. При объективном конфликте выданного контракта с требованиями опиши конкретный конфликт аналитику простыми словами.

Совместимость выбранных версий, security notices и фактический RPO/RTO проверяются при реализации и поставке. Это критерии приёмки работ, не основание требовать согласующего для написания ТЗ. Если выбранная версия объективно несовместима, приложи диагностическое доказательство и предложи минимальную замену; не меняй стек молча.

## Порядок реализации, который закрепить в ТЗ

Платформа/доступ → локальные предметные модули и документы/отчёты → эксплуатационная готовность → ВетИС получение → отдельный этап ВетИС гашение. Внутренний порт ВетИС проектируется заранее, реальное подключение реализуется последним. Сначала только GetVetDocumentListOperation, затем ProcessIncomingConsignmentOperation и служебное чтение для подтверждения результата. В ADR не добавляй проработку отдельной тестовой среды ВетИС: владелец явно исключил её из этого документа.

Неизвестный исход гашения не даёт локального успеха. Только импорт входящих ВСД не объявляется готовностью полного рабочего MVP: создание ВСЭ требует доказанной приёмки.

## Критерии готовности ТЗ

Все 81 FT и 82 CHK/VSE-поля имеют адресное покрытие. SC-001–101/AT-01–25 используются с приоритетом O-01–09. Нет плавающих архитектурных альтернатив, необъяснённых TBD и фиктивных внешних фактов. Все параметры определены типом/источником/валидацией/этапом. Зафиксированы серверная граница дня Europe/Moscow, отзыв прав со следующего запроса, одна ВСЭ партии, сохранность проб, неизменяемый снимок, идемпотентность и отказ после неизвестного внешнего исхода. Верификация документа отделена от будущих тестов приложения.
