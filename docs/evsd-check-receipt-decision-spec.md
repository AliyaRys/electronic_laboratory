# Техническое задание: поле «Решение о приёмке»

**Экран:** сверка данных входящего эВСД (`evsd-check-usmanov.html`)  
**Раздел:** блок «Результаты сверки»  
**Версия:** 1.1 от 02.11.2026  
**Статус:** готово к реализации макета и последующей интеграции с API «Меркурия»

## 1. Цель изменения

Добавить в сверку данных обязательное поле, в котором ветеринарный врач самостоятельно принимает решение о результате приёмки партии.

Система не должна автоматически выбирать способ гашения. Она должна:

1. проанализировать заполненные результаты сверки;
2. показать все три решения;
3. сделать недоступными только те решения, которые невозможно корректно передать через `ProcessIncomingConsignment`;
4. объяснить причину недоступности каждого решения;
5. перед отправкой повторно проверить выбранное решение на сервере.

## 2. Новое поле

### 2.1. Название и расположение

В блок «Результаты сверки» после поля «Специалист Госветслужбы» добавить поле:

**Решение о приёмке \***

Тип поля — раскрывающийся список. Поле обязательное. Значение по умолчанию не выбрано, плейсхолдер: «Выберите решение».

Варианты должны всегда отображаться в списке в следующем порядке:

1. Полное гашение;
2. Частичное гашение;
3. Полный возврат.

Недоступные варианты не скрываются: они отображаются выключенными. Под полем выводится пояснение, почему вариант недоступен и какие поля препятствуют его выбору.

### 2.2. Принцип принятия решения

- Система может показывать рекомендацию, но не выбирает решение вместо врача.
- Расхождение само по себе не означает частичное гашение или возврат.
- Недостача относительно объёма в эВСД не является возвращаемой частью: нельзя автоматически вычислять возврат как `объём по эВСД − фактически доставленный объём`.
- Частичное гашение возможно только тогда, когда часть фактически доставленной продукции принимается, а другая фактически доставленная часть возвращается отправителю.
- Полный возврат возможен только для фактически прибывшей партии, которую можно вернуть отправителю в рамках операции гашения входящего эВСД.

## 3. Соответствие вариантов операциям API

| Значение поля | `deliveryFacts/decision` | Когда формируется акт | Что передаётся дополнительно |
|---|---|---|---|
| Полное гашение | `ACCEPT_ALL` | Автоматически, если есть допустимое расхождение, требующее акта | Принятая партия; при необходимости — `discrepancyReport` |
| Частичное гашение | `PARTIALLY` | Автоматически, если одновременно имеются допустимые расхождения | Принятая часть, возвращаемая часть, причина возврата; при необходимости — `discrepancyReport` |
| Полный возврат | `RETURN_ALL` | В сценарии API v2 акт расхождений не передаётся | Возвращаемая партия и причина возврата |

Акт несоответствия не является отдельным решением врача. Система определяет необходимость акта по результатам сверки и автоматически добавляет `discrepancyReport` к полному или частичному гашению. Если акт требуется, пользователь видит информационную плашку и перечень расхождений до отправки запроса.

### 3.1. Два сценария частичного гашения

Одно значение интерфейса «Частичное гашение» должно поддерживать два официальных сценария API:

| Сценарий «Меркурия» | Когда применяется | `docInspection/result` | `decision` | Акт |
|---|---|---|---|---|
| 1.1.2 — сведения соответствуют, партия принимается частично | Нет расхождений, требующих акта; врач реально принимает часть доставленной партии и возвращает другую часть | `CORRESPONDS` | `PARTIALLY` | Не передаётся |
| 1.2.2 — сведения не соответствуют, партия принимается частично | Есть разрешённые API расхождения; часть фактически доставленной партии принимается, другая часть возвращается | `MISMATCH` | `PARTIALLY` | Передаётся `discrepancyReport` |

Отдельный вариант списка «Частичное гашение с актом» добавлять не требуется: решение врача в обоих случаях остаётся «Частичное гашение», а необходимость акта система определяет по результатам сверки.

Для сценария 1.2.2 запрос должен включать:

- `delivery/consignment` с фактическими сведениями о принимаемой части;
- `deliveryFacts/decision=PARTIALLY`;
- `deliveryFacts/docInspection/result=MISMATCH`;
- `discrepancyReport` с причиной или описанием расхождения;
- `returnedDelivery` со сведениями о реально возвращаемой части и причиной возврата.

Если выбран вариант «Частичное гашение» и есть хотя бы одно расхождение, требующее акта, в интерфейсе необходимо явно показать сообщение «Будет сформирован акт несоответствия» и сводку включаемых в акт расхождений.

## 4. Группы полей сверки

### 4.1. Информационные поля — не влияют на доступность решения

- Номер эВСД;
- Дата оформления;
- Назначение груза;
- сведения блока «Ранее проведённая ВСЭ»;
- Специалист Госветслужбы;
- Необходимость повторной ВСЭ.

Поле «Статус эВСД» является предварительным техническим условием: операция доступна только для эВСД в статусе, допускающем гашение. Если статус не допускает гашение, все три решения недоступны.

### 4.2. Расхождения, которые разрешено оформить актом

В MVP к этой группе относятся:

- тип, серия, номер и дата оформления транспортного документа;
- Номер ТС;
- Номер прицепа — обрабатывается как часть номера транспортного средства;
- Вес;
- Количество и маркировка фактически доставленных туш/частей;
- Срок годности;
- Название продукции — четвёртый уровень справочника продукции (`productItem`).

Для каждого отмеченного расхождения должны быть заполнены предусмотренные макетом фактическое значение и причина несоответствия. Из этих данных система формирует единый `discrepancyReport`.

### 4.3. Блокирующие расхождения

Следующие сведения нельзя заменять фактическими значениями при приёмке через рассматриваемый метод API:

- Отправитель;
- Адрес отправителя;
- Получатель;
- Адрес получателя;
- Тип продукции;
- Продукция;
- Вид продукции;
- Производитель;
- Дата выработки;
- Вид транспорта;
- Способ хранения продукции при перевозке.

Если хотя бы одно из этих полей отмечено как «Не соответствует», система не должна предлагать врачу принять партию с заведомо некорректными данными по текущему входящему эВСД. Варианты «Полное гашение» и «Частичное гашение» становятся недоступны. «Полный возврат» остаётся доступен, если данный вид входящего документа допускает возврат через API и данные возвратного эВСД проходят предварительную проверку.

Над полем выводится блокирующее сообщение со списком полей:

> Принять партию по этому эВСД невозможно: фактические сведения отличаются в полях, которые нельзя исправить при приёмке через API «Меркурия». Можно оформить полный возврат либо привести эВСД в соответствие в «Меркурии».

Это правило в том числе исключает ситуацию, когда указан другой получатель, а пользователь пытается выбрать полное или частичное гашение. Полный возврат при расхождении разрешён официальным сценарием `RETURN_ALL`: принимаемая партия и акт расхождений в запросе не передаются, формируется возвратный эВСД.

### 4.4. Связанные документы

Несоответствие поля «Связанные документы» нельзя передать как исправление принятой партии в текущем сценарии MVP.

При таком несоответствии:

- «Полное гашение» недоступно;
- «Частичное гашение» недоступно;
- «Полный возврат» доступен, если возвращаемая партия проходит предварительную проверку данных API.

Для полного возврата система предлагает подходящую причину возврата, например ошибку в производственном эВСД, но окончательную причину выбирает врач.

### 4.5. Результаты ветеринарно-санитарной оценки транспорта

Поля:

- Состояние грузового отделения;
- Совместная перевозка с другими грузами

определяют результат ветеринарного осмотра, но сами по себе не предопределяют способ гашения. Даже при значениях «Есть загрязнения или повреждения» или «Да, разделение не обеспечено» врач может принять всю партию, принять часть либо вернуть всю партию.

Эти значения:

- сами по себе не являются основанием для формирования акта несоответствия;
- не блокируют «Полное гашение», «Частичное гашение» и «Полный возврат»;
- должны приводить к передаче результата ветеринарного осмотра как несоответствия.

## 5. Матрица доступности решений

Обозначения:

- **Доступно** — вариант можно выбрать;
- **Условно** — вариант доступен после заполнения дополнительных данных;
- **Недоступно** — вариант выключен.

| Результат заполнения сверки | Полное гашение | Частичное гашение | Полный возврат |
|---|---:|---:|---:|
| Все сравниваемые сведения соответствуют | Доступно, без акта | Условно: нужно выделить принятую и возвращаемую части; без акта | Условно: нужна причина возврата |
| Есть только допустимое расхождение, для которого API не требует акт | Доступно, без акта | Условно: нужен реальный раздел партии; без акта | Условно: нужна причина возврата |
| Есть допустимое расхождение, требующее акт | Доступно после заполнения факта и причин; показывается плашка об акте | Условно: нужен раздел партии; показывается плашка, акт формируется автоматически | Условно: нужна причина возврата; акт не формируется |
| Есть хотя бы одно блокирующее расхождение из п. 4.3 | Недоступно | Недоступно | Условно: нужна причина возврата и успешная предварительная проверка |
| Не соответствуют только связанные документы | Недоступно | Недоступно | Условно: нужна причина возврата и успешная предварительная проверка |
| Есть только неблагоприятный результат осмотра транспорта | Доступно, без акта | Условно: нужен реальный раздел партии; без акта | Условно: нужна причина возврата |
| Статус эВСД не допускает гашение | Недоступно | Недоступно | Недоступно |

Если одновременно имеются разные виды расхождений, применяется самое строгое правило. Например, допустимое расхождение веса не отменяет блокировку из-за другого получателя.

## 7. Вес и количество

### 7.1. Разделение бизнес-подсказки и ограничения API

Правило продукта об отклонении фактического веса до 5% в любую сторону используется только для подсказки врачу:

- до 5% включительно — отдельное предупреждение о превышении бизнес-порога не показывается;
- более чем на 5% в любую сторону — система сообщает, что для принятия потребуется акт, и рекомендует проверить выбранное решение;
- рекомендация не выбирает решение автоматически.

Допустимость гашения без акта или с актом определяется порогом интеграции с API «Меркурия». Для макета и MVP отклонение объёма до 5% включительно в любую сторону считается допустимой погрешностью и не требует акта. При большем отклонении для принятия партии требуется акт. В рабочей системе порог должен находиться в конфигурации интеграции и быть подтверждён на тестовом контуре.

### 7.2. Недостача

Если в эВСД указано 120 кг, а фактически прибыло и принято 100 кг, отсутствующие 20 кг не считаются возвратом. В зависимости от правил API это полное гашение фактически прибывших 100 кг с актом расхождений либо без него.

### 7.3. Частичная приёмка

При выборе «Частичное гашение» система должна запросить состав:

- фактически доставлено;
- принято;
- возвращается.

Должны выполняться условия:

- принятый объём больше нуля;
- возвращаемый объём больше нуля;
- `принято + возвращается = фактически доставлено` с учётом единиц измерения и допустимого округления;
- одна и та же туша или часть не может одновременно входить в принятую и возвращаемую части;
- на страницу создания ВСЭ передаются только принятые туши/части.

Если возвращаемая часть равна нулю, «Частичное гашение» нельзя сохранить. Врач должен выбрать «Полное гашение».

## 8. Дополнительные поля по выбранному решению

### 8.1. Полное гашение

Если акт не требуется, дополнительные поля не открываются. Если акт требуется, показывается плашка из п. 8.2.

### 8.2. Плашка об акте несоответствия

Плашка показывается, когда пользователь выбрал «Полное гашение» или «Частичное гашение» и имеется хотя бы одно расхождение, для которого API требует акт.

Заголовок плашки:

> Будет сформирован акт несоответствия

Под заголовком выводится пояснение:

> В фактических сведениях обнаружены допустимые расхождения с эВСД. После подтверждения «Меркурий» сформирует акт несоответствия.

В плашке показывается сводка всех расхождений, включаемых в акт. Для каждого расхождения выводятся:

- название поля;
- значение из эВСД;
- фактическое значение;
- причина несоответствия;
- при необходимости — пояснение.

Правила поведения:

- плашка носит информационный, а не ошибочный характер;
- плашка обновляется при изменении результатов сверки;
- если оснований для акта больше нет, плашка скрывается;
- при «Полном возврате» плашка не показывается, поскольку `discrepancyReport` в этом сценарии не передаётся;
- до успешного ответа API используется только формулировка «Будет сформирован»;
- если хотя бы одно фактическое значение или обязательная причина не заполнены, отправить запрос нельзя;
- после успешного ответа API на странице результата можно показать статус «Акт несоответствия сформирован» и реквизиты акта, если они получены от «Меркурия».

### 8.3. Частичное гашение

Показываются:

- выбор возвращаемых туш/частей;
- итоговый вес и количество принятой части;
- итоговый вес и количество возвращаемой части;
- обязательное поле «Причина возврата»;
- поле «Другая причина», если выбрано значение «Другая причина»;
- сводка акта расхождений, если имеются расхождения, требующие акта.

Если расхождений, требующих акта, нет, выполняется сценарий 1.1.2 и `discrepancyReport` не передаётся. Если такие расхождения есть, выполняется сценарий 1.2.2 и заполненный `discrepancyReport` обязателен. Наличие акта не отменяет необходимость передать одновременно и принятую, и возвращаемую части партии.

### 8.4. Полный возврат

Показываются:

- весь состав фактически прибывшей партии без возможности исключить отдельные позиции;
- обязательное поле «Причина возврата»;
- поле «Другая причина», если выбрано значение «Другая причина».

## 9. Причины возврата

Для «Частичного гашения» и «Полного возврата» использовать следующий справочник:

- Некачественный товар;
- Повреждение упаковки;
- Посторонние включения или нарушение безопасности;
- Несоответствие результатам лабораторных исследований;
- Ошибка в производственном эВСД;
- Критический срок годности;
- Проблемы с маркировкой;
- Расхождение по количеству;
- Несоответствие даты выработки;
- Незаказанная продукция;
- Несоответствие спецификации;
- Отказ отправителя;
- Нарушение условий договора;
- Другая причина.

Внутреннее значение должно храниться кодом справочника «Меркурия». Для «Другой причины» пользователь вводит обязательное пояснение; перед отправкой применяется ограничение длины, соответствующее версии API.

## 10. Динамическое поведение

1. До заполнения всех обязательных результатов сравнения поле «Решение о приёмке» недоступно.
2. Доступность вариантов пересчитывается при любом изменении сравнения, фактического значения, состава партии или статуса эВСД.
3. Если ранее выбранный вариант стал недоступен, значение очищается. Пользователю показывается причина.
4. Рядом с доступными вариантами может выводиться нейтральная рекомендация, но окончательное действие всегда подтверждает врач.
5. При наличии нескольких причин недоступности выводится полный список полей, а не только первая ошибка.
6. Сервер выполняет ту же проверку повторно непосредственно перед вызовом API. Проверка только в браузере недостаточна.
7. Если ни один вариант недоступен из-за статуса или вида документа, кнопка завершения сверки выключена и показывается причина. При блокирующем расхождении из п. 4.3 доступным остаётся полный возврат, если он поддерживается для данного документа.
8. Плашка об акте пересчитывается после каждого изменения сверки и показывается только для полного или частичного гашения, если акт действительно требуется.

## 11. Кнопка завершения

Текст основной кнопки зависит от выбранного решения:

- «Полное гашение» без акта → «Погасить эВСД»;
- «Полное гашение» с автоматически формируемым актом → «Погасить эВСД с актом»;
- «Частичное гашение» без акта → «Погасить эВСД частично»;
- «Частичное гашение» с автоматически формируемым актом → «Погасить эВСД частично с актом»;
- «Полный возврат» → «Оформить полный возврат».

Перед отправкой показывается подтверждение с выбранным решением, принятым и возвращаемым объёмом и наличием акта.

## 12. Переход после успешной операции

- После полного или частичного гашения — с автоматически сформированным актом либо без него — дальнейший маршрут определяется необходимостью проведения ВСЭ.
- Если ВСЭ требуется, открывается страница создания ВСЭ. При частичной приёмке на неё передаются только принятые туши/части.
- Если ранее проведённой ВСЭ достаточно и повторная ВСЭ не требуется, открывается сохранённая сверка.
- После полного возврата страница создания ВСЭ не открывается, потому что принятая часть отсутствует. Открывается карточка завершённой сверки/возврата.
- При ошибке API пользователь остаётся на странице, введённые данные сохраняются, а операция не считается завершённой.

## 13. Критерии приёмки

1. В блоке «Результаты сверки» отображается обязательное поле с тремя вариантами: полное гашение, частичное гашение и полный возврат.
2. Система не выбирает решение автоматически.
3. Недоступные варианты видимы и сопровождаются понятной причиной.
4. Несоответствие получателя, отправителя или другого блокирующего поля не позволяет принять партию полностью или частично, но позволяет выбрать полный возврат, если он поддерживается для данного документа.
5. Допустимое расхождение, требующее акт, не создаёт отдельного решения: полное или частичное гашение остаётся выбранным, а акт формируется автоматически.
6. При необходимости акта до отправки показывается плашка «Будет сформирован акт несоответствия» со всеми включаемыми расхождениями.
7. В плашке для каждого расхождения видны поле, значение из эВСД, фактическое значение и причина.
8. Если обязательные данные акта не заполнены, завершить операцию нельзя.
9. При полном возврате плашка об акте не показывается и `discrepancyReport` не передаётся.
10. Частичное гашение нельзя завершить без положительных принятой и возвращаемой частей.
11. Частичное гашение без расхождений формирует запрос по сценарию 1.1.2 без `discrepancyReport`.
12. Частичное гашение при разрешённых расхождениях формирует запрос по сценарию 1.2.2 с `docInspection=MISMATCH` и обязательным `discrepancyReport`.
13. Недостача не превращается системой в фиктивный возврат.
14. Полный возврат и частичное гашение требуют причину возврата.
15. При частичном гашении на создание ВСЭ попадают только принятые туши/части.
16. Неблагоприятное состояние транспорта не заставляет систему автоматически выбрать возврат.
17. Отклонение веса более чем на 5% в любую сторону показывает рекомендацию и требует акт для принятия, но не подменяет решение врача и техническую проверку API.
18. Клиентская и серверная проверки доступности решений дают одинаковый результат.
19. При изменении исходных данных недействительное выбранное решение очищается.
20. При ошибке «Меркурия» данные сверки не теряются и успешный результат не отображается.

## 14. Источники и ограничения

- Официальное описание операции: [ProcessIncomingConsignment_v2](https://help.vetrf.ru/wiki/ProcessIncomingConsignment_v2).
- Внутренние бизнес-правила: PDR `vse-product-foundation-v1.5`.
- Реализованный состав полей: `evsd-check-usmanov.html` и `components/checks/CheckUi.js`.

Перед разработкой интеграции необходимо подтвердить на тестовом контуре точные допустимые отклонения веса и направление допустимого изменения срока годности. Интерфейс должен получать результат этой проверки от слоя интеграции, а не хранить неподтверждённые числовые ограничения локально.
