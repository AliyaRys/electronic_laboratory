# DR13 — полнота сверки, области тарифов услуг сверки, повторное сохранение (evidence)

Дата: 2026-11-12. Ветка: `feature/DR13-pricing-completeness` (от main fc50e99).
Отчёт владельца: страница `/labs/:lab/arrivals/:party/reconciliation` — «Сохранить сверку»
не создаёт расчёт стоимости; повторные нажатия дают 409 «Запись была изменена другим
пользователем».

## Дефект 1 (главный) — сверка никогда не становится полной (CHK-F06/F15 не отправляются)

**Root cause.** `comparedFields()` в `frontend/src/features/arrivals/api.ts` вручную
строила список сравниваемых полей и содержала только CHK-F05/F07/F10/F16/F17/F18/F20/F21.
Backend `FIELD_SPECS` (`backend/src/modules/arrivals/validation.py`) помечает CHK-F06
«участники» (`senderOwner`) и CHK-F15 «продукция» (`productType`) как сравнимые
(`inadmissible`). На живых данных сохранённый `checks` не содержит ни того, ни другого →
`validate_receipt` возвращает ошибки CHK-F06/CHK-F15 → `complete=False` → по ТЗ DR11
R-DR11-3 неполное сохранение осознанно не получает snapshot расчёта (правило корректно,
не менялось).

**Проверка проекции.** `source_projection()` (`backend/src/modules/arrivals/reconciliation.py`)
уже отдаёт `senderOwner` (имя `businessEntity` отправителя) и `productType`
(`classification.product_type`, число) — бэкенд-проекция правок не потребовала.

**Fix.** Список `comparedFields()` теперь зеркалит backend `COMPARABLE_SPECS`
(каждый сравнимый FieldSpec имеет свой push, те же id и блоки): добавлены
CHK-F06 «Отправитель — владелец», CHK-F08 «Получатель — владелец», CHK-F09/F11/F12
(транспорт), CHK-F15 «Тип продукции», CHK-F19, CHK-F22, CHK-F23 (продукция),
CHK-F25/F26/F27 (сопроводительные документы). Отсутствующее в проекции значение
остаётся отсутствующим (push пропускает его) — фиктивные отметки не создаются.
Числовое значение CHK-F15 показывается честной десятичной строкой (прецедент —
`SampleSelection`), без выдуманных русских наименований кода. Экран: карточка
сравнения CHK-F06 заменяет справочную карточку «Владелец продукции» в блоке
отправителя (и CHK-F08 — получателя); блок «Сопроводительные документы» показывает
карточки сравнения, когда проекция несёт реквизиты, иначе — прежнее честное пустое
состояние.

## Дефект 2 — тарифы CHECK сохранены с неверной областью вида продукции

**Обнаруженное.** Живые тарифы PRODUCT_IDENTIFICATION=110.00 и
TRANSPORT_INSPECTION=140.00 сохранены с `product_species_id` = UUID лаборатории
(2812e437…), тогда как вид партии — 362aa885… (говядина): расчёт честно даёт
CONFIGURATION_MISSING, область никогда не совпадёт. Источник подмены — резервное
правило назначений в `backend/src/modules/identity/commands.py` (`product_scope_id or
laboratory.id`, композитный PK без NULL): область продукции пользователя может
содержать UUID лаборатории, который редактор добросовестно сохраняет в тариф.

**Fix (без изменения живых данных БД).**
- `CheckServicesEditorPage` больше не открывает редактор цен, когда область не несёт
  настоящего вида продукции: показывается честная блокировка «Вид продукции для этой
  лаборатории не настроен», кнопка сохранения недоступна. Контекст вида продукции
  всегда виден в списке (`check-services-species`: честная формулировка с GUID, когда
  локального словаря видов ещё нет; «Вид продукции не настроен» для резервной области).
- `use-catalog-context` добавил `productSpeciesLabel` / `productSpeciesValid`
  (область = null или = id лаборатории → не вид).
- Backend `create_tariff` / `update_tariff` (а также `create_method_rule` /
  `update_method_rule`) отвергают `product_species_id == laboratory_id` (422
  VALIDATION_ERROR, путь `product_species_id`: «Вид продукции не может совпадать с
  лабораторией…»). Локального словаря видов продукции в БД нет, поэтому проверка
  против записи вида невозможна — отказ от заведомо ложной области честный и
  проверяемый. Существующие строки БД не изменялись (владелец перезапишет цены после
  исправления редактора).

## Дефект 3 — повторное «Сохранить сверку» даёт 409

**Root cause.** Форма отправляла `If-Match` от версии ПОСТАВКИ (`revisionEtag(party)`)
при каждом сохранении, а PUT-эндпоинт сверяет первую отправку с `party.rev`, а
последующие — с `rev` сохранённой сверки. После успешного сохранения клиент не
переключался на новую версию → следующий PUT со старым If-Match → 409
REVISION_CONFLICT. Кроме того, `useCommand` освобождал idempotency-key после
каждого однозначного ответа, поэтому повторный клик создавал новую команду.

**Fix.**
- Форма отправляет `If-Match` показанной версии сверки
  (`reconciliationEtag(initial)`): пустая OPEN-вью несёт версию партии, сохранённая —
  свою; это ровно те значения, с которыми сверяется эндпоинт.
- Стабильный ключ сессии сохранения (ТЗ DR13): ключ повторно используется, пока
  payload и показанная версия не меняются (сервер отвечает сохранённым состоянием —
  replay); после правки пользователя или сдвига версии ключ обновляется. Расширен
  `useCommand` (`SubmitOptions.idempotencyKey`).
- После 409 REVISION_CONFLICT форма автоматически перечитывает актуальное состояние
  (`command.refresh()`), и сообщение честное: «Данные обновлены, сверка
  перезагружена.» вместо «изменена другим пользователем». STATE_CONFLICT
  (замороженная подтверждённая сверка) сохраняет прежнюю формулировку.
