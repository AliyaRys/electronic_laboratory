# E02 — исправление и позднее завершение (жизненный цикл ВСЭ)

Дата реализации: 07.11.2026.

## Результат

`backend/src/modules/examinations/lifecycle.py` добавляет к карточке E01 две команды и два маршрута API-05:

- `update_examination(ctx, id, payload) -> ExaminationView` и `PUT /examinations/:id` — одна полная правка, допустимая **только в день создания** (Europe/Moscow по `created_at` команды, SPEC-05). Статус обычной правкой не меняется: WAITING не завершается отправкой полного итога, COMPLETED не возвращается в ожидание (409 STATE_CONFLICT в обе стороны).
- `complete_waiting(ctx, id, outcome) -> ExaminationView` и `POST /examinations/:id/complete-waiting` — явное подтверждение ответа спецлаборатории действием; тело `OutcomeWrite` содержит только `outcome/direction/reason` (extra=forbid, лишние поля → 422), доступно в любой день, только для WAITING (иначе 409), и не перезаписывает пробу, исследования, стоимость, клеймо и `sent_to_lab`.

## Порядок проверок (SPEC-04)

Блокировка строки карточки → чтение времени сервером **после ожидания блокировки** (без «now на старте транзакции») → требование idempotency-ключа и фиксация записи команды → `ensure_revision` по If-Match карточки (устаревшая ревизия — 409 REVISION_CONFLICT без слияния полей, отсутствие — 422 REVISION_REQUIRED) → правило дня (иначе 409 `DAY_CLOSED`) → повторная проверка фактов партии под блокировкой (подтверждение приёмки, маршрут, обязательные и типизированные исследования, уникальность номера) → расчёт → отбор пробы → одна атомарная запись карточки, события и команды.

`test_lock_crosses_midnight` удерживает блокировку строки во втором соединении, двигает часы через полночь, пока команда ждёт, и получает `DAY_CLOSED` — время действительно читается после блокировки.

## Неизменяемые факты

`created_by` и `first_completed_at` ни одной командой не присваиваются заново: первое завершение ставится ровно один раз, правка от другого пользователя не меняет автора (`test_original_author_and_completion`).

## Стоимость и отбор

Существующий показатель сохраняет закреплённый снимок нормы/тарифа через `evaluate_and_price(..., previous)` — изменение тарифа после сохранения не переклеивает старые строки; новый показатель считается по текущему каталогу. Сообщение пользователю о новом тарифе — задача формы (в API-05 нет поля предупреждений; менять контракт представления в рамках E02 не стал). Отбор применяется через тот же внутренний контракт S01; схема допускает ровно одну связь карточка→проба, поэтому явный NEW при правке замещает текущую связь, а прежние факты остаются в реестре проб.

## Итоговая матрица

FIT → только SALE и причина очищается; UNFIT → DISPOSAL|DESTRUCTION и непустая причина; «условно-пригодно» отвергается схемой; завершённая карточка не завершается повторно и не возвращается в ожидание (`test_outcome_matrix`). Медицинский итог остаётся решением врача — сервер его не вычисляет.
