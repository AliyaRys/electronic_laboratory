# Чек-лист обязательных данных для гашения входящего эВСД

**Метод:** `ProcessIncomingConsignment`  
**Сравниваемый макет:** `evsd-check-usmanov.html`  
**Дата проверки:** 02.11.2026

## 1. Краткий вывод

В макете есть почти все сведения, которые ветеринарный врач должен проверить или ввести вручную. Однако одного отображаемого текста недостаточно для формирования XML-запроса: интеграция должна хранить исходный эВСД вместе с UUID/GUID и кодами справочников.

До реализации интеграции необходимо закрыть четыре пользовательских пробела:

- структурировать фактическую ТТН при несоответствии;
- зафиксировать результат ветеринарного осмотра груза либо утвердить правило его автоматического вычисления;
- для частичного и полного возврата подтверждать, что возврат выполняется немедленно тем же транспортом;
- при необходимости дать врачу подтвердить условия регионализации обратного маршрута.

Кроме этого, в данных пользователя обязательно должен храниться его личный логин «Меркурия». ФИО специалиста из текущего макета логин не заменяет.

## 2. Важное ограничение по версии API

- Страница документации называется `ProcessIncomingConsignment_v2`, но сервис `mercury-g2b.service:2.0` выведен из эксплуатации.
- Для разработки следует использовать действующий профиль `mercury-g2b.service:2.1`, его WSDL и XSD, если отдельный договор интеграции не требует другой версии.
- Пространство имён прикладных объектов при этом по-прежнему содержит `/v2`.

Необходимо подтвердить версию на тестовом контуре до фиксации XML-контракта.

## 3. Что не нужно добавлять на страницу сверки

Следующие обязательные технические значения должны формироваться системой, а не вводиться врачом:

- `apiKey` — из защищённой конфигурации интеграции;
- `serviceId` — из конфигурации версии сервиса;
- `issuerId` — идентификатор ХС, от имени которого работает система;
- `issueDate` — текущее время формирования заявки;
- `localTransactionId` — уникальный идентификатор операции в нашей системе;
- UUID входящего эВСД — из ответа «Меркурия», а не из отображаемого номера;
- `vetCertificatePresence=ELECTRONIC` — константа для рассматриваемого сценария;
- коды решения `ACCEPT_ALL`, `PARTIALLY`, `RETURN_ALL` — из поля «Решение о приёмке»;
- UUID/GUID участников, площадок, продукции, единицы измерения, страны, производителя и назначения груза — из полного объекта входящего эВСД;
- дата формирования возвратной партии — текущее время;
- отправитель возврата — получатель входящего эВСД;
- получатель возврата — отправитель входящего эВСД.

Если система сохраняет только значения, показанные в HTML, например «ИП Усманов И.К.» или «Говядина», запрос сформировать нельзя. Необходимо сохранять исходный объект эВСД или нормализованную модель со всеми идентификаторами.

## 4. Общие обязательные данные операции

| Данные API | Обязательность | Что есть в макете | Что требуется |
|---|---|---|---|
| `localTransactionId` | Всегда | Нет | Генерировать на сервере, обеспечить уникальность и идемпотентность |
| `initiator/login` | Всегда | Есть только ФИО специалиста | Хранить личный логин «Меркурия» в профиле пользователя; перед отправкой проверять его наличие и полномочия |
| `delivery/consignor` — ХС и площадка | Для операции с электронным эВСД | Показываются имя и адрес | Сохранять UUID/GUID ХС и предприятия из входящего эВСД |
| `delivery/consignee` — ХС и площадка | Для операции с электронным эВСД | Показываются имя и адрес | Сохранять UUID/GUID ХС и предприятия из входящего эВСД |
| UUID входящего эВСД | Всегда | Показывается только номер эВСД | Сохранять UUID документа из API; не пытаться получить его из номера |
| `docInspection/result` | Всегда | Есть отметки по каждому полю | Вычислять: есть документарное расхождение — `MISMATCH`, иначе `CORRESPONDS` |
| `docInspection/responsible` | Всегда как объект; логин в таблице метода указан как необязательный | Есть ФИО | Передавать личный логин активного пользователя для однозначной трассировки |
| `vetInspection/result` | Всегда | Нет отдельного итогового поля | Добавить поле либо утвердить автоматическое правило из п. 5 |
| `vetInspection/responsible/login` | Всегда | Есть только ФИО | Передавать личный логин активного пользователя |
| `deliveryFacts/decision` | Всегда | Добавлено поле «Решение о приёмке» | Сопоставлять с кодом API |

## 5. Результат ветеринарного осмотра

API обязательно требует `vetInspection/result`, но в макете нет отдельного итогового поля.

Возможны два решения.

### Вариант А — без нового поля

Зафиксировать правило:

- `CORRESPONDS`, если «Состояние грузового отделения» = «Соответствует требованиям» и совместная перевозка отсутствует либо грузы разделены;
- `MISMATCH`, если есть загрязнения/повреждения или разделение грузов не обеспечено;
- `UNSUPERVISED` в этом интерфейсе не используется, поскольку сверку завершает ветврач после осмотра.

Этот вариант допустим, только если два указанных поля полностью определяют ветеринарный осмотр при приёмке.

### Вариант Б — рекомендуемый

Добавить в «Результаты сверки» обязательное поле «Результат ветеринарного осмотра груза»:

- Соответствует ветеринарным требованиям;
- Не соответствует ветеринарным требованиям.

Транспортные наблюдения могут предзаполнять результат, но окончательное значение подтверждает врач. Это позволит отразить несоответствие, не связанное только с состоянием кузова или совместной перевозкой.

## 6. Полное гашение без акта

### Обязательные сведения о принимаемой партии

- тип продукции `productType`;
- продукция `product` — UUID/GUID;
- вид продукции `subProduct` — UUID/GUID;
- наименование `productItem` — UUID/GUID или текстовое `name`;
- принятый объём `volume`;
- единица измерения `unit` — UUID/GUID;
- дата выработки `dateOfProduction`;
- признак скоропортящейся продукции `perishable`;
- происхождение `origin`, включая UUID/GUID страны;
- сведения входящего эВСД в `accompanyingForms/vetCertificate/UUID`.

Срок годности передаётся, если он установлен для продукции; для скоропортящейся продукции дата должна иметь необходимую точность.

### Проверка макета

- [x] Тип продукции, продукция, вид и название отображаются.
- [x] Вес отображается и может быть указан фактически.
- [x] Единица измерения видна в значении веса.
- [x] Дата выработки и срок годности отображаются.
- [x] Производитель отображается.
- [ ] UUID/GUID перечисленных объектов отсутствуют в HTML — их нужно сохранять из ответа API.
- [ ] В макете нет признака `perishable` и страны происхождения — новые видимые поля не требуются, если исходные коды всегда копируются из эВСД без изменения.
- [ ] Не определено, что делать, если полный объект входящего эВСД не загружен или не содержит необходимого идентификатора. В этом случае кнопку гашения нужно блокировать до повторной загрузки документа.

**Вывод:** новых ручных полей для обычного полного гашения не требуется. Нужна полноценная серверная модель исходного эВСД и личный логин врача.

## 7. Полное гашение с актом

Помимо данных полного гашения требуется `discrepancyReport`.

В акте обязательно должно быть заполнено хотя бы одно из значений:

- `reason/name`;
- `description`.

Текущие поля «Фактическое значение» и «Причина несоответствия» позволяют собрать электронный акт.

### Проблема фактической ТТН

Текущий макет предоставляет одно свободное поле «Фактическая ТТН». Этого недостаточно. Если блок `waybill` передаётся, «Меркурию» требуются структурированные реквизиты:

- тип документа — обязательный код 1–5;
- номер;
- дата;
- серия — при наличии.

При выборе «ТТН не соответствует» вместо одного текстового поля нужно показать:

- «Тип ТТН» — обязательный раскрывающийся список;
- «Номер ТТН» — обязательное поле;
- «Дата ТТН» — обязательное поле;
- «Серия ТТН» — необязательное поле;
- «Причина несоответствия» — обязательное поле.

Если ТТН отсутствует и в исходном эВСД, блок `waybill` не передаётся. Отсутствие фактической ТТН при наличии ТТН в эВСД должно быть отдельно описано как расхождение.

### Форматы дат

Текущие одиночные поля дат подходят для точной календарной даты. Интеграция также должна уметь без ручного ввода сохранить исходные:

- диапазоны дат;
- дату со временем;
- разрешённые текстовые значения `informalDate`.

Если врачу разрешается изменять такую дату, одного HTML-поля `date` недостаточно — потребуется соответствующий составной редактор.

## 8. Частичное гашение

Для частичного гашения одновременно передаются:

- `delivery/consignment` — принятая часть;
- `returnedDelivery/consignment` — возвращаемая часть;
- `deliveryFacts/decision=PARTIALLY`;
- возвратный эВСД;
- акт расхождений, если сумма принятого и возвращаемого объёмов отличается от входящего более чем на допустимую погрешность либо имеются другие разрешённые расхождения.

### Проверка макета

- [x] Есть выбор возвращаемых туш/частей.
- [x] Есть «Фактически доставлено».
- [x] Есть «Принято».
- [x] Есть «Возвращается».
- [x] Проверяется равенство `принято + возвращается = фактически доставлено`.
- [x] Есть обязательная причина возврата.
- [x] Для `OTHER_REASON` есть пояснение до 240 символов.
- [ ] Нужно дополнительно сравнивать `принято + возвращается` с объёмом входящего эВСД. Отклонение более 5% требует акта.
- [ ] Для каждой выбранной туши/части нужно хранить не только подпись, но и устойчивый идентификатор/маркировку и объём, чтобы одна часть не попала одновременно в принятую и возвращаемую партии.
- [ ] Необходимо подтвердить единицу измерения: принятая и возвращаемая части должны использовать единицу входящего эВСД.
- [ ] Нужно выполнить условия возврата из п. 10 и проверку регионализации из п. 11.

## 9. Полный возврат

При полном возврате `delivery/consignment` не передаётся. Передаются решение `RETURN_ALL` и `returnedDelivery`.

### Проверка макета

- [x] Есть решение «Полный возврат».
- [x] Показывается состав возвращаемой партии.
- [x] Есть обязательная причина возврата.
- [x] Для `OTHER_REASON` есть пояснение до 240 символов.
- [ ] Возвращаемый объём нужно определять из фактического веса, а не всегда копировать из эВСД.
- [ ] Возвращаемый объём не может отличаться от объёма входящего эВСД более чем на 5%. Для полного возврата `discrepancyReport` не передаётся, поэтому превышение нельзя исправить актом в этом сценарии.
- [ ] При превышении 5% вариант «Полный возврат» должен становиться недоступным с объяснением ограничения API.
- [ ] Нужно выполнить условия возврата из п. 10 и проверку регионализации из п. 11.

## 10. Обязательные условия возврата

По документации возвратом в рамках `ProcessIncomingConsignment` считается отправка груза:

- непосредственно в момент приёмки;
- исходному отправителю;
- в том же транспортном средстве.

Если возврат выполняется позднее или другим транспортом, это отдельное перемещение и отдельный транспортный эВСД, а не `returnedDelivery` рассматриваемого метода.

### Что добавить в макет

При выборе «Частичное гашение» или «Полный возврат» показать обязательное подтверждение:

> Возврат выполняется сейчас тем же транспортным средством, которым партия была доставлена.

- [ ] Без подтверждения отправку запроса блокировать.
- [ ] При несоответствии вида транспорта способ возврата через этот метод блокировать.
- [ ] При несоответствии номера ТС/прицепа выполнить предварительную проверку допустимости запроса. Для возвратного эВСД документация требует сведения транспорта, соответствующие входящему документу, а физически возврат должен выполняться тем же ТС.
- [ ] Если условие не выполняется, показать врачу, что возврат нужно оформить отдельным транспортным эВСД в «Меркурии».

## 11. Данные возвратного эВСД, которых нет в форме

`returnedDelivery` содержит много обязательных данных, но врач не должен вводить их повторно. Их нужно копировать или вычислять.

| Данные возврата | Источник |
|---|---|
| Отправитель возврата — ХС и площадка | Получатель входящего эВСД |
| Получатель возврата — ХС и площадка | Отправитель входящего эВСД |
| Тип, продукция, вид и наименование | Входящий эВСД |
| Единица измерения | Входящий эВСД |
| Дата выработки, срок годности, `perishable` | Входящий эВСД |
| Страна происхождения и производители | Входящий эВСД |
| Транспорт и способ хранения | Входящий эВСД с проверкой фактического ТС |
| ТТН возврата | Реквизиты входящего документа по правилам метода |
| Назначение груза `purpose` — UUID/GUID | Входящий эВСД, а не видимый текст |
| Результат ранее проведённой ВСЭ `cargoExpertized` | Машинное значение входящего эВСД: `VSEFULL`, `VSERAW` или `UNFULFILLED` |
| Причина возврата | Поле макета; для API v2 записывается в `specialMarks` после фразы «Причина возврата:» |

### Критический пробел данных

Блок «Ранее проведённая ВСЭ» в макете показывает человекочитаемые сведения, но не гарантирует наличие машинного `cargoExpertized`. Для возвратного эВСД этот элемент обязателен.

- [ ] Сохранять исходный код `cargoExpertized` из входящего документа, в том числе когда блок ранее проведённой ВСЭ не показывается.
- [ ] Не вычислять код только из текста «Результат осмотра» или заключения.
- [ ] Если код отсутствует в реально полученном документе и API не позволяет корректно восстановить его, возврат блокировать и показывать интеграционную ошибку.

## 12. Регионализация обратного маршрута

Для возврата правила регионализации проверяются заново и могут отличаться от правил исходной перевозки. Если обратный маршрут разрешён только при выполнении условий, в возвратном эВСД требуется передать `r13nClause/condition` с UUID/GUID условия.

- [ ] Перед показом доступного возврата выполнить проверку обратного маршрута через сервис регионализации.
- [ ] Если обязательных условий нет — ничего не спрашивать у врача.
- [ ] Если условия есть — показать их текст и обязательные флажки подтверждения.
- [ ] В запрос передавать UUID/GUID только подтверждённых условий.
- [ ] Если перевозка запрещена, отключить частичный и полный возврат с объяснением.

## 13. Необязательные данные, отсутствие которых не блокирует MVP

Следующие элементы есть в схеме, но не являются обязательными для рассматриваемого запроса во всех случаях:

- дата поступления/оформления `deliveryDate`;
- перевозчик `broker`;
- номер производственной партии `batchID`;
- упаковка и количество мест `packageList`;
- маркировка `productMarks`;
- признак некачественного груза `lowGradeCargo`;
- связанные документы;
- серия, номер и дата бумажного акта расхождений;
- благополучие местности и дополнительные ветеринарные мероприятия.

Их можно копировать из входящего эВСД, если они нужны для сохранения полноты данных. Отсутствие этих элементов в макете само по себе не мешает отправить базовый запрос.

### Важное замечание о связанных документах

Поле «Связанные документы» не является обязательным для гашения. Если система решит передавать связанные документы в возвратном эВСД, свободного текста текущего макета недостаточно: для каждого документа потребуются тип, тип связи и номер или дата. Альтернатива для MVP — не редактировать и не формировать их из текста, а копировать структурированные данные исходного эВСД, когда это разрешено.

## 14. Ошибки текущей логики макета, которые нужно исправить до интеграции

- [ ] Не считать полный возврат доступным при любом расхождении веса: действует предел 5% от входящего объёма.
- [ ] Не считать разницу между объёмом в эВСД и фактически доставленным объёмом автоматически возвращаемой продукцией.
- [ ] Проверять сумму принятого и возвращаемого объёмов относительно входящего эВСД, а не только относительно введённого «Фактически доставлено».
- [ ] Не разрешать возврат позднее или другим транспортом через `returnedDelivery`.
- [ ] Не пытаться сформировать ТТН из одной произвольной строки.
- [ ] Не использовать ФИО специалиста вместо логина пользователя «Меркурия».
- [ ] Не использовать отображаемый номер эВСД вместо UUID документа.
- [ ] Не использовать русские подписи справочников вместо UUID/GUID и кодов API.
- [ ] Не считать изменение маркировки автоматическим основанием для акта: актуальная документация указывает, что начиная с версии 6.7 изменение маркировки не требует акта. Расхождение объёма и количества упаковок нужно оценивать отдельно.
- [ ] Проверять тип документа: для импортного сертификата интеграционный шлюз не поддерживает частичный возврат и полный возврат.
- [ ] Для мультимодальной перевозки использовать транспорт последнего плеча и убедиться, что номера ТС внесены в «Меркурий» до гашения.

## 15. Минимальный набор изменений в макете

### Обязательно добавить

1. Структурированные реквизиты фактической ТТН при её несоответствии.
2. Подтверждение «Возврат выполняется сейчас тем же транспортным средством» для частичного и полного возврата.
3. Условия регионализации — условно, только когда их вернёт API.
4. Итоговый результат ветеринарного осмотра либо утверждённое автоматическое правило его получения.

### Не добавлять как ручные поля

- UUID/GUID объектов;
- логин «Меркурия» на каждой сверке;
- `issuerId`, `apiKey`, `serviceId`;
- страна происхождения и `perishable`, если они неизменно копируются из эВСД;
- назначение и результат прежней ВСЭ для возврата, если сохраняются их машинные значения;
- отправитель и получатель возврата — они меняются местами автоматически.

## 16. Интеграционные проверки перед отправкой

- [ ] Загружен полный актуальный объект входящего эВСД.
- [ ] Статус документа допускает гашение.
- [ ] Это тип документа, для которого выбранное решение поддерживается API.
- [ ] У активного пользователя есть личный логин «Меркурия» и необходимые полномочия.
- [ ] ХС и площадка лаборатории соответствуют получателю входящего эВСД.
- [ ] Все обязательные UUID/GUID доступны.
- [ ] Для принятой партии сформированы обязательные атрибуты `consignment`.
- [ ] Результаты документарного и ветеринарного осмотра определены.
- [ ] При акте есть причина или описание.
- [ ] При частичном возврате принятый и возвращаемый объёмы положительные.
- [ ] При полном возврате возвращаемый объём находится в разрешённом диапазоне.
- [ ] Возврат выполняется сразу и тем же транспортом.
- [ ] Проверена регионализация обратного маршрута.
- [ ] Для возвратного эВСД доступны `purpose` и `cargoExpertized` в машинном виде.
- [ ] Причина возврата преобразована в формат `specialMarks`, требуемый API v2.
- [ ] Запрос провалидирован по XSD выбранной версии.
- [ ] Операция не показывается успешной до получения успешного результата «Меркурия».
