## Реальный disposable PostgreSQL drill

Использован PostgreSQL 18.6 по digest из Compose, отдельные одноразовые Docker-
тома primary/backup/restore и physical slot `vse_backup`. Получатель достиг
`streaming:sync`; `pg_basebackup` прошёл `pg_verifybackup`.

Контрольный полный WAL-прогон:

- base backup + verify: 3,3 с;
- `SET LOCAL synchronous_commit=on`, tombstone+DELETE: 189,8 мс;
- delete LSN `0/3009A78`, receiver flush LSN `0/4000060`;
- restore+promotion: 3,2 с;
- после восстановления: examinations=0, tombstones=1, recovery=false.

Отдельный partial-WAL прогон оставил активный сегмент `.partial`, восстановил
его через fallback restore_command и остановился по XID 755:

- restore+promotion: 3,1 с;
- после восстановления: examinations=0, tombstones=1, recovery=false.

Все контейнеры, сеть и одноразовые тома обоих прогонов удалены после проверки.

## Честный внешний not-run

Не выполнено развёртывание на фактическом отдельном backup-хосте организации:
адрес, SSH host key, диски ≥2 TiB, replication secret и эксплуатационные ключи
не предоставлены. Поэтому измеренные 3,1–3,3 с не объявляются производственным
RTO, а production readiness/`DELETE_DURABILITY_ENABLED` остаются false.

Для открытия gate оператор должен выполнить `backup.md` и ежемесячный drill из
`restore.md` на целевых хостах, зафиксировать реальные RPO/RTO/capacity и
опубликовать свежий read-only readiness manifest. Без этого DELETE честно даёт
503, а остальные локальные сохранения продолжают работать.
