# ТЗ на приведение страниц «Поступления» к макетам

## 1. Задача

Необходимо переработать фронтенд раздела «Поступления», чтобы рабочая React-страница визуально соответствовала утверждённым HTML-макетам:

- `C:\electronic_lab_dev\arrivals.html` — этап «Ожидаемые»;
- `C:\electronic_lab_dev\arrivals-work.html` — этап «В работе»;
- `C:\electronic_lab_dev\arrivals-accepted.html` — этап «Завершенные».

Текущая реализация использует одну упрощённую универсальную таблицу и один набор фильтров для всех очередей. Это не соответствует макетам: три этапа имеют разный состав столбцов, разные фильтры и разные действия.

Задание предназначено для ИИ-агента, который будет менять код проекта.

Приоритет: высокий. Требуется именно визуальное соответствие макетам, а не косметическая правка существующей таблицы.

## 2. Границы задачи

### Входит в задачу

- маршрут `/labs/:labId/arrivals`;
- этапы `EXPECTED`, `WORK`, `ACCEPTED`;
- заголовок, описание, вкладки, счётчики, фильтры, таблицы, кнопки, меню, пагинация, состояния загрузки/ошибки/пустого результата;
- адаптивность и доступность;
- общие React-компоненты и stories для трёх этапов;
- визуальные регрессионные проверки по исходным HTML-макетам.

### Не входит в задачу

- изменение backend, БД, OpenAPI и правил формирования очередей;
- изменение серверной пагинации, поиска, прав доступа, синхронизации с ВетИС и скрытия поступления;
- изменение переходов между `EXPECTED`, `WORK` и `ACCEPTED`;
- добавление фиктивных значений, которых нет в API;
- реализация новых функций заключений, печати, отправки в Max или повторного осмотра, если соответствующего действующего API ещё нет;
- изменение страницы сверки данных — для неё существует отдельное ТЗ;
- реальный вызов гашения ВСД.

## 3. Источники истины

При расхождениях использовать следующий приоритет:

1. Внешний вид и композиция этапов — соответствующий HTML-макет из раздела 1.
2. Общая дизайн-система — `DESIGN.md`, `UX-CONTRACT.md`, `STORYBOOK.md`.
3. Общая шапка — существующий React-компонент `frontend/src/shared/ui/AppHeader.tsx`.
4. Реальные данные, переходы и доступность действий — текущие API-контракты и функциональные требования.
5. Существующие React-компоненты и тесты — доказательство текущей реализации, но не основание сохранять визуальное расхождение.

Макеты содержат демонстрационные данные. Их нельзя переносить в рабочий код. Нужно воспроизвести дизайн, заполняя экран реальными данными `IncomingView` и других уже существующих read-моделей.

## 4. Известные расхождения текущей реализации

Сейчас:

- рабочая область React-приложения допускает ширину 1440 px, а макеты поступлений используют максимум 1180 px;
- отсутствует подзаголовок страницы из макетов;
- вкладки выглядят как обычные прямоугольные кнопки, а должны быть компактными округлыми сегментами;
- счётчики этапов не показаны;
- фильтры одинаковые на всех этапах;
- есть отдельная кнопка «Найти», которой нет в макетах;
- таблица имеет одинаковые столбцы на всех этапах;
- кнопка перехода к сверке текстовая, а в макете действие компактное иконное;
- скрытие поступления спрятано в меню `…`, а в макете для ожидаемой строки есть отдельная красная контурная иконная кнопка;
- «В работе» не показывает требуемую структуру столбцов и различие действий «Создать ВСЭ»/«Продолжить создание ВСЭ»;
- «Завершенные» не имеют своей структуры, статусов, настройки столбцов и компактных действий;
- общая таблица не воспроизводит высоты, ширины, закреплённую колонку действий и геометрию исходных макетов;
- подсказка автоматической синхронизации визуально занимает место в основном фильтре, хотя в макете фильтр компактный.

## 5. Общее правило реализации

Нужно создать три визуально разных представления очереди на общей компонентной основе:

- `ExpectedArrivalsTable` или бизнес-эквивалент;
- `WorkArrivalsTable`;
- `CompletedArrivalsTable`.

Это могут быть композиции одного расширенного табличного примитива, но не одна неизменная таблица с одинаковыми столбцами для всех этапов.

Запрещено:

- копировать три большие таблицы с независимыми стилями;
- вставлять HTML-макеты целиком в React;
- переносить встроенный JavaScript из макетов;
- рисовать локальные SVG при наличии общей иконки;
- создавать вторую шапку приложения;
- менять API ради удобства верстки.

Сначала агент должен инвентаризировать общие владельцы: `AppHeader`, `Button`, `DataTable`, `Dialog`, `StatusView`, `Icon`, общие токены и Storybook. Если текущий `DataTable` не поддерживает нужную геометрию, его следует безопасно расширить через явно названные варианты и рендереры ячеек, не ломая другие таблицы.

## 6. Общая геометрия страницы

### 6.1. Рабочая область

- Максимальная ширина содержимого всех трёх этапов — 1180 px.
- Центрирование по горизонтали.
- Горизонтальный padding — 24 px на широком экране.
- Верхний padding — около 37 px.
- Нижний padding — около 96 px.
- На ширине до 800 px: горизонтальные отступы 16 px и верхний отступ около 28 px.
- Фон страницы — `#f5f9f8`.
- Общий документ не должен прокручиваться горизонтально; горизонтальная прокрутка принадлежит только таблице.

Не менять глобальную ширину всех экранов приложения. Для поступлений создать бизнес-вариант рабочей области или локальный контейнер, который использует общие токены.

### 6.2. Заголовок

На всех этапах:

- `h1`: «Поступления»;
- размер около 30 px;
- line-height около 1.15;
- letter-spacing около `-0.035em`;
- под заголовком — пояснение текущего этапа приглушённым цветом;
- расстояние от заголовка до вкладок соответствует макету.

Тексты:

- «Ожидаемые»: «Транспортные эВСД из системы „Меркурий“, где получателем указана текущая лаборатория»; название лаборатории брать из реального контекста, не хардкодить Казань.
- «В работе»: «Партии с пройденной сверкой данных».
- «Завершенные»: «Завершенные партии: сверка завершена, ВСЭ проведена или подтверждена, можно оформить заключение» — показывать только если это не противоречит реальному состоянию данных. Для возвращённых партий использовать честное пояснение.

## 7. Вкладки этапов

Вкладки должны выглядеть как в макетах:

- горизонтальный ряд с gap 9 px;
- высота не менее 40 px;
- форма pill, радиус 999 px;
- неактивная вкладка: белый фон, граница `#dfe9e9`, текст `#4d676d`;
- активная: фон и граница `#146c73`, белый текст, лёгкая тень;
- внутренние отступы около 15 px;
- шрифт плотный, около weight 760;
- справа от подписи — счётчик с отступом 7 px и пониженной контрастностью;
- до 800 px ряд вкладок прокручивается горизонтально внутри себя, не расширяя страницу.

Названия отображать точно:

- «Ожидаемые»;
- «В работе»;
- «Завершенные».

Не использовать пользовательские названия «Ожидается» и «Принято» в самих вкладках.

Состояние этапа продолжает храниться в URL `queue=expected|work|accepted`. Вкладки должны быть настоящими навигационными действиями с доступным текущим состоянием. Допустимы ссылки или tab-подобные кнопки, если URL и история браузера обновляются корректно.

### Счётчики

- Показывать реальное количество записей каждого этапа.
- Если текущий API не возвращает все три числа одним ответом, разрешается получить `total` существующими read-запросами для каждой очереди.
- Не считать общее количество по 20 строкам только текущей страницы.
- Не показывать демонстрационные `4`, `2`, `3`.
- Ошибка загрузки отдельного счётчика не должна блокировать основную очередь; допускается нейтральный прочерк.

## 8. Панель фильтров

### 8.1. Общий вид

Панель должна соответствовать макетам:

- белая поверхность;
- граница `#dfe9e9`;
- радиус 16 px;
- padding 16 px;
- лёгкая тень `0 8px 24px rgba(31, 90, 91, 0.03)`;
- нижний отступ 18 px;
- поля выровнены по нижнему краю;
- gap 12 px;
- подписи 11 px, плотные, приглушённые, в верхнем регистре с letter-spacing около 0.06em;
- высота input/select/trigger — 41 px;
- радиус поля — 9 px;
- граница `#cbdadb`;
- focus — бирюзовая граница и заметное кольцо;
- поиск имеет явную кнопку очистки, когда значение непустое;
- системный крестик `input[type=search]` не должен быть единственным способом очистки.

Видимую кнопку «Найти» удалить: в макетах её нет. Поиск запускается по Enter и/или после безопасного debounce 300 ms. При этом значение `q` остаётся в URL, смена фильтра сбрасывает страницу на 1, устаревший ответ не должен заменять новый.

### 8.2. «Ожидаемые»

Сетка фильтров:

```text
[ Поиск — широкое поле                         ] [ Сортировка ]
```

Поля макета:

- поиск: «Номер эВСД, хозяйство, продукция или ТС»;
- сортировка: «Сначала оформленные раньше / Сначала оформленные позже».

Важно: текущий серверный endpoint не принимает параметр сортировки. В рамках этой визуальной задачи нельзя делать ложную сортировку только внутри одной загруженной страницы. Если сервер не поддерживает глобальную сортировку, агент обязан:

1. воспроизвести визуальный вариант панели только для реально поддержанных контролов;
2. не добавлять работающий лишь на текущих 20 строках псевдофильтр;
3. зафиксировать сортировку как отдельный API-gap в отчёте, не меняя backend в этой задаче.

### 8.3. «В работе»

Сетка макета:

```text
[ Поиск                       ] [ Дата сверки данных       ] [ Сортировка ]
```

Дата в макете открывает компактный popover:

- переключатель «Дата / Диапазон»;
- для даты — одно поле;
- для диапазона — «С» и «По»;
- кнопки «Сбросить» и «Применить»;
- popover шириной поля, радиус 14 px, белый фон и тень;
- Escape закрывает и возвращает фокус в trigger;
- на узком экране popover помещается в viewport.

Текущий endpoint поступлений не содержит `date_from`, `date_to` и сортировку. Нельзя имитировать полноценную серверную фильтрацию только на текущей странице. Эти контролы реализовывать функционально только при наличии уже действующего read-контракта; иначе сохранить визуально согласованную компоновку доступных фильтров и честно указать API-gap.

### 8.4. «Завершенные»

Сетка макета:

```text
[ Поиск ] [ Дата сверки ] [ Результат ВСЭ ] [ Сортировка ] [ Столбцы ]
```

Требуемый внешний вид:

- поиск — широкое поле;
- дата — тот же общий date-filter, что у «В работе»;
- результат — нативный select в визуальном стиле макета;
- сортировка — нативный select;
- «Выбрать столбцы» — кнопка с иконкой сетки и popover чекбоксов.

Нельзя переименовывать существующие значения `WAITING / RETURNED / COMPLETED` в «Пригодно / Условно-пригодно / Непригодно»: это разные предметные понятия. Если API не предоставляет результат местной ВСЭ в списке и фильтре, не создавать ложный фильтр «Результат ВСЭ». Указать это как отдельный API-gap вне этой фронтенд-задачи.

### 8.5. Кнопка обновления ВетИС

Существующую функцию ручного обновления не удалять.

- Для ролей VET/HEAD разместить компактную вторичную кнопку «Обновить» справа в строке заголовка или в отдельной служебной зоне над фильтрами.
- Она не должна менять ширины полей фильтра из макета.
- На узком экране переносится под заголовок.
- Во время выполнения сохраняет размер и показывает busy-состояние.
- Автоматическое обновление каждые 15 минут остаётся без изменений.
- Постоянную длинную техническую подсказку не размещать внутри ряда фильтров. Обычный режим можно показать короткой приглушённой подписью; success/failure — через общий status/notification без скачка таблицы.

## 9. Табличная оболочка

Для всех этапов:

- белый фон;
- граница `#dfe9e9`;
- радиус 16 px (13 px на узком экране);
- лёгкая тень;
- overflow скрывает радиус оболочки, горизонтальная прокрутка находится во внутреннем контейнере;
- семантический `<table>`, не ARIA-grid;
- шапка таблицы высотой около 54 px;
- фон шапки `#f7faf9`;
- заголовки 11–12 px, приглушённые, плотные;
- строки высотой около 68–72 px;
- разделитель `#e8efef`;
- hover строки `#f8fcfb`;
- последняя колонка действий закреплена справа и имеет собственный белый фон;
- длинные значения сокращаются многоточием только там, где полный текст доступен через `title`, tooltip либо доступное имя;
- номер эВСД, дата и номер транспорта не переносятся на несколько строк;
- таблица не растягивает весь документ.

Убрать видимый generic-caption «Поступления лаборатории», если его нет в макете. Сохранить доступное имя таблицы через visually hidden caption.

## 10. Этап «Ожидаемые»

### 10.1. Столбцы и порядок

Строго как в `arrivals.html`:

1. Дата создания ВСД.
2. Номер эВСД.
3. Хозяйство.
4. Вид продукции.
5. Объём / масса.
6. Количество.
7. ТС.
8. Действия.

Не показывать отдельный столбец «Очередь»: активная вкладка уже задаёт контекст.

Использовать реальные доступные поля. Если дата создания или ТС отсутствуют в текущей read-модели, выводить `—`, не подставлять данные макета.

### 10.2. Действия

В строке две кнопки 40 × 40 px с радиусом около 11 px:

- красная контурная иконка корзины — существующая операция скрытия поступления;
- нейтральная контурная кнопка с иконкой сверки — ссылка «Перейти к сверке данных».

Важно:

- операция остаётся именно скрытием из локальной очереди, а не удалением эВСД из Меркурия;
- доступное имя: «Скрыть поступление из очереди»;
- диалог сохраняет текущие `If-Match`, idempotency, пояснение последствий и безопасный фокус;
- переход к сверке — отдельная ссылка, не действие меню и не клик по строке;
- tooltip доступен по hover и keyboard focus;
- иконки брать из общего реестра или добавить туда до использования.

## 11. Этап «В работе»

### 11.1. Столбцы и порядок

Строго как в `arrivals-work.html`:

1. Дата сверки данных.
2. Номер эВСД.
3. Хозяйство.
4. Вид продукции.
5. Объём / масса.
6. Количество.
7. Стоимость сверки.
8. Автор сверки данных.
9. Действие.

Не показывать столбец «Очередь».

Данные, которых нет в текущем API, обозначать `—`. Не вычислять цену или автора на клиенте и не брать текущего пользователя вместо реального автора.

### 11.2. Действия

- Обычная партия: квадратная бирюзовая кнопка 40 × 40 px с иконкой плюса и доступным именем «Создать ВСЭ».
- Существующая незавершённая форма/черновик: строка получает светло-серый фон `#eceff1`, действие меняется на серую кнопку с карандашом и именем «Продолжить создание ВСЭ».
- Если создание ВСЭ недоступно по реальному состоянию или правам, кнопка остаётся на месте для стабильной геометрии, но disabled и имеет доступное объяснение.
- Не определять наличие черновика по внешнему виду или локальному хранилищу; использовать существующий серверный факт.
- Переход использует реальный `party_id`/`examination_id` и действующий маршрут.

Если текущий API не отличает незавершённую форму от отсутствующей, агент не должен фабриковать состояние черновика; это отдельный read-model gap.

## 12. Этап «Завершенные»

### 12.1. Столбцы и порядок

Строго как в `arrivals-accepted.html`:

1. Дата сверки данных.
2. Номер эВСД.
3. Хозяйство.
4. Вид продукции.
5. Объём / масса.
6. Статус ВСД.
7. ВСЭ.
8. Стоимость.
9. Срок реализации.
10. Действия.

Дополнительные отключаемые столбцы макета:

- Автор сверки данных.
- Автор ВСЭ.
- Номер ВСЭ.

Не подменять недостающие сведения текущим пользователем или демонстрационными значениями. Не вычислять нормативный срок реализации на клиенте.

### 12.2. Статусы

- Статус ВСД показывать обычным текстом: например, «Погашен», «Частично погашен», «Возвращён» — только из реального состояния.
- Результат ВСЭ показывать текстом и смысловым цветом: пригодно — зелёный, условно-пригодно — предупреждение, непригодно — красный.
- Цвет не является единственным носителем смысла.
- Не обозначать ожидание окончательного результата как «Пригодно».
- Если отдельного результата ВСЭ в read-модели нет, выводить `—`, не выводить `COMPLETED` как ветеринарное заключение.

### 12.3. Настройка столбцов

- Кнопка высотой 41 px с иконкой сетки и текстом «Выбрать столбцы».
- Popover шириной около 308 px, с белым фоном, границей, радиусом 13 px и собственной вертикальной прокруткой при нехватке высоты.
- Чекбоксы имеют нормальные подписи и touch-target.
- Основные и дополнительные столбцы разделены визуально.
- Escape и клик вне закрывают popover, фокус возвращается на trigger.
- Настройка не должна скрывать колонку действий.
- Предпочтения можно держать только в текущей сессии, если отдельного требования хранения нет.

### 12.4. Действия завершённой строки

Визуально использовать компактные кнопки 36 × 36 px с радиусом 10 px, как в макете.

- Меню заключения с действиями «Скачать», «Печать», «В Max» показывать только если соответствующие функции реально реализованы и разрешены.
- Кнопку просмотра с иконкой глаза показывать только при существующем маршруте карточки/сводки.
- Не добавлять неработающие ссылки `#`, демонстрационные SVG или фиктивную отправку в Max.
- Если действие пока отсутствует в API, его не имитировать; допускается disabled-состояние только если оно действительно помогает объяснить ожидаемый следующий шаг и имеет tooltip.
- Меню и popover не должны обрезаться таблицей; при открытии имеют достаточный z-index.

## 13. Пагинация

Внешний вид как в макетах:

- центрирована под таблицей;
- верхний отступ около 18 px;
- кнопки 40 × 40 px;
- радиус 10 px;
- активная страница на бирюзовом tint;
- стрелки отдельными иконными кнопками;
- disabled визуально и семантически недоступны;
- доступные имена «Предыдущая страница» и «Следующая страница»;
- показывать номера страниц, когда их больше одной, а не только текст «Страница N из M».

Серверная пагинация по 20 записей сохраняется. Фильтр или смена этапа переводит на первую страницу. После скрытия последней строки текущей страницы перейти на существующую страницу, а не оставлять пустой номер.

## 14. Состояния экрана

Для каждого этапа реализовать:

- loading без скачка ширины таблицы;
- данные;
- пустая очередь;
- фильтр без совпадений;
- ошибка сети с повтором;
- отказ в доступе;
- длинные данные;
- открытое меню действия;
- узкий экран;
- загрузка следующей страницы;
- обновление из ВетИС в процессе, успешно и с ошибкой.

Тексты пустых состояний:

- «По заданным условиям эВСД не найдены»;
- «По заданным условиям поступления в работе не найдены»;
- «По заданным условиям завершенные поступления не найдены».

Пустое состояние должно отличаться от сетевой ошибки. При обновлении фильтра прежние строки нельзя внезапно заменять устаревшим ответом.

## 15. Storybook

Storybook является обязательной частью выполнения.

Текущая story `A01/Очередь поступлений` показывает только общий `ArrivalList` и не является достаточным доказательством соответствия макетам. Нужно создать/обновить stories на двух уровнях.

### 15.1. Компоненты

- Вкладки этапов: default, active, counts loading, узкий экран.
- Панель фильтров: expected, work, completed, date popover open, columns popover open.
- Таблица ожидаемых.
- Таблица в работе, включая серый черновик.
- Таблица завершённых, включая три тона результата.
- Иконные действия: default, hover/focus, disabled, danger.
- Пагинация: первая, средняя, последняя страница.

### 15.2. Полные страницы

- «Поступления / Ожидаемые».
- «Поступления / В работе».
- «Поступления / Завершенные».
- Каждый этап с длинными реальными по форме данными.
- Каждый этап на ширине 390 px.
- Loading, empty, no-results и network error.

Stories используют тот же React-код и стили, что рабочий маршрут. Запрещено копировать HTML-макет внутрь story для получения красивого снимка.

## 16. Адаптивность

Контрольные ширины: 1440, 1180, 1024, 800, 620 и 390 px, а также 200% browser zoom.

- До 1120 px фильтры перестраиваются в две колонки там, где это возможно.
- До 800 px фильтры становятся одноколоночными.
- Вкладки прокручиваются внутри ряда.
- Таблица остаётся таблицей и прокручивается горизонтально внутри оболочки; не преобразовывать строки в несвязанные карточки без отдельного согласования.
- Закреплённая колонка действий остаётся доступной.
- Popover даты и столбцов помещается в viewport.
- Tooltip и меню не обрезаются.
- На странице нет горизонтального скролла документа.
- Focus не скрывается sticky-колонкой или краями контейнера.

## 17. Доступность

- Цель — WCAG 2.2 AA.
- Использовать семантическую таблицу и `scope="col"`.
- У таблицы есть доступное название, но не обязательно видимый caption.
- Активная вкладка обозначена семантически, а не только цветом.
- Иконные кнопки имеют полные русские доступные имена.
- Tooltip не заменяет `aria-label`.
- Меню открывается клавиатурой, закрывается Escape, фокус возвращается к trigger.
- Поиск имеет label и кнопку очистки.
- Все поля фильтров имеют label.
- Результаты и ошибки объявляются через live-region общего компонента.
- Контраст, focus-visible и disabled соответствуют общим правилам приложения.
- Минимальная зона основных действий — 40 × 40 px; допустимые 36 × 36 px в плотной таблице должны иметь достаточный промежуток и быть проверены на touch.

## 18. Данные и честность интерфейса

- Использовать только реальные read-модели.
- Не показывать GUID/UUID вместо номера эВСД, названия продукции или хозяйства.
- Не хардкодить ИП Усманова, Казань, номера, даты, цены и результаты макетов.
- Не вычислять стоимость, срок реализации или автора на клиенте.
- Не выдавать очередь `ACCEPTED` за ветеринарный результат «Пригодно».
- Не выполнять клиентскую сортировку/фильтрацию только текущей серверной страницы, если пользователь ожидает фильтр всего набора.
- Все unsupported control/data gaps перечислить отдельно, но не расширять backend в рамках этой задачи.
- Ручное обновление ВетИС остаётся доступно только существующим ролям.
- Скрытие ожидаемого поступления остаётся локальной операцией и не удаляет ВСД из Меркурия.

## 22. Критерии приёмки

Задача принимается, если одновременно выполнены все условия:

1. Три этапа визуально соответствуют трём указанным HTML-макетам.
2. Рабочая область поступлений ограничена 1180 px и не использует текущую растянутую компоновку 1440 px.
3. Вкладки pill-формы имеют правильные названия и реальные счётчики.
4. Панели фильтров повторяют геометрию макетов; универсальный одинаковый фильтр для всех этапов удалён.
5. Нет лишней видимой кнопки «Найти».
6. Каждый этап имеет свой набор столбцов и действий.
7. В `EXPECTED` есть отдельные иконные действия скрытия и перехода к сверке.
8. В `WORK` действие создания/продолжения ВСЭ визуально соответствует состоянию.
9. В `ACCEPTED` статусы и компактные действия не фабрикуют отсутствующие функции и данные.
10. Пагинация и таблицы визуально совпадают с макетами.
11. Страница адаптивна, доступна с клавиатуры и не имеет горизонтального переполнения документа.
12. Реальные API, права, очередь, пагинация, синхронизация и скрытие работают как до изменения.
13. Не добавлены ложные фильтры текущей страницы вместо серверной фильтрации всего набора.
14. Storybook содержит состояния компонентов и три полных экранных примера.
15. Unit-, Storybook-, build- и e2e-проверки проходят; контрольные скриншоты приложены к отчёту.
