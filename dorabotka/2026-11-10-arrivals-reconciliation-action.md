# Доработка: явный переход из поступления к сверке данных

## Статус и причина

Это исправление дефекта реализации, а не новое продуктовое требование.

Переход к сверке уже закреплён источниками проекта:

- `Функциональные требования/v2.0/02-arrivals-and-receipt.md`, FT-ARR-02/03 — поступление проходит сохраняемую сверку;
- `docs/TZ_development/plans/ui-mapping.md` — канонический маршрут `/labs/:labId/arrivals/:partyId/reconciliation`;
- `docs/TZ_development/plans/2026-11-06-04-arrivals.md`, A01 — переход по реальному `party_id` и возврат с сохранением URL/context;
- `arrivals.html` — в каждой строке ожидаемого поступления есть отдельное действие с доступным именем «Перейти к сверке данных».

Текущая React-реализация в `frontend/src/features/arrivals/ArrivalList.tsx` помещает ссылку только в текст первой ячейки («Продукция»). `DataTable` не показывает отдельное действие перехода в последнем столбце. Пользователь не получает предусмотренную макетом явную кнопку и воспринимает строку как неоткрываемую.

## Цель

В таблице поступлений сделать заметное и доступное действие «Перейти к сверке данных», ведущее на сверку выбранной партии по её реальному `party_id`.

## Перед началом

1. Прочитать `AGENTS.md`, `DESIGN.md`, `UX-CONTRACT.md`, `STORYBOOK.md` полностью.
2. Изучить `arrivals.html`, существующие `ArrivalList`, `DataTable`, их CSS, tests и stories.
3. Не менять фреймворк, маршруты, API поступлений, модель данных или правила гашения.
4. Не выполнять живой `ProcessIncomingConsignment` и не гасить тестовый эВСД.

## Требуемое поведение

### Список поступлений

1. В последнем столбце каждой строки показать отдельную ссылку-кнопку перехода к сверке.
2. Доступное имя действия: `Перейти к сверке данных`.
3. Адрес строить только так:
   `/labs/{laboratory_id}/arrivals/{party_id}/reconciliation`.
4. Использовать `party_id` из API. Запрещено подставлять `incoming_document.id`, UUID эВСД или идентификатор из XML.
5. Действие присутствует в очередях `EXPECTED`, `WORK` и `ACCEPTED`: в незавершённой сверке открывает редактирование, в сохранённой/завершённой — существующий экран в разрешённом сервером режиме.
6. Для ожидаемой неподтверждённой партии рядом остаётся самостоятельное действие «Скрыть из очереди». Переход к сверке не должен находиться внутри меню скрытия.
7. Клик по переходу не открывает диалог скрытия и не отправляет мутацию.
8. Ссылка работает мышью, клавишей Enter и при последовательном Tab-переходе. Фокус видим.
9. На узком экране действие остаётся доступным внутри горизонтально прокручиваемой таблицы и не перекрывается меню строки.
10. После возврата со сверки сохраняются лаборатория, очередь, поиск и страница списка согласно FT-COM-02. Если для этого используется параметр возврата или состояние маршрута, в URL не должны попадать секреты и исходный XML.

### Внешний вид

1. Ориентир — действие сверки в `arrivals.html`, но реализация должна использовать существующие React-компоненты и токены, без копирования локального SVG/CSS из HTML-макета.
2. Сначала расширить существующий API `DataTable`, если он не умеет показывать ссылку-действие рядом с меню. Не создавать отдельную копию таблицы для поступлений.
3. Если добавляется постоянное публичное свойство общего компонента, описать его рядом с компонентом/в README и показать в Storybook.
4. Иконка без текста допустима только при наличии `aria-label="Перейти к сверке данных"` и не должна зависеть от hover-подсказки для понимания назначения. Предпочтителен видимый текст «Сверить», если общий компонент не поддерживает согласованную иконку.

## Обязательные проверки

### Компонентные тесты

1. Строка содержит ссылку с доступным именем `Перейти к сверке данных`.
2. `href` содержит `labId` и реальный `party_id`.
3. В `href` отсутствует `evsd_uuid`.
4. Ссылка присутствует для `EXPECTED`, `WORK`, `ACCEPTED`.
5. Для `EXPECTED` одновременно доступны переход и «Скрыть из очереди»; одно действие не вызывает другое.
6. Строка без права скрытия всё равно имеет переход к сверке при наличии права чтения партии.

### Маршрутный/e2e сценарий

1. Открыть `/labs/:labId/arrivals?queue=expected` с одной реальной строкой.
2. Нажать `Перейти к сверке данных`.
3. Убедиться, что открыт `/labs/:labId/arrivals/:partyId/reconciliation` и показаны данные той же партии.
4. Вернуться к поступлениям и проверить сохранение queue/search/page.
5. Повторить переход клавиатурой.
6. Проверить ширину 390 px и длинные значения.

## Критерии приёмки

- Пользователь `VET` или `HEAD`, имеющий область лаборатории, видит у каждой доступной партии явное действие перехода.
- Для импортированной партии Агропромышленного парка открывается сверка партии, а не UUID документа.
- Нет заглушки, пустого клика, полной перезагрузки на неправильный URL или скрытой зависимости от текста продукции.
- Существующие фильтры, синхронизация ВетИС и скрытие ожидаемого поступления не сломаны.
- Backend-контракты и миграции не изменялись без доказанной необходимости.
- `npm.cmd run test:unit`, `npm.cmd run build`, `npm.cmd run build-storybook` и целевой Playwright-сценарий проходят.
- Живое гашение ВетИС не выполнялось; в evidence это явно записано.

## Результат агента

Агент должен:

1. реализовать доработку в отдельной ветке;
2. приложить перечень изменённых файлов и результаты проверок;
3. сделать скриншот строки с действием и экрана сверки после перехода;
4. слить ветку в `main` только после прохождения критериев приёмки;
5. не менять и не коммитить реальные credentials ВетИС.
