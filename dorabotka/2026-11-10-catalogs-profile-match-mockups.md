# ТЗ на приведение страниц «Справочники» и «Профиль» к эталонным макетам

## 1. Задача

Переработать только фронтенд React SPA для двух маршрутов:

- `http://127.0.0.1:8080/catalogs` — раздел «Справочники»;
- `http://127.0.0.1:8080/profile` — профиль пользователя.

Эталон внешнего вида:

- `C:\electronic_lab_dev\directories.html`;
- `C:\electronic_lab_dev\profile.html`;
- связанные стили и компоненты из `components/profile/`, `components/app/`,
  `components/shell/`.

Цель — визуально приблизить рабочие SPA-страницы к этим макетам, не перенося
демонстрационные данные и старый встроенный JavaScript в production-код.
Маршруты, реальные данные, API, права доступа, обработчики сохранения и
смены пароля должны продолжить работать.

Это ТЗ предназначено для ИИ-агента, который будет вносить изменения в
существующий репозиторий.

## 2. Критические ограничения по сохранности данных

Это обязательные правила, нарушение которых является провалом задачи.

1. Не менять backend, миграции, OpenAPI, модели БД, seed-скрипты и правила
   формирования ВСД/ВСЭ.
2. Не удалять и не пересоздавать пользователей, лаборатории, продукцию,
   справочники, поступления, ВСД, ВСЭ, пробы или отчёты.
3. Не выполнять `docker compose down -v`, не удалять Docker volume
   `postgres_data`, не очищать БД и не запускать destructive seed/reset.
4. Не добавлять временные DELETE-запросы, массовые мутации или «очистку для
   удобства теста». Проверять изменения только на существующих данных либо
   на изолированных тестовых фикстурах.
5. Не заменять реальные данные макетными значениями из HTML. Имена Анна
   Кузнецова, UUID, числа и подписи из макета — только образец композиции.
6. Не менять контракты API ради удобства вёрстки. Если данных для элемента
   макета нет в API, не выдумывать их: скрыть элемент, показать честное
   состояние или зафиксировать API-gap.
7. Перед началом проверить `git status`. Не перезаписывать и не удалять уже
   существующие пользовательские изменения, в том числе:
   `frontend/tests/e2e/seed_identity.py`, `DESIGN.md` и другие незакоммиченные
   файлы. Изменять только файлы, относящиеся к задаче.

## 4. Область изменений

### Входит в задачу

- визуальная композиция `/catalogs` и его вкладок/редакторов;
- визуальная композиция `/profile` и адаптивное поведение;
- активные состояния пунктов шапки для этих маршрутов;
- замена галочки в бренде SPA-шапки на логотип;
- локальные React-компоненты, CSS, stories и адресные тесты, необходимые для
  безопасного результата;
- проверка в браузере на широком и узком экране;
- пересборка frontend-контейнера Docker.

### Не входит в задачу

- backend, БД, миграции и API;
- изменение состава или смысла полей профиля;
- реализация новых операций со справочниками, пользователями или ВСД;
- изменение прав ролей и областей видимости данных;
- изменение legacy-макетов `directories.html` и `profile.html`;
- перенос приложения на другой фреймворк;
- удаление существующих тестов ради прохождения сборки.

## 5. Общие правила реализации

1. Текущий стек сохраняется: React/TypeScript/Vite внутри `frontend/`.
2. Один источник шапки — `frontend/src/shared/ui/AppHeader.tsx` и его CSS.
   Не создавать шапку локально внутри `CatalogsPage` или `ProfilePage`.
3. Использовать рабочие компоненты, а не auth-варианты: `Button`, `InfoField`,
   `Dialog`, `StatusView`, `Icon` и текущие API редакторов.
4. Стили строить на существующих токенах из `frontend/src/shared/ui/ui.css`
   и согласованной палитре: фон `#f5f9f8`, поверхность `#fff`, линия
   `#dfe9e9`, основной бирюзовый `#146c73`, тёмный бирюзовый `#0d5358`,
   текст `#17323a`, приглушённый текст `#566e75`/`#668087`.
5. Не менять глобальную ширину всех страниц приложения. Для каждой страницы
   использовать локальный контейнер с геометрией эталона.
6. Не скрывать данные только потому, что их неудобно разместить. Длинные
   значения должны переноситься или быть доступны полностью через `title`/
   доступный текст.
7. Сохранить видимый `focus`, управление клавиатурой, `aria-label`,
   `aria-current`, `aria-expanded`, `aria-invalid` и безопасное закрытие
   диалогов по Escape.
8. Состояния `loading`, `empty`, `forbidden`, `network-error`, ошибки
   сохранения и недоступные действия должны оставаться честными и визуально
   согласованными с приложением.

## 6. Единая шапка и логотип

Сейчас React-шапка выводит:

```tsx
<span className="brand-logo" aria-hidden="true">
  <Icon name="check" className="brand-mark" />
</span>
```

Нужно заменить это на логотип из файла:

`C:\electronic_lab_dev\vse-lab-icon-transparent.png`

В результате в бренде не должно быть иконки `check`. Нельзя рисовать логотип
новым SVG или заменять его другой картинкой.

Требования:

- использовать содержимое именно указанного PNG;
- сохранять размер слота логотипа `43 × 43 px` и текущую геометрию шапки;
- изображение декоративное: `alt=""`, `aria-hidden="true"`;
- сохранить ссылку бренда и доступное имя «Электронная лаборатория ВСЭ —
  главная»;
- логотип должен работать в локальном Vite и внутри production Docker image;
- не подключать файл из `C:\...` во время выполнения браузера.

Так как `deploy/frontend.Dockerfile` копирует в образ `frontend/`, сделать
исходный PNG доступным SPA безопасно: положить копию исходного файла в
`frontend/public/vse-lab-icon-transparent.png` либо изменить сборку
эквивалентным способом. Копия должна побайтно совпадать с корневым файлом;
не создавать новый вариант логотипа. Проверить, что после Docker-сборки
запрос к `/vse-lab-icon-transparent.png` возвращает изображение.

В `/catalogs` пункт «Справочники» должен иметь активное состояние и
`aria-current="page"`. В `/profile` должна быть активна ссылка пользователя
/ профиля с доступным текущим состоянием. Геометрию шапки не переопределять
локальными стилями страниц.

## 7. Страница «Справочники» — `/catalogs`

### 7.1. Общая композиция

Маршрут без выбранной вкладки должен быть обзором, визуально соответствующим
`directories.html`:

```text
Шапка приложения

[ Справочники ]
Управление справочниками

┌──────────────────────────────────────────────────────────────┐
│ [иконка] Список справочников                                 │
│          Настройки, которые используются при заполнении ...  │
│                                                              │
│ [иконка] Стоимость исследований ВСЭ       [Редактировать]    │
│          описание                           [действие*]       │
│                                                              │
│ [иконка] Платные услуги                     [Редактировать]   │
│          описание                           [действие*]       │
│                                                              │
│ [иконка] Нормы исследований                 [Редактировать]   │
│          описание                           [действие*]       │
└──────────────────────────────────────────────────────────────┘
```

`*` — только реально существующее действие. Не добавлять фиктивное удаление
только ради совпадения с демонстрационным HTML.

Геометрия:

- локальный максимум страницы около `1180 px`;
- горизонтальные поля `24 px`, верхний отступ около `37 px`, нижний около
  `96 px`;
- фон `#f5f9f8`;
- заголовок `h1` около `30 px`, line-height `1.15`, letter-spacing около
  `-0.035em`;
- маленький текст «Справочники» над заголовком — бирюзовый eyebrow;
- одна белая секция с границей, радиусом около `18 px`, лёгкой тенью и
  внутренним отступом около `25 px`;
- строки справочников — белые, с тонкой рамкой, радиусом около `13 px`,
  внутренним отступом около `17–18 px`;
- кнопки должны использовать рабочий `Button`/его согласованный стиль, а не
  кнопку авторизации.

### 7.2. Отображаемые справочники и маршруты

Сохранить соответствие между человеческим названием карточки и текущим API:

| Карточка макета | Текущий раздел SPA | URL/состояние |
| --- | --- | --- |
| «Стоимость исследований ВСЭ» | tariffs | `tab=tariffs` |
| «Платные услуги» | check-services | `tab=check-services` |
| «Нормы исследований» | methods | `tab=methods` |

Порядок карточек именно такой. Ссылки/кнопки «Редактировать» должны открывать
соответствующий существующий редактор, сохраняя лабораторию и вид продукции
в query-параметрах.

Существующие маршруты `/catalogs/methods` и `/catalogs/tariffs` должны
продолжить открывать нужный раздел. Если введён неизвестный `tab`, выбрать
безопасное обзорное состояние либо текущий согласованный fallback, но не
запрашивать данные с пустыми/чужими идентификаторами.

### 7.3. Реальные данные и действия

- Карточки обзора не должны показывать демонстрационные строки из
  `directories.html` как данные API.
- Описания карточек можно взять из эталона как статический UI-текст, но
  значения, статусы, UUID и списки должны поступать из текущей модели.
- Сохранить добавление, редактирование, удаление и массовую цену там, где
  такие операции уже есть в текущих редакторах и разрешены ролью.
- Не переносить демонстрационные кнопки удаления из HTML, если у конкретного
  раздела нет действующего delete-контракта. Никакого fake delete.
- При отсутствии `laboratory_id`/`product_species_id` показать честное
  состояние выбора области и компактный рабочий контрол, но не заполнять
  UUID из макета и не угадывать лабораторию.
- Сохранить `If-Match`, ревизии, обработку 409/403, повтор загрузки и
  отображение `readiness`.
- Формы редакторов остаются диалогами с текущим API; переделывается их
  визуальная композиция только настолько, насколько нужно для единого вида.

### 7.4. Вкладки и редакторы

Если вкладки остаются видимыми в режиме конкретного редактора, оформить их как
согласованные с макетом компактные pill-кнопки/ссылки:

- активная: `#146c73` с белым текстом;
- неактивная: белая с границей `#dfe9e9`;
- радиус около `999 px`, высота около `40 px`, gap около `9 px`;
- активное состояние доступно через `aria-current` или эквивалентный
  семантический атрибут.

Обзор не должен превращаться в таблицу только потому, что текущая реализация
начинается с таблицы. Таблицы списков и редакторы остаются доступны после
выбора карточки.

## 8. Страница «Профиль» — `/profile`

### 8.1. Общая композиция

Страница должна использовать композицию `profile.html` и CSS-владельца
`components/profile/profile.css`, адаптированную к React без копирования
vanilla-разметки один в один:

```text
Шапка приложения

Профиль пользователя

┌───────────────────┐  ┌────────────────────────────────────────┐
│      [аватар]     │  │ [иконка пользователя] Данные пользователя│
│  Фамилия и имя    │  │ [Фамилия и имя] [Логин]                 │
│  логин            │  │ [Учреждение/область] [Роль/должность]  │
│                   │  │ [Email/другая доступная информация]    │
│ Права доступа     │  │                                        │
│ [теги прав]       │  │ ───── Безопасность ─────────────────── │
│                   │  │ Смена пароля                           │
│ Доступные типы    │  │ [текущий] [новый] [Сохранить]           │
│ [мясо]            │  │                                        │
│ [молоко]          │  └────────────────────────────────────────┘
└───────────────────┘
```

Геометрия:

- локальный максимум `1180 px`, горизонтальный padding `24 px`, верхний
  padding около `37 px`, нижний около `96 px`;
- заголовок около `30 px`;
- grid: левая колонка около `330 px`, правая — оставшееся место, gap около
  `18 px`;
- обе карточки белые, border `#dfe9e9`, radius около `18 px`, лёгкая тень;
- левая карточка выравнивает аватар и идентификацию по центру;
- правая карточка содержит заголовок с иконкой, сетку информационных полей и
  отдельный блок безопасности с верхним разделителем;
- информационные поля — `InfoField`, не редактируемые inputs;
- не использовать большие auth-кнопки и auth-поля в рабочем профиле.

### 8.2. Левая карточка

Сохранить визуальные элементы эталона:

- круглый аватар/инициалы примерно `112 × 112 px`;
- демонстрационный выбор фото допускается только как визуальная функция:
  файл не загружать, не сохранять, не отправлять в API и не помещать в URL;
- камера появляется при hover/focus, но не должна быть единственным способом
  понять действие;
- ФИО и логин — из `GET /me`, без хардкода демонстрационного пользователя;
- права доступа — компактные бирюзовые теги из реального `capabilities`;
- доступные виды продукции показывать только если их можно получить из
  реальных scope/контекста; при отсутствии назначений блок не рисовать,
  как требует `components/profile/README.md`;
- не выводить сырые технические UUID как замену названию продукта или
  учреждения, если API не предоставляет человекочитаемое имя.

### 8.3. Правая карточка и безопасность

- Отображать реальные поля пользователя: ФИО, логин, email, роль,
  должность и доступные области в понятной русской форме.
- Если в текущем API отсутствуют «дата регистрации», точное учреждение или
  другое поле из макета, не выдумывать значение и не брать его из HTML.
  Сохранить сетку и показать только подтверждённые данные.
- `ROLE_LABELS` и существующие русские подписи использовать вместо сырых
  enum-значений там, где это уже поддержано кодом.
- Форму смены пароля оставить рабочей: текущий/новый пароль не сохраняются,
  не попадают в URL/localStorage/логи; повторная отправка блокируется; ошибки
  остаются у полей; обработка успешной смены и отзыв сессий сохраняется.
- Сохранить текущий переход «Войти заново» после успешной смены пароля и
  возврат на `/login`.
- Не добавлять редактирование ФИО, логина, email, роли, прав или scope на
  странице профиля, если такого API уже нет.

### 8.4. Адаптивность

- До `900 px` две карточки переходят в одну колонку.
- До `800 px` поля профиля и поля пароля переходят в одну колонку.
- Боковые отступы на узком экране — около `16 px` для контента и текущая
  компактная геометрия общей шапки.
- Не должно быть горизонтальной прокрутки всего документа.
- Длинные ФИО, логины и email должны переноситься.

## 10. Тесты и визуальная проверка

До изменений зафиксировать текущие результаты тестов, после изменений
сравнить их с новыми.

Обязательно выполнить:

```powershell
cd C:\electronic_lab_dev\frontend
npm.cmd run typecheck
npm.cmd run lint
npm.cmd run build
npm.cmd run test -- --run
```

Если изменены stories или общие библиотечные компоненты:

```powershell
npm.cmd run build-storybook
```

Проверить в браузере/Playwright:

1. Авторизованный пользователь с существующими данными открывает `/catalogs`:
   видит обзор из трёх карточек; переходы в нормы, тарифы и услуги сверки
   открывают правильные существующие состояния.
2. `/catalogs?laboratory_id=...&product_species_id=...&tab=methods` и
   `tab=tariffs` сохраняют редакторы, загрузку, readiness, права и реальные
   строки.
3. Создание/изменение/удаление существующих поддержанных записей продолжает
   использовать текущие API и не затрагивает другие записи.
4. `/profile` показывает данные текущего пользователя, права и scope, не
   показывает данные другого пользователя и не использует demo-имя.
5. Смена пароля сохраняет текущий e2e-контракт, ошибки и переход на login.
6. В шапке на обеих страницах показывается PNG-логотип, а не галочка; у
   запроса картинки нет 404.
7. Проверить размеры минимум `1440`, `1024`, `768`, `390 px`.

## 12. Git, ветка и GitHub

Работать в отдельной ветке от актуального `main`. Не коммитить чужие
незакомченные изменения и не делать force-push.

Перед завершением:

1. проверить `git diff`, `git status` и список изменённых файлов;
2. убедиться, что изменения ограничены этой задачей;
3. создать понятный коммит, например:
   `feat: align catalogs and profile pages with mockups`;
4. отправить ветку в GitHub;
5. обновить локальный `main` через `git pull --ff-only`;
6. объединить рабочую ветку с `main` без потери истории;
7. отправить обновлённый `main` в `origin`.

Рекомендуемый безопасный порядок после коммита рабочей ветки:

```powershell
git push -u origin HEAD
git switch main
git pull --ff-only
git merge --no-ff <имя-рабочей-ветки>
git push origin main
```

Если GitHub запрещает прямой push/merge в `main`, агент не должен обходить
защиту или делать force-push. В этом случае создать Pull Request в `main`,
указать результаты тестов и Docker-проверки и явно сообщить, что объединение
ожидает разрешения владельца.
