# ТЗ на исправление потери подходящих входящих ВСД в поступлениях

Дата: 11.11.2026  
Приоритет: высокий  
Тип задачи: backend/integration + read model + frontend diagnostics + tests

## 1. Проблема

На странице:

`http://127.0.0.1:8080/labs/2812e437-facc-432f-9242-5162c9d9f49f/arrivals?queue=expected`

отображается один входящий ВСД, хотя при разрешённом read-only запросе
`GetVetDocumentList` из `docs/TZ_development/plans/API REQUESTS.txt`/текущего
тестового профиля ВетИС могут приходить два и более подходящих документа.
Количество документов не ограничено двумя: система должна показывать все
документы, удовлетворяющие критериям, независимо от их количества.

## 2. Результат расследования и корневая причина

### 2.1. Что делает экран сейчас

Экран не запрашивает ВетИС из браузера. Цепочка такая:

```text
ВетИС GetVetDocumentList
        ↓ read-only sync worker
upsert_incoming → PostgreSQL parties/incoming_documents
        ↓
GET /api/v1/arrivals
        ↓
ArrivalsPage → таблица «Ожидаемые»
```

`frontend/src/pages/ArrivalsPage.tsx` запрашивает локальный
`GET /api/v1/arrivals`, а `backend/src/modules/arrivals/queries.py` читает
только уже сохранённые локальные `parties`. Поэтому отсутствие строки на
экране означает, что документ не был импортирован в локальную БД либо был
отфильтрован до импорта. Frontend не может показать документ, которого нет в
локальном read model.

### 2.2. Фактическое состояние локального окружения

Для лаборатории `2812e437-facc-432f-9242-5162c9d9f49f` read-only проверка БД
показала:

- `parties` для лаборатории: **1**;
- единственный локальный UUID: `e13bda81-7cf6-4b2b-b1aa-3c99e25adaac`;
- последние операции синхронизации: `FAILED`;
- причина последних операций: `INTEGRATION_NOT_CONFIGURED`;
- `pages_done=0`, `imported=0`.

В `backend/resources/vetis/manifest.json` сейчас:

```json
"schema_pins": {
  "status": "PENDING",
  "wsdl": null,
  "xsd": []
}
```

`VetisReadAdapter.require_live_ready()` намеренно запрещает сетевой вызов,
если WSDL и XSD не закреплены checksum. Поэтому worker останавливается до
первого SOAP-вызова и не может импортировать второй ВСД. Единственная строка
в БД — ранее импортированная запись, а не результат текущего полного
успешного прохода.

### 2.3. Что не является причиной

- Не найден лимит «один ВСД» в `GET /api/v1/arrivals`.
- Локальная пагинация использует 20 строк на страницу, а не 1.
- `arrival_page()` применяет `.limit(20)` и возвращает `Page.total`.
- `ArrivalsPage` отображает все `items`, полученные от API, без `slice(0, 1)`.
- В adapter уже предусмотрен обход внешних страниц через `next_cursor`.

При этом эти утверждения нужно закрепить автоматическими тестами на 2, 21 и
большее число документов.

### 2.4. Важное замечание об API REQUESTS

В сохранённом примере `API REQUESTS.txt` в одном из ответов указан
`total="1"`. Это пример ответа, а не доказательство текущего состояния
внешнего контура. Если фактический read-запрос сейчас возвращает два
документа, при приёмке нужно сохранить только обезличенное доказательство:
UUID документов, критерии их соответствия и счётчики, без credentials,
apiKey, issuerId, логинов, паролей и полного SOAP XML.

## 5. Бизнес-критерий подходящего входящего ВСД

После получения внешних страниц документ импортируется в мясную очередь
только если одновременно выполнено:

```text
consignee.enterprise.guid == привязанная площадка лаборатории
AND vd:vetDType == TRANSPORT
AND vd:vetDStatus == CONFIRMED
AND vd:certifiedConsignment/vd:batch/vd:productType == 1
```

Это соответствует `mercury-test-integration-contract.md`, V01 и FT-ARR-01.

Важно:

- `productType` нельзя угадывать по названию продукции;
- отсутствующий/неразбираемый `productType` не считается равным `1`;
- неподходящий документ не должен появляться в мясной очереди;
- но подходящий документ нельзя молча потерять;
- для каждого внешнего документа должна быть диагностическая причина
  `kept` или `filtered: receiver|transport|status|product_type`.

## 6. Исправление конфигурации read-only интеграции

### 6.1. Закрепление схем

Сделать разрешённым read-only запуск только после корректной установки:

1. Получить WSDL и все импортируемые XSD из закреплённого endpoint.
2. Проверить namespace, SOAP actions, serviceId и структуру операций по
   manifest и документации ВетИС.
3. Рассчитать SHA-256 каждого ресурса.
4. Разместить схемы и файл pins в server-side конфигурации установки.
5. Перевести `schema_pins.status` в `PINNED` только после проверки checksum.
6. При несовпадении checksum оставить интеграцию заблокированной с понятной
   ошибкой, а не выполнять сетевой вызов.

Нельзя обходить `require_live_ready()` или хардкодить `PINNED` без файлов и
проверки SHA-256.

### 6.2. Server-side secret profile

Оператор установки должен передать backend и `vetis-worker` один и тот же
внешний secret profile через `VETIS_SECRET_PROFILE`; schema pins и каталог
схем — через существующие `VETIS_SCHEMA_PINS`/`VETIS_SCHEMA_DIR` или
эквивалентную поддержанную конфигурацию.

Секреты не должны попадать во frontend, OpenAPI, БД, логи, Git или ТЗ с
конкретными значениями.

Проверить отдельно:

- worker видит secret profile;
- worker видит pins и схемы;
- `issuer_id`, apiKey, gateway credentials и read initiator загружаются из
  server-side profile;
- binding лаборатории указывает на правильный `PILOT`-контур,
  `business_member_id` и `enterprise_id`;
- `write_capability=false` и `VETIS_WRITE_ENABLED=false` сохраняются.

### 6.3. Ошибка конфигурации должна быть видна

Если интеграция не настроена, UI не должен создавать впечатление, что
«подходящих ВСД нет» или что полный sync выполнен. Сохранить честное состояние
операции `FAILED / INTEGRATION_NOT_CONFIGURED`, а на странице показать:

> Обновление из ВетИС недоступно: интеграция не настроена.

Кнопка «Обновить» не должна показывать успешное обновление при таком исходе.
В диагностике должны быть доступны код проблемы, число обработанных страниц и
число импортированных документов, но не credentials/raw SOAP.

## 7. Полный импорт всех страниц

### 7.1. Внешний запрос

Сохранить read-only запрос `GetVetDocumentList` с:

- `vetDocumentType=INCOMING`;
- `vetDocumentStatus=CONFIRMED`;
- привязкой к текущей площадке;
- `count <= 1000`;
- корректным `offset`/cursor.

`productType` не фильтруется внешним API, поэтому локальная фильтрация из
раздела 5 обязательна.

### 7.2. Обход страниц

Проверить и при необходимости исправить adapter/worker так, чтобы:

1. первый запрос начинался с `offset=0`;
2. каждый ответ обрабатывал все `vetDocument` страницы;
3. следующий запрос выполнялся, пока не достигнут внешний `total`;
4. `next_cursor` не терялся между итерациями и после restart;
5. повтор страницы не создавал дубль по `(contour, evsd_uuid)`;
6. изменение порядка/перекрытие страниц не теряло новый UUID;
7. полный проход из 2, 21, 100 и 100+ подходящих документов импортировал
   соответственно 2, 21, 100 и все доступные документы;
8. checkpoint `last_success` двигался только после полного успешного прохода;
9. частичный/ошибочный проход не очищал локальные документы и не объявлялся
   успешным пустым результатом;
10. повторный полный проход был идемпотентным.

### 7.3. Ошибка одного документа

Если один документ не проходит бизнес-предикат — сохранить счётчик причины и
продолжить страницу. Если подходящий документ не удаётся нормализовать или
сохранить из-за ошибки данных:

- не терять его молча;
- записать обезличенную диагностику с внешним UUID, этапом и кодом ошибки;
- не подменять его другим документом;
- определить и покрыть тестом политику атомарности страницы: допустимо
  продолжить импорт остальных валидных документов, но операция обязана быть
  `FAILED`/неуспешной до исправления проблемного документа, если полный
  проход не завершён.

## 8. Локальная очередь и API `/arrivals`

Проверить, что после успешного sync:

- для каждой импортированной подходящей записи создаётся ровно одна пара
  `incoming_documents` + `parties`;
- `GET /api/v1/arrivals?laboratory_id=...&queue=EXPECTED&page=1` возвращает
  `total` равный числу локальных ожидаемых записей;
- `items` содержит до 20 записей первой страницы;
- `page=2`, `page=3` и последующие возвращают оставшиеся записи без пропусков;
- сортировка стабильна (`created_at DESC`, `id DESC` или текущий закреплённый
  контракт), но не удаляет записи;
- поиск `q` фильтрует только после scope и не раскрывает чужую лабораторию;
- скрытый через пользовательскую операцию документ не воскресает при
  неизменённом повторном импорте;
- новый UUID с тем же `issueNumber` создаёт новую партию;
- повторный тот же UUID обновляет существующую запись без дубля;
- локальное поле `queue=EXPECTED` вычисляется корректно для партии без
  reconciliation/confirmation.

Не менять серверный размер страницы с 20 на 1 и не добавлять frontend
ограничение `slice(0, 1)`, `find()` или `limit=1`.

## 9. Frontend поступлений

1. Не выполнять SOAP/API ВетИС из браузера. Источник страницы остаётся
   локальный `/api/v1/arrivals`.
2. После успешного ручного sync инвалидировать и перечитать:
   - текущий список `arrivals`;
   - счётчики `arrivals-count` для EXPECTED/WORK/ACCEPTED.
3. После sync с двумя подходящими документами таблица должна показать обе
   строки на первой странице.
4. При 21 подходящем документе показать 20 на первой странице и 1 на второй;
   переходы и URL `page` должны работать.
5. При ошибке sync показывать честный код/состояние, не заменять ошибку
   сообщением «ВСД не найдены».
6. Сохранить действующие колонки, дизайн, доступность, кнопки сверки и
   скрытия из существующего ТЗ на поступления.
7. Не менять бизнес-предикат на клиенте и не добавлять демонстрационные ВСД.

## 10. Тесты до и после исправления

### 10.1. Backend/VetIS adapter

Добавить или расширить обезличенные fixture-тесты:

- одна страница с двумя подходящими документами → `items.length == 2`;
- одна страница с двумя подходящими и тремя неподходящими → 2 items и
  правильные `filtered` counters;
- два документа на двух страницах → оба импортированы;
- 21 документ → все импортированы, не только первые 20;
- 100/1000 документов → нет фиксированного лимита 1/2/20;
- duplicate UUID на overlapping/replayed page → одна локальная запись;
- два разных UUID с одинаковым `issueNumber` → две локальные записи;
- error на последней странице → операция FAILED, checkpoint не двигается,
  предыдущие импортированные страницы не удаляются;
- `INTEGRATION_NOT_CONFIGURED` → нет SOAP-вызова, нет ложного SUCCESS,
  причина видна в operation state;
- настроенный pinned fixture adapter → полный read-only проход импортирует
  все подходящие записи.

### 10.2. Backend API

Добавить проверки:

- `GET /arrivals` с двумя локальными партиями возвращает `total=2` и две
  строки при `page_size=20`;
- 21 партия даёт `total=21`, `len(page1.items)=20`, `len(page2.items)=1`;
- `queue=EXPECTED` не исключает вторую партию без reconciliation;
- фильтры применяются к полному scoped-набору до pagination/count;
- чужой `laboratory_id` не раскрывается.

### 10.3. Frontend

В `ArrivalsPage`/MSW-тестах:

- ответ с двумя `items` действительно отображает две строки;
- ответ с 21 записью позволяет открыть вторую страницу;
- после успешного sync обновляются и таблица, и счётчики;
- failed sync не показывает success и не заменяет список ошибкой «пусто»;
- loading/empty/forbidden/network-error остаются различимыми.

### 10.4. Разрешённая live read-only проверка

После установки server-side secret profile и schema pins выполнить только
read-only проверку:

1. запустить полный sync лаборатории указанным ручным действием или worker;
2. зафиксировать `external_total`, `pages`, `received`, `kept`,
   `filtered_by_reason`, `imported`, `local_total`;
3. сравнить список обезличенных внешних UUID с локальными UUID;
4. открыть `/arrivals?queue=expected` и проверить число строк/страниц;
5. повторить sync и доказать отсутствие дублей;
6. доказать `ProcessIncomingConsignment calls = 0`.

Если из двух внешних документов только один соответствует предикату раздела
5, второй не должен появляться в мясной очереди, но причина фильтрации должна
быть указана в диагностике. Если оба соответствуют — в локальной БД и UI
обязаны появиться оба.

## 13. Критерии готовности

Задача принимается только если:

- причина `INTEGRATION_NOT_CONFIGURED` устранена корректной конфигурацией
  read-only интеграции, а не обходом проверки схем;
- полный read-only проход импортирует все подходящие документы со всех страниц;
- для двух подходящих внешних ВСД в БД две разные партии и UI показывает две
  строки;
- для 21+ документов работает серверная пагинация без потери строк;
- неподходящие документы отфильтрованы только по закреплённым критериям и
  причина фильтрации диагностируется;
- повторный UUID не создаёт дубль, новый UUID не теряется;
- ошибка sync не выдаётся за пустой успешный результат;
- состояние операции и счётчики позволяют объяснить разницу «пришло извне /
  прошло фильтр / импортировано / показано»;
- не удалены пользователи, ВСД, ВСЭ, партии, справочники или Docker volume;
- все backend/frontend тесты и read-only браузерная проверка пройдены;
- контейнеры пересобраны;
- ветка отправлена в GitHub и объединена с `main` либо создан PR с указанием
  причины, если прямое объединение запрещено.

## 14. Отчёт исполнителя

В финальном отчёте указать:

- подтверждённую причину первоначального отсутствия второго ВСД;
- статус manifest/schema pins и способ безопасной конфигурации;
- число внешних страниц и документов;
- число документов после каждого фильтра с причинами;
- число импортированных и локально отображаемых партий;
- доказательство отсутствия дублей после повторного sync;
- результаты API/UI/backend/frontend тестов;
- результаты Docker-пересборки;
- подтверждение отсутствия внешних write-вызовов ВетИС;
- все ограничения `not-run` и оставшиеся API/integration gaps.
