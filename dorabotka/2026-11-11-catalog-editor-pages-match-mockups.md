# ТЗ на приведение редакторов справочников к утверждённым HTML-макетам

Дата: 11.11.2026

Исполнитель: ИИ-агент, вносящий изменения в проект `C:\electronic_lab_dev`

Тип задачи: преимущественно frontend; существующая серверная бизнес-логика и данные сохраняются

## 1. Цель

Привести три рабочих экрана редактирования справочников React SPA к композиции, геометрии и визуальным состояниям утверждённых HTML-макетов:

| Рабочий URL | Эталонный макет |
| --- | --- |
| `http://127.0.0.1:8080/catalogs?tab=tariffs` | `C:\electronic_lab_dev\directory-price-edit.html` |
| `http://127.0.0.1:8080/catalogs?tab=check-services` | `C:\electronic_lab_dev\directory-paid-services-edit.html` |
| `http://127.0.0.1:8080/catalogs?tab=methods` | `C:\electronic_lab_dev\directory-norms-edit.html` |

После доработки редакторы должны выглядеть как отдельные страницы из макетов, но продолжать работать с реальными данными, правами, ревизиями и API production-приложения.

Задача не разрешает подменять реальные значения демонстрационными числами `100`, нормами или пользователями из HTML.

## 2. Подтверждённые решения владельца

Эти решения обязательны и не требуют повторного согласования:

1. Вкладка `tab=check-services` должна показывать редактор **стоимости двух платных услуг сверки**, соответствующий `directory-paid-services-edit.html`. Технические глобальные правила расчёта `CheckServiceRule` не являются основным содержимым этой страницы.
2. Для роли `HEAD` («Заведующий») переключатель лаборатории не показывается. У заведующего ровно одна лаборатория, назначенная администратором в карточке пользователя; все справочники открываются в её контексте.
3. Для ролей, которым доступно несколько лабораторий или территория, переключение лаборатории в справочниках сохраняется.
4. Добавление, удаление и массовое применение стоимости, предусмотренные ФТ, сохраняются как вторичные действия, даже если они не нарисованы в макетах.
5. Основная форма и её поля должны визуально соответствовать макету; дополнительные обязательные действия не должны разрушать его композицию.
6. После выполнения агент создаёт отдельную ветку, объединяет её с `main`, отправляет результат в GitHub и пересобирает рабочий контейнер.

### 3.2. Ошибка текущей SPA-реализации

Текущая `frontend/src/pages/CatalogsPage.tsx` ошибочно сопоставляет карточку/вкладку «Платные услуги» с CRUD глобальных `CheckServiceRule`:

```text
GET/POST/PUT /api/v1/catalogs/check-services
```

Эти записи определяют единицу, базу множителя и применимые решения о приёмке, но **не содержат цену**. Макет `directory-paid-services-edit.html` и `ui-mapping.md` требуют две цены из `Tariff` для контекста CHECK:

- `PRODUCT_IDENTIFICATION` — «Идентификация продукции по наименованию и визуальным осмотром»;
- `TRANSPORT_INSPECTION` — «Ветеринарно-санитарная оценка и идентификация транспорта».

Следовательно, экран `tab=check-services` должен читать и изменять соответствующие записи тарифов текущей лаборатории/продукции через существующий tariff API. `CheckServiceRule` остаётся в backend и продолжает участвовать в расчёте; удалять таблицу, endpoint, модель или тесты нельзя. На этом экране технический rule-editor больше не показывается как пользовательский редактор цены.

### 3.3. Ошибка текущего выбора контекста

Текущий экран:

- требует вручную выбрать лабораторию даже у заведующего;
- показывает лабораторию как сокращённый UUID;
- требует вручную вводить `Вид продукции (UUID)`;
- не подставляет доступный `product_scope_id` из назначенного контекста пользователя.

Это противоречит FT-ACC-02 и PDR-002: одна лаборатория не требует выбора, а переключатель появляется только при нескольких доступных контекстах.

## 6. Контекст лаборатории и продукции

### 6.1. Матрица ролей

| Роль | Лаборатория на экране справочника | Возможность изменения |
| --- | --- | --- |
| `VET` | текущая назначенная лаборатория; без выбора при одном контексте | только чтение по `catalog:read` |
| `HEAD` | единственная лаборатория, назначенная администратором; переключателя нет | редактирование своей лаборатории |
| `ADMIN` | обязательный выбор одной лаборатории из назначенной административной области | редактирование выбранной лаборатории; массовая цена в разрешённом охвате |
| `ANALYST` | обязательный выбор одной лаборатории из доступных лабораторий Татарстана | редактирование выбранной лаборатории; массовая цена в разрешённом охвате |

Роль определяется серверной сессией/capabilities. Скрытие контрола не заменяет серверную проверку области.

### 6.2. Заведующий

Для `HEAD`:

- использовать лабораторию из назначения пользователя (`/me`/`/contexts`/текущий context store);
- не рисовать select, UUID, кнопку «Выбрать лабораторию» или пустое состояние «Выберите лабораторию»;
- не разрешать подменить лабораторию query-параметром;
- при несогласованной учётной записи с нулём или более чем одной лабораторией показать блокирующую ошибку конфигурации и контакт администратора, а не выбирать первую молча;
- название лаборатории можно показать спокойным информационным текстом, только если оно приходит из доверенного read model.

### 6.3. Администратор и аналитик

Для `ADMIN`/`ANALYST`:

- показать над формой компактный selector «Лаборатория»;
- список содержит только разрешённый сервером охват;
- показывать человекочитаемое название, а UUID использовать только как `value`;
- выбранную лабораторию хранить в URL для восстанавливаемого deep link;
- при переключении отменять/инвалидировать прежние запросы и не показывать данные предыдущей лаборатории;
- при несохранённых изменениях требовать подтверждение ухода через общий app-owned dialog;
- после выбора загружать данные только выбранной лаборатории;
- не показывать объединённую таблицу всех лабораторий.

### 6.4. Названия контекстов и допустимый API-gap

Сначала переиспользовать существующий источник названий лабораторий и продукции. Если текущий `/contexts` действительно возвращает только UUID и в проекте нет безопасного read endpoint с названиями, допускается **только минимальное аддитивное расширение read model**:

- добавить к доступному контексту `laboratory_name` и `product_scope_name` либо отдельный scoped read endpoint;
- не менять правила авторизации, записи и область данных;
- не отдавать названия лабораторий вне разрешённого охвата;
- обновить OpenAPI-клиент и тесты;
- не использовать сокращённый UUID как «человекочитаемое название».

Это единственное допустимое backend-изменение в рамках задачи. Если оно не требуется, backend не менять.

### 6.5. Продукция

- Контекст продукции берётся из назначенного пользователю `product_scope_id` и общего переключателя продукции в шапке.
- При одном доступном направлении отдельный selector не показывается.
- При нескольких доступных направлениях используется существующий общий переключатель; второй локальный raw-UUID input не создаётся.
- Query может хранить технический ID, но интерфейс показывает русское название.
- Смена продукции применяет те же правила защиты несохранённых изменений, отмены старых запросов и сброса неподходящей лаборатории.

## 8. Общая визуальная система трёх страниц

Все три страницы используют один набор общих React-компонентов и CSS-вариантов. Не создавать три копии одинаковой разметки.

### 8.1. Геометрия

- локальная ширина контента: `min(1180px, 100%)`;
- центрирование страницы;
- горизонтальный padding `24px` на широком экране;
- верхний padding около `37px`, нижний около `96px`;
- фон страницы `#f5f9f8`;
- `h1`: около `30px`, line-height `1.15`, letter-spacing около `-0.035em`;
- eyebrow «Редактирование справочника»: `12px`, бирюзовый, насыщенный;
- расстояние от заголовка до формы около `28px`;
- основная секция: белая поверхность, border `#dfe9e9`, radius около `18px`, padding около `25px`, лёгкая тень;
- section icon: `37×37px`, radius около `11px`, tint-фон;
- карточки/строки внутри секции: белые, border `#dfe9e9`, radius около `13px`;
- рабочие inputs: высота около `43px`, radius около `9px`;
- основная кнопка: высота около `43px`, radius около `10px`, бирюзовая;
- нижняя панель действий: sticky в пределах страницы, белая полупрозрачная поверхность, border, radius около `15px`, blur/лёгкая тень.

Использовать текущие app tokens; приведённые числа — геометрический контракт макета, а не повод дублировать глобальные токены в каждом компоненте.

### 8.2. Общие компоненты

Выделить или расширить переиспользуемые компоненты, например:

- `CatalogEditorPage` — eyebrow, заголовок, описание, section, sticky actions;
- `CatalogContextSelector` — role-aware выбор лаборатории;
- `CatalogSectionHeader`;
- `CatalogPriceCard`;
- `CatalogNormRow`;
- `CatalogSaveSummary` для частичного результата сохранения.

Названия файлов могут отличаться, но код страниц и stories должен использовать одну реализацию.

### 8.3. Шапка и иконки

- использовать существующий `frontend/src/shared/ui/AppHeader.tsx`;
- не задавать локально высоту/интервалы шапки;

## 9. Страница «Стоимость исследований ВСЭ»

Эталон: `directory-price-edit.html`.

### 9.1. Заголовок

- eyebrow: `Редактирование справочника`;
- `h1`: `Стоимость исследований ВСЭ`;
- описание: `Значения используются для автоматического расчёта стоимости услуг в журнале.`

### 9.2. Основная секция

- заголовок `Исследования ВСЭ`;
- пояснение `Укажите стоимость каждого исследования.`;
- сетка из двух колонок на широком экране;
- каждая реальная tariff-запись представлена отдельной карточкой;
- название исследования берётся из общего каталога показателей, не из UUID/service code;
- цена редактируется одним decimal-полем с суффиксом `₽`;
- обязательность исследования берётся из ФТ/policy и может быть показана `*`, но пользователь не меняет её тарифным справочником;
- отсутствие цены отображается пустым полем и статусом `Не настроено`, а не нулём;
- явный `0,00`/`0.00` остаётся валидной ценой;
- ввод принимает пользовательскую запятую/точку согласно действующему frontend-контракту, в API отправляется DecimalString без float;
- не показывать service UUID, unit UUID, version и source в основной карточке; эти сведения допускаются в доступной дополнительной информации, если нужны для аудита.

### 9.3. Действия

- `Сохранить справочник` сохраняет только изменённые карточки;
- `Отменить` возвращает в обзор после проверки dirty-state;
- `Добавить тариф` остаётся вторичным действием в header секции для разрешённых ролей;
- удаление доступно как спокойное вторичное действие карточки/меню, а окончательное подтверждение — в app-owned danger dialog;
- `ADMIN`/`ANALYST` видят отдельную вторичную кнопку `Применить стоимость к лабораториям`;
- `HEAD` не видит массовую цену;
- `VET` видит те же карточки без inputs/действий изменения либо с корректно disabled read-only представлением.

### 9.4. Массовая цена

Сохранить существующий контракт `BulkPriceDialog`:

- вид продукции, исследование, цена и список затронутых лабораторий;
- полный охват до подтверждения;
- человекочитаемые названия лабораторий;
- отдельные фактические результаты;
- retry только неуспешных;
- succeeded не выполняются повторно;
- отсутствие постоянного наследования.

Диалог визуально привести к общей рабочей системе, но не смешивать его с обычным сохранением текущей лаборатории.

- заголовок `Услуги сверки данных`;
- две карточки в две колонки на широком экране:
  1. `Идентификация продукции по наименованию и визуальным осмотром` — service code `PRODUCT_IDENTIFICATION`;
  2. `Ветеринарно-санитарная оценка и идентификация транспорта` — service code `TRANSPORT_INSPECTION`;
- каждая карточка содержит цену с суффиксом `₽`;
- обе услуги обязательны как состав справочника CHECK, но отсутствие цены отображается как конфигурационная проблема, не как `0`;
- тарифы scoped по лаборатории и продукции;
- массовое применение этих двух услуг не добавлять: PDR v1.9 сохраняет массовую операцию только для стоимости исследований ВСЭ;
- изменение цены не меняет глобальные `multiplier_basis`, `applicable_decisions` и техническую единицу `CheckServiceRule`.

### 10.3. Источник данных

Страница использует существующий tariff API для двух service codes. Разрешается добавить frontend-параметр/фильтрацию `context=check`, если это только представление существующих записей.

Запрещено:

- показывать вместо цены таблицу `Услуга / База начисления / Решения / Единица / Версия`;
- открывать `CheckServiceEditor` по основной кнопке;
- создавать произвольную третью CHECK-услугу;
- удалять `CheckServiceRule` или менять его значения при сохранении цены.

Если tariff list содержит и VSE, и CHECK записи, frontend обязан разделять их по точным service codes/контексту, а не по русской подстроке.

### 10.4. Сохранение и удаление

- одна кнопка `Сохранить справочник` сохраняет изменённые из двух цен;
- существующая запись обновляется с `If-Match`/revision;
- отсутствующая создаётся через действующий create contract;
- удаление цены остаётся вторичным действием с предупреждением, что новые платные операции будут заблокированы;
- сохранённые исторические снимки не изменяются.

## 11. Страница «Нормы исследований»

Эталон: `directory-norms-edit.html`.

### 11.1. Заголовок

- eyebrow: `Редактирование справочника`;
- `h1`: `Нормы исследований`;
- описание: `Диапазоны используются для автоматической отметки нормы и отклонений в карточке ВСЭ.`

### 11.2. Числовые нормы

Интервальные `MethodRule` отображаются строками макета:

```text
[Название исследования и пояснение] [Норма от + unit] [Норма до + unit]
```

Требования:

- широкая сетка `minmax(260px, 1fr) 180px 180px`;
- название/описание слева;
- подписи `Норма от` и `Норма до`;
- единица показана внутри/рядом с полем как в макете;
- отсутствующая граница остаётся пустой и сохраняется как `null`, а не `0`;
- включённость границ сохраняется; если она редактируема, дать компактный доступный control в дополнительной части строки, не теряя основной геометрии;
- нижняя граница не может превышать верхнюю;
- pH ограничен форматом `0..14`, микроскопия — integer `>=0`, но эти ограничения не подменяют клиническую норму;
- дозиметрия сохраняет два отдельных показателя/правила по действующей модели и не склеивается в одно выдуманное поле.

### 11.3. Качественные нормы и «Проба варки»

Для качественных/ENUM правил использовать композицию макета:

```text
Проба варки                                    [+]
[Вариант результата] [Оценка: Норма/Отклонение] [-]
```

Источником полного списка вариантов «Пробы варки» служит общий каталог показателей/ФТ, уже используемый формой ВСЭ (`INDICATORS`/единый вынесенный registry). Не создавать вторую копию строк внутри редактора.

`accepted_values` текущего `QualitativeRule` определяет оценку:

- значение входит в `accepted_values` → `Норма`;
- значение не входит → `Отклонение`.

Добавление/удаление строк допускается только в пределах реально поддержанного enum-каталога и серверного контракта. Нельзя сохранять вариант, который backend/форма ВСЭ затем не сможет выбрать. Для `Иное (указать)` сохранить стабильный код/поведение действующей формы.

Для остальных qualitative rules применять тот же общий паттерн, если он соответствует их типу; не заставлять все правила выглядеть как числовой интервал.

### 11.4. Метаданные нормы

Version, source, edition, effective date, product state и inclusivity остаются частью server payload. Их нельзя терять при визуальном упрощении.

Допустимые способы:

- сворачиваемая доступная область `Методика и версия` внутри строки;
- отдельный общий диалог дополнительных параметров;
- заполнение неизменяемых значений из текущей записи при обычной правке границ.

Запрещено отправлять пустые/дефолтные metadata поверх существующей записи только потому, что их нет в макете.

### 11.5. Добавление и удаление

- `Добавить норму` остаётся вторичным действием section header;
- создание использует реальный список показателей и состояний продукции, а не ручной ввод UUID;
- удаление доступно через вторичное действие строки и app-owned confirmation;
- обязательная настройка получает явное предупреждение о блокировке будущего завершения;
- удаление не затрагивает исторические snapshots.

## 12. Сохранение нескольких карточек без изменения серверной логики

Макеты используют одну кнопку сохранения для всей страницы, а текущий API изменяет одну запись за запрос. Backend batch endpoint в рамках этой задачи не требуется.

Frontend обязан:

1. вести dirty-state отдельно по каждой записи;
2. отправлять только изменённые записи через существующие create/update endpoints;
3. использовать текущие idempotency/`If-Match` требования;
4. не объявлять общий успех до получения фактического ответа каждой изменённой записи;
5. после частичного отказа:
   - успешные карточки отметить сохранёнными;
   - неуспешные оставить изменёнными;
   - показать результат по каждой ошибочной карточке;
   - повторять только неуспешные;
6. при `409` загрузить актуальную ревизию и предложить понятное разрешение конфликта, не перезаписывая чужую правку молча;
7. блокировать повторное нажатие во время активного сохранения, сохраняя размеры кнопки;
8. не использовать `Promise.all` как основание скрыть частичные результаты.

Если действующий API/UX уже задаёт более строгий безопасный порядок, сохранить его.

## 13. Состояния интерфейса

Для каждой страницы предусмотреть:

- loading без скачка геометрии;
- обычное заполненное состояние;
- отсутствие записей/неполная конфигурация;
- read-only для `VET`;
- forbidden для отсутствующего `catalog:read`;
- network error с повтором;
- validation errors у конкретных полей;
- conflict `409`;
- partial save;
- busy;
- длинные названия;
- узкий экран;
- отсутствие допустимого контекста;
- несогласованную учётную запись `HEAD` с числом лабораторий не равным одной.

Readiness не скрывать. Его сообщение оформить в общей визуальной системе и разместить перед основной секцией, не заменяя форму демонстрационными значениями.

## 14. Доступность и поведение

- WCAG 2.2 AA как целевой уровень;
- реальные `<label>` и доступные имена полей;
- видимый `focus-visible`;
- действия — `<button>`, навигация — `<a>`/`Link`;
- цвет не является единственным признаком ошибки/статуса;
- ошибки связаны с полями через `aria-invalid`/`aria-describedby`;
- sticky actions не закрывают сфокусированный control;
- диалоги используют общий `Dialog`, trap/return focus и Escape;
- подтверждение удаления первоначально фокусирует безопасное действие;
- status/toast имеет live region, но исправляемая ошибка остаётся у поля;
- нативный select допустим только если его системное оформление не является частью точного визуального контракта; для role/context selector переиспользовать поддерживаемый проектом доступный вариант;
- на странице нет горизонтального overflow; горизонтальная прокрутка не используется как замена адаптивной сетке.

## 15. Адаптивность

Проверить минимум `1440`, `1024`, `768`, `390 px`.

- до `900px` строки норм переходят в две колонки, информационная часть занимает всю строку;
- до `800px` карточки тарифов переходят в одну колонку;
- формы норм и qualitative rows переходят в одну колонку;
- section padding уменьшается примерно до `18px`;
- контекстный selector занимает доступную ширину;
- sticky actions остаются видимыми и не перекрывают поля;
- secondary actions переносятся без наложения;
- шапка использует собственную существующую адаптацию.

## 16. Storybook и переиспользование

Общие компоненты редакторов должны иметь stories рядом с реализацией. Минимальные stories:

- price card: заполнена, отсутствующая цена, `0.00`, ошибка, busy, read-only, длинное название;
- norm row: две границы, одна граница, ошибка порядка, длинная единица;
- qualitative block: обычный, добавление, удаление, ошибка;
- context selector: скрыт для `HEAD`, одна/несколько лабораторий, loading, error;
- save summary: success/partial/conflict;
- полные три страницы на широком и узком viewport с MSW fixtures.

Storybook и приложение используют один и тот же компонент. Копия разметки только в story запрещена.

## 17. Автоматические тесты

### 17.1. Роли и контекст

- `HEAD` с одной лабораторией не видит selector и запросы используют назначенный ID;
- query с чужой лабораторией не меняет scope заведующего;
- `HEAD` с 0/2 лабораториями получает честную блокирующую ошибку;
- `ADMIN` видит только лаборатории своей области и может переключиться;
- `ANALYST` видит доступный список Татарстана и работает с одной выбранной лабораторией;
- `VET` читает справочник без mutate controls;
- переключение контекста отменяет/изолирует поздний ответ прежнего контекста;
- raw UUID не показывается как label.

### 17.2. Тарифы исследований

- карточки формируются из реальных tariff/indicator данных;
- пустая цена не становится `0`;
- `0.00` сохраняется как валидное значение;
- Decimal не проходит через float;
- одна кнопка сохраняет только dirty rows;
- partial failure и retry не повторяют succeeded;
- delete confirmation и исторический snapshot contract сохраняются;
- массовая цена доступна только `ADMIN`/`ANALYST`.

### 17.3. Платные услуги

- страница показывает ровно две price cards с правильными service codes;
- чтение/создание/изменение выполняется через tariff API выбранного scope;
- страница не открывает `CheckServiceEditor`;
- сохранение цены не отправляет запрос изменения `CheckServiceRule`;
- отсутствующая цена показана как `Не настроено`;
- массовая цена на этой странице отсутствует.

### 17.4. Нормы

- interval отображает lower/upper/unit без потери inclusivity/metadata;
- lower > upper блокируется;
- `null` граница не превращается в `0`;
- qualitative mapping корректно строит `Норма/Отклонение` из `accepted_values`;
- варианты «Пробы варки» берутся из общего registry;
- unknown indicator не получает выдуманное название и показывает честное диагностическое состояние;
- create/delete и mandatory warning продолжают работать.

### 17.5. Визуальные и e2e

- screenshot comparison трёх страниц с соответствующими HTML-макетами на `1440px`;
- отдельные screenshots `390px`;
- keyboard Tab/Shift+Tab/Escape;
- no horizontal document overflow;
- dirty-leave confirmation;
- loading/empty/error/read-only/partial states;
- сохранение на MSW/e2e fixture, не на демонстрационных HTML-данных.

## 20. Критерии приёмки

Задача считается выполненной только если одновременно выполнены условия:

1. Три рабочие страницы визуально соответствуют своим HTML-макетам по ширине, иерархии, карточкам, полям, секциям и sticky actions.
2. На edit-страницах нет текущей полосы pill-вкладок.
3. `HEAD` не видит переключатель лаборатории и всегда работает в единственной назначенной лаборатории.
4. `ADMIN`/`ANALYST` сохраняют выбор разрешённой лаборатории с человекочитаемыми названиями.
5. Raw UUID продукции/лаборатории не требуется вводить вручную и не показывается как пользовательское название.
6. `VET` получает предусмотренное требованиями чтение без возможности записи.
7. «Платные услуги» показывают две цены из tariff scope, а не таблицу технических `CheckServiceRule`.
8. Сохранение цены не изменяет `CheckServiceRule`.
9. Тарифы исследований отображаются карточками в две колонки и используют реальные значения.
10. Нормы отображаются как range/qualitative редакторы по типу данных, включая композицию «Пробы варки».
11. Добавление, удаление и массовая цена сохранены в рамках ролевых правил.
12. Отсутствующая цена не превращается в ноль; исторические snapshots не пересчитываются.
13. Частичный отказ общего сохранения показан честно, повторяет только неуспешные записи.
14. Пройдены frontend tests/build/Storybook/e2e и применимые backend-тесты.
15. Проверены `1440`, `1024`, `768`, `390 px`, клавиатура и основные состояния.
16. Feature-ветка отправлена, объединена с `main` или создан защищённый PR без обхода правил.
17. Контейнер пересобран, health/status проверен, три страницы повторно открыты в рабочем стенде.
18. Пользовательские данные, справочники, volumes и чужие изменения не удалены и не перезаписаны.
