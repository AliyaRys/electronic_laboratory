# ТЗ: убрать технические поля из справочников цен и норм ВСЭ

Дата: 11.11.2026  
Статус: к реализации  
Основание: замечание владельца продукта по страницам `/catalogs?tab=tariffs`, `/catalogs?tab=check-services`, `/catalogs?tab=methods`; `vse-product-foundation-v1.9`, ФТ v2.0, `TZ_development`, макеты `directory-price-edit.html`, `directory-paid-services-edit.html`, `directory-norms-edit.html`, `electronic-vse-journal.html`.

## 1. Проблема

Пользователю показаны поля внутреннего контракта (`unit_id`, `source`, `version`, UUID показателя, UUID состояния продукции, тип схемы результата). Они не являются самостоятельными бизнес-настройками справочника и требуют знания устройства базы данных.

Особенно ошибочна форма создания цены: цена уже является денежной суммой в рублях, а поле `unit_id` означает не валюту, а техническую единицу начисления, которая должна соответствовать настройке исследования или платной услуги. Поле `source` является служебным происхождением записи и также не должно заполняться пользователем.

## 2. Цель

Оставить на страницах только действия, понятные заведующему лабораторией:

- в стоимости исследований ВСЭ — ввод цены в рублях для готового перечня исследований;
- в платных услугах — ввод цены в рублях для двух установленных услуг сверки;
- в нормах исследований — редактирование границ нормы или допустимых результатов для готового перечня исследований.

Изменение цены влияет только на будущую тарификацию в карточке ВСЭ/сверки. Ранее сохранённые расчёты не пересчитываются.

## 3. Бизнес-правила

### 3.1. Стоимость исследований ВСЭ

1. Список исследований строится из единого реестра VSE-F18–VSE-F29, уже используемого карточкой ВСЭ.
2. В карточке исследования редактируется только поле `Стоимость, ₽`.
3. Не показывать и не запрашивать `unit_id`, источник прейскуранта, версию, UUID или код услуги.
4. При создании записи система сама передаёт:
   - `service_code` — идентификатор выбранного исследования из общего реестра;
   - `unit_id` — единицу результата из общего реестра исследования, а для безразмерного/качественного результата — внутреннее значение `result`;
   - `version` — `1` для новой записи;
   - `source.name` — системное значение `Ручная настройка справочника`.
5. При изменении существующей цены служебные значения сохраняются без изменения.
6. Рубли обозначаются в подписи поля и отображении цены, но не записываются в `unit_id`.

### 3.2. Платные услуги

1. На странице всегда ровно две услуги:
   - «Идентификация продукции по наименованию и визуальным осмотром»;
   - «Ветеринарно-санитарная оценка и идентификация транспорта».
2. Пользователь редактирует только `Стоимость, ₽`.
3. Не показывать и не запрашивать единицу, источник, версию или код услуги.
4. Для новой цены система сама передаёт `unit_id = service`, `version = 1`, `source.name = Ручная настройка справочника`.
5. Страница меняет только тарифы. Глобальные правила расчёта `CheckServiceRule` не редактируются.
6. Изменённая цена применяется к будущему расчёту соответствующей услуги в сверке данных; касса, оплата и фискализация не входят в задачу.

### 3.3. Нормы исследований

1. Пользователь не создаёт произвольное исследование и не вводит UUID, схему результата, единицу измерения, версию или источник методики.
2. Кнопку «Добавить норму» и техническую форму `MethodEditor` убрать со страницы справочника.
3. Показывать только правила, связанные с утверждённым общим реестром исследований. Неизвестные старые записи показывать как диагностическое сообщение без редактирования.
4. Для количественного исследования пользователь изменяет только нижнюю/верхнюю границу и, при необходимости, включение границ.
5. Для качественного исследования пользователь выбирает, какие варианты из общего реестра считаются нормой. Свободное добавление неизвестных вариантов не допускается.
6. Служебные сведения о версии и источнике не показывать в обычном интерфейсе, но сохранять без изменения при обновлении.
7. Удаление действующей нормы оставить вторичным действием с предупреждением: после удаления новые результаты этого показателя нельзя оценить/рассчитать, сохранённые записи не меняются.

## 4. Роли и область данных

1. Для роли «Заведующий» лаборатория берётся из назначения пользователя; переключатель лаборатории не показывается.
2. Для ролей с доступом к нескольким лабораториям сохраняется выбор лаборатории.
3. Вид продукции остаётся частью области справочника.
4. Проверки прав и области на сервере не ослаблять.

## 5. Интерфейс и доступность

1. Сохранить структуру и размеры согласованных макетов.
2. Удаление технических полей не должно оставлять пустой раскрывающийся блок `<details>`.
3. Денежные поля имеют подпись `Стоимость, ₽`, принимают точку или запятую и не более двух знаков после разделителя.
4. Состояния загрузки, ошибки, отсутствия настройки, конфликта редакций и недоступности сохраняются.
5. Клавиатурная навигация, подписи полей, сообщения ошибок и фокус после диалогов должны работать как прежде.

## 6. Ограничения реализации

1. Не менять формулы тарификации и снимки сохранённых расчётов.
2. Не менять серверную модель справочников без необходимости; скрытые обязательные поля формируются адаптером страницы из канонического реестра и существующей записи.
3. Не дублировать перечень исследований: использовать `INDICATORS` из общей реализации карточки ВСЭ.
4. Не создавать второй компонент карточки цены или нормы — расширять существующие общие компоненты.
5. Старые записи с неизвестным кодом нельзя автоматически переименовывать или удалять.

## 7. Приёмочные сценарии

1. В новой цене исследования пользователь вводит только сумму, сохраняет и после обновления страницы видит эту сумму.
2. В новой цене каждой из двух платных услуг пользователь вводит только сумму; запись сохраняется без ручного ввода единицы или источника.
3. На обеих страницах отсутствуют тексты «Данные новой записи», «Единица измерения», «Источник прейскуранта».
4. На странице норм отсутствуют «Добавить норму», «Показатель (UUID)», «Состояние продукции (UUID)», «Тип результата», «Версия», «Источник методики».
5. Изменение существующей цены не меняет её `service_code`, `unit_id`, `source` и область лаборатории/продукции.
6. Изменение нормы не меняет `indicator_id`, `product_state_id`, `result_schema`, `unit_id`, `version` и `source`.
7. Значение `0,00` сохраняется как валидная цена, пустое значение не превращается в ноль.
8. Конфликт параллельного изменения по-прежнему предлагает взять серверное или сохранить своё значение относительно свежей редакции.
9. Для заведующего нет выбора лаборатории; для пользователя с несколькими доступными лабораториями выбор остаётся.
10. Юнит-тесты страниц, сборка приложения и Storybook проходят; страницы проверены в браузере в обычном и узком окне.

## 8. Завершение задачи

1. Сделать отдельный коммит с настоящим ТЗ до коммита реализации.
2. Сделать отдельный коммит с кодом и тестами.
3. Объединить ветку задачи с `main`, отправить `main` в удалённый репозиторий.
4. Пересобрать рабочие контейнеры без удаления томов данных и проверить `/catalogs?tab=tariffs`, `/catalogs?tab=check-services`, `/catalogs?tab=methods`.
