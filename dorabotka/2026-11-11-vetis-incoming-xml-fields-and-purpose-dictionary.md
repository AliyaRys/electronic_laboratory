## 1. Цель

Исправить разбор XML входящего транспортного эВСД, чтобы система не подменяла количество весом и человекочитаемо показывала обязательные реквизиты документа во всех связанных разделах.

После доработки система должна:

1. брать количество грузовых мест из `dt:quantity` внутри `vd:packageList`, а массу — отдельно из `vd:volume`;
2. брать дату оформления ВСД из `vd:issueDate`;
3. показывать UUID ВСД из верхнеуровневого `bs:uuid`, не выдавая `vd:issueNumber` за UUID;
4. показывать русский статус, сохраняя исходный код ВетИС для бизнес-логики;
5. извлекать GUID/UUID назначения груза из `vd:authentication/vd:purpose` и показывать его название из локального справочника;
6. первоначально наполнить справочник назначений данными из приложенного ответа `purpose_guid.txt`, затем полностью обновлять его из ВетИС не чаще одного раза в 14 суток;
7. применить исправленный разбор не только к будущим загрузкам, но и к уже сохранённым сырым XML входящих документов;
8. использовать одни и те же значения в «Ожидаемых», «В работе», «Завершённых», на сверке, в журнале ВСЭ, создании/просмотре ВСЭ, подтверждении гашения, документах и других местах, где эти реквизиты уже выводятся.

## 3. Обнаруженный дефект текущей реализации

Сейчас `normalizer.py` пытается прочитать количество по пути `vd:batch/vd:quantity`. В фактическом ответе ВетИС количество упаковок находится по пути:

```xml
vd:certifiedConsignment
  /vd:batch
  /vd:packageList
  /dt:package
  /dt:quantity
```

Когда `vd:batch/vd:quantity` не найден, `backend/src/modules/arrivals/queries.py::_quantity_set` выполняет подмену:

```python
quantity = batch.quantity or batch.volume
```

Из-за этого при массе `500.0` и восьми крюках интерфейс показывает количество `500.0`. Это запрещено. Масса и количество — разные сущности, отсутствие количества нельзя компенсировать массой.

Дополнительно текущая проекция:

- сохраняет `issue_date`, но не публикует его в `ExternalFields` как `issuedOn`;
- уже хранит внешний UUID документа в `IncomingDocument.evsd_uuid`, но интерфейс вместо него использует `issueNumber` под названием «Номер эВСД»;
- хранит только сырой код статуса;
- вообще не извлекает `vd:authentication/vd:purpose`;
- не имеет локального справочника назначений груза и его фонового обновления.

| Масса/объём | `vd:certifiedConsignment/vd:batch/vd:volume` | decimal string | `documentary.mass_kg` при единице кг | `Объём / масса`, `Вес, кг` |

| Количество мест | `vd:certifiedConsignment/vd:batch/vd:packageList/dt:package/dt:quantity` | package list + вычисленное documentary quantity | nullable decimal/integer string, без float | `Количество` |

## 5. Разбор количества и упаковки

### 5.1. Обязательный алгоритм

Нормализатор должен извлечь все `dt:package` из `vd:packageList` и сохранить для каждого:

- `level`;
- `packingType.uuid`;
- `packingType.guid`;
- `packingType.globalID`;
- `packingType.name`;
- `quantity` как исходную строку/целое без преобразования через float;
- все `productMarks` с их `class` и текстом.

Количество транспортных мест вычислять по правилу документации Меркурия:

1. найти максимальный числовой `dt:level`, для которого имеются упаковки;
2. взять только упаковки этого максимального уровня;
3. сложить их заполненные `dt:quantity`;
4. не складывать количества разных уровней между собой;
5. результат хранить строкой без потери точности.

Пример из предоставленного XML:

- `level = 6`;
- `packingType.name = Крюк`;
- `quantity = 8`;
- `volume = 500.0`.

Ожидаемый результат:

- вес/масса — `500.0` кг;
- количество — `8`;
- тип упаковки — `Крюк`;
- маркировка — `112211`.

### 5.2. Пограничные случаи

- Если на максимальном уровне несколько типов упаковки, количество равно сумме их `dt:quantity`; список типов упаковки сохранить отдельно.
- Если `packageList` отсутствует или на максимальном уровне ни у одной упаковки нет `quantity`, source quantity равно `null`/«не указано».
- Никогда не подставлять `vd:volume` вместо количества.
- Никогда не подставлять `0`, если источник не передал количество.
- Незаполненное source quantity в списках показывать как `—`.
- Фактическое количество при сверке пользователь может ввести в предусмотренное поле, но source value остаётся отсутствующим и не фабрикуется.
- Невалидные `level`/`quantity` не должны падать на всём пакете документов: документ получает контролируемую ошибку импорта/диагностику согласно существующему контракту V02, без частично выдуманного значения.
- Единица `vd:batch/vd:unit` относится к `volume`; её нельзя подписывать возле количества упаковок как будто это одна сущность.

### 5.3. Совместимость с гашением

Исправление read model не должно менять сохранённый сырой XML и не должно ломать `ProcessIncomingConsignment`:

- raw XML и checksum остаются источником для формирования юридически значимого запроса;
- documentary quantity, delivered/accepted/returned quantity означают количество упаковок/мест, а не килограммы;
- `mass_kg` остаётся отдельной величиной;
- тесты гашения используют фикстуры и transport spy;
- реальный `ProcessIncomingConsignment_v2` не вызывать.

## 8. Русские статусы эВСД

Использовать согласованную карту из `status_vetis.txt`:

| Исходный код | Русское отображение |
| --- | --- |
| `CONFIRMED` | `Оформлен` |
| `WITHDRAWN` | `Аннулирован` |
| `UTILIZED` | `Погашен` |
| `FINALIZED` | `Закрыт` |

Особенности:

- `FINALIZED` поддержать в отображении защитно, хотя документация указывает, что финализация производственного сертификата обычно определяется отдельным признаком, а `vetDStatus` остаётся `CONFIRMED`;
- исходный `statusCode` обязательно сохранять и использовать для фильтров, допустимости операций, синхронизации и аудита;
- русский `statusLabel` предназначен только для UI/документов;
- неизвестный новый код не должен падать или ошибочно считаться `CONFIRMED`: UI показывает `Неизвестный статус`, код остаётся в backend-диагностике;
- не рассыпать словарь переводов по React-компонентам. Один backend/domain owner формирует человекочитаемое значение, все экраны потребляют его;
- после гашения/обновления внешний статус должен отображаться актуально, но подтверждённые локальные юридические факты не переписываются.

## 9. Назначение груза

### 9.1. Разбор входящего XML

Нормализатор должен читать:

```xml
<vd:authentication>
  <vd:purpose>
    <bs:uuid>d4f9b0ea-f4d9-4cd7-92f0-016e1299160e</bs:uuid>
    <bs:guid>0778b8cb-f49d-4ed9-88b9-5f70af00a211</bs:guid>
  </vd:purpose>
</vd:authentication>
```

В source snapshot сохранить оба идентификатора. По приложенному справочнику этот GUID должен отображаться как `реализация в пищу людям`.

Разрешение выполняется по стабильному `guid`, а не по `uuid` версии. UUID версии хранится для аудита и диагностики.

Если GUID отсутствует в локальном справочнике:

- импорт входящего ВСД не отклонять;
- GUID/UUID сохранить в backend;
- в UI показать `Назначение не найдено в справочнике`, а не сырой GUID;
- создать структурированную диагностическую запись/метрику;
- следующий успешный двухнедельный sync может автоматически дать название без изменения raw XML и без вызова метода для каждого документа.

### 9.2. Новая таблица

Создать отдельный справочник, не смешивать его с `mercury_product_guid_lvl_2`.

Рекомендуемое имя: `mercury_purpose_guid`.

Минимальные поля:

| Поле | Тип/ограничение |
| --- | --- |
| `contour` | `PILOT`/`PRODUCTION`, часть PK |
| `guid` | UUID, стабильный идентификатор, часть PK |
| `current_uuid` | UUID текущей версии, unique внутри contour |
| `name` | непустая строка до 255 символов |
| `active` | boolean |
| `is_last` | boolean |
| `external_status` | integer/string согласно XSD без потери исходного значения |
| `source_created_at` | timestamptz nullable |
| `source_updated_at` | timestamptz nullable |
| `previous_uuid` | UUID nullable |
| `source` | версия/происхождение начальной загрузки |
| `synchronized_at` | timestamptz |

Добавить индекс `(contour, name)` и ограничение уникальности `(contour, current_uuid)`.

Идентификаторы разных контуров не объединять неявно. Read model входящего документа ищет название в том же contour, в котором получен документ.

### 9.4. Обновление раз в две недели

Реализовать отдельный read-only адаптер `GetPurposeList` к:

`https://api2.vetrf.ru:8002/platform/services/2.0/DictionaryService`

Требования к запросу:

- использовать `getPurposeListRequest` из namespace `http://api.vetrf.ru/schema/cdm/registry/ws-definitions/v2`;
- запрашивать `count=160`, `offset=0`, как указано владельцем и в `API REQUESTS.txt`;
- всё равно поддержать пагинацию: если `total` стал больше полученного count, увеличивать offset до полного прохода;
- максимумы, SOAPAction, WSDL/XSD и импортируемые схемы брать из закреплённого manifest/WSDL, не угадывать;
- отдельный endpoint DictionaryService и его schema imports включить в allowlist с fail-closed политикой;
- использовать только серверные credentials из secret profile;
- никогда не вызывать `GetPurposeList` при открытии страницы или для каждого входящего ВСД.

Периодика:

- полный sync при пустой таблице;
- далее — если с последнего успешного полного sync прошло не менее 14 суток;
- проверка срока при старте worker и периодическим scheduler tick;
- overlap protection: одновременно только один sync на contour;
- checkpoint передвигается только после полного успешного прохода всех страниц и атомарного применения;
- частичный/ошибочный ответ не очищает и не портит прежний справочник;
- временные ошибки повторяются с ограниченным backoff, но не превращаются в частые запросы;
- после полного ответа новые/изменённые записи upsert; записи, исчезнувшие из полного актуального списка, не удалять физически, а помечать неактивными/непоследними;
- логировать только количество страниц, записей, длительность, contour, результат и problem code — без credentials и полного XML;
- предусмотреть метрики `last_success`, `last_attempt`, `records`, `failures` и видимое состояние для диагностики;
- обновление имени в справочнике не меняет checksum/revision входящего XML и само по себе не инвалидирует сохранённую сверку.

Реализация может использовать отдельную таблицу checkpoint или существующий журнал операций, но тип операции и диагностика должны однозначно отличаться от `vetis.sync` входящих документов и от `vetis.receipt`.

- purpose ref (`guid`, `uuid`);
- полный package list;
- вычисленное package quantity;
- package type names/ids;
- product marks.

Не складывать всё в неструктурированный `dict`, если для поля есть устойчивый контракт.

### 10.2. Read model

`IncomingView` должен отдавать без двусмысленности:

- UUID ВСД;
- дату оформления ВСД;
- status code;
- русский status label;
- purpose guid/uuid только как backend/API-реквизиты;
- purpose name для интерфейса;
- массу отдельно от количества;
- количество упаковок nullable;
- сведения о типе упаковки, если UI/форме нужна подпись единицы.

Запрещено сохранять старый fallback `quantity = volume` ради обратной совместимости.

### 10.3. Обратная совместимость

- Если `documentNumber` нужен внешним потребителям, временно оставить его только как deprecated alias с чётко зафиксированным смыслом `issueNumber`; новый UI его для UUID не использует.
- Не менять ETag/If-Match/idempotency без необходимости.
- Сравнения и акты продолжают использовать стабильные CHK-ID; `CHK-F20` остаётся количеством, `CHK-F21` — весом.
- Статусные бизнес-проверки используют исходный enum, не русский текст.
- Генерация XML гашения использует закреплённый raw XML и не зависит от локализованной подписи.

## 11. Переразбор уже загруженных документов

Одной новой логики импорта недостаточно: существующий ВСД уже записан с неверным source snapshot.

Добавить идемпотентный backfill/re-normalization:

1. читать последнюю сохранённую версию `vetis_source_documents.raw_xml`;
2. пропускать её через новый нормализатор;
3. обновлять `incoming_documents.source_snapshot` и производные поля только при реальном изменении;
4. пересчитывать content hash по установленным правилам;
5. не менять raw XML/checksum;
6. корректно обновлять revision и существующую инвалидацию незавершённой сверки при изменении source-фактов;
7. не переписывать подтверждённые receipt/examination/report snapshots и другие неизменяемые юридические факты;
8. выдавать итоговые счётчики: просмотрено, исправлено, без изменений, ошибка;
9. повторный запуск не создаёт новые изменения.

Если для документа отсутствует raw XML, его не исправлять догадками: записать диагностическую ошибку и дождаться следующего read-sync.

## 12. Изменения интерфейса во всех потребителях

### 12.1. «Поступления → Ожидаемые»

- `Дата создания ВСД` → `Дата оформления ВСД`;
- значение даты — `vd:issueDate`;
- `Номер эВСД` → `UUID ВСД`;
- значение — верхнеуровневый `bs:uuid`;
- `Количество` — число упаковок с максимального уровня, в примере `8`;
- `Объём / масса` — `500.0 кг`, не смешивать с количеством;
- поиск принимает полный/частичный UUID ВСД.

### 12.2. «Поступления → В работе»

- колонка даты остаётся `Дата сверки данных`;
- `Номер эВСД` → `UUID ВСД`;
- количество берётся из package list;
- масса остаётся отдельной;
- черновик/автор/стоимость и действия не менять этой задачей.

### 12.3. «Поступления → Завершённые»

- `Номер эВСД` → `UUID ВСД`;
- статус, если показывается как внешний статус документа, выводить по-русски;
- не заменять результат местной ВСЭ внешним статусом ВСД;
- не добавлять новые колонки вопреки макету, но все существующие потребители исправить.

### 12.4. Сверка данных

Блок «Документ»:

- `UUID ВСД`;
- `Дата оформления ВСД`;
- `Статус эВСД` с русским значением;

Блок продукции:

- `CHK-F20 Количество` показывает количество упаковок/мест;
- `CHK-F21 Вес, кг` показывает массу;
- delivered/accepted/returned не инициализируются массой вместо количества;
- при наличии типа упаковки показать понятную подпись, например `Количество (крюки)`/`Тип упаковки: Крюк`, без хардкода;

## 13. Миграция и развёртывание

Исполнитель обязан:

1. добавить следующую Alembic-миграцию для purpose dictionary/checkpoint;
2. обеспечить downgrade без удаления пользовательских/юридических данных вне новой структуры;
3. добавить первоначальный ресурс из 151 записи;
4. выполнить миграцию до запуска новой версии worker/backend;
5. запустить backfill после миграции;
6. не очищать таблицы пользователей, лабораторий, входящих ВСД и справочников;
7. не использовать destructive e2e seed против локальной установки;
8. не менять фактический флаг гашения и не выполнять живое гашение;
9. после установки выполнить безопасный read-only sync и убедиться, что текущий входящий ВСД показывает ожидаемые значения.

При несовпадении схемы и кода backend должен fail fast/readiness false, а не молча работать со старой трактовкой количества.

### 13.1. Синхронизация проектной документации

- различие между массой груза (`vd:volume`) и количеством транспортных мест (`dt:package/dt:quantity` максимального уровня упаковки);

- единый термин `Дата оформления ВСД` и источник `vd:issueDate`;
