## 4. Дефект кнопки «Войти»

### 4.1. Требуемое поведение

Для enabled-кнопки:

```html
<button type="submit" class="app-button primary">Войти</button>
```

состояние при наведении мышью должно быть визуально таким же, как обычное:

- тот же градиент фона;
- тот же белый цвет текста;
- тот же border;
- та же тень;
- без превращения в белую кнопку, затемнения, подсветки или скачка размеров.

Наведение не является отдельным промежуточным состоянием. Нажатие выполняет
обычный submit и существующий вход.

### 4.2. Реализация

Исправить auth-стили, а не рабочие кнопки приложения. Для hover-селектора
enabled auth primary-кнопки явно повторить базовые значения `.vse-auth
.app-button.primary`.

Сохранить без изменений:

- `:focus-visible` и доступное кольцо фокуса;
- disabled;
- `aria-busy`/loading;
- field/form error;
- submit, блокировку повторной отправки и переход после входа.

Не добавлять анимацию или отдельный hover-цвет.

### 4.3. Проверка

Добавить/обновить UI-тест:

1. открыть `/login`;
2. снять computed style enabled-кнопки до hover;
3. навести мышь;
4. сравнить background/color/border/box-shadow/размеры;
5. убедиться, что Tab-фокус по-прежнему видим;
6. убедиться, что submit работает.

Проверить также disabled/busy/error, чтобы hover override их не сломал.

## 5. Фильтр сортировки поступлений

### 5.1. UI

В очереди `EXPECTED` добавить в существующую панель фильтров поле как в
`arrivals.html`:

```html
<div class="filter-field">
  <label for="sort-order">Сортировка</label>
  <select id="sort-order">
    <option value="asc">Сначала оформленные раньше</option>
    <option value="desc">Сначала оформленные позже</option>
  </select>
</div>
```

В React сохранить существующую стилизацию `.arrivals-filter-field` и общие
токены. Не создавать второй фильтр и не менять внешний вид других очередей.

Для `EXPECTED`:

- добавить `sort` в URL: `sort=asc|desc`;
- значение должно переживать обновление страницы и возврат назад;
- изменение сортировки сбрасывает `page=1`;
- select имеет доступное имя «Сортировка»;
- клавиатура и visible focus работают;
- на 390 px фильтр переносится по правилам существующей панели.

Рекомендуемое значение по умолчанию — `desc` («сначала оформленные позже»),
так как FT-COM-01 требует новые записи первыми. Если текущий утверждённый
макет/контракт задаёт другое начальное значение, явно зафиксировать его в
тесте; варианты select и смысл asc/desc не менять.

Для `WORK` и `ACCEPTED` не добавлять этот контрол в рамках данной задачи,
если для них нет согласованного требования.

### 5.2. API-контракт

Добавить query-параметр в `GET /api/v1/arrivals`:

```text
sort=asc|desc
```

Сохранить совместимость: отсутствие параметра использует текущий default
(`desc`, новые оформленные ВСД первыми).

Обновить OpenAPI/generated TypeScript schema, router и frontend client.
Недопустимое значение должно возвращать понятный `422`, а не игнорироваться.

### 5.3. Серверная сортировка

Сортировать именно по дате оформления ВСД из:

```text
source_snapshot.vdDocument.issueDate
```

Это значение отображается в колонке «Дата оформления ВСД». Не использовать:

- `Party.created_at`;
- `IncomingDocument.fetched_at`;
- дату синхронизации;
- дату сохранения сверки;
- дату подтверждения гашения.

Сортировка выполняется в SQL/read model **до** `count`, `offset` и `limit`.
Нельзя сортировать на frontend после загрузки страницы.

Правила:

- `asc`: самые ранние даты первыми;
- `desc`: самые поздние даты первыми;
- одинаковые даты имеют устойчивый tie-breaker: `Party.created_at DESC,
  Party.id DESC`;
- отсутствующая/некорректная дата не должна ломать запрос; использовать
  явное детерминированное положение и fallback tie-breaker;
- сортировка не меняет scope, поиск, скрытие или queue predicate;
- `total` остаётся количеством всех записей после scope/search/queue-фильтров.

Для plain date `YYYY-MM-DD` и dateTime из ВетИС сохранить корректный порядок
без timezone-сдвига. Если JSONB-сортировка недостаточно надёжна, допустимо
добавить безопасное derived-поле `issue_date`/индекс с backfill, но raw XML и
существующие юридические данные не менять.

## 6. Состояние URL и frontend data flow

Расширить `Filters` в `ArrivalsPage`:

```text
queue, result, q, page, sort
```

`fetchArrivals()` должен передавать `sort` в API только когда он выбран/нужен.
React Query key обязан включать `sort`, чтобы старые ответы не заменяли новый.

При изменении сортировки:

1. обновить URL;
2. установить page=1;
3. выполнить новый серверный запрос;
4. сохранить таблицу и pagination согласованными с новым total.

При возврате со страницы сверки сохранить `queue`, `sort`, `q` и `page` по
общему правилу FT-COM-02.

## 7. Тесты

### Backend

1. Вставить записи с датами оформления в порядке, отличающемся от
   `created_at`.
2. `sort=asc` возвращает даты оформления от ранних к поздним.
3. `sort=desc` возвращает от поздних к ранним.
4. `page_size=20`, `total=21`: сортировка применяется до выдачи page 1/page 2.
5. Одинаковые даты дают стабильный порядок при повторных запросах.
6. Отсутствующая/некорректная дата не вызывает 500.
7. Scope/search/queue применяются до сортировки и pagination согласно API-01.
8. Отсутствующий `sort` сохраняет текущий default и старые API-тесты.

1. В EXPECTED виден select с точными двумя подписями из макета.
2. Выбор `asc`/`desc` меняет URL и отправляет параметр API.
3. Выбор сортировки сбрасывает page на 1.
4. Ответ с переставленными датами отображается в порядке сервера, без
   локальной сортировки `items`.
5. В WORK/ACCEPTED новый select не появляется.
6. Проверить loading/error/empty, keyboard focus и 1440/1024/768/390 px.
