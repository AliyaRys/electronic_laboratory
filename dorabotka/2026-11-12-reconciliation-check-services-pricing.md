# ТЗ на расчёт стоимости двух услуг сверки

Дата: 12.11.2026  
Тип задачи: backend pricing + reconciliation snapshot + frontend invoice

## 1. Проблема и корневая причина

На странице сверки после сохранения показывается:

> Стоимость будет рассчитана после сохранения и подтверждения сверки.

Стоимость не рассчитывается по трём причинам:

1. `frontend/src/features/arrivals/ReconciliationForm.tsx` всегда отправляет
   `services: []`.
2. `backend/src/modules/arrivals/reconciliation.py::save_reconciliation()`
   сохраняет этот пустой список и не вызывает `catalog_pricing.evaluate_and_price()`.
3. `ReconciliationView` не содержит сохранённого `PricingSnapshot`, а frontend
   показывает invoice только из `initial.services`. Поэтому каталог тарифов
   фактически не участвует в сохранении сверки.

Дополнительное состояние live БД:

- `check_service_rules` для двух услуг не настроены;
- тарифы `PRODUCT_IDENTIFICATION` и `TRANSPORT_INSPECTION` существуют, но
  должны проверяться по лаборатории и `product_species_id` партии;
- `product_species_id` целевой партии: `362aa885-9b9f-ae95-05d0-f9570f4fbdc6`;
- отсутствие/несовпадение такой конфигурации нельзя показывать как пустой
  invoice или как нулевую стоимость.

## 2. Требуемый результат

После успешного сохранения полной сверки в блоке «Расчёт стоимости услуг»
должны появиться ровно две строки:

1. `PRODUCT_IDENTIFICATION` — «Идентификация продукции по наименованию и
   визуальным осмотром»;
2. `TRANSPORT_INSPECTION` — «Ветеринарно-санитарная оценка и идентификация
   транспорта».

Для каждой строки показывать:

- услугу;
- единицу расчёта;
- количество;
- тариф;
- сумму.

Ниже показывать общий итог в рублях. Использовать реальные тарифы из
`/catalogs?tab=check-services` для лаборатории и вида продукции текущей партии.

## 4. Правила расчёта

### 4.1. Две услуги

Использовать только точные коды:

```text
PRODUCT_IDENTIFICATION
TRANSPORT_INSPECTION
```

Не создавать дубликаты услуг по русскому названию. Не смешивать их с тарифами
исследований ВСЭ.

### 4.2. Источник тарифа

Для каждой услуги найти `Tariff` по точному составному scope:

```text
laboratory_id текущей партии
product_species_id текущей партии
service_code
```

Цена берётся из сохранённого тарифа с точностью до копеек. Тарифы другой
лаборатории или другого вида продукции использовать запрещено.

Экран «Платные услуги» должен сохранять именно эти два `Tariff` с указанным
scope. Глобальные `CheckServiceRule` отвечают за базу начисления и применимые
решения, а не заменяют денежный тариф.

### 4.3. База начисления

Использовать `CheckServiceRule.multiplier_basis`:

- `ONE_SERVICE` — количество `1`;
- `ACCEPTED_QUANTITY` — принятое количество и его source unit;
- `DELIVERED_QUANTITY` — доставленное количество и его source unit.

Применимость решения проверять по `applicable_decisions`. Если правило,
тариф или применимая единица отсутствуют, вернуть `CONFIGURATION_MISSING` с
конкретным кодом услуги и не создавать пустой/фиктивный snapshot.

В соответствии с ФТ-06, две услуги должны рассчитываться отдельно. Возврат
не означает автоматически отсутствие оказанной услуги. Фактически выполненная
услуга должна быть явно закреплена в snapshot.

### 4.4. Ярмарка

Если `fair=true`:

- обе услуги сохраняются как выполненные строки;
- количество и сумма в сохранённом snapshot должны быть корректны по модели
  проекта, но денежные строки и итог равны `0.00`;
- обычная цена не должна сохраняться скрытым значением;
- тариф не должен подставляться как обычная сумма.

## 5. Серверная интеграция с reconciliation

Расчёт выполнять на сервере после успешной валидации сверки и до commit:

1. загрузить текущую партию, source classification, delivered/accepted
   quantities, unit и decision;
2. определить две выполненные CHECK-услуги по правилам продукта;
3. собрать `PricingRequest(context="CHECK")`;
4. вызвать существующий `evaluate_and_price()`;
5. получить полный `PricingSnapshot`;
6. сохранить snapshot в reconciliation атомарно с сохранением сверки;
7. вернуть snapshot в `ReconciliationView`.

Расчёт не должен выполняться только в браузере. Клиентские значения не могут
задавать тариф, итог или серверную применимость.

Сохранение неполной начатой сверки допускается без pricing snapshot, если
требования текущего API это разрешают. Для полной валидной сверки итоговый
расчёт обязателен. Если конфигурация отсутствует, сохранить открытые вводимые
факты только в разрешённом состоянии и вернуть понятную
`CONFIGURATION_MISSING`, не объявлять расчёт равным нулю.

## 6. Контракт данных

Расширить `ReconciliationView` полем `pricing` либо `costs` с типом,
совместимым с существующим `PricingSnapshot`:

```json
{
  "lines": [
    {
      "service_code": "PRODUCT_IDENTIFICATION",
      "name": "Идентификация продукции по наименованию и визуальным осмотром",
      "unit_id": "...",
      "quantity": "1",
      "unit_price": "100.00",
      "amount": "100.00"
    },
    {
      "service_code": "TRANSPORT_INSPECTION",
      "name": "Ветеринарно-санитарная оценка и идентификация транспорта",
      "unit_id": "...",
      "quantity": "1",
      "unit_price": "130.00",
      "amount": "130.00"
    }
  ],
  "total": "230.00",
  "currency": "RUB",
  "fair": false
}
```

Названия услуг должны быть едиными в каталоге, backend snapshot, сверке,
печати и экспорте. Старое поле `services` не использовать как замену
денежному snapshot: оно может оставаться для факта выполненной услуги, но не
должно быть единственным источником invoice.

Snapshot сохраняется в `reconciliations` и не пересчитывается автоматически
при последующем изменении тарифа. Старый расчёт должен оставаться неизменным.

## 7. Frontend

Изменить `ReconciliationForm`:

- убрать постоянное состояние «Стоимость будет рассчитана…» после успешного
  сохранения, если pricing snapshot уже рассчитан;
- отображать `pricing.lines` и `pricing.total`;
- показывать количество, единицу, тариф и сумму каждой строки;
- показывать `0.00 ₽` для ярмарки без скрытой обычной цены;
- при `CONFIGURATION_MISSING` показать, какая услуга/цена/rule отсутствует;
- не очищать введённую сверку при ошибке расчёта;
- после сохранения обновлять reconciliation query и invoice без перезагрузки;
- на узком экране таблица должна оставаться читаемой и не создавать overflow.

Нельзя подставлять демонстрационные цены 50/94/100/130 ₽ из макетов или
вычислять итог на клиенте.

## 8. Проверка каталога

На странице `/catalogs?tab=check-services` должны быть видны и сохраняться
ровно две цены с правильным scope:

- `PRODUCT_IDENTIFICATION`;
- `TRANSPORT_INSPECTION`.

Если пользователь редактирует тариф для другой продукции/лаборатории, он не
должен использоваться в сверке текущей партии. UI обязан показывать текущую
лабораторию и вид продукции в контексте редактора.

Если `check_service_rules` пусты, расчёт не должен молча исчезать. Нужно либо
использовать разрешённое правило `ONE_SERVICE` с явной lineage-отметкой, либо
показать конфигурационную ошибку согласно принятому контракту. Не выбирать
множитель скрытым предположением.

## 9. Тесты

### Backend

1. Сохранение полной сверки рассчитывает две строки CHECK и сохраняет snapshot.
2. В snapshot есть правильные коды, русские имена, quantity, unit, tariff,
   amount и total.
3. Отсутствующий тариф даёт `CONFIGURATION_MISSING`, а не пустой invoice/0 ₽.
4. Неверный `product_species_id` не использует чужой тариф.
5. `ACCEPT_ALL`, `PARTIAL`, `RETURN_ALL` проверяют applicable decisions.
6. `ACCEPTED_QUANTITY`, `DELIVERED_QUANTITY`, `ONE_SERVICE` дают ожидаемое
   количество и сумму.
7. `fair=true` сохраняет нулевой расчёт без обычной скрытой цены.
8. Повторное сохранение той же сверки идемпотентно и не создаёт двойных строк.
9. Изменение текущего тарифа не меняет сохранённый старый snapshot.
10. Конкурентное изменение тарифа/сверки возвращает конфликт и не теряет ввод.

### Frontend

1. После save с pricing snapshot вместо empty-state отображаются две строки.
2. Отображаются точные русские названия услуг.
3. Ошибка конфигурации показывает конкретную отсутствующую услугу или тариф.
4. Ярмарка отображает нулевые суммы.
5. После повторной загрузки страницы snapshot остаётся видимым.
6. Проверить состояния loading/error/empty/configuration-missing и ширины
   1440/1024/768/390 px.

### API/e2e

Проверить live read-only запросами, что для target party используется scope:

```text
laboratory_id = 2812e437-facc-432f-9242-5162c9d9f49f
product_species_id = реальный product species партии
```

Не выполнять внешний write ВетИС.

## 11. Критерии готовности

- после сохранения сверки видны две услуги и итог;
- цены взяты из правильного scope каталога;
- расчёт выполняется сервером и сохраняется snapshot;
- отсутствующая конфигурация не маскируется пустым блоком или нулём;
- ярмарка даёт сохранённый нулевой расчёт;
- старые расчёты не меняются после редактирования каталога;
- backend/frontend tests и browser-проверка проходят;
- контейнеры пересобраны, ветка отправлена и объединена с main либо создан PR.
