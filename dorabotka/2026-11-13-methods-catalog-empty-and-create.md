# ТЗ на исправление справочника норм исследований ВСЭ

Дата: 13.11.2026  
Тип задачи: исправление контекста каталога + создание/редактирование MethodRule + UI норм исследований

## 1. Симптом

При открытии:

`http://127.0.0.1:8080/catalogs?tab=methods`

пользователь видит:

```text
Нормы для этой области не заданы.
```

При этом на странице нет действия «Добавить норму», поэтому пользователь не
может создать первую норму и настроить показатели ВСЭ.

## 2. Подтверждённая причина

Обнаружены две независимые причины.

### 2.1. В рабочем контексте используется неверный внутренний scope

В БД для назначений текущей лаборатории:

```text
laboratory_id    = 2812e437-facc-432f-9242-5162c9d9f49f
product_scope_id = 2812e437-facc-432f-9242-5162c9d9f49f
```

`product_scope_id`, совпадающий с UUID лаборатории, является запрещённым legacy
fallback и не является видом продукции Меркурия. Это внутренний технический
идентификатор, который вообще не должен вводиться пользователем. Пользователь
должен выбирать доступную область словами, например «Мясо и мясопродукты», а
система сама должна использовать соответствующее внутреннее сопоставление.
Код
`useCatalogContext()` это распознаёт (`productSpeciesValid=false`), но
`MethodsEditorPage` проверяет только:

```text
laboratoryId !== null && productSpeciesId !== null
```

и всё равно вызывает:

```text
GET /api/v1/catalogs/methods?
  laboratory_id=2812e437-facc-432f-9242-5162c9d9f49f&
  product_species_id=2812e437-facc-432f-9242-5162c9d9f49f
```

Backend фильтрует `method_rules` по точному
`laboratory_id + product_species_id`, поэтому возвращает пустую страницу.
Ошибка показывается как будто нормы отсутствуют, хотя на самом деле рабочий
вид продукции не настроен.

В текущей БД есть 13 исторических/тестовых строк `method_rules`, но они
относятся к другой лаборатории (`e926e655-...`) и другому scope. Их нельзя
молча копировать в лабораторию 2812.

### 2.2. Создание нормы не подключено к странице

Backend уже имеет рабочий API:

- `POST /api/v1/catalogs/methods`;
- `PUT /api/v1/catalogs/methods/{rule_id}`;
- `DELETE /api/v1/catalogs/methods/{rule_id}`.

Frontend также содержит `MethodEditor` и `createMethod()`, однако
`MethodsEditorPage`:

- импортирует только `deleteMethod`, `fetchMethods`, `updateMethod`;
- не показывает `MethodEditor`;
- не вызывает `createMethod()`;
- не передаёт `actions` в `CatalogSectionHeader`;
- при пустом результате выводит только empty state.

Существующий тест прямо фиксирует отсутствие кнопки:

```text
expect(screen.queryByRole("button", { name: "Добавить норму" })).toBeNull()
```

Даже после исправления product scope пустой справочник невозможно было бы
заполнить через интерфейс.

### 2.3. Не хватает состояния продукции во внутреннем контексте

`MethodRule` имеет обязательный ключ применимости:

```text
laboratory_id + product_species_id + product_state_id + indicator_id
```

`useCatalogContext()` сейчас передаёт лабораторию и product species, но не
передаёт `product_state_id`. `MethodEditor` предлагает вводить состояние как
сырой UUID. Это не подходит для рабочего справочника: ни вид продукции, ни
состояние продукции не должны запрашиваться у пользователя в виде GUID.

В рабочем контексте нужно использовать стабильный идентификатор состояния
продукции; в текущем ВСЭ этот идентификатор соответствует уровню `subProduct`
из классификации партии. Нельзя подставлять UUID лаборатории, UUID вида
продукции вместо состояния или случайный UUID.

## 3. Важное ограничение по предметным данным (INPUT-02)

ФТ и `docs/TZ_development` задают состав показателей, типы результата и
структуру `MethodRule`, но не содержат утверждённых клинических числовых
границ для всех видов продукции.

ИИ-агенту запрещено:

- брать нормы из демонстрационного HTML-макета;
- придумывать значения температуры, pH, микроскопии, дозиметрии;
- автоматически копировать норму свинины на конину, субпродукты или другое
  состояние;
- использовать `0`, пустую границу или «Норма» как фиктивную настройку.

Справочник должен позволять методисту ввести подтверждённые значения и источник.
До ввода значения показываются как «Не настроено», а не как готовая норма.

## 4. Канонический перечень показателей

В справочнике норм должны быть представлены показатели VSE-F18–VSE-F29:

| Код | Показатель | Тип результата | Обязательность |
|---|---|---|---|
| VSE-F18 | Органолептическое исследование | `ENUM` / соответствие | обязательно |
| VSE-F19 | Идентификация продукции | `ENUM` / соответствие | обязательно |
| VSE-F20 | Температура в толще мышц | `DECIMAL`, °C | обязательно |
| VSE-F21 | Трихинеллоскопия | тип из методики | условно обязательно по точному GUID продукции |
| VSE-F22 | Люминесцентный анализ | `ENUM` / соответствие | необязательно |
| VSE-F23 | Бактериоскопия | `TEXT` | необязательно |
| VSE-F24 | Микроскопия | `INTEGER_NONNEGATIVE` | необязательно |
| VSE-F25 | pH | `DECIMAL`, 0–14 | необязательно |
| VSE-F26 | Проба варки | `ENUM` | необязательно |
| VSE-F27 | Реакция с сернокислой медью | `ENUM` | необязательно |
| VSE-F28 | Пероксидаза | `ENUM` | необязательно |
| VSE-F29 | Дозометрическое исследование | `DOSIMETRY_PAIR`, мкЗв/ч | необязательно |

VSE-F30 «Инвазионные болезни» и VSE-F31 «Незаразные болезни» являются
партийными словарями/полями формы, а не числовыми `MethodRule` нормами. Не
добавлять их в этот список как фиктивные нормы. Их списки должны оставаться в
соответствующем разделе формы ВСЭ согласно ФТ.

Обязательность VSE-F18–F20 принадлежит ФТ и не должна редактироваться флажком
в справочнике. VSE-F21 обязательна только для согласованных точных GUID:

- свинина;
- конина;
- свиные субпродукты/жиры;
- конские субпродукты/жиры.

## 5. Требуемое исправление рабочего контекста и выбора продукции

### 5.1. Запрет неверного fallback

Исправить контекст так, чтобы UUID лаборатории никогда не использовался как
`product_species_id` или `product_state_id`.

Если scope не настроен или равен `laboratory_id`:

- не вызывать `GET /catalogs/methods`;
- не показывать «Нормы для этой области не заданы»;
- показать понятное состояние:
  «Вид продукции и состояние продукции не настроены для этой лаборатории.»;
- указать, что требуется назначение рабочего product scope ответственным
  администратором;
- оставить действие возврата/повторной загрузки;
- не создавать нормы в недействительном scope.

### 5.2. Человекочитаемый выбор области продукции

Добавить в страницу справочника явный блок «Вид продукции» с обычными
названиями, а не UUID:

```text
Вид продукции: [ Мясо и мясопродукты ▾ ]
```

В список попадают только области, назначенные текущему пользователю и
разрешённые сервером. На первом этапе должна быть доступна область
«Мясо и мясопродукты».

В будущем список может содержать «Молоко и молочная продукция» и другие
поддержанные области, но их нельзя показывать пользователю только потому, что
они существуют в макете: область должна быть реально назначена и поддержана
backend.

Внутри приложения selector хранит внутреннюю пару идентификаторов, но:

- UUID не показываются в option label, заголовке или сообщении об ошибке;
- URL содержит стабильный безопасный ключ/код области, а не сырой GUID;
- при смене области перечитываются нормы только новой области;
- нормы одной области не копируются в другую;
- если пользователь имеет только одну область, она выбирается автоматически,
  но всё равно отображается её русское название.

### 5.3. Реальный контекст состояния

Расширить read model контекста каталога одним из согласованных способов:

1. добавить `product_state_id` и человекочитаемое имя в назначенный контекст;
2. добавить отдельный scoped endpoint списка допустимых состояний продукции;
3. дать администратору выбрать состояние из существующего защищённого
   классификационного read model.

Предпочтительный вариант — сервер возвращает выбранной человекочитаемой области
назначенную пару внутренних ключей:

```text
product_species_id
product_state_id
```

из server-side scope. Frontend не должен предлагать свободное поле UUID.

Если внутри «Мясо и мясопродукты» нормы различаются по виду/состоянию
продукции, показать второй человекочитаемый selector, например «Свинина» или
«Продукты убоя свиные». Его варианты должны приходить из разрешённого
классификационного read model. Если для текущей области задано ровно одно
состояние, выбрать его автоматически и показать название.

Если для лаборатории поддерживается несколько product species/state, добавить
явный selector только из разрешённых значений и включить выбранную пару в URL
для восстанавливаемой ссылки. Нельзя выбирать чужую область или произвольный
UUID.

### 5.4. Исправление данных окружения

Для текущей лаборатории 2812 необходимо отдельным безопасным provisioning-шагом
создать/исправить сопоставление человекочитаемой области «Мясо и
мясопродукты» с реальными внутренними product species/state IDs.

Эти IDs должны быть получены из существующего классификационного справочника и
скрыты от пользователя. Пользователь не должен знать их и не должен вводить их
самостоятельно.

Агент не должен сам выбирать для лаборатории 2812 внутренние значения из:

- тестового scope `11111111-...`;
- другой лаборатории `e926e655-...`;
- первого найденного incoming ВСД;
- UUID лаборатории.

Если сопоставление области с внутренними scope не настроено, код должен
остановиться на честном экране «Вид продукции не настроен», а не показывать
пустой справочник и не создавать ложные нормы. Настройка должна выполняться
через административный context/provisioning интерфейс с человекочитаемыми
названиями.

## 6. Требуемое исправление страницы справочника

### 6.1. Список ожидаемых показателей

После получения валидного контекста страница должна показывать полный список
VSE-F18–F29, даже если активной строки `method_rules` ещё нет.

Состояния строки:

- активная настройка — показывает текущую норму и позволяет редактировать;
- нет активной настройки — показывает «Не настроено» и кнопку «Настроить»;
- исторические неактивные версии — не дублируются как отдельные рабочие нормы,
  доступны только через read-only техническое состояние при необходимости;
- неизвестный indicator ID — диагностируется отдельно и не получает придуманное
  название.

Для interval-показателя показывать:

```text
Показатель | Норма от | Норма до | единица | включённость границ | источник
```

Для qualitative/enum — список допустимых значений и отметку, какие значения
считаются нормой.

### 6.2. Подключить создание

В заголовке блока «Диапазоны нормы» добавить кнопку:

```text
Добавить норму
```

Она открывает существующий общий `MethodEditor` в режиме create, а не новую
копию формы.

Форма создания должна:

- выбирать показатель из VSE-F18–F29 по русскому названию и коду;
- получать внутренние `product_species_id` и `product_state_id` из выбранной
  человекочитаемой области/состояния;
- не показывать пользователю технические UUID вместо названий;
- выбирать тип результата и единицу из канонического определения показателя;
- принимать границы/accepted values;
- требовать источник методики, редакцию/ссылку при наличии;
- отправлять `POST /catalogs/methods` с Idempotency-Key;
- после успеха закрывать диалог и перечитывать scoped список;
- после `ALREADY_EXISTS`, `VALIDATION_ERROR`, `ACCESS_DENIED` привязывать ошибку
  к полю и не терять введённые значения.

Для уже созданной нормы сохранить текущий `PUT`/If-Match, ревизии и удаление с
предупреждением о влиянии на будущие расчёты.

### 6.3. Не копировать registry в нескольких местах

Использовать существующий frontend registry `features/examinations/indicators.ts`
и согласованный backend `mandatory.py`/stable IDs. Не создавать второй список
с другими UUID или названиями.

Если backend должен возвращать ожидаемый список, расширить API typed DTO, но
сохранить один источник идентификаторов и русских названий.

## 7. Backend/API

Допустимы два варианта реализации:

### Вариант A — минимальный

- исправить server context/provisioning;
- оставить `GET /catalogs/methods` списком только существующих rows;
- frontend объединяет ответ с каноническим VSE-F18–F29 registry;
- create использует существующий `POST`.

### Вариант B — предпочтительный

Добавить read model для scoped editor:

```text
GET /api/v1/catalogs/methods/context
  → laboratory, product_species, product_state,
    indicators[], active_rules[], missing[]
```

`missing[]` содержит ожидаемые показатели без подставленной нормы. Это
исключает расхождение между frontend registry и backend applicability.

Выбрать вариант B, если backend уже является владельцем readiness и typed
catalog scope; иначе реализовать вариант A без дублирования бизнес-правил.

Backend обязан:

- сохранить точный scoped filter laboratory/species/state/indicator;
- не считать отсутствие строки нормой;
- не позволять создать метод с `product_species_id == laboratory_id`;
- требовать реальный `product_state_id`;
- сохранять `source`, `version`, `effective_from`, `result_schema`, `unit_id`;
- соблюдать одну active version на applicability key;
- не менять старые pricing/examination snapshots после удаления или правки
  текущей нормы;
- сохранять authz: HEAD своей лаборатории, ADMIN/ANALYST разрешённой области,
  VET read-only.

## 8. Тесты

### Контекст и backend

1. `product_scope_id == laboratory_id` не вызывает каталог и возвращает честный
   `CONFIGURATION_MISSING`/no-scope.
2. Валидная пара species/state отдаёт только свой scoped набор.
3. Чужая лаборатория/species/state возвращает `ACCESS_DENIED` или пустой
   недоступный scope, но не данные другой области.
4. `POST /catalogs/methods` создаёт правило с реальными species/state/indicator.
5. Неверный scope, неизвестный обязательный ID и пустая норма блокируются.
6. Повторный POST с тем же Idempotency-Key не создаёт дубль.
7. If-Match/409 revision conflict сохраняются.
8. Удаление active rule не удаляет snapshots и старые расчёты.
9. Readiness перечисляет отсутствующие обязательные F18–F20 и условный F21 по
   policy mapping.

### Frontend

1. При invalid/missing context нет запроса с laboratory UUID как species и нет
   вводящей в заблуждение empty state.
2. При валидном context пустая страница показывает VSE-F18–F29 со статусом
   «Не настроено» и кнопкой «Добавить/Настроить».
3. Кнопка открывает `MethodEditor` create, а submit вызывает `createMethod()`.
4. После успешного создания строка появляется без перезагрузки страницы.
5. Поля отправляют реальные indicator/state IDs, но технические UUID не
   показываются пользователю: он выбирает область/вид/состояние словами.
6. VSE-F18–F29 отображаются с правильными типами, единицами и состояниями;
   F30/F31 не появляются как нормы.
7. Проверить loading, no-scope, empty-but-configured, access denied, validation,
   save success, conflict, delete warning, 1440/1024/768/390 px и keyboard.

Все тесты используют fixtures/MSW и не создают реальные клинические значения
без явной fixture-настройки методиста.

Не удалять существующие строки, snapshots, пользователей или PostgreSQL volume.
Не выполнять `docker compose down -v`, destructive seed/reset и не копировать
нормы из другой лаборатории.

После реализации:

## 10. Критерии готовности

- URL `/catalogs?tab=methods` не показывает ложное «нормы не заданы» при
  невалидном scope: пользователь видит понятную проблему конфигурации;
- после назначения реальной пары species/state страница показывает все
  VSE-F18–F29;
- пользователь с правом редактирования может нажать «Добавить норму», ввести
  подтверждённые показатели и сохранить их;
- новые правила читаются в том же scoped контексте и участвуют в readiness/
  оценке ВСЭ;
- обязательность показателей не редактируется справочником;
- реальные числовые нормы не выдумываются и не копируются между видами;
- текущие данные и snapshots сохранены;
- frontend/backend tests, Storybook и Docker-проверки выполнены;
- feature-ветка с кодом и ТЗ объединена с `main` и отправлена в GitHub либо
  создан Pull Request.

## 11. Требование к provisioning без запроса GUID пользователю

Для лаборатории `2812e437-facc-432f-9242-5162c9d9f49f` сейчас отсутствует
валидное назначение области продукции; вместо этого в `user_scopes` записан
UUID лаборатории как legacy fallback.

Агент не должен просить пользователя вводить `product_species_id` или
`product_state_id`. Он должен реализовать/использовать административную
настройку доступных областей с человекочитаемыми названиями. В текущем MVP
оператор выбирает «Мясо и мясопродукты», а backend хранит соответствующее
внутреннее сопоставление. Если в системе ещё нет реального классификационного
сопоставления для этой области, агент обязан показать блокирующую задачу
конфигурации и указать, что требуется заполнить защищённый справочник
сопоставлений; подставлять UUID из тестов или другой лаборатории запрещено.
