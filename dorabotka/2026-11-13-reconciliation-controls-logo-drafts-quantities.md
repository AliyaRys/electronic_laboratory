## 3. Подтверждённые текущие проблемы

### 3.1. Расположение кнопок

Макет использует геометрию:

```text
Название поля
[ Значение из Меркурия                         ][✓][×]
```

`ComparisonField` уже содержит grid из значения и двух controls, но необходимо
проверить фактическую ширину/переносы и неразрешённые participant-поля. При
длинном значении кнопки не должны уходить под значение или за границу карточки.

### 3.2. Логотип

Сейчас `ReconciliationPage.tsx` выводит только:

```html
<span class="vse-rec-mercury-badge">Меркурий</span>
```

В репозитории есть исходный файл:

`C:\electronic_lab_dev\mercury-logo.webp`

Он не должен подключаться через абсолютный путь Windows. Для frontend-сборки
разместить копию/ресурс в `frontend/public/mercury-logo.webp` либо подключить
его через поддерживаемый asset import так, чтобы он попадал в Docker build.

Целевая разметка:

```html
<span class="vse-rec-mercury-badge">
  <img src="/mercury-logo.webp" alt="">
  <span>Меркурий</span>
</span>
```

Логотип декоративный, поэтому `alt=""`; доступное имя бейджа даёт текст
«Меркурий». Сохранить размеры, округление и responsive-геометрию макета.

### 3.3. Почему появляются зелёные отметки

Текущий `initialValues()` переносит `initial.checks` в form state. Это правильно
для ранее нажатого пользователем «Сохранить сверку», но новая форма с пустым
`checks` должна получать:

```text
matches = null
actual = ""
reason = ""
```

По указанной партии

`a560d943-38e3-467f-956c-e2a885514cad`

в БД уже существует строка `reconciliations` со `state=OPEN`, `rev=1`,
`saved_at=2026-11-12 10:51:59+00` и несколькими `checks.matches=true`. Поэтому
зелёный цвет этой конкретной партии приходит из сохранённых серверных данных,
а не возникает сам по себе в CSS.

Требуемая семантика:

- новая партия без строки сверки — все кнопки нейтральны;
- изменение формы только в памяти браузера — кнопки меняются, но API не
  вызывается;
- переход/закрытие без submit — изменения не сохраняются;
- «Сохранить сверку» — единственный обычный путь записи marks/facts;
- ранее действительно сохранённая сверка при повторном открытии восстанавливает
  сохранённые отметки;
- существующие сохранённые строки нельзя автоматически удалять или обнулять
  без отдельного подтверждённого решения владельца данных.

Не добавлять autosave в `localStorage`, `sessionStorage`, query cache или
`beforeunload`. Query cache не должен получать изменённую форму до успешного
ответа `PUT`. `useDirtyGuard` должен продолжать предупреждать о несохранённых
изменениях, но само предупреждение не должно выполнять save.

### 3.4. Поля получателя

Для состояния `PENDING` сейчас используется `ParticipantNameField` без
controls, поэтому в получателе отображаются только два нейтральных reference
поля. Это расходится с требованием владельца.

Поля получателя должны использовать общую геометрию comparison card:

- `CHK-F07` — «Предприятие»;
- `CHK-F08` — «Хозяйствующий субъект».

То же правило сохраняется для отправителя (`CHK-F05`/`CHK-F06`).

Если имя ещё не разрешено:

- показывать честный текст «Уточняем названия организаций…»;
- controls присутствуют в том же месте, но disabled;
- ни одна отметка не выбирается автоматически;
- GUID не показывается;
- после получения имени controls становятся доступными без потери других
  несохранённых значений формы.

Для `ERROR`/`MISSING` сохранить согласованные тексты и disabled-состояние.
Для `SOURCE_XML`/`VETIS_LOOKUP` controls активны.

## 4. Требования к layout comparison cards

### 4.1. Desktop

На ширине более 1020 px — две колонки карточек. Внутри каждой карточки:

```text
┌────────────────────────────────────────────────────┐
│ Название поля                                      │
│ Значение из Меркурия                     [✓] [×]   │
│ Фактическое значение / причина — при mismatch     │
└────────────────────────────────────────────────────┘
```

Требования:

- значение занимает всё доступное пространство до controls;
- controls справа от значения, touch target не менее 40×40 px;
- controls не переносятся под значение;
- длинное значение переносится в пределах value либо сокращается с полным
  `title`, но не расталкивает кнопки;
- состояние выражено одновременно фоном, иконкой, доступным именем и live
  текстом, не только цветом;
- focus-visible остаётся заметным.

### 4.2. Узкий экран

До 1020 px карточки переходят в одну колонку, но внутри каждой карточки
значение и две кнопки сохраняют горизонтальную схему. При недостатке места:

- допускается перенос текста value;
- кнопки остаются справа;
- горизонтального скролла документа нет;
- `390 px`, 200% zoom и keyboard navigation обязательны.

## 5. Числовые значения и форматирование

### 5.1. Назначение полей

В source snapshot текущей партии:

```text
vd:volume  → масса партии (в текущем API mass_kg)
vd:quantity/packageList → количество мест/упаковок
vd:unit    → идентификатор единицы измерения массы/объёма партии
```

Например, `volume=60.0`, `quantity=5`, `unit.guid=...` означает 60 кг/другая
единица массы и 5 мест, а не «60 единиц товара». Масса и количество мест
нельзя смешивать.

### 5.2. Правило отображения decimal

Добавить единый frontend formatter, работающий со строками, без преобразования
через JavaScript `number/float`:

| Источник/API | Отображение |
| --- | --- |
| `60` | `60` |
| `60.0` | `60` |
| `60.000000` | `60` |
| `60.45` | `60,45` |
| `60.450000` | `60,45` |
| `0.000000` | `0` |

Правила:

- заменить точку на запятую только на presentation layer;
- удалить только незначащие нули в дробной части;
- не округлять и не менять значение;
- сохранить все значащие цифры;
- не использовать `toFixed`, `parseFloat` или арифметику JS для вывода;
- принимать в пользовательском поле и точку, и запятую, а в API отправлять
  каноническую decimal-строку по существующему контракту;
- не ломать промежуточный ввод пользователя (`60,`, пустое поле при очистке)
  до blur/submit;
- применить правило к блокам «Доставлено», «Принято», «Возвращается», а также
  к сводке подтверждения, где отображаются эти же decimal facts.

Подписи разделить:

- `Вес, кг`/согласованная единица массы — для `mass_kg`;
- `Количество мест, шт.` либо согласованная подпись package quantity — для
  `quantity`.

Нельзя показывать `Количество (кг)`: кг относится к массе, а не к числу мест.

## 6. Понятное отображение единицы

### 6.1. Что означает текущий GUID

Поле:

```html
Единица измерения (из эВСД)
Единица из ВСД (GUID: ...)
```

показывает `vd:batch/vd:unit/bs:guid`. Это технический идентификатор
справочного объекта единицы измерения, который нужен backend для проверки
совместимости и формирования XML гашения. В текущем контракте он относится к
единице массы/объёма партии (например, кг или т), а не к количеству мест.

Количество мест хранится отдельно в `vd:quantity`/`packageList`.

### 6.2. Требуемый UI

Убрать из видимой формы техническую строку с GUID. При этом:

- `unit_id` сохраняется в `QuantitySet` и payload;
- серверная проверка равенства source unit и введённой unit остаётся;
- receipt mapping продолжает использовать исходный GUID;
- отсутствие имени единицы не блокирует сверку, если GUID присутствует;
- отсутствие самого GUID по-прежнему даёт существующую ошибку невозможности
  гашения.

Вместо технической строки использовать одно из согласованных представлений:

1. предпочтительно — не показывать отдельный блок вообще, а оставить понятные
   подписи «Вес, кг» и «Количество мест, шт.»;
2. если бизнесу нужно явно видеть единицу — показывать только человекочитаемое
   «Единица массы: кг/т» без GUID; при отсутствии имени не выводить случайный
   GUID и показать нейтральное «Единица массы указана в эВСД».

В рамках этой задачи выбрать вариант 1, если нет существующего обязательного
требования показывать единицу на экране. Это минимизирует путаницу и не меняет
юридический payload.

## 7. Сохранность состояния и API

- Не менять `CHK-F05`…`CHK-F08` и остальные IDs.
- Не изменять backend validation и правила решений.
- `matches=null` означает «пользователь ещё не отметил» и не отправляется в
  `checks` при сохранении.
- `matches=true/false` попадает в payload только после действия пользователя и
  сохраняется только успешным `PUT /reconciliation`.
- Нажатие «Все соответствует» считается явным действием пользователя и меняет
  форму, но не отправляет данные без отдельного «Сохранить сверку».
- При сетевой ошибке сохранения введённые marks/facts остаются в форме и могут
  быть отправлены повторно.
- Не очищать и не мигрировать существующие `reconciliations.checks` без
  отдельного решения владельца данных; добавить диагностический тест,
  показывающий источник предвыбранной отметки.

## 8. Тесты

### Comparison/UI

1. У каждой активной comparison card value и кнопки находятся в одной строке,
   buttons — справа.
2. На 390 px value не скрывает и не выталкивает controls.
3. `CHK-F07` и `CHK-F08` имеют buttons; при resolved name controls активны.
4. При PENDING/ERROR/MISSING controls видимы, disabled и не отмечены.
5. Клавиатурный focus, radio semantics/aria и live status сохранены.
6. В бейдже присутствуют `img[src="/mercury-logo.webp"]`, `alt=""` и текст
   «Меркурий».
7. Storybook показывает обычное, mismatch, loading, disabled и narrow states.

### Draft/save regression

1. Новая reconciliation с `checks={}` рендерит все marks нейтральными.
2. Click mark → route unmount без PUT → повторное открытие снова нейтральное.
3. Click mark → «Сохранить сверку» → повторное открытие восстанавливает mark.
4. «Все соответствует» без save не создаёт сетевой запрос.
5. Query cache не получает draft form values до успешного PUT.
6. Существующая сохранённая `OPEN`-сверка восстанавливает только реально
   сохранённые checks; тест не считает это автоматической отметкой.

### Decimal/unit

1. `60`, `60.0`, `60.000000` отображаются как `60`.
2. `60.45` и `60.450000` отображаются как `60,45`.
3. Значение `60,45` при сохранении уходит как каноническая decimal-строка и
   не меняет numeric meaning.
4. Большие/точные decimal-строки не проходят через JS float.
5. Масса и количество мест отображаются раздельно и не меняют payload.
6. В интерфейсе нет текста `GUID:` в блоке количеств.
7. `unit_id` сохраняется в payload и receipt XML mapping использует исходный
   GUID.

Все frontend tests используют MSW/fixtures. Живые VetIS write-вызовы не
выполняются.
