# Доработка: надёжное гашение входящего ВСД через асинхронный API ВетИС

Дата: 2026-11-15  
Исполнитель: ИИ-агент  
Область: backend, интеграция ВетИС, журнал операций, контейнер обработчика

## 1. Проблема

При гашении входящего ВСД операция завершается состоянием `UNKNOWN` и кодом
`VETIS_SUBMIT_OUTCOME_UNKNOWN`, хотя ВетИС использует двухшаговый асинхронный
контракт:

1. `submitApplicationRequest` принимает заявление и возвращает
   `applicationId`;
2. `receiveApplicationResultRequest` по этому `applicationId` возвращает
   промежуточный либо окончательный результат.

Текущая реализация сворачивает **любую** ошибку HTTP/SOAP при первом шаге в
«результат неизвестен». В том числе так обрабатывается SOAP Fault — однозначный
ответ ВетИС о том, что заявление отклонено и внешнее изменение не выполнено.
Текст Fault не сохраняется, поэтому невозможно отличить ошибку XML/прав доступа
от реального обрыва связи после отправки.

Дополнительно действие SOAP для второго шага захардкожено как
`receiveApplicationResultRequest`, тогда как закреплённый WSDL
`ApplicationManagementService` задаёт действие `receiveApplicationResult`.

Операция `2c2049f5-3d6e-5174-8c4c-e10222b3039a` для ВСД
`59dc501a-6217-46f6-9cad-4287005f000b` уже зафиксирована как `UNKNOWN` без
`applicationId`. Выполненная 2026-11-15 свежая read-only выборка ВетИС всё ещё
возвращает этот ВСД со статусом `CONFIRMED`. Следовательно, прежняя попытка не
погасила его, но повторять отправку без такой внешней проверки запрещено.

При первой диагностической отправке после включения корректного опроса ВетИС
вернул `applicationId`, а затем однозначный schema-отказ: значение количества
мест сериализовано как `6.000000`, хотя `dt:quantity` требует целое число.
Маппинг обязан передавать целые количества без десятичного масштаба (`6`) и
отклонять дробное количество до сетевого обращения.

Следующая диагностическая отправка выявила второй business-дефект: генератор
не переносил ТТН из vetDocument-level `referencedDocument` исходного ВСД в
`delivery/accompanyingForms/waybill`. В результате ВетИС отклонял заявление
из-за несовпадающего типа ТТН. Номер, дата, серия (при наличии) и тип ТТН
должны копироваться из закреплённого исходного XML; пользователь не вводит их
повторно.

## 2. Цель

Система должна один раз отправить корректное заявление на гашение, сохранить
полученный `applicationId`, безопасно опрашивать результат до терминального
ответа и подтверждать локальное поступление только по доказанному успешному
ответу ВетИС.

## 3. Требования к реализации

### 3.1. Транспорт и классификация ошибок

- Действия SOAP брать из runtime manifest, а не дублировать строковыми
  литералами в worker/transport.
- Для `submitApplicationRequest` сохранить действие
  `submitApplicationRequest`.
- Для элемента `receiveApplicationResultRequest` использовать действие WSDL
  `receiveApplicationResult`.
- Разбирать SOAP Envelope и SOAP Fault даже при HTTP 4xx/5xx.
- Сериализовать `dt:package/dt:quantity` целым числом без дробной части и
  завершающих нулей; дробное количество блокировать локальной валидацией.
- Переносить ТТН из `vd:referencedDocument` исходного ВСД в
  `vd:delivery/vd:accompanyingForms/vd:waybill`; не выдумывать тип или номер.
- Ввести типизированную ошибку транспорта с признаком:
  - `DEFINITE_REJECTION`: получен HTTP-ответ/SOAP Fault, однозначно
    отклоняющий заявление; повтор по новой пользовательской команде допустим;
  - `OUTCOME_UNKNOWN`: таймаут чтения, разрыв соединения либо иная ситуация,
    где сервер мог принять заявление, но ответ с `applicationId` утрачен.
- При `DEFINITE_REJECTION` переводить операцию в `REJECTED`, сохранять
  безопасный код и очищенный текст причины ВетИС. Не сохранять и не показывать
  API key, Basic Auth, полный XML или персональные данные.
- При `OUTCOME_UNKNOWN` сохранять существующую блокировку повторной отправки и
  состояние `UNKNOWN`.
- Записывать в серверный журнал класс исключения и безопасный код, чтобы
  следующую неисправность можно было диагностировать без изменения кода.

### 3.2. Асинхронный жизненный цикл

- После успешного submit атомарно сохранить `applicationId`, `submitted_at` и
  состояние `PROCESSING` до первого опроса.
- Опрос `receiveApplicationResultRequest` разрешён повторно и не должен
  повторять submit.
- Статусы `ACCEPTED`, `IN_PROCESS` и их контрактные аналоги оставляют операцию
  в `PROCESSING` и планируют следующий опрос с текущим backoff.
- Только доказанный успешный `COMPLETED` с результатом
  `processIncomingConsignmentResponse` переводит операцию в `CONFIRMED` и
  открывает локальный gate.
- SOAP Fault/отказ результата переводит операцию в `REJECTED`; временная
  ошибка опроса оставляет `PROCESSING`.
- Таймаут ожидания результата не вызывает повторный submit.

### 3.3. Безопасное восстановление старого UNKNOWN

- Автоматический повтор неизвестного submit запрещён.
- Разрешить закрыть `UNKNOWN` без `applicationId` как «не применено» только
  после свежего успешного read-only `GetVetDocumentByUuidOperation`, который
  возвращает точную версию того же UUID со статусом `CONFIRMED`. Проверка по
  UUID обязательна: список входящих может обновляться с задержкой.
- После такого доказательства старая операция получает терминальное состояние
  `REJECTED` и код `VETIS_SUBMIT_NOT_APPLIED`; повторное гашение создаётся как
  новая операция с новым `localTransactionId` и только по явному действию
  пользователя/владельца.
- Если документ отсутствует или read-only проверка не завершилась успешно,
  старая операция остаётся `UNKNOWN`, отправка запрещена.

### 3.4. Контейнер обработчика

- `vetis-worker` должен входить в итоговую Compose-конфигурацию, запускаться из
  того же актуального backend image и получать тот же VetИС-профиль и schema
  pins, что backend.
- После изменения пересобрать и пересоздать backend, frontend и
  `vetis-worker`; старый orphan-контейнер недопустим.

## 4. Проверки

- Unit: точные SOAPAction для submit/receive.
- Unit: успешный submit сохраняет `applicationId`; повторный запуск не делает
  второй submit и только опрашивает результат.
- Unit: SOAP Fault при submit становится `REJECTED`, а таймаут после отправки —
  `UNKNOWN`.
- Unit: временная ошибка receive остаётся `PROCESSING`.
- Unit/интеграционная: UNKNOWN разрешается только свежим внешним
  `CONFIRMED`; отсутствие документа и неуспешный проход повтор не разрешают.
- Регрессия: существующие тесты ВетИС, поступлений и подтверждения проходят.
- Live smoke в тестовом контуре: по прямому разрешению владельца погасить
  только ВСД `59dc501a-6217-46f6-9cad-4287005f000b`; зафиксировать новый
  `applicationId`, терминальный ответ и исчезновение документа из свежего
  списка `CONFIRMED`. Не отправлять второй submit при неизвестном результате.

## 5. Готовность

- Пользователь не видит `VETIS_SUBMIT_OUTCOME_UNKNOWN` для однозначного SOAP
  Fault: отображается фактическая безопасная причина отказа.
- Успешное гашение проходит цепочку `QUEUED → SUBMITTING → PROCESSING →
  CONFIRMED` с сохранённым `applicationId`.
- Конкретный разрешённый тестовый ВСД погашен один раз, результат подтверждён
  через `receiveApplicationResultRequest` и read-only выборку.
- Ветка с ТЗ и кодом объединена с `main`, отправлена в GitHub, контейнеры
  обновлены и находятся в рабочем состоянии.
