# ТЗ: создание пользователей из раздела «Управление пользователями»

Дата: 16.11.2026  
Статус: к реализации  
Исполнитель: ИИ-агент  
Тип задачи: frontend + backend, восстановление утверждённого административного сценария

## 1. Проблема

Пользователь с ролью `ADMIN`, в том числе `local-admin`, открывает `/users`, но не видит кнопку создания пользователя и не может начать предусмотренный требованиями сценарий из списка.

В проекте уже существуют:

- маршрут `/users/new`;
- React-страница создания пользователя;
- `POST /api/v1/users`;
- серверная проверка уникальности логина, пароля, области и идемпотентности.

Однако сценарий нельзя считать реализованным:

1. На `/users` нет видимой кнопки перехода к созданию.
2. Текущая форма требует вручную вводить UUID лаборатории и продукции. Администратор не должен знать или копировать технические идентификаторы.
3. Форма исключает роль `ADMIN`, а backend безусловно отклоняет её. Это противоречит утверждённым O-08, FT-ACC-09 и FT-ADM-01: уполномоченный администратор может назначать любую из четырёх ролей в пределах делегированных полномочий.
4. Текущий экран не доведён до эталонного вида `admin-users` / `admin-user-create`.
5. Право на создание не должно определяться состоянием «данные текущего пользователя ещё не загружены».

## 2. Цель

Дать пользователю с действующим правом `users:create` полный, понятный и безопасный сценарий:

`Управление пользователями → Создать пользователя → заполнить данные и область → сохранить → увидеть нового пользователя в списке`.

Сценарий должен:

- соответствовать эталонным макетам;
- не показывать пользователю UUID;
- назначать только разрешённые роли и области;
- не позволять администратору расширить собственные полномочия;
- создавать активную учётную запись один раз даже при повторе запроса;
- сохранять фильтры списка при возврате.

### 5.2. Условие показа

Кнопка показывается только после успешной загрузки текущего пользователя и подтверждения права `users:create`.

Запрещено считать пользователя администратором, пока `/me` ещё не загрузился. Текущую логику вида `me === null || me.role === "ADMIN"` заменить честным состоянием загрузки/ошибки/доступа.

Для пользователя без права:

- кнопка отсутствует;
- прямое открытие `/users/new` даёт понятное состояние `Доступ запрещён`;
- backend всё равно отвечает 403 на попытку POST;
- содержание административных областей не раскрывается.

### 5.3. Возврат и фильтры

Перед переходом на создание сохранить текущие query-параметры списка (`q`, `role`, `status`, `page` и добавленные поддерживаемые фильтры) в безопасном `returnTo` либо navigation state.

После отмены или успешного создания пользователь возвращается на тот же URL списка. Если новый пользователь не попадает под активные фильтры, показать успешное сообщение, но не сбрасывать фильтры молча.

## 7. Роль и область доступа

### 7.1. Четыре роли

Форма поддерживает:

- `VET` — `Ветеринарный врач`;
- `HEAD` — `Заведующий лабораторией`;
- `ANALYST` — `Аналитик`;
- `ADMIN` — `Администратор`.

Показывать только роли, которые текущий администратор вправе делегировать. Нельзя просто добавить `ADMIN` в HTML-select и полагаться только на интерфейс.

### 7.2. Серверный контракт разрешённых назначений

Backend должен быть единственным источником разрешённых ролей и областей. Добавить либо расширить read-only endpoint, возвращающий для текущего администратора:

- разрешённые к назначению роли;
- допустимые территории для административной роли;
- допустимые лаборатории с `id` и человекочитаемым названием;
- применимые продуктовые области с `id` и названием, если они реально используются выбранной ролью;
- правила кратности выбора, необходимые форме.

Endpoint:

- требует сессию и административное право чтения/создания пользователя;
- возвращает только делегируемое подмножество;
- не раскрывает чужие UUID и названия;
- имеет типизированную схему и документирован в OpenAPI/frontend types;
- не заменяет серверную проверку POST.

Существующий `/api/v1/contexts/laboratories` можно переиспользовать для названий лабораторий, если он действительно возвращает полный и точный набор, допустимый именно для назначения пользователя. Если это лишь рабочий контекст текущего пользователя и его недостаточно для O-08, создать специализированный scoped endpoint, а не расширять доступ на клиенте.

### 7.3. Человекочитаемый интерфейс

В форме запрещены поля:

- `Лаборатория (UUID)`;
- `Продукция (UUID)`;
- ручной ввод territory/product/laboratory ID.

Пользователь выбирает названия. В payload отправляются соответствующие UUID, выбранные из серверного набора. Технический ID можно показывать только в диагностике для поддержки, не как рабочее поле.

### 7.4. Правила ролей

- `VET`: назначение в разрешённую лабораторию и применимую продуктовую область согласно актуальной модели scope.
- `HEAD`: одна назначенная администратором лаборатория; переключение лаборатории в рабочем интерфейсе заведующего не появляется. Если серверная модель допускает несколько scope-строк для иных задач, создание должно всё равно соблюдать подтверждённое продуктовое правило «одна лаборатория заведующего».
- `ANALYST`: область, предусмотренная FT-ADM-01; интерфейс не должен искусственно превращать республиканского аналитика в городского. Назначение доступно лишь при соответствующем grant.
- `ADMIN`: создаётся с `DelegationGrant`, а не с рабочим `UserScope`; можно выбрать только роль/территорию, которую actor вправе делегировать (`may_delegate=true`). Созданный администратор не получает рабочие данные автоматически.

При смене роли форма должна:

- очистить несовместимые скрытые значения;
- запросить подтверждение, если уже выбранная область будет потеряна;
- не отправлять устаревшие scope-поля;
- озвучить новое правило области понятным текстом.

## 8. Исправление backend-расхождения с FT-ADM-01

Удалить безусловный запрет `payload.role == ADMIN` из обычной команды создания и заменить его реальной проверкой делегирования.

Требования к серверу:

1. `users:create` остаётся обязательным.
2. Под блокировкой читаются актуальные grants actor и целевая территория.
3. Actor может выдать только роль и территорию, прямо разрешённые его grant с `may_delegate=true`.
4. Нельзя выдать область выше, шире или вне делегированного поддерева.
5. Нельзя расширить собственные grants через создание/редактирование.
6. Создание `ADMIN` атомарно создаёт User, DelegationGrant и UserEvent.
7. Для рабочих ролей атомарно создаются User и UserScope.
8. Ошибка проверки не оставляет частичного пользователя или grant.
9. Событие истории содержит роль и безопасное описание области, но не пароль/hash.
10. Конкурентные запросы с одинаковым логином дают ровно один 201 и один 409.
11. Повтор одного intent с тем же `Idempotency-Key` не создаёт второго пользователя/grant/event.

Bootstrap-CLI остаётся способом создания первого корневого администратора на пустой установке. Он не должен оставаться единственным способом создать последующего администратора, если делегирование разрешено O-08.

Если текущая модель grants не позволяет однозначно выразить «какую роль разрешено делегировать», выполнить минимальную миграцию/уточнение модели. Нельзя трактовать наличие `ADMIN` у actor как право выдать любую роль в любой области.

## 9. Отправка и результат

Использовать существующий `POST /api/v1/users` и CSRF/session transport.

- Генерировать один `Idempotency-Key` на пользовательский intent сохранения.
- При сетевой неопределённости повторять тот же intent с тем же ключом, пока пользователь не изменил данные и не начал новую попытку.
- Во время отправки блокировать повторное нажатие и показывать `Создаём…`.
- После 201 обновить query cache списка, показать `Пользователь создан` и вернуться на сохранённый URL `/users?...`.
- Созданная строка должна появиться без ручной перезагрузки, если соответствует фильтрам.

Не использовать искусственную задержку как гарантию отображения результата. Навигация выполняется после подтверждённого ответа и обновления клиентского состояния.

## 10. Ошибки и доступность

Серверные ошибки привязываются к конкретным полям по `Problem.errors.path`.

Обязательные случаи:

- занятый логин — ошибка у `Логин`;
- пароли не совпадают — у подтверждения;
- недопустимая роль/область — у блока доступа плюс общее сообщение;
- область устарела между открытием и сохранением — перечитать варианты, сохранить основные введённые данные и попросить выбрать область заново;
- 403 — `Недостаточно прав для создания пользователя` без раскрытия чужой области;
- 409 — понятная предметная причина;
- сеть/5xx — введённые несекретные данные остаются, доступен безопасный повтор.

После неуспешного submit фокус переводится на первую ошибку или общий error summary. Все поля имеют видимые label, ошибки связаны через `aria-describedby`, обязательность не обозначается только цветом.

## 13. Тесты

### 13.1. Backend

Добавить/обновить тесты:

1. ADMIN с `users:create` и допустимым grant создаёт VET в своей лаборатории — 201.
2. Создаёт HEAD только с одной разрешённой лабораторией.
3. Уполномоченный grant создаёт ANALYST в подтверждённой области.
4. Уполномоченный grant создаёт ADMIN с корректным DelegationGrant.
5. ADMIN без права делегировать ADMIN получает 403, записей нет.
6. Подмена role/territory/laboratory UUID в POST отклоняется.
7. Чужая область не появляется в endpoint вариантов.
8. Self-escalation невозможна.
9. Создание администратора не даёт actor или target рабочие UserScope автоматически.
10. Один Idempotency-Key не создаёт дубль.
11. Параллельный одинаковый логин: один 201, один 409.
12. История не содержит пароль или hash.

Не ослаблять и прогнать существующие identity/platform tests, включая проверки последнего администратора и чужих UUID.

### 13.2. Frontend/component

Проверить:

- кнопка присутствует только при подтверждённом `users:create`;
- loading `/me` не показывает кнопку и не запускает admin-query преждевременно;
- кнопка открывает `/users/new`;
- UUID-поля отсутствуют;
- варианты отображаются названиями и отправляют правильные ID;
- список ролей соответствует серверным разрешениям;
- смена роли очищает несовместимые данные;
- ошибки backend привязаны к полям;
- успешное создание обновляет список и сохраняет query-параметры;
- dirty guard работает;
- пароль очищается;
- мобильная компоновка не имеет горизонтальной прокрутки.

### 13.3. E2E

Минимальные сценарии в изолированной тестовой базе:

1. Войти как уполномоченный администратор → `/users` → `Создать пользователя` → создать VET → увидеть его в списке → войти созданной учётной записью.
2. Создать HEAD и проверить одну назначенную лабораторию без переключателя лабораторий.
3. Проверить делегированное создание ADMIN и запрет для actor без такого grant.
4. Попытаться подменить чужую лабораторию через network request и получить 403/404 без записи.
5. Повторить submit/ответ после сетевой неопределённости и убедиться, что запись одна.

Не использовать `local-admin` и рабочие данные как удаляемую тестовую фикстуру.

## 14. Команды проверки

Исполнитель определяет точные команды по `package.json` и `pyproject.toml`, но обязан выполнить минимум:

- целевые frontend unit/component tests;
- целевые backend identity tests;
- полный релевантный backend regression suite;
- `npm.cmd run build-storybook` при изменении stories;
- `npm.cmd run test:ui` при затронутых общих UI-компонентах;
- production frontend build;
- e2e сценарий создания пользователя в отдельной тестовой базе;
- браузерную проверку `/users` и `/users/new` на desktop и 390 px.

Нельзя отмечать проверку выполненной, если команда не запускалась. Все not-run указать в отчёте.

## 15. Критерии приёмки

Задача принята, когда одновременно выполнено следующее:

- `local-admin` видит на `/users` кнопку `Создать пользователя`;
- кнопка соответствует макету и открывает рабочую форму;
- форма визуально соответствует `admin-user-create` с учётом общей SPA-шапки;
- нет ручного ввода UUID;
- обязательные поля и пароль проверяются;
- варианты ролей и областей приходят из server-authoritative scoped read model;
- уполномоченный администратор может назначить любую из четырёх ролей;
- неуполномоченный не может назначить роль/область подменой запроса;
- новый пользователь создаётся активным и появляется в списке;
- созданный пользователь может войти;
- фильтры списка сохраняются;
- пароль не попадает в историю и логи;
- повтор запроса не создаёт дубль;
- loading/error/forbidden/empty/long/mobile состояния проверены;
- тесты, Storybook build и браузерная приёмка завершены без новых ошибок.

## 16. Git, объединение и обновление стенда

1. Создать отдельную ветку с префиксом `codex/`, например `codex/admin-create-user`.
2. Включить это ТЗ в ту же ветку вместе с кодом и тестами.
3. Делать логически разделённые коммиты; в сообщениях указать FT-ACC-08/09, FT-ADM-01.
4. До объединения убедиться, что ветка основана на актуальном `main`, и разрешить конфликты без потери чужих изменений.
5. После успешных проверок объединить ветку в `main` без переписывания истории уже опубликованного `main`.
6. Пересобрать и обновить затронутые контейнеры штатным способом проекта.
7. Проверить в обновлённом стенде вход `local-admin`, `/users`, `/users/new`, создание тестового пользователя и его вход.
8. В итоговом отчёте указать commit/merge commit, выполненные тесты, обновлённые контейнеры и честные not-run.
