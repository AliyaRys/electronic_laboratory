# ТЗ: исправить верхний слой и затемнение диалога подтверждения гашения эВСД

Дата: 16.11.2026  
Статус: к реализации  
Исполнитель: ИИ-агент  
Тип задачи: frontend, общий компонент модального диалога

## 1. Проблема

На странице сверки при подготовке гашения открывается диалог:

`Подтвердите гашение эВСД`.

Сейчас карточка диалога визуально смешивается с содержимым страницы. Текст страницы остаётся виден под текстом диалога, из-за чего невозможно уверенно прочитать резюме и выполнить юридически значимое действие.

Ожидаемое поведение:

- диалог находится выше всех элементов приложения;
- карточка диалога имеет полностью непрозрачный фон;
- вся остальная страница равномерно затемняется;
- шапка, закреплённые панели, меню и содержимое сверки находятся под подложкой;
- через подложку нельзя нажимать элементы страницы;
- фокус остаётся внутри диалога.

## 2. Затронутый пользовательский сценарий

Основной маршрут:

`/labs/:labId/arrivals/:partyId/reconciliation`

Последовательность:

1. пользователь полностью заполняет и сохраняет сверку;
2. выбирает параметры гашения;
3. нажимает `Подготовить гашение`;
4. получает preview;
5. открывается диалог `Подтвердите гашение эВСД`;
6. пользователь проверяет резюме и выбирает `Вернуться к проверке` или `Погасить эВСД`.

Серверную логику подготовки и отправки гашения в рамках этой задачи не менять.

## 3. Подтверждённая техническая причина

Общий компонент использует `@radix-ui/react-dialog` и `RadixDialog.Portal`:

`frontend/src/shared/ui/Dialog.tsx`.

Portal выводит overlay и content в `document.body`, то есть за пределы корневого контейнера `.vse-app`.

При этом основные токены оформления объявлены только внутри `.vse-app`:

```css
.vse-app {
  --app-ink: #17323a;
  --app-line: #dfe9e9;
  --app-panel: #fff;
  ...
}
```

Диалог использует эти переменные:

```css
.app-dialog {
  background: var(--app-panel);
  color: var(--app-ink);
  border: 1px solid var(--app-line);
}
```

Так как portal-узлы не являются потомками `.vse-app`, значения переменных могут быть не определены. В результате декларация фона становится невалидной, карточка оказывается прозрачной либо получает непредусмотренное оформление и визуально сливается со страницей.

Текущий CSS уже содержит `z-index: 1000` для overlay и `1001` для content, однако существующий тест проверяет только наличие этих чисел в тексте CSS. Он не проверяет:

- вычисленный непрозрачный фон карточки;
- фактическое затемнение viewport;
- наследование токенов portal-контентом;
- положение относительно шапки и sticky-панели;
- блокировку кликов по странице.

Следовательно, простое повторное увеличение `z-index` без исправления области токенов не является достаточным решением.

## 4. Цель

Исправить общий компонент `Dialog`, чтобы любой модальный диалог приложения, включая подтверждение гашения, всегда:

- отображался в отдельном верхнем слое;
- имел корректную тему и непрозрачную поверхность;
- затемнял всё приложение;
- блокировал взаимодействие с фоном;
- сохранял требования доступности Radix.

Исправление должно быть общим. Запрещено делать отдельный локальный overlay или специальный `z-index` только в `ReceiptConfirmationDialog` или `reconciliation.css`.

## 5. Требуемая архитектура слоя

### 5.1. Portal и тема

Выбрать один централизованный способ, гарантирующий доступность токенов внутри portal:

**Предпочтительный вариант:** создать общий portal-layer/portal-root, который находится в `body`, получает класс темы приложения и содержит `Overlay` и `Content`.

Допустимые реализации:

- общий контейнер `#app-dialog-root` с каноническим theme-классом;
- wrapper внутри `RadixDialog.Portal`, которому доступны все `--app-*` токены;
- перенос только определений общих токенов на `:root`/общий theme-root, если это не меняет оформление остальных экранов.

Выбранное решение должно:

- работать в приложении, тестах и Storybook;
- не зависеть от конкретной страницы;
- не искать родителя через хрупкие цепочки DOM;
- не копировать значения токенов в `ReceiptConfirmationDialog`;
- не добавлять вторую несогласованную палитру.

### 5.2. Порядок слоёв

Закрепить единый порядок:

1. обычное содержимое страницы;
2. AppHeader, dropdown и sticky-панели;
3. модальная подложка;
4. карточка модального диалога.

Подложка и карточка должны иметь централизованные layer tokens либо согласованные значения. Карточка всегда выше подложки. Подложка всегда выше:

- `AppHeader`;
- меню шапки;
- таблиц и dropdown;
- `.vse-rec-actions`;
- sticky-панелей справочников;
- toast/popover, не являющихся отдельным системным модальным сообщением.

Не использовать отрицательные `z-index`. Не разбрасывать `!important` по feature-CSS.

### 5.3. Подложка

`.app-dialog-overlay` должна:

- иметь `position: fixed`;
- покрывать viewport через `inset: 0`;
- иметь непрозрачность, достаточную для уверенного отделения фона — ориентир текущего дизайна `#17323a59` или визуально эквивалентное затемнение;
- принимать pointer events;
- находиться выше всей страницы;
- не иметь разрывов вокруг шапки или краёв viewport.

Фоновое содержимое не размывать настолько, чтобы возникала нагрузка на слабых устройствах. Затемнения достаточно; blur допустим только если уже является согласованным токеном и не ухудшает производительность.

### 5.4. Карточка диалога

`.app-dialog` должна:

- находиться выше overlay;
- иметь полностью непрозрачный белый/канонический `var(--app-panel)` фон;
- иметь корректные `color`, границу и тень;
- быть визуально отделена от затемнённой страницы;
- сохранять центрирование;
- иметь максимальную высоту относительно viewport и внутреннюю вертикальную прокрутку;
- не позволять длинному fingerprint или UUID расширить окно за пределы экрана.

Нельзя задавать карточке `opacity`, которая одновременно делает полупрозрачным текст и фон.

## 6. Диалог подтверждения гашения

Сохранить существующее содержание и порядок фактов:

- эВСД;
- решение;
- ревизия источника/сверки;
- принято;
- возвращается;
- дата поступления;
- осмотры;
- причина возврата/акт несоответствия при наличии;
- маршрут после гашения;
- fingerprint подготовленного запроса.

Сохранить действия:

- безопасное `Вернуться к проверке`;
- опасное `Погасить эВСД`;
- кнопка закрытия;
- Escape.

В рамках задачи не менять текст юридического предупреждения и не отправлять реальное гашение для визуальной проверки. Для тестирования использовать fixture/MSW preview.

### 6.1. Читаемость длинного резюме

Для данного диалога проверить:

- UUID и fingerprint переносятся внутри карточки;
- термины и значения не накладываются друг на друга;
- на узком экране пары `dt/dd` перестраиваются в одну колонку;
- кнопки остаются видны либо доступны после внутренней прокрутки;
- закрытие не теряется при прокрутке.

Если используется закрепление заголовка или панели действий внутри длинного диалога, оно должно быть частью общего поддерживаемого варианта, а не случайным feature-хаком.

## 7. Доступность и взаимодействие

Сохранить действующий контракт Radix:

1. `role="dialog"` и модальность.
2. Заголовок связан через `aria-labelledby`.
3. Описание/ошибка связаны через `aria-describedby`.
4. При открытии фокус получает безопасная кнопка `Вернуться к проверке`.
5. Tab/Shift+Tab не выводят фокус на страницу.
6. Escape закрывает окно, если операция ещё не находится в небезопасном busy-состоянии.
7. После закрытия фокус возвращается на кнопку, открывшую диалог.
8. При открытом диалоге элементы страницы недоступны для pointer interaction.
9. Фоновая страница не прокручивается независимо от модального окна.
10. Видимый focus-ring работает и в portal, а не только внутри `.vse-app`.

Проверить поведение закрытия во время отправки. Если текущий контракт запрещает закрытие при `busy`, сохранить его; нельзя позволить пользователю случайно создать неоднозначность отправки только ради визуального изменения.

## 8. Общий охват

Так как исправляется `shared/ui/Dialog`, выполнить регрессионную проверку всех использующих его сценариев:

- подтверждение гашения эВСД;
- удаление/скрытие поступления;
- удаление карточки ВСЭ;
- утилизация проб;
- удаление нормы/тарифа;
- массовые цены;
- предупреждение о несохранённых изменениях;
- другие Radix-диалоги SPA.

Не изменять нативные `<dialog>` старых HTML-экранов в рамках этой задачи, если они не используют общий React-компонент.

## 9. Тесты

### 9.1. Unit/component

Сохранить текущие проверки:

- safe cancel получает первый фокус;
- Escape закрывает;
- фокус возвращается на trigger;
- ошибка связана через `aria-describedby`;
- confirm вызывает только переданный callback.

Добавить проверку, что portal-слой получает канонический theme-контекст. Тест не должен ограничиваться поиском строки `z-index: 1000` в CSS.

### 9.2. Браузерный e2e — обязательный

На реальной странице сверки с fixture/MSW preview:

1. открыть подтверждение гашения;
2. получить `getComputedStyle()` overlay:
   - `position: fixed`;
   - rect совпадает с viewport;
   - фон не `transparent` и имеет ненулевую альфу;
   - `z-index` больше header/sticky-actions;
3. получить `getComputedStyle()` content:
   - фон непрозрачный;
   - цвет текста определён;
   - `z-index` больше overlay;
4. проверить через `document.elementFromPoint()` в центре окна, что верхний интерактивный слой относится к диалогу;
5. проверить точку вне карточки — она принадлежит overlay, а не странице;
6. попытка нажать кнопку/ссылку страницы под overlay не выполняет действие;
7. Tab остаётся внутри диалога;
8. Escape закрывает и возвращает фокус;
9. сделать скриншот на ширинах `1440`, `1024`, `768`, `390`;
10. подтвердить отсутствие горизонтальной прокрутки и читаемость fingerprint.

### 9.3. Storybook

Обновить/проверить stories общего Dialog:

- обычный;
- danger;
- длинное описание и длинное содержимое;
- ошибка;
- busy;
- узкий экран;
- резюме гашения с длинным UUID/fingerprint.

Storybook должен использовать тот же portal/theme-контракт, что и рабочее приложение.

## 10. Критерии приёмки

Задача завершена, если:

1. Диалог подтверждения гашения визуально находится выше всех элементов страницы.
2. Всё приложение, включая шапку и sticky-панель, затемнено единой подложкой.
3. Карточка диалога полностью непрозрачна, текст не смешивается с фоном.
4. Клики не проходят к странице.
5. UUID и fingerprint читаемы и не ломают ширину.
6. Диалог работает на `1440/1024/768/390px`.
7. Фокус, Escape, возврат фокуса и `aria-*` сохранены.
8. Исправление выполнено в общем `Dialog`, без локального слоя только для гашения.
9. Остальные общие диалоги не получили визуальную или функциональную регрессию.
10. E2E проверяет вычисленные стили и реальное наложение, а не только текст CSS.
11. Для визуальной проверки не выполнено реальное гашение эВСД.
