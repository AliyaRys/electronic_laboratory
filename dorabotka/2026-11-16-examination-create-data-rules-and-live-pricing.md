## 2. Цель

Исправить страницу создания ВСЭ так, чтобы:

- она показывала те же подтверждённые данные партии, что и завершённая сверка;
- пользователь не видел технических GUID/UUID вместо названий;
- числовые значения были человекочитаемыми;
- условно обязательная трихинеллоскопия действительно была закреплена в форме;
- новый отбор был единственным режимом при создании новой карточки;
- итоговая секция соответствовала эталонному макету и сохраняла корректное авторство;
- стоимость пересчитывалась сервером по мере заполнения исследований;
- окончательное сохранение оставалось атомарным и использовало ту же формулу, что предварительный расчёт.

## 3. Нельзя ограничиться косметическим исправлением

Текущие проблемы возникли не только в CSS:

- `ExaminationSections.tsx` читает legacy-проекции `consignor/consignee`, тогда как сверка использует четыре нормализованных поля участников;
- в принятом количестве к значению приписывается `accepted_unit_id`, являющийся техническим GUID;
- страница выводит decimal-строки без пользовательского форматирования;
- frontend лишь сообщает, что цена будет рассчитана после сохранения: preview API отсутствует;
- UI считает трихинеллоскопию обычным дополнительным исследованием, хотя backend знает условие обязательности;
- режим `REUSE` является частью frontend и backend-контракта;
- специалист сейчас жёстко равен создателю, тогда как новый эталонный сценарий требует явного выбора допустимого специалиста.

Исполнитель обязан исправить источник и контракт данных. Запрещено подменять проблему статическим текстом, локальными демонстрационными значениями или CSS-скрытием неверных данных.

## 4. Источник данных и неизменяемость шага сверки

### 4.1. Общее правило

Создание ВСЭ не должно повторно обращаться к SOAP-методам ВетИС и не должно заново разрешать GUID участников.

После сохранения сверки и подтверждения приёмки система должна иметь локальный неизменяемый снимок данных, применённых на этом шаге. Страница ВСЭ читает именно его.

В снимок должны входить минимум:

- отправитель — предприятие;
- отправитель — хозяйствующий субъект;
- получатель — предприятие;
- получатель — хозяйствующий субъект;
- четыре уровня классификации и их GUID/UUID/name;
- тип продукции;
- принятый вес;
- принятое количество мест;
- смысл/наименование единицы, если он нужен в других представлениях;
- идентификатор ревизии исходного эВСД и ревизии сверки.

### 4.2. Legacy-записи

Для уже существующих партий:

- сначала читать сохранённые значения завершённой сверки/confirmation snapshot;
- если старый снимок не содержит новых полей, выполнить контролируемый backfill из закреплённой source revision и локального кэша названий;
- не выполнять SOAP lookup из браузера;
- не подставлять GUID/UUID вместо имени;
- если имя невозможно восстановить, показать честное `Название не получено` и диагностический статус, а не `—` при наличии идентификатора.

Миграция/backfill должны быть повторяемыми и не менять уже закреплённый непустой текст.

## 5. Участники: одинаковые сущности на сверке и создании ВСЭ

### 5.1. Названия полей

В обеих карточках участников использовать строго:

- `Предприятие`;
- `Хозяйствующий субъект`.

Удалить пользовательские названия:

- `Название предприятия`;
- `Владелец продукции`.

Применить к блокам:

- `Сведения об отправителе`;
- `Сведения о получателе`.

### 5.2. Сопоставление

| Карточка | Поле | Источник шага сверки |
|---|---|---|
| Отправитель | Предприятие | сохранённое `senderEnterprise` / CHK-F05 source value |
| Отправитель | Хозяйствующий субъект | сохранённое `senderOwner` / CHK-F06 source value |
| Получатель | Предприятие | сохранённое `receiverEnterprise` / CHK-F07 source value |
| Получатель | Хозяйствующий субъект | сохранённое `receiverOwner` / CHK-F08 source value |

Названия полей backend могут отличаться, но в API должен существовать один однозначный read model без параллельных `consignor`, `owner`, `senderOwner` с разной семантикой.

### 5.3. Требования к реализации

- Переиспользовать нормализатор/проекцию `participantName` либо вынести общий resolver для сверки и ВСЭ.
- На странице ВСЭ не брать `consignor/consignee` как основной источник.
- Не перепутать предприятие и хозяйствующий субъект, даже если их текст совпадает.
- Длинные названия полностью доступны; перенос допускается, горизонтальная прокрутка — нет.
- Не показывать controls сравнения на странице ВСЭ: это readonly результат предыдущего шага.
- Открытие страницы ВСЭ не создаёт lookup job и не меняет сохранённый снимок.

## 6. Поле «Тип продукции»

Вместо цифрового значения показать русское название.

Обязательная карта:

| Код | Название в интерфейсе |
|---:|---|
| 1 | Мясо и мясопродукты |
| 2 | Корма и кормовые добавки |
| 3 | Живые животные |
| 4 | Лекарственные средства |
| 5 | Пищевые продукты |
| 6 | Непищевые продукты и другое |
| 7 | Рыба и морепродукты |
| 8 | Продукция, не требующая разрешения |

Создать единый типизированный справочник представления `productType → label` в общей Mercury/domain-части frontend либо вернуть код и label из backend read model. Нельзя дублировать mapping в нескольких страницах.

Правила:

- не выполнять отдельный API-запрос ради расшифровки при каждом открытии;
- не подменять тип вторым уровнем продукции;
- неизвестный код показывать как `Неизвестный тип продукции (код: N)` и регистрировать диагностическое предупреждение;
- пустой код показывать как `Название типа продукции не получено`;
- во всех пользовательских представлениях ВСЭ и партии по возможности использовать тот же formatter.

## 7. Человекочитаемые масса и количество

### 7.1. Принятый вес

Поле называется `Принятый вес, кг`.

Отображение decimal-строки выполняется без преобразования через JavaScript `Number`/`parseFloat`:

- `120.000000` → `120`;
- `45.120000` → `45,12`;
- `2.500000` → `2,5`;
- `0.010000` → `0,01`;
- значимые цифры не округляются и не теряются.

Переиспользовать существующую безопасную логику `formatDecimalDisplay`, при необходимости перенести её в общий domain formatter, чтобы сверка, диалог гашения, ВСЭ и журнал не копировали функцию.

### 7.2. Принятое количество

Поле называется `Принятое количество мест, шт.`.

Источник — сохранённое `accepted.quantity`, которое пользователь подтвердил/ввёл в поле `Количество мест, шт.` при сверке, а не:

- исходный вес;
- документарное количество до исправления;
- количество исследований;
- количество строк болезней;
- UUID единицы.

Пример:

- на сверке принято `5` мест;
- на создании ВСЭ должно быть `5`, даже если source XML до сверки содержал другое документарное значение.

Форматировать по тем же decimal-правилам. GUID `21ed96c9-…` и любые другие UUID рядом со значением не показывать.

### 7.3. Согласованность подтверждения

Проверить путь:

`сохранённая сверка → подготовленный запрос гашения → внешний результат → ReceiptConfirmation → IncomingView → форма ВСЭ`.

Успешный внешний результат не должен незаметно заменить подтверждённое локальное количество другим полем. Если ВетИС возвращает несовместимый состав, операция получает отдельное состояние расхождения/ошибки и требует проверки; система не открывает ВСЭ с подменённым количеством.

## 8. Удаление бесполезной надписи

Полностью убрать из формы создания:

`Партия подтверждена внешним результатом`.

Удалить сам элемент `.vse-confirm-note`, относящиеся только к нему стили и тестовые ожидания. Не заменять другой служебной фразой. Возможность открыть создание ВСЭ уже является достаточным признаком подтверждённой партии.

В карточке просмотра готовой ВСЭ также не выводить эту фразу как отдельное бизнес-поле `Статус приёмки`, если она не нужна для конкретного пользовательского решения. Технический provenance остаётся в данных/аудите.

## 9. Трихинеллоскопия как закреплённое исследование

### 9.1. Условие

Трихинеллоскопия обязательна ровно для четырёх категорий второго уровня Меркурия:

- Свинина;
- Конина;
- Субпродукты и жиры свиные;
- Субпродукты и жиры конские.

Проверка выполняется по точному GUID второго уровня / сохранённому policy mapping `requires_trichinelloscopy`, не сравнением русского текста и не UUID текущей версии.

### 9.2. Поведение формы

Для применимой партии карточка `Трихинеллоскопия *`:

- присутствует сразу при открытии;
- имеет тот же `primary`-вид, что органолептика и другие закреплённые исследования;
- содержит `Выберите результат`, `Соответствует`, `Не соответствует` согласно фактической typed schema;
- не имеет кнопки удаления;
- не появляется в списке `Добавить исследование`;
- обязательна и в client, и в server validation.

Для остальных категорий сохранить утверждённое текущее правило применимости: не делать исследование обязательным. Если оно разрешено как дополнительное, оно добавляется обычным способом; если каталог не допускает его, не показывать.

### 9.3. Контракт обязательности

Frontend не должен сам угадывать обязательность по названию. Backend/read model должен вернуть применимый набор обязательных indicator IDs либо эквивалентный признак, рассчитанный по закреплённой классификации партии. Сохранение всё равно повторно проверяет правило сервером.

## 10. Инвазионные и незаразные болезни

### 10.1. Свёрнутое состояние

Привести кнопки к эталону `electronic-vse-journal`:

- `＋ Добавить инвазионные болезни`;
- `＋ Добавить незаразное заболевание`.

В свёрнутом состоянии это компактные пунктирные add-кнопки того же вида, размера и расположения, что `.add-test` эталона. Не показывать вокруг пустой кнопки тяжёлую отдельную карточку с лишним вертикальным пространством.

### 10.2. После добавления

Сохранить предметную логику:

- инвазионная находка — болезнь + орган/ткань;
- незаразные болезни — до 10 строк;
- `Другое` требует текста;
- строку можно удалить;
- удалённая строка не отправляется;
- доступные имена, focus и keyboard navigation обязательны.

Использовать существующий `FindingsFields`/общий компонент, расширив вариант оформления. Не копировать HTML/JS макета внутрь React-страницы.

## 11. Проба: всегда новый отбор

### 11.1. Новое решение владельца

Для каждой новой карточки ВСЭ выполняется новый отбор. Повторное использование прежней пробы в форме создания исключается.

Это правило заменяет O-04, FT-SMP-03 и строки E03/E04 о `REUSE default` в части создания новой ВСЭ. Исполнитель обязан одновременно обновить:

- Product Foundation;
- `Функциональные требования/v2.0/owner-decisions.md`;
- `Функциональные требования/v2.0/05-samples.md`;
- `Функциональные требования/v2.0/10-field-catalog.md`;
- `docs/TZ_development/plans/2026-11-06-06-examinations.md`;
- traceability/acceptance, где ожидается REUSE.

Нельзя изменить только UI и оставить backend принимающим скрытый `REUSE` для новой карточки.

### 11.2. Создание новой карточки

- Удалить radio `Использовать имеющуюся пробу`.
- Не показывать переключатель режима, если режим один.
- Новый отбор создаётся с обязательной датой и положительным весом.
- Значение веса по умолчанию `0,8 кг` оставить, если владелец отдельно не изменил норматив.
- Описание заменить на предметное, например: `Новый отбор пробы этой партии.`
- API создания не принимает `REUSE`; подмена запроса отклоняется.
- Повтор того же idempotent intent не создаёт второй отбор.

### 11.3. Редактирование существующей карточки

Обычное сохранение правки не является новым отбором.

- Для карточки, уже связанной с отбором, редактируется тот же факт по действующим правилам ревизии.
- Не показывать выбор `NEW/EDIT/REUSE`; режим определяется состоянием карточки.
- Утилизированный отбор не переписывается.
- Старые записи, ранее созданные с REUSE, остаются читаемыми и не мигрируют в фиктивный новый отбор задним числом.

### 11.4. Удаление и повторное создание

После удаления карточки сохранённый физический факт пробы остаётся. Новая карточка по той же партии создаёт новый отбор. Остаток увеличивается на массу нового факта; это ожидаемое следствие нового решения и должно быть отражено в документации и тестах.

## 12. Секция «Итог экспертизы»

### 12.1. Композиция

Секция визуально следует `electronic-vse-journal`:

- заголовок `Итог экспертизы`;
- пояснение `Заключение, стоимость и специалист, проводивший ВСЭ.`;
- поле `Дата отбора проб`;
- checkbox `Пробы отправлены на спец. лабораторные исследования`;
- select `Результат ВСЭ *`;
- select `Направление по результатам ВСЭ *`;
- select `Специалист Госветслужбы *`.

Дата отбора является тем же значением нового отбора из раздела «Проба». Не создавать вторую независимую дату. Если дата визуально перенесена в итоговый блок, в разделе пробы она повторно не выводится.

### 12.2. Результат и направление

Использовать select-компоненты в стиле макета, но не обязательно подключать Choices.js в React, если общий доступный select приложения обеспечивает тот же вид и поведение.

Правила остаются серверными:

- `Пригодно` → только `В реализацию без ограничений`;
- `Непригодно` → `На утилизацию` или `На уничтожение` и обязательная причина;
- итог не выбирается автоматически по результатам исследований;
- пустой итог не маскируется значением по умолчанию;
- для WAITING итог может оставаться незаполненным согласно FT-VSE-06/08;
- смена результата очищает несовместимое направление и причину.

### 12.3. Специалист Госветслужбы

Новый UI требует явного выбора специалиста, однако автор технического действия и специалист исследования — разные аудируемые сущности.

Backend должен хранить:

- `created_by` / `updated_by` — текущий вошедший пользователь, неизменяемый аудит операции;
- `specialist_id` — выбранный специалист Госветслужбы;
- закреплённые ФИО специалиста для исторического отображения/документа либо надёжную ссылку с сохранением имени при блокировке пользователя.

Список специалистов:

- только активные VET/HEAD, которым доступно создание/проведение ВСЭ в текущей лаборатории и применимой продукции;
- только из server-authoritative scoped endpoint;
- текущий пользователь выбран по умолчанию, если он входит в список;
- чужого/заблокированного/неуполномоченного пользователя нельзя назначить подменой запроса;
- UUID в интерфейсе не показываются.

Если текущий пользователь не имеет права назначать другого специалиста, select содержит только его либо отображается readonly в том же визуальном формате. Не давать право выбора коллеги одной лишь доступностью route.

Это изменение заменяет прежнее правило D-36/FT-VSE-02 `Специалист — создатель`. Обновить Product Foundation, FT-VSE-02, field catalog, API-05/DATA-03, план E01/E04 и traceability. В документах явно различить `оператор сохранения` и `специалист ВСЭ`.

## 13. Живой расчёт стоимости исследований

### 13.1. Пользовательское поведение

Секция `Расчёт стоимости услуг` обновляется по мере того, как пользователь полностью заполняет или удаляет исследования.

Показывать таблицу:

| Исследование | Количество | Единица | Тариф | Сумма |
|---|---:|---|---:|---:|

И ниже `Итого к оплате`.

В строку входит только полностью выполненное исследование. Пустое/только добавленное исследование не начисляется.

### 13.2. Формула

Для каждой выполненной строки:

`сумма = действующий тариф исследования × принятое количество мест из подтверждённой сверки`.

Общий итог — сумма округлённых строк по FT-CAL-04.

Количество:

- берётся из frozen `accepted.quantity`;
- не вычисляется из числа form controls, болезней или исследований;
- не заменяется массой;
- не изменяется пользователем на странице ВСЭ.

Для ярмарки строки и итог равны `0 ₽`, но факт выполненного исследования сохраняется. Отсутствующий тариф не равен нулю.

### 13.3. Серверный preview

Добавить read/compute endpoint предварительного расчёта, например:

`POST /api/v1/examinations/parties/{party_id}/pricing-preview`.

Точное имя согласовать с API-стилем проекта. Endpoint:

- не создаёт ВСЭ, пробу, событие, command record или черновик;
- принимает только данные, необходимые для определения полностью выполненных исследований;
- использует текущую ревизию партии и закреплённую confirmation;
- проверяет scope пользователя;
- вызывает ту же доменную функцию `evaluate_and_price`, что окончательное сохранение;
- возвращает typed `PricingSnapshot`/preview с lines, total, currency, fair и понятными blocking problems;
- не принимает цену/количество/сумму от клиента;
- не обращается к ВетИС;
- не изменяет каталоги;
- не логирует медицинские значения сверх существующей политики.

Frontend не должен загружать все тарифы и считать деньги самостоятельно.

### 13.4. Обновление preview

- Запрашивать preview после изменения полного результата исследования или удаления исследования.
- Использовать debounce ориентировочно 250–400 мс.
- Отменять устаревший запрос; старый ответ не заменяет новый.
- Во время первого расчёта показывать skeleton/`Рассчитываем стоимость…`.
- При последующем пересчёте можно сохранять предыдущую таблицу с индикатором обновления, но нельзя выдавать её за окончательную.
- Если обязательное исследование ещё пустое, оно не начисляется; секция может дополнительно показать `Заполните результат, чтобы добавить исследование в расчёт`.
- Ошибка сети даёт `Не удалось обновить предварительный расчёт` и действие повтора без потери формы.
- Отсутствующий тариф/норма показывается названием конкретного исследования и блокирует завершение согласно FT-CAL-04; не выводить ложные `0 ₽`.

### 13.5. Сохранение

Preview информационный. При `Завершить ВСЭ` backend в той же транзакции повторно:

- проверяет ревизию партии;
- валидирует результаты;
- читает актуальные применимые тарифы/нормы либо закрепляет правила согласно действующему snapshot-контракту;
- пересчитывает и сохраняет pricing snapshot.

Если цена изменилась между preview и сохранением, вернуть управляемый conflict с новым расчётом и потребовать повторного подтверждения; не сохранять молча другую сумму.

Для `Отправить в ожидание результата` применить действующее правило полноты расчёта. В ТЗ и тестах явно закрепить, какие заполненные исследования начисляются в WAITING и когда snapshot окончательно фиксируется.

## 14. Backend/read-model изменения

Исполнитель должен определить минимальную миграцию, но итоговый контракт обязан содержать:

- Использовать общий `AppHeader`, `FormSection`, `Field`, `ReadonlyField`, `Button`, `Dialog` и реестр иконок.

## 20. E2E-приёмка

В изолированной тестовой базе/fixtures:

1. Завершить сверку с четырьмя участниками, весом `120.000000` и 5 местами.
2. Открыть создание ВСЭ и увидеть те же четыре имени, `120`, `5`, без GUID.
3. Для свинины увидеть неснимаемую `Трихинеллоскопия *`.
4. Заполнить исследования; убедиться, что таблица и итог меняются до сохранения.
5. Выбрать разрешённого специалиста, создать карточку и проверить audit actor отдельно.
6. Убедиться, что создан ровно один новый отбор.
7. Повторить при сетевой неопределённости — дублей карточки/пробы нет.
8. Открыть сохранённую карточку, журнал и заключение: специалист, цена и числа совпадают.
9. Проверить WAITING и позднее завершение.
10. Проверить узкий экран 390 px и клавиатуру.

Живые юридически значимые операции ВетИС для этой приёмки не нужны. Не гасить реальный эВСД ради проверки формы.

## 21. Критерии приёмки

Задача принята, когда одновременно:

- участники на сверке и ВСЭ имеют одинаковые названия и значения;
- открытие ВСЭ не делает повторный SOAP lookup;
- тип продукции показан по-русски;
- вес/количество форматируются без лишних нулей и потери точности;
- количество мест берётся из подтверждённой сверки, UUID не виден;
- служебная фраза о внешнем результате удалена;
- трихинеллоскопия закреплена для четырёх GUID;
- add-buttons болезней совпадают с визуальным эталоном;
- повторное использование пробы недоступно и сервером, и интерфейсом;
- итоговый блок соответствует макету и использует один sample date;
- специалист выбирается только из разрешённого server-side списка, а audit actor сохраняется отдельно;
- стоимость пересчитывается до сохранения одной серверной формулой;
- preview ничего не сохраняет;
- финальная сумма совпадает с подтверждённым preview либо пользователь видит conflict;
- связанные страницы и документы показывают согласованные данные;
- документация обновлена и больше не предписывает REUSE/`специалист = создатель`;
- тесты, Storybook build, production build и браузерная проверка завершены без новых ошибок.

## 22. Git, объединение и контейнеры

1. Создать отдельную ветку с префиксом `codex/`, например `codex/examination-create-fixes`.
2. Добавить настоящее ТЗ, изменения документации, миграции, код и тесты в эту ветку.
3. Разделить коммиты по смыслу: snapshot/read model; sample/specialist contracts; pricing preview; frontend/UI; docs/tests.
4. Не переписывать опубликованную историю `main` и не удалять чужие изменения.
5. Перед объединением обновить ветку от актуального `main` и выполнить полный релевантный regression.
6. Объединить feature-ветку с `main` только после успешной приёмки.
7. Пересобрать и обновить затронутые backend/frontend/worker контейнеры штатным compose-профилем проекта, применить миграции один раз под migration lock.
8. После обновления проверить health/readiness, страницу создания ВСЭ, preview стоимости и сохранение на тестовой fixture-партии.
9. В отчёте указать commit/merge commit, миграцию, тесты, обновлённые контейнеры и честные not-run.
