## 1. Проблема

Справочник уже переведён на единый набор норм категории `Мясо и мясопродукты`, однако его рабочий интерфейс всё ещё не соответствует макету `directory-norms-edit`.

Основные расхождения текущей реализации:

- ненастроенные исследования показаны отдельным списком `Не настроено` с кнопками `Настроить`;
- поля нормы появляются только после дополнительного действия;
- заголовок `Нормы исследований` повторяется внутри белой секции вместо заголовка макета `Диапазоны нормы`;
- перед списком присутствует отдельная технически выглядящая строка категории;
- внутри строк отображаются раскрывающиеся `Настройка границ`, источник и вторичные кнопки, которых нет в основном интерфейсе макета;
- качественные нормы отличаются от блока `Проба варки` по размеру кнопок, строк и визуальному ритму;
- кнопка добавления варианта не соответствует квадратной кнопке `＋` из макета;
- удаление варианта оформлено текстовой кнопкой вместо компактной `−`;
- общая плотность, группировка и последовательность элементов отличаются от эталона.

## 2. Цель

Сделать рабочую страницу визуально и композиционно соответствующей `directory-norms-edit.html`, сохранив:

- реальный список VSE-F18–VSE-F29;
- единый scope `Мясо и мясопродукты`;
- существующие API, права, ревизии и проверки;
- честные loading/error/empty/conflict состояния;
- создание первой настройки без UUID и технических полей;
- неизменность ранее сохранённых снимков ВСЭ.

Пользователь должен сразу видеть исследования и поля для норм в той же форме, что в макете, без промежуточной кнопки `Настроить`.

## 9. Порядок и группировка исследований

Источник порядка — канонический server registry VSE-F18–VSE-F29, а не порядок записей БД.

Внутри основной секции использовать две визуальные группы без создания тяжёлых вложенных карточек-разделов:

1. числовые диапазоны;
2. качественные результаты.

Числовые исследования отображаются строками макета. Качественные — блоками по образцу `Проба варки`.

Текстовые исследования, для которых автоматическая норма неприменима, не должны выглядеть как аварийная жёлтая диагностика. Показать спокойную информационную строку в общей геометрии:

- название исследования;
- пояснение `Результат вводится текстом; диапазон нормы не задаётся.`;
- без полей границ и без кнопки `Настроить`.

Не скрывать VSE-F18–VSE-F29 только потому, что часть строк отсутствует в демонстрационном HTML. Макет задаёт вид, а ФТ — состав.

## 10. Числовые нормы

### 10.1. Геометрия строки

Каждая строка повторяет `.norm-row`:

- desktop grid: `minmax(260px, 1fr) 180px 180px`;
- gap `12px`;
- выравнивание по нижней границе полей;
- border, radius около `13px`, белый фон, padding около `16px`.

Первая колонка:

- название — около `15px`, насыщенное;
- короткое предметное пояснение/единица исследования — около `12px`, muted;
- условная применимость трихинеллоскопии показывается спокойным пояснением, без GUID.

Вторая и третья колонки:

- `Норма от`;
- `Норма до`;
- высота поля около `43px`;
- radius около `9px`;
- штатные hover/focus/error/disabled состояния;
- единица отображается внутри справа как в макете и не редактируется.

### 10.2. Ненастроенная норма

Для строки без активной нормы сразу показать пустые поля `Норма от` и `Норма до`.

Запрещено:

- отдельное действие `Настроить`;
- перенос ненастроенных строк в верхний отдельный список;
- скрытие полей до клика;
- подстановка нуля;
- создание записи от одного фокуса без сохранения.

Пустая строка может иметь вторичную подпись `Не настроено`. После ввода значение остаётся локальным draft до общей команды `Сохранить справочник`.

Если оба поля остались пустыми, строка не отправляется как новая настройка и не превращается в нулевой диапазон.

### 10.3. Включённость границ

В макете нет постоянно раскрытых checkbox `нижняя/верхняя граница включена`, поэтому они не должны занимать основную поверхность строки.

Сохранить текущую серверную семантику:

- при создании новой нормы использовать утверждённые значения по умолчанию, предусмотренные текущим контрактом;
- для существующей нормы сохранить её включённость при обычном редактировании границ;
- если пользователю действительно разрешено менять включённость, поместить это в компактное действие `Дополнительные настройки`/overflow без вывода источника, версии или UUID;
- изменение advanced-настройки также участвует в dirty guard и save.

Не менять inclusivity молча при сохранении.

### 10.4. Дозиметрическое исследование

Макет визуально показывает `Мощность дозы от партии` и `Гамма-фон в помещении` отдельными строками. Текущий server contract хранит VSE-F29 как `DOSIMETRY_PAIR` с одной методической записью.

В рамках этой преимущественно дизайнерской задачи запрещено изображать две независимо сохраняемые нормы, если API их не поддерживает.

Допустимые варианты:

1. одна карточка `Дозометрическое исследование` с двумя визуальными подстроками компонентов и честно общей нормой, если это соответствует действующему доменному правилу;
2. отдельное предварительно согласованное изменение server schema, если Product Foundation/ФТ уже требуют разные диапазоны.

Без отдельного решения владельца выбрать вариант 1. Нельзя показывать два разных поля как независимо работающие и сохранять одно значение за обоими.

## 11. Качественные нормы

### 11.1. Общий вид

Каждое качественное исследование оформляется по образцу `Проба варки`:

- единая карточка в общем списке;
- header с названием и коротким пояснением;
- справа квадратная кнопка `＋` размером около `43 × 43px`;
- ниже список вариантов.

Строка варианта:

- grid `minmax(260px, 1fr) 170px 43px`;
- поле/readonly-значение `Вариант результата`;
- select `Оценка` со значениями `Норма` и `Отклонение`;
- компактная квадратная кнопка `−` только там, где вариант разрешено удалять;
- border, radius и padding как у `.boil-row` макета.

Текстовые кнопки `Добавить вариант` и `Удалить` не использовать в основном виде.

### 11.2. Канонические варианты

Варианты, пришедшие из канонического registry:

- не переименовываются произвольно;
- сохраняют возможность менять только оценку, если это предусмотрено текущим API;
- не удаляются, если удаление нарушает registry;
- при необходимости занимают зарезервированную третью колонку без активной кнопки либо имеют disabled `−` с понятной подсказкой.

Пользовательские дополнительные варианты:

- редактируются;
- удаляются кнопкой `−`;
- пустой добавленный вариант не сохраняется;
- после добавления фокус переходит в новое поле.

Хотя бы один вариант должен оставаться отмеченным как `Норма`, если этого требует серверная схема.

### 11.3. Ненастроенный качественный блок

Не показывать кнопку `Настроить`. Сразу вывести канонические варианты со select оценки.

До первого изменения запись в БД не создаётся. После изменения/ввода блок становится dirty и сохраняется общей кнопкой.

Если варианты отсутствуют в read model, показать честное состояние конфигурации, а не пустую работающую карточку.

## 12. Вторичные действия и метаданные

Основная поверхность не должна содержать:

- `Источник: Ручная настройка…`;
- `Методика и версия`;
- UUID/GUID;
- `Настройка границ` в каждой строке;
- крупные кнопки `Удалить норму`;
- диагностические тексты для разработчика.

При этом предусмотренное FT-CAL-08 удаление действующей нормы сохраняется. Разместить его как вторичное действие:

- в доступном overflow-меню строки/блока;
- либо в компактном раскрытии `Дополнительные действия`;
- с существующим подтверждающим Dialog и предупреждением о последствиях.

Кнопка удаления не должна конкурировать с основными полями или менять ширину колонок.

Технические метаданные остаются в backend/history и не удаляются из модели.

## 13. Панель действий

Повторить `.actions` макета:

- sticky, bottom около `18px`;
- действия выровнены вправо;
- padding около `15px 18px`;
- полупрозрачный белый фон с blur;
- border, radius около `15px`, лёгкая тень;
- `Отменить` — secondary;
- `Сохранить справочник` — primary.

Правила:

- save disabled, пока нет изменений;
- во время запроса — `Сохранение…`, повторный submit недоступен;
- `Отменить`, Back, смена лаборатории и уход со страницы при dirty form открывают общий app-owned dialog;
- после успешного сохранения dirty state очищается;
- кнопки не перекрывают последние поля;
- на mobile панель остаётся читаемой; при недостатке ширины кнопки могут занять по строке/полной ширине.

## 14. Сохранение и ошибки

Существующую серверную логику не ослаблять:

- create использует Idempotency-Key;
- update/delete используют If-Match;
- 409 не теряет ввод;
- partial save честно сообщает сохранённые и неуспешные строки;
- чужая лаборатория отклоняется сервером;
- пустое значение не равно нулю.

Визуальные требования:

- ошибка конкретной нормы располагается возле её строки/блока;
- summary partial save располагается над основной секцией и не сдвигает sticky-actions поверх полей;
- success отображается компактным status/toast только после подтверждённого ответа;
- 409 показывает серверное и введённое значения в компактном блоке внутри соответствующей строки;
- после ошибки фокус переходит к первой проблеме;
- введённые значения остаются.

## 15. Состояния страницы

### 15.1. Loading

Сохранять геометрию заголовка и основной секции. Внутри секции показать skeleton строк, близкий к реальному размеру, а не отдельную маленькую надпись посреди пустой страницы.

### 15.2. Ошибка сети

Показать ошибку внутри основной рабочей области с кнопкой `Повторить`. Заголовок, контекст и безопасная навигация остаются.

### 15.3. Нет доступа

Понятный русский текст без технических кодов. Прямой запрос к API всё равно защищён server-side.

### 15.4. Read-only

Для роли только с `catalog:read`:

- та же композиция и значения;
- controls имеют честный readonly/disabled вид;
- save отсутствует либо недоступен с пояснением;
- не показывать кнопки добавления/удаления;
- страница не выглядит сломанной.

### 15.5. Пустой справочник

Показывается полный registry с пустыми полями/вариантами. Это рабочее состояние настройки, а не заглушка `Добавьте первую запись`.

### Desktop

- от `901px`: три колонки числовой строки;
- качественная строка: значение, оценка, действие.

### Tablet

- до `900px`: информация исследования занимает всю первую строку, два поля границ идут ниже в две колонки;
- качественная строка сохраняет две рабочие колонки и кнопку.

### Mobile

- до `800px`: все поля в одну колонку;
- качественная строка в одну колонку;
- кнопки `＋`/`−` могут занять доступную ширину как в макете;
- заголовок секции перестраивается без наложений;
- sticky-actions не перекрывает контент;
- отсутствует горизонтальная прокрутка страницы на `390px`.

## 17. Переиспользование компонентов

Предпочтительно доработать существующие:

- `CatalogEditorPage`;
- `CatalogSectionHeader`;
- `NormRow`;
- `QualitativeBlock`;
- `SaveSummary`.

Не создавать отдельную копию страницы только для визуального сходства. Если общий компонент используется тарифами и платными услугами, изменения должны быть variant/scoped и не ломать их дизайн.

Storybook импортирует те же компоненты, что рабочая страница.

## 18. Storybook

Расширить истории страницы/компонентов:

- заполненные числовые нормы;
- полностью ненастроенный справочник с сразу видимыми полями;
- качественный блок с registry-вариантами;
- добавленный пользовательский вариант;
- read-only;
- loading skeleton;
- network error;
- field validation error;
- partial save;
- 409 conflict;
- длинные названия;
- tablet;
- ширина 390px.

Добавить отдельную визуальную историю `Соответствие directory-norms-edit`, чтобы сравнение не требовало демонстрационных production-данных.

## 19. Тесты frontend

Обновить/добавить проверки:

1. На странице один `h1` `Нормы исследований` и одна секция `Диапазоны нормы`.
2. Пояснения совпадают с настоящим ТЗ.
3. Все VSE-F18–F29 присутствуют в порядке registry.
4. Ненастроенная числовая норма сразу имеет поля `Норма от`/`Норма до`.
5. Кнопки `Настроить` отсутствуют.
6. Пустые поля не создают запись при сохранении других строк.
7. Первое введённое значение создаёт правильную норму.
8. Числовые строки имеют единицы из read model, без UUID.
9. Качественный блок использует `＋`, `−`, `Вариант результата`, `Оценка`.
10. Registry-вариант нельзя удалить, пользовательский можно.
11. Технические metadata не видны на основной поверхности.
12. Удаление нормы остаётся доступно вторичным действием и требует Dialog.
13. Save disabled без dirty state.
14. 409/partial save сохраняют ввод.
15. HEAD не видит переключатель лаборатории.
16. ADMIN/ANALYST видят только разрешённые лаборатории.
17. Read-only не имеет mutation controls.
18. На 390px нет горизонтального overflow.

## 20. Визуальная приёмка

Сделать браузерные снимки рабочего экрана и эталона при одинаковом viewport:

- `1440 × 1000`;
- `1024 × 900`;
- `768 × 900`;
- `390 × 844`.

Сравнить минимум:

- положение и размеры заголовка;
- ширину и padding секции;
- иконку и заголовок `Диапазоны нормы`;
- высоту, сетку, border и radius строк;
- положение labels и единиц;
- качественный блок;
- кнопки `＋`/`−`;
- sticky-actions;
- отсутствие горизонтального overflow.

Расхождения допускаются только для:

- реальных данных вместо демонстрационных;
- полного VSE-F18–F29 вместо сокращённого набора макета;
- штатной SPA-шапки;
- обязательных states/errors/permissions, которых нет в статическом HTML.

Фраза `примерно похоже` не является приёмкой. Существенные расхождения геометрии должны быть устранены либо перечислены с обоснованием.

## 21. Проверки

Обязательный минимум:

- адресные `MethodsEditorPage` tests;
- все frontend catalog tests;
- production frontend build;
- `npm.cmd run build-storybook`;
- релевантный `npm.cmd run test:ui`, если затронуты общие UI-компоненты;
- e2e сохранения первой и существующей нормы;
- браузерная проверка четырёх viewport;
- backend catalog-pricing regression, если изменён API или payload.

Все not-run честно указать в итоговом отчёте.

## 22. Критерии приёмки

Задача завершена, когда:

- страница визуально соответствует `directory-norms-edit`;
- заголовок, секция, строки, качественные блоки и действия имеют геометрию макета;
- полный registry виден сразу;
- ненастроенные нормы редактируются без `Настроить`;
- технические поля, UUID, источники и крупные delete-кнопки не загромождают страницу;
- реальные нормы сохраняются через действующий API;
- пустые значения не превращаются в нули;
- ролевой контекст и безопасность не изменены;
- полный VSE-F18–F29 сохранён;
- демонстрационные числа не попали в БД;
- 390px не имеет горизонтальной прокрутки;
- tests, Storybook build и визуальная приёмка выполнены.

## 23. Git, объединение и контейнеры

1. Создать отдельную ветку с префиксом `codex/`, например `codex/methods-catalog-design`.
2. Добавить настоящее ТЗ, код, styles, stories и тесты в одну feature-ветку.
3. Не коммитить несвязанные пользовательские изменения.
4. Перед объединением обновить ветку от актуального `main` и выполнить проверки.
5. Объединить feature-ветку с `main` после успешной приёмки без переписывания опубликованной истории.
6. Отправить актуальный `main` в настроенный remote либо создать PR, если ветка защищена.
7. Пересобрать затронутый frontend-контейнер; backend — только если реально изменён контракт.
8. Не удалять volumes и не выполнять destructive reseed.
9. После обновления открыть `/catalogs?tab=methods`, проверить загрузку, ввод, сохранение, refresh и узкий экран.
10. В итоговом отчёте указать commit/merge commit, проверки, контейнеры и not-run.
