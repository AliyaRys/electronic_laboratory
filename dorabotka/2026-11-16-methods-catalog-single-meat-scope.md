# ТЗ: единый справочник «Нормы исследований» для категории «Мясо и мясопродукты»

Дата: 16.11.2026  
Статус: к реализации  
Исполнитель: ИИ-агент  
Тип задачи: изменение бизнес-логики справочника, backend/API/БД/frontend/документация

## 1. Основание и решение владельца продукта

Рабочая страница:

`/catalogs?tab=methods`

Владелец продукта уточнил область действия справочника:

> В MVP нормы исследований задаются один раз для категории продукции «Мясо и мясопродукты», а не отдельно для свинины, конины, говядины, субпродуктов, жиров, конкретного `subProduct` или иного вида/состояния продукции Меркурия.

Для каждой лаборатории должен существовать один набор норм категории «Мясо и мясопродукты».

Это решение заменяет реализованное ранее правило, при котором `MethodRule` привязан к сочетанию:

`laboratory_id + product_species_id + product_state_id + indicator_id`.

Также оно заменяет противоречащие ему части ТЗ от 13.11.2026:

`dorabotka/2026-11-13-methods-catalog-empty-and-create.md`.

Из прежнего ТЗ сохраняются требования к каноническому перечню исследований, типизированным значениям, сохранению снимков, ролям, конфликтам редакций и запрету выдумывать клинические нормы. Выбор конкретного вида/состояния продукции и зависимость от GUID больше не применяются к справочнику норм.

## 2. Подтверждённая причина текущего поведения

Текущий код построен вокруг слишком узкой области действия нормы:

- таблица `method_rules` хранит обязательные `product_species_id` и `product_state_id`;
- уникальность активной нормы включает оба идентификатора;
- `GET /api/v1/catalogs/methods/context` сначала получает виды мяса из `mercury_product_guid_lvl_2`;
- состояния продукции формируются из `subProduct` ранее загруженных партий конкретной лаборатории;
- страница требует выбрать вид и состояние продукции;
- create/update отправляют технические GUID;
- расчёт ВСЭ ищет норму по точному виду и состоянию конкретной партии.

В результате один предметный справочник искусственно разделён на множество наборов. Пользователь не может просто открыть справочник и заполнить нормы: он зависит от наличия партий, справочника Меркурия, конкретных GUID и дополнительной настройки области.

## 3. Цель

После доработки пользователь с уже существующим правом редактирования справочников своей лаборатории должен:

1. открыть вкладку `Нормы исследований`;
2. сразу увидеть один полный перечень исследований для категории `Мясо и мясопродукты`;
3. ввести или изменить только предметные значения норм;
4. сохранить справочник;
5. применять этот набор норм ко всем мясным партиям лаборатории независимо от конкретного вида/подвида продукции.

Пользователь не должен:

- выбирать свинину, конину, говядину, субпродукты или жиры;
- выбирать состояние продукции;
- ждать появления подходящей входящей партии;
- вводить или видеть GUID/UUID;
- вводить тип результата, единицу, версию, источник или служебный scope;
- получать указание обратиться к администратору для назначения `product_species_id`/`product_state_id`.

## 4. Область действия нормы

### 4.1. Новый ключ применимости

Активная норма определяется ключом:

`laboratory_id + product_area_code + indicator_id`.

Для текущего MVP:

- `product_area_code = meat`;
- человекочитаемое название — `Мясо и мясопродукты`;
- внешний фильтр входящих ВСД `productType = 1` относится к этой же категории.

В пользовательском интерфейсе код `meat` и значение `1` не являются полями ввода. Пользователь видит только название категории.

### 4.2. Что больше не входит в ключ нормы

Из ключа применимости и пользовательского контракта исключить:

- `product_species_id`;
- `product_state_id`;
- GUID второго уровня Меркурия;
- GUID/UUID `product`, `subProduct`, `productItem`;
- наличие ранее импортированной партии определённого вида.

### 4.3. Трихинеллоскопия

Точные GUID четырёх групп продукции продолжают использоваться только для определения, обязательно ли выполнять трихинеллоскопию в конкретной карточке ВСЭ:

- свинина;
- конина;
- субпродукты и жиры свиные;
- субпродукты и жиры конские.

Это правило не создаёт четыре разных нормы. В справочнике существует одна строка `Трихинеллоскопия` для категории `Мясо и мясопродукты`. Если для партии исследование обязательно или было выполнено дополнительно, результат оценивается по этой единой норме.

## 5. Канонический перечень исследований

Страница всегда показывает перечень из единого реестра ФТ:

| Код | Исследование | Канонический тип результата | Обязательность выполнения |
|---|---|---|---|
| VSE-F18 | Органолептическое исследование | `ENUM` | обязательно для всех мясных партий |
| VSE-F19 | Идентификация продукции | `ENUM` | обязательно для всех мясных партий |
| VSE-F20 | Температура в толще мышц | `DECIMAL`, °C | обязательно для всех мясных партий |
| VSE-F21 | Трихинеллоскопия | `BOOLEAN_MATCH` | условно обязательно для четырёх утверждённых GUID |
| VSE-F22 | Люминесцентный анализ | `ENUM` | дополнительное |
| VSE-F23 | Бактериоскопия | `TEXT` | дополнительное |
| VSE-F24 | Микроскопия | `INTEGER_NONNEGATIVE` | дополнительное |
| VSE-F25 | pH | `DECIMAL` | дополнительное |
| VSE-F26 | Проба варки | `ENUM` | дополнительное |
| VSE-F27 | Реакция с сернокислой медью | `ENUM` | дополнительное |
| VSE-F28 | Пероксидаза | `ENUM` | дополнительное |
| VSE-F29 | Дозометрическое исследование | `DOSIMETRY_PAIR`, мкЗв/ч | дополнительное |

VSE-F30 `Инвазионные болезни` и VSE-F31 `Незаразные болезни` остаются полями/списками находок карточки ВСЭ и не становятся строками справочника норм.

Перечень, названия, схемы и единицы нельзя дублировать отдельными несогласованными массивами. Backend-реестр `mandatory.CATALOG_INDICATORS` и frontend-реестр исследований должны иметь один проверяемый контракт.

## 6. Что вводит пользователь

### 6.1. Общий принцип

Пользователь редактирует только норму конкретного исследования.

Система сама определяет и сохраняет:

- лабораторию из текущего контекста пользователя/выбранной доступной лаборатории;
- область `Мясо и мясопродукты`;
- идентификатор исследования;
- схему результата;
- единицу результата;
- версию и ревизию;
- системное происхождение ручной настройки.

Технические поля не показываются и не запрашиваются.

### 6.2. Числовые исследования

Для числовой нормы показывать только предметные поля:

- `Норма от`;
- `Норма до`;
- включение нижней границы;
- включение верхней границы.

Единица (`°C`, `мкЗв/ч` и т. п.) показывается рядом как readonly-суффикс из канонического реестра. Пользователь не вводит её вручную.

Пустая нижняя или верхняя граница означает открытую границу. Обе границы одновременно пустыми сохранить нельзя. Нижняя граница не может быть больше верхней.

### 6.3. Качественные исследования

Для показателей с утверждёнными вариантами результата показать варианты человекочитаемым списком и позволить отметить, какие считаются нормой.

Нельзя требовать вводить варианты одной строкой через запятую, если они уже заданы каноническим реестром. Нельзя позволять пользователю менять тип результата исследования.

### 6.4. Свободный текст и сложные схемы

Не придумывать клиническое правило, которого нет в документации.

- Для `TEXT` сохранить действующее предметное правило: значение фиксируется, но автоматическая оценка нормы не фабрикуется. В интерфейсе показать понятное readonly-пояснение вместо неработающего числового диапазона или требования ввести GUID.
- Для `DOSIMETRY_PAIR` использовать поддерживаемую сервером типизированную схему. Если текущая модель применяет один диапазон к обоим показаниям, не менять медицинский смысл без отдельного решения владельца; интерфейс должен честно подписать, к чему применяется введённый диапазон.

Наличие строки исследования в общем перечне не означает право агента выдумать нормативное значение. До ввода методистом/заведующим строка имеет состояние `Не настроено`.

## 7. Роли и отсутствие «дополнительных разрешений»

Под отсутствием дополнительных разрешений понимается:

- не требуется отдельное назначение вида/состояния продукции;
- не требуется административное сопоставление GUID;
- не требуется наличие данных Меркурия;
- не требуется новая роль или новый permission сверх уже имеющегося права редактировать справочники лаборатории.

Действующая ролевая безопасность сохраняется:

- `Заведующий` редактирует нормы своей назначенной лаборатории и не выбирает лабораторию, если у него она одна;
- администратор/аналитик работает только в разрешённой области и при необходимости выбирает доступную лабораторию;
- ветеринарный врач имеет только чтение, если это задано действующей матрицей прав;
- чужая лаборатория недоступна прямым запросом.

Не добавлять новый permission вида `methods:configure-scope`. Если пользователь уже имеет действующее `catalog:write` для лаборатории, он сразу может заполнять нормы.

## 8. Требования к backend и базе данных

### 8.1. Модель данных

Изменить `MethodRule`, чтобы актуальная область нормы хранилась через стабильный код категории продукции, а не через конкретные GUID Меркурия.

Предпочтительная модель:

- добавить обязательное поле `product_area_code` с текущим значением `meat`;
- убрать `product_species_id` и `product_state_id` из активного ключа и новых write-контрактов;
- новая уникальность активной нормы:
  `laboratory_id + product_area_code + indicator_id`, где `active = true`;
- сохранить версионность, `result_schema`, `unit_id`, `rule`, `source`, `effective_from`, `rev` и историю.

Допускается оставить старые колонки nullable только на переходный период, но новый код не должен читать или записывать их как область применимости нормы.

### 8.2. Миграция существующих данных

Миграция должна быть недеструктивной и повторяемой.

Для каждой группы старых активных строк одной лаборатории и одного `indicator_id`:

1. если правила полностью эквивалентны по схеме, единице и значению нормы — создать/оставить одну активную норму области `meat`, остальные старые строки деактивировать, сохранив историю;
2. если нормы различаются — не выбирать значение по первому GUID, имени вида, максимальной версии или случайной строке;
3. конфликтующие старые значения сохранить для аудита, а новую единую норму оставить `Не настроено` либо записать отдельный диагностический конфликт, который требует явного ввода пользователем;
4. сохранённые snapshots ранее созданных ВСЭ не изменять и не пересчитывать;
5. миграция не должна удалять партии, карточки ВСЭ, тарифы или справочники Меркурия.

В отчёте реализации указать количество:

- автоматически объединённых эквивалентных норм;
- конфликтующих групп;
- норм, которые пользователь должен заполнить заново.

### 8.3. Контекст справочника

`GET /api/v1/catalogs/methods/context` больше не должен:

- читать `MercuryProductGuidLvl2` для построения вариантов справочника норм;
- искать наблюдаемые `subProduct` в партиях;
- принимать `species`/`state`;
- возвращать ошибку из-за отсутствия видов или состояний продукции.

Контекст должен определяться по лаборатории и `area=meat` и возвращать:

- лабораторию;
- область `Мясо и мясопродукты`;
- полный реестр VSE-F18–VSE-F29;
- по одной активной норме каждого показателя или состояние `Не настроено`;
- сведения, необходимые для сохранения и разрешения конфликтов редакций.

### 8.4. Write API

Новый create/update-контракт не должен требовать от frontend:

- `product_species_id`;
- `product_state_id`;
- UUID показателя, введённый пользователем;
- `result_schema`;
- `unit_id`;
- `version`;
- `source`.

Frontend может передавать стабильный код строки (`VSE-F18`–`VSE-F29`) либо внутренний ID из context-ответа, но пользователь не видит и не вводит его. Backend обязан сверить код с каноническим реестром и сам дополнить технические поля.

Сохранить:

- idempotency create;
- `If-Match` для update/delete;
- `409 REVISION_CONFLICT` с возможностью выбрать серверное или своё значение;
- серверную типовую валидацию;
- неизменяемость старых снимков.

### 8.5. Применение нормы в ВСЭ

При оценке результата мясной партии сервер должен:

1. убедиться, что партия относится к поддерживаемой категории `productType = 1`;
2. получить норму по `laboratory_id + meat + indicator_id`;
3. не добавлять в запрос `product_species_id` и `product_state_id`;
4. применить одну и ту же норму к говядине, свинине, конине, субпродуктам, жирам и другим мясным позициям MVP;
5. отдельно определить по точным GUID, обязательна ли для партии трихинеллоскопия;
6. сохранить фактически применённую норму в pricing/examination snapshot как прежде.

### 8.6. Readiness

Готовность расчёта проверяется по единому мясному набору:

- обязательные F18–F20 требуют активной нормы области `meat`;
- F21 требуется для завершения конкретной партии только при попадании продукции в четыре утверждённые группы;
- дополнительное исследование требует норму, если оно выполнено и его схема предусматривает автоматическую оценку;
- отсутствие нормы не должно ошибочно диагностироваться отдельно для каждого вида мяса.

Тарифы не входят в эту задачу и не должны автоматически менять область действия вместе с нормами.

## 9. Требования к frontend

### 9.1. Убрать лишний контекст

Со страницы удалить:

- selector вида мяса;
- selector состояния/подвида продукции;
- тексты `Выберите вид продукции, чтобы открыть нормы`;
- тексты `Выберите состояние продукции, чтобы открыть нормы`;
- ошибки о ненастроенном scope;
- параметры URL `species` и `state`;
- любое отображение GUID/UUID.

### 9.2. Состояние при открытии

После открытия вкладки пользователь сразу видит:

- заголовок `Нормы исследований`;
- readonly-контекст `Мясо и мясопродукты`;
- полный список VSE-F18–VSE-F29;
- текущие нормы либо `Не настроено`;
- доступные поля предметной настройки;
- кнопку `Сохранить справочник`.

Если у заведующего одна лаборатория, переключатель лаборатории отсутствует. Для ролей с несколькими разрешёнными лабораториями действующий переключатель сохраняется.

### 9.3. Создание первой настройки

Пустой справочник не должен требовать отдельной технической формы `Добавить норму` с выбором GUID.

Предпочтительный сценарий:

- все строки реестра уже присутствуют;
- в строке `Не настроено` пользователь сразу вводит значение или нажимает понятную кнопку `Настроить`;
- система знает исследование, тип и единицу из выбранной строки;
- после сохранения строка становится настроенной без полной перезагрузки страницы.

### 9.4. Не показывать технические поля

На странице и в редакторе отсутствуют:

- `Показатель (UUID)`;
- `Состояние продукции (UUID)`;
- `Тип результата`;
- `Единица измерения нормы` как свободный ввод;
- `Тип нормы` как технический selector;
- `Версия`;
- `Источник методики`, редакция и ссылка как обязательные поля пользователя;
- коды и GUID в сообщениях ошибок.

Источник новой ручной настройки система сохраняет автоматически, например:

`Ручная настройка справочника норм`.

Это служебное значение не является пользовательским полем.

- `product_species_id + product_state_id` являются обязательным ключом MethodRule.

## 11. Тесты backend

Добавить/изменить тесты:

1. Пустая БД и отсутствие записей `mercury_product_guid_lvl_2` не мешают открыть мясной справочник.
2. Отсутствие входящих партий и `subProduct` не мешает открыть и заполнить справочник.
3. Context для `area=meat` возвращает VSE-F18–VSE-F29 без `species/state`.
4. Один indicator имеет не более одной активной нормы на лабораторию и `meat`.
5. Create/update не требуют GUID продукции, состояния, schema, unit, version или source от клиента.
6. Неизвестный код исследования отклоняется без создания произвольного показателя.
7. Одна настроенная норма применяется к двум партиям разных видов/состояний мяса.
8. Трихинеллоскопия использует одну норму, но остаётся обязательной только для четырёх утверждённых групп.
9. Говядина не получает обязательную трихинеллоскопию только из-за общей области норм.
10. Readiness не создаёт отдельные missing-ошибки по каждому виду мяса.
11. Миграция объединяет одинаковые старые нормы и не выбирает случайно одну из различающихся.
12. Старый pricing snapshot остаётся байт-в-байт/семантически неизменным после миграции и редактирования новой нормы.
13. `If-Match`, idempotency и права лаборатории продолжают работать.
14. Прямой запрос к чужой лаборатории отклоняется.

## 12. Тесты frontend и e2e

1. При открытии `/catalogs?tab=methods` сразу видны `Мясо и мясопродукты` и полный перечень исследований.
2. На странице нет selector видов мяса и состояний продукции.
3. На странице и в формах нет GUID/UUID и перечисленных технических полей.
4. Пустой справочник позволяет настроить первую норму.
5. Числовая норма сохраняется и остаётся после обновления страницы.
6. Качественная норма сохраняется через человекочитаемые варианты.
7. Пустое значение не превращается в ноль.
8. Нижняя граница больше верхней блокируется рядом с полем.
9. Частичный успех массового сохранения показывает, какие строки сохранены, а какие нет, и не теряет ввод.
10. `409` сохраняет черновое значение и предлагает взять серверное или оставить своё.
11. У заведующего с одной лабораторией нет переключателя лаборатории.
12. Для роли с несколькими лабораториями переключатель работает и загружает независимый набор норм.
13. Проверены загрузка, ошибка, повтор, read-only, длинные названия, 1440/1024/768/390 px и клавиатура.

## 13. Запреты

Агенту запрещено:

- подставлять UUID лаборатории вместо вида или состояния;
- использовать первый найденный ВСД для настройки справочника;
- создавать по одной копии нормы на каждый GUID;
- автоматически выбирать одну из различающихся старых клинических норм;
- брать числовые нормы из HTML-макетов, тестов или интернета;
- считать отсутствие нормы нулевой нормой;
- ослаблять ролевой доступ к чужим лабораториям;
- менять тарифы в рамках этой задачи;
- пересчитывать ранее сохранённые ВСЭ;
- удалять PostgreSQL volume или выполнять destructive reseed.

## 14. Приёмочные критерии

Задача завершена, если:

1. Справочник больше не разделён по видам мяса и мясопродуктов.
2. Для каждой лаборатории существует один набор норм категории `Мясо и мясопродукты`.
3. Справочник открывается без данных Меркурия, партий и административного назначения GUID.
4. Пользователь вводит только значения норм.
5. Все VSE-F18–VSE-F29 видны сразу; F30/F31 не добавлены как нормы.
6. Технические идентификаторы и служебные поля скрыты от пользователя и не требуются клиентскому write-запросу.
7. Норма применяется ко всем мясным партиям лаборатории.
8. Условная обязательность трихинеллоскопии по четырём группам сохранена.
9. Старые snapshots не изменены.
10. Конфликтующие старые нормы не объединены произвольно.
11. Документация, OpenAPI, backend и frontend описывают один и тот же новый scope.
12. Backend/frontend/e2e/Storybook проверки проходят.
