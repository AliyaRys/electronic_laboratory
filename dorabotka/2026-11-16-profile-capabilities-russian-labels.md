# ТЗ: русские названия прав доступа в профиле пользователя

Дата: 16.11.2026  
Статус: к реализации  
Исполнитель: ИИ-агент  
Тип задачи: frontend, представление прав доступа без изменения авторизации

## 1. Проблема

На странице `/profile` в блоке `Права доступа` напрямую выводятся технические capability-коды из `GET /api/v1/me`:

```text
arrivals:count
catalog:update
examination:create-complete
receipt:submit
report:5vet-preview
...
```

Эти строки являются внутренними идентификаторами Casbin/API, а не пользовательскими названиями. Они написаны на английском языке, содержат двоеточия и технические сокращения, поэтому пользователю сложно понять фактические возможности своей роли.

После перевода русские названия станут длиннее. Они не должны ломать ширину карточки профиля или растягивать страницу.

## 2. Цель

В профиле пользователя показывать понятные русские названия всех фактически полученных прав, сохранив технические capability-коды без изменений в backend, API и механизме авторизации.

Если русское название не помещается в метку:

- видимая строка сокращается многоточием;
- полное русское название доступно при наведении курсора;
- полный текст остаётся доступен assistive technology;
- страница не получает горизонтальную прокрутку.

## 3. Границы задачи

### 3.1. Входит в задачу

- перевод capability-кодов, возвращаемых `GET /me`;
- единый frontend-реестр `код → русское название`;
- использование реестра в SPA-профиле;
- корректное сокращение длинных названий;
- подсказка с полным названием;
- тесты, Storybook и браузерная проверка;
- при необходимости — использование того же реестра в других React-экранах, где показываются эти же capability-коды пользователю.

### 3.2. Не входит в задачу

- изменение `PERMISSION_MATRIX`;
- изменение ролей VET/HEAD/ADMIN/ANALYST;
- выдача или отзыв прав;
- изменение Casbin policy;
- изменение формата `UserView.capabilities: string[]`;
- перевод технических кодов в базе данных;
- изменение серверных проверок scope/state;
- показ пользователю запрещённых прав.

## 4. Источники истины

Технические коды определены в:

- `backend/src/modules/identity/policies.py`;
- `docs/TZ_development/plans/permissions.md`.

Профиль реализован в:

- `frontend/src/pages/ProfilePage.tsx`;
- `frontend/src/features/identity/identity.css`;
- `frontend/src/pages/ProfilePage.test.tsx`.

API продолжает возвращать технические коды. Перевод является presentation layer и не должен участвовать в принятии решений о доступе.

## 5. Единый реестр русских названий

Создать один типизированный frontend-реестр, например:

`frontend/src/features/identity/capabilityLabels.ts`.

Реестр должен экспортировать:

- неизменяемое отображение `code → label`;
- функцию получения пользовательского названия;
- безопасный fallback для неизвестного кода;
- при необходимости — данные для стабильной пользовательской сортировки.

Запрещено:

- писать цепочку `replace(':', ' ')`;
- переводить части кода автоматически;
- дублировать mapping внутри `ProfilePage` и stories;
- изменять capability-код перед проверкой доступа;
- получать русский label из демонстрационных `components/admin/AdminData.js`, где используется старый сокращённый набор прав.

## 7. Неизвестный capability-код

Новый backend-код не должен снова появиться в интерфейсе как необработанная английская строка.

Для неизвестного кода:

- видимый текст — `Неизвестное право доступа`;
- полная подсказка — `Неизвестное право доступа: <technical-code>`;
- технический код допустимо хранить в `data-capability-code` для диагностики;
- код не должен интерпретироваться как разрешение и не должен менять доступ;
- в development/test необходимо выдавать диагностическое предупреждение либо падение contract-теста, чтобы перевод был добавлен осознанно.

Не скрывать неизвестное право полностью: пользователь должен видеть, что сервер вернул дополнительную возможность, а поддержка должна иметь способ определить код.

## 8. Отображение меток

### 8.1. Текст

Внутри `.vse-profile-right-tag` рендерится полное русское название. Нельзя заранее обрезать строку в JavaScript и добавлять многоточие вручную.

CSS выполняет визуальное сокращение:

- разумная максимальная ширина метки — ориентир `220–260px` на широком экране;
- `min-width: 0`;
- `white-space: nowrap`;
- `overflow: hidden`;
- `text-overflow: ellipsis`;
- метка не шире доступной ширины карточки.

Конкретная максимальная ширина выбирается по браузерной проверке макета профиля. Нельзя задавать ширину, из-за которой короткие названия получают лишнее пустое место.

### 8.2. Подсказка

Каждая метка получает полное русское название в подсказке при наведении.

Минимально допустимый вариант:

- атрибут `title` содержит полное русское название;
- реальный текстовый узел также содержит полное название, а CSS только визуально его сокращает;
- доступное имя содержит полное название.

Предпочтительный вариант при наличии/создании общего tooltip-компонента:

- подсказка открывается при hover и focus;
- `role="tooltip"`;
- связь через `aria-describedby`;
- Escape закрывает подсказку;
- подсказка не выходит за viewport;
- та же реализация используется в Storybook и приложении.

Не создавать tooltip только псевдоэлементом без доступного полного текста.

### 8.3. Перенос контейнера

Контейнер прав продолжает переносить метки на новые строки. Не превращать список в одну горизонтально прокручиваемую строку.

На ширине `390px`:

- метка не выходит за границы карточки;
- блок профиля не создаёт горизонтальную прокрутку;
- длинное русское название сокращается многоточием;
- полное значение остаётся в подсказке и доступном имени.

## 9. Порядок и группировка

На первом этапе сохранить компактный набор тегов без добавления раскрывающихся групп, если это не требуется для устранения переполнения.

Порядок должен быть стабильным. Допустимо:

- сохранить порядок, полученный от API;
- либо закрепить предметный порядок разделов из настоящего ТЗ.

Если вводится пользовательская сортировка, она выполняется по заранее заданному порядку разделов, а не по русскому алфавиту и не влияет на сами capability-коды.

Не объединять несколько отдельных прав в одну метку, если из-за этого пользователь перестанет видеть фактически назначенный набор.

## 10. Backend и API

Backend продолжает возвращать:

```ts
capabilities: string[]
```

Технические коды остаются единственным источником проверок доступа. Русские названия:

- не отправляются обратно на сервер;
- не сохраняются в Casbin;
- не используются в `if`/route guards;
- не заменяют `PERMISSION_MATRIX`;
- не требуют миграции БД.

Backend можно не менять. Если агент предлагает передавать labels с сервера, это отдельное архитектурное изменение и не должно выполняться без необходимости.

## 11. Повторное использование

Если технические capability-коды видны на других React-экранах пользователя, использовать тот же реестр.

Старые HTML-макеты в `components/profile/` уже работают с демонстрационными русскими названиями. Не подключать их сокращённый список как источник истины для SPA и не смешивать старые условные коды (`vse_write`, `directory_edit`) с реальными Casbin actions.

## 12. Тесты

### 12.1. Реестр переводов

1. Каждый action из актуальной `PERMISSION_MATRIX` имеет непустое русское название.
2. Русские названия не равны техническим кодам.
3. В видимых названиях нет необработанных `:` и kebab-case capability-кодов.
4. Неизвестный код возвращает русский fallback и сохраняет исходный код только для диагностики.
5. Дублирующиеся русские названия допускаются только после осознанной проверки; разные действия не должны случайно стать неразличимыми.

### 12.2. ProfilePage

Обновить fixture реальными кодами из `PERMISSION_MATRIX`. Текущий тестовый `examination:create` не является актуальным action и должен быть заменён, например, на `examination:create-complete`.

Проверить:

1. `arrivals:read` отображается как `Просмотр поступления`.
2. `examination:create-complete` отображается как `Создание и завершение ВСЭ`.
3. Технические коды не видны на странице для известных прав.
4. Полное русское название присутствует в DOM/accessible name.
5. Метка имеет подсказку с полным названием.
6. При пустом массиве остаётся `Прав не назначено.`.
7. Неизвестный код отображается русским fallback, а не самим кодом.
8. Перевод никак не меняет маршруты и доступные действия.

### 12.3. Полная роль

Добавить тест/Story с большим набором прав, соответствующим HEAD или ADMIN:

- все метки рендерятся;
- ни одна не теряется;
- список переносится;
- длинные названия сокращаются только визуально;
- карточка профиля сохраняет ширину.

### 12.4. Браузерная проверка

Проверить `/profile` на ширинах:

- `1440px`;
- `1024px`;
- `768px`;
- `390px`.

Для длинной метки проверить вычисленные стили:

- `scrollWidth > clientWidth` при фактическом сокращении;
- видимое многоточие;
- полное значение в tooltip/title;
- отсутствие горизонтальной прокрутки документа.

## 13. Storybook

Обновить или добавить stories:

- ветеринарный врач с базовыми правами;
- заведующий с длинным набором прав;
- администратор с правами управления пользователями;
- без прав;
- неизвестный capability;
- длинные названия;
- узкий экран.

Stories используют тот же registry и тот же компонент метки, что рабочая страница. Не писать отдельные русские строки непосредственно в story.

## 14. Доступность

1. Скринридер читает полное русское название, даже если оно визуально сокращено.
2. Цвет и многоточие не являются единственным способом получить полное значение.
3. Если используется интерактивный tooltip, он доступен с клавиатуры и связан через ARIA.
4. Tooltip не перекрывает соседние права без возможности закрыть его.
5. Технический код не заменяет доступное имя известного права.

## 15. Критерии приёмки

Задача завершена, если:

1. В профиле все известные права отображаются на русском языке.
2. Ни один код текущей `PERMISSION_MATRIX` не показан пользователю в исходном английском виде.
3. Перевод выполнен единым реестром, а не локально в JSX.
4. Длинные названия не ломают карточку и сокращаются многоточием.
5. Полное название доступно при наведении и assistive technology.
6. Неизвестный будущий код получает русский fallback.
7. Авторизация, роли, scope и API не изменены.
8. Профиль проверен на `1440/1024/768/390px` без горизонтальной прокрутки.
9. Unit/component tests, frontend build и Storybook проходят.
10. Рабочая страница проверена в браузере после обновления контейнера.
