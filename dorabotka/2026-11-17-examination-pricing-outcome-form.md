# ТЗ на исправление расчёта стоимости и формы карточки ВСЭ

Дата: 17.11.2026  
Тип задачи: catalog/pricing scope + examination evaluation + examination form UI

## 1. Цель

После заполнения справочников и выбора исследований карточка ВСЭ должна:

1. сразу рассчитывать предварительную стоимость по мере заполнения
   исследований;
2. не выдавать ложную ошибку отсутствующего тарифа при реально настроенной
   стоимости;
3. показывать блок «Итог экспертизы» визуально как
   `electronic-vse-journal.html`, включая стилизованные раскрывающиеся списки;
4. принимать дробные значения во всех **числовых** полях исследований,
   включая микроскопию;
5. сохранять карточку ВСЭ без ошибок при полном корректном заполнении.

## 2. Подтверждённая причина ошибки стоимости

Сообщение:

```text
Не хватает настройки справочника
Для выполненного показателя нет тарифа; обратитесь к ответственному за прейскурант.
```

возникает в backend `catalog_pricing.service._price_vse()` при отсутствии
результата `_tariff_for()`.

Технический код такой ошибки — `CONFIGURATION_MISSING`; он должен сохраняться
для диагностики, но пользователь должен видеть понятное сообщение с названием
конкретного исследования.

На момент расследования в БД цены текущей лаборатории были сохранены примерно
так:

```text
laboratory_id      = 2812e437-facc-432f-9242-5162c9d9f49f
product_species_id = 2812e437-facc-432f-9242-5162c9d9f49f
service_code       = <indicator UUID>
```

Это неверный scope: UUID лаборатории не является видом продукции. Pricing при
заполнении ВСЭ ищет тариф по реальному `product_species_id` партии, например
по GUID продукта из `party.classification_snapshot`, поэтому созданная в
каталоге цена не находится.

Дополнительный источник дефекта — frontend `TariffsEditorPage` использует
устаревший контекст `productSpeciesId` и отправляет его как species scope,
тогда как backend/Methods catalog уже переходят на область `meat`.

### Обязательное решение по scope тарифов

До реализации зафиксировать в коде и тестах один из вариантов:

**Вариант A — сохранить текущий DR14-контракт (рекомендуется, если тарифы
зависят от конкретного продукта):**

- нормы — область «Мясо и мясопродукты»;
- тарифы ВСЭ — конкретный вид продукции Меркурия;
- в каталоге пользователь выбирает вид продукции человеческим названием;
- backend хранит внутренний species ID, пользователь GUID не вводит;
- pricing и tariff editor используют одну и ту же выбранную species scope.

**Вариант B — сделать тарифы областью «Мясо и мясопродукты»:**

- добавить `product_area_code` в тарифный контракт/таблицу;
- pricing ищет тариф по `laboratory_id + product_area_code + service_code`;
- выполнить безопасную миграцию старых строк только после явного решения
  владельца, не копируя цены между лабораториями.

Нельзя одновременно сохранять species lookup в pricing и сохранять новые цены
с `product_species_id=лаборатория`. Нельзя подставлять первый найденный GUID.
В отчёте агента указать выбранный вариант и доказать его тестом.

## 3. Требования к каталогу стоимости

- Страница «Стоимость исследований ВСЭ» должна использовать тот же актуальный
  контекст, что и «Нормы исследований».
- Пользователь выбирает «Мясо и мясопродукты»/вид продукции словами; UUID
  остаётся внутренним полем API.
- POST/PUT тарифа должны сохранять ровно тот scope, который использует
  `PricingRequest` для карточки ВСЭ.
- Старые некорректные строки с `product_species_id=лаборатория` не удалять
  молча: показать их как устаревшие/требующие миграции либо обработать отдельной
  безопасной миграцией с отчётом.
- После сохранения тарифа каталог должен возвращать свежий revision и новая
  pricing preview должна видеть цену без перезагрузки всего приложения.
- Не менять сохранённые pricing snapshots старых ВСЭ.

## 4. Расчёт стоимости во время заполнения ВСЭ

### 4.1. Общий поток

```text
изменение результата исследования
→ debounce pricing preview
→ сервер разрешает актуальный tariff/method scope
→ возвращает PricingSnapshot
→ карточка стоимости обновляется
```

Использовать существующий read-only endpoint pricing preview; frontend не должен
вычислять деньги самостоятельно.

### 4.2. Условия корректного preview

Server pricing должен:

- использовать laboratory текущей партии;
- использовать согласованный product area/species scope по выбранному варианту
  раздела 2;
- сопоставлять `service_code` с canonical indicator ID, а не с русским именем;
- использовать принятое количество из подтверждённой партии;
- считать каждое выполненное исследование один раз;
- не считать невыполненное исследование;
- применять `ROUND_HALF_UP` и decimal-строки без float;
- сохранять ярмарочный режим `0.00` без скрытой обычной цены;
- возвращать конкретную диагностику с indicator code и scope при отсутствии
  тарифа;
- не показывать общий «тариф отсутствует», если проблема на самом деле в
  неверном scope.

Если тариф не найден, сообщение должно содержать понятное действие:

```text
Не настроена стоимость исследования «Микроскопия» для выбранного вида продукции.
Откройте справочник «Стоимость исследований» и настройте этот показатель.
```

Сохранённые исследования/введённые значения не очищать из-за ошибки preview.

### 4.3. Norm/evaluation snapshot

Evaluation mode values are `FIXED`, `CONFIGURABLE` and `NONE`; the mode is part
of the read-only evaluation response and is not chosen by the browser.

Норма и цена — разные настройки. Preview должен возвращать и отображать:

- `method_snapshot`/применённую норму;
- `evaluation` (`IN_NORM`, `DEVIATION`, `UNKNOWN`);
- tariff/quantity/amount.

Смена каталога после завершённой ВСЭ не перекрашивает старый snapshot и не
пересчитывает старую цену.

## 5. Числовые поля исследований

Пользователь требует дробные значения во всех числовых полях. Под «числовыми»
понимаются температура, микроскопия, pH, оба значения дозиметрии и иные
будущие числовые исследования; enum/text/boolean остаются своими типами.

### 5.1. Микроскопия

Сейчас `VSE-F24` имеет `INTEGER`/`INTEGER_NONNEGATIVE`, а frontend проверяет
`/^\d+$/`, поэтому `2.5` отклоняется. Изменить канонический тип VSE-F24 на
неотрицательную десятичную величину:

- frontend `ResearchKind` → `DECIMAL`;
- backend `result_schema` → `DECIMAL`;
- форма принимает `2`, `2.5`, `2,5`;
- wire payload использует каноническую строку с точкой (`2.5`);
- отрицательные, NaN, Infinity, экспоненциальная форма и пустое выполненное
  значение отклоняются;
- не использовать `parseFloat`, `toFixed` и binary float для проверки/сохранения;
- единица/точность сохраняются согласно методике и не округляются без правила.

Если изменение `INTEGER_NONNEGATIVE → DECIMAL` требует миграции старых
snapshots, старые значения должны продолжить читаться и не измениться.

### 5.2. Остальные числовые поля

Проверить единообразно:

- температура — decimal;
- pH — decimal в диапазоне 0–14;
- дозиметрия — две decimal величины;
- микроскопия — decimal ≥ 0;
- десятичная запятая нормализуется в точку до API;
- промежуточный ввод (`2,`) не ломает форму до blur/submit.

## 6. Блок «Итог экспертизы»: визуальный контракт

Текущий React-блок перестроить по макету `electronic-vse-journal.html`, не
копируя HTML/inline JavaScript. Использовать общие React-компоненты и styles.

Целевая структура:

```text
┌ Итог экспертизы ─────────────────────────────────────┐
│ Заключение, стоимость и специалист, проводивший ВСЭ. │
│                                                      │
│ Дата отбора проб        [ date ]                     │
│ [ ] Пробы отправлены на спец. лабораторные исслед.   │
│                                                      │
│ Результат ВСЭ *        [ Выберите результат       ▾ ]│
│ Направление *          [ Выберите направление     ▾ ]│
│ Специалист *           [ Выберите специалиста    ▾ ]│
└──────────────────────────────────────────────────────┘
```

Требования:

- белая секция с существующими section tokens, иконкой `check-complete`,
  заголовком и описанием;
- дата и checkbox занимают широкую строку как в макете;
- result/direction/specialist размещаются в grid-колонках макета;
- сохранить текущую бизнес-матрицу FIT/UNFIT, направления, reason и правила
  обязательности;
- ничего не предвыбирать автоматически, кроме уже сохранённых значений;
- disabled/loading/error/focus-visible остаются доступными и читаемыми;
- responsive 1440/1024/768/390 px без горизонтального overflow.

### 6.1. Раскрывающиеся списки

Нативный browser default select заменить на единый стилизованный select,
визуально соответствующий `electronic-vse-journal`/Choices markup:

- одинаковая высота, border, radius, padding, arrow и typography;
- dropdown имеет panel background, border, shadow и активный пункт;
- placeholder disabled и визуально приглушён;
- selected item виден в закрытом trigger;
- keyboard arrows/Home/End/Enter/Escape работают;
- focus-visible заметен;
- dropdown не обрезается section overflow и имеет корректный stacking layer;
- `aria-expanded`, `role=listbox`, option semantics и связанный label;
- один переиспользуемый React-компонент для трёх полей, не три копии.

Допустимо использовать установленный `choices.js` через общий React adapter,
либо сделать эквивалентный существующим компонентам controlled select. Не
оставлять три необработанных `<select>` с системным видом.

## 7. Полный сценарий заполнения и сохранения

Добавить regression flow:

```text
Открыть подтверждённую партию
→ открыть карточку ВСЭ
→ заполнить обязательные и выбранные дополнительные исследования
→ ввести дробную микроскопию, например 2.5
→ увидеть pricing preview без configuration error при корректных scope/tariff
→ увидеть оценку нормы по каждому результату
→ заполнить дату, checkbox, result, direction, specialist, stamp и sample
→ сохранить COMPLETED либо WAITING по существующей матрице
→ повторно открыть карточку
→ значения, pricing snapshot и evaluation snapshot восстановлены
```

При отсутствии настройки обязательно показывать конкретно отсутствующую
конфигурацию и сохранять ввод в открытой форме; не подставлять тариф/норму/ноль.

## 8. Tests

### Pricing/catalog

1. Тариф, сохранённый в выбранном каталожном scope, находится pricing preview.
2. Неверный `product_species_id=лаборатория` не считается действующим scope и
   даёт понятную конфигурационную ошибку.
3. В preview есть строка каждого выполненного исследования с tariff/amount.
4. Missing tariff содержит indicator code/name и scope action.
5. Цена 0 отличается от отсутствующей цены.
6. Смена каталога не меняет старый pricing snapshot.
7. Preview использует decimal и accepted quantity без float.

### Numeric research

1. Микроскопия `2.5` и `2,5` проходят и уходят как decimal string.
2. Микроскопия `0` проходит.
3. `-1`, `abc`, `Infinity`, пустое выполненное значение отклоняются.
4. Температура/pH/dosimetry принимают дробные значения с существующими
   диапазонами.
5. Сохранённые старые integer snapshots продолжают читаться.

### Evaluation/highlight

1. Fixed rule результата показывает правильный IN_NORM/DEVIATION.
2. Configurable rule below/on/above границы даёт правильную подсветку.
3. Unknown не окрашивается зелёным и не меняет итог врача.
4. Evaluation snapshot сохраняется и восстанавливается после reload.
5. Критерий нормы виден пользователю рядом с оценкой.

### UI

1. Block «Итог экспертизы» совпадает с макетом по grid/spacing/labels.
2. Все три dropdown не имеют browser-default вида.
3. Dropdown keyboard/focus/aria tests проходят.
4. Проверить loading/error/disabled/long names/narrow 390 px.
5. E2E Save/Complete и Save/Waiting проходят без «Проверьте введённые значения»
   при корректных данных.

Тесты используют fixtures/MSW/transport spy. Реальные VetIS write-вызовы не
выполняются.

## 9. Docker, subagents и Git

ИИ-агент использует **subagent-driven-development**: отдельные subtask для
pricing scope/catalog, numeric/evaluation backend, examination UI/select и
integration tests; затем review/integration subtask.

После реализации:

```powershell
cd C:\electronic_lab_dev\frontend
npm.cmd run format:check
npm.cmd run lint
npm.cmd run typecheck
npm.cmd run test
npm.cmd run build-storybook
npm.cmd run build
npm.cmd run test:e2e

cd C:\electronic_lab_dev
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build backend frontend vetis-worker
docker compose -f docker-compose.yml -f docker-compose.dev.yml ps
```

Не выполнять `docker compose down -v`, destructive reset/seed и не удалять
пользователей, лаборатории, партии, ВСД, ВСЭ, пробы, отчёты или PostgreSQL
volume.

ТЗ добавить в тот же commit с кодом. После тестов проверить diff, отправить
feature-ветку, выполнить `git pull --ff-only` для `main`, объединить без
force-push и отправить обновлённый `main`. При защищённой ветке создать PR.

## 10. Вопрос по scope тарифов

В текущем коде нормы уже переводятся в область `meat`, но VSE-тарифы исторически
ищутся по конкретному `product_species_id`. Именно из-за этого ранее сохранённые
тарифы с неверным scope не находятся pricing.

Перед реализацией нужно подтвердить одно правило:

1. тарифы отдельные для каждого вида продукции (говядина/свинина и т.д.);
2. один тариф действует на всю область «Мясо и мясопродукты».

Агент не должен самовольно менять это правило или мигрировать существующие
цены. В отчёте указать выбранный scope и миграцию/совместимость.

## 11. Критерии готовности

- предварительная стоимость появляется сразу после ввода выполненного
  исследования при корректно настроенных норме и тарифе;
- ошибка отсутствующего тарифа не возникает из-за рассинхронизации scope;
- блок «Итог экспертизы» визуально соответствует `electronic-vse-journal`;
- dropdown имеют стили, keyboard и accessible states;
- дробная микроскопия сохраняется и участвует в расчёте;
- карточка ВСЭ заполняется и сохраняется в COMPLETED/WAITING сценариях;
- тесты, Storybook, Docker и subagent review выполнены;
- feature-ветка с кодом и ТЗ объединена с `main` и отправлена в GitHub либо
  создан Pull Request.
