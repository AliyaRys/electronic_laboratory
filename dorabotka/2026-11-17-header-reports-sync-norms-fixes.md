# ТЗ на исправление шапки, отчётов, статуса синхронизации и справочника норм

Дата: 17.11.2026  
Тип задачи: frontend shell + reports navigation + arrivals UX + catalog/evaluation rules

## 1. Цель

Исправить следующие дефекты:

1. В шапке показывать инициалы пользователя вместо длинного полного имени.
2. Под логотипом показывать лабораторию для ВЕТ/заведующего и «Республика
   Татарстан» для аналитика/администратора.
3. Убрать ссылку «← Поступления» с hub-страницы раздела «Отчёты».
4. Заменить длинный технический текст после обновления поступлений коротким
   понятным сообщением.
5. Скорректировать справочник «Нормы исследований»: фиксированные qualitative
   правила не должны настраиваться как клинические нормы, бактериоскопия не
   должна отображаться в этом справочнике.
6. Подсвечивать результаты исследований в карточке ВСЭ по результату оценки
   нормы: зелёный — норма, красный — отклонение, нейтральный — оценка не
   определена/не применяется.

Работу выполнять через **subagent-driven-development**. Общие компоненты и
stories не дублировать. После завершения агент обязан объединить feature-ветку
с `main`, добавить это ТЗ в тот же commit/ветку и обновить контейнеры.

## 3. Шапка системы

### 3.1. Инициалы

В правой части шапки вместо полного имени показывать инициалы фамилии и имени:

```text
Рысаева Алия Илдаровна → РА
```

Правила:

- брать фамилию и имя из `full_name`, отчество не использовать;
- поддержать лишние/двойные пробелы;
- приводить инициалы к верхнему регистру;
- пустое/неразбираемое имя даёт fallback `?`;
- полное имя сохранить в `title`/доступном имени ссылки профиля;
- не менять avatar geometry, profile route, logout и keyboard focus.

### 3.2. Подпись под логотипом

В строке под логотипом показывать:

| Роль | Текст |
|---|---|
| `VET` | название назначенной лаборатории |
| `HEAD` | название назначенной лаборатории |
| `ANALYST` | `Республика Татарстан` |
| `ADMIN` | `Республика Татарстан` |

Для VET/HEAD название брать из доверенного `ScopeView.laboratory_name` текущего
назначенного scope. UUID не показывать. При отсутствии названия —
«Лаборатория не указана».

Для ANALYST/ADMIN не использовать название случайной выбранной лаборатории.
Сохранить первую строку бренда и адаптивность; длинное название переносится или
сокращается без горизонтального overflow.

## 5. Пользовательский статус обновления поступлений

Технический текст с counters, страницами и попыткой убрать из основного visible
status. Counters оставить в operation state/diagnostics и тестах.

Рекомендуемые сообщения:

| Состояние | Сообщение |
|---|---|
| ожидание | «Автообновление из ВетИС каждые 15 минут» |
| выполнение | «Обновляем поступления…» |
| retry | «Повторяем обновление…» |
| успех, новые документы > 0 | «Обновление завершено. Новых поступлений: N.» |
| успех, новых документов = 0 | «Обновление завершено. Новых поступлений нет.» |
| финальная ошибка | понятная причина без технических counters |

`N` брать из безопасного `new_documents`. Если такого счётчика нет — показать
«Обновление завершено» без подмены imported на «новые». Оставить один компактный
`role=status`; не показывать одновременно старый и новый текст.

## 6. Справочник «Нормы исследований»

### 6.1. Фиксированные правила — без карточек справочника

Не показывать в справочнике норм:

| Показатель | Норма | Отклонение |
|---|---|---|
| Органолептическое исследование (VSE-F18) | `Соответствует` | `Не соответствует` |
| Идентификация продукции (VSE-F19) | `Соответствует` | `Не соответствует` |
| Люминесцентный анализ (VSE-F22) | `Соответствует` | `Не соответствует` |
| Реакция с сернокислой медью (VSE-F27) | `Отрицательная` | `Положительная` |
| Пероксидаза (VSE-F28) | `Положительная` | `Отрицательная` |

Эти правила должны находиться в едином backend/frontend registry и не зависеть
от ввода методиста.

### 6.2. Без оценки нормы

Бактериоскопия (VSE-F23) — текстовый результат. Убрать её строку из
справочника. Исследование остаётся в форме ВСЭ и сохраняет введённый текст,
но не получает зелёную/красную оценку нормы.

### 6.3. Настраиваемые нормы

В справочнике оставить:

- температура в толще мышц (VSE-F20);
- трихинеллоскопия (VSE-F21), если применяется подтверждённая методика;
- микроскопия (VSE-F24);
- pH (VSE-F25);
- проба варки (VSE-F26);
- дозометрическое исследование (VSE-F29).

Тип, единица, accepted values и форма нормы разрешаются каноническим registry.
Клинические границы не придумывать и не брать из демонстрационных макетов.

### 6.4. Backend catalog/readiness

Добавить к canonical indicator definitions режим:

```text
FIXED         фиксированная оценка, MethodRule не нужен
CONFIGURABLE  оценка по MethodRule
NONE          оценка нормы не применяется
```

Требования:

- FIXED/NONE не требуют active MethodRule в readiness;
- POST/PUT нормы для FIXED/NONE отклоняются;
- F18/F19/F22/F27/F28 получают фиксированную оценку;
- F23 не получает оценку нормы и не блокируется отсутствием MethodRule;
- F20/F21/F24/F25/F26/F29 используют active MethodRule;
- старые snapshots не удаляются и не переоцениваются после изменения каталога.

## 7. Подсветка результатов в форме ВСЭ

### 7.1. Сервер — источник истины

Typed evaluator должен возвращать для каждого выполненного результата:

```json
{
  "status": "IN_NORM | DEVIATION | UNKNOWN | NOT_APPLICABLE",
  "mode": "FIXED | CONFIGURABLE | NONE",
  "criterion": "текст применённого правила"
}
```

Для FIXED:

- F18/F19/F22: `MATCH` → `IN_NORM`, `MISMATCH` → `DEVIATION`;
- F27: `NEGATIVE` → `IN_NORM`, `POSITIVE` → `DEVIATION`;
- F28: `POSITIVE` → `IN_NORM`, `NEGATIVE` → `DEVIATION`.

Для NONE показывать нейтральное «Оценка по норме не применяется». Для UNKNOWN
не показывать зелёное состояние и не превращать его в «Норма».

### 7.2. UI карточки исследований

После ввода/изменения результата форма получает evaluation из server pricing/
evaluation preview и показывает его прямо в карточке исследования:

- `IN_NORM` — спокойная зелёная подложка/граница и текст «Норма»;
- `DEVIATION` — спокойная красная подложка/граница и текст «Отклонение»;
- `UNKNOWN` — нейтральный текст «Оценка не определена»;
- `NOT_APPLICABLE` — нейтральный текст «Оценка по норме не применяется».

Цвет не единственный носитель смысла: рядом всегда должен быть текст. Результат
врача `FIT/UNFIT` не подменять оценкой нормы: отклонение только предупреждает и
не выбирает медицинский итог автоматически.

Evaluation preview должен запускаться после изменения результата и при
первоначальной загрузке формы с уже введёнными данными. При изменении нормы в
справочнике открытая форма получает новую оценку только после нового preview;
сохранённые старые ВСЭ используют свой evaluation snapshot.

Не показывать цену вместо оценки и не привязывать подсветку к состоянию
`performed` без typed evaluation.

2. VET/HEAD видят название назначенной лаборатории.
3. ANALYST/ADMIN видят «Республика Татарстан».

### Отчёты и обновление

1. Hub «Отчёты» не содержит ссылки «← Поступления».
2. Running/retry/success/error statuses имеют новые короткие тексты.
3. `new_documents` отображается корректно; технические counters не видны в
   основном status.
4. Capability navigation и другие report routes не сломаны.

### Нормы и evaluation

1. Справочник не показывает F18/F19/F22/F23/F27/F28.
2. Справочник показывает configurable F20/F21/F24/F25/F26/F29.
3. POST/PUT fixed/none indicators блокируется сервером.
4. Fixed mappings дают правильные `IN_NORM/DEVIATION`.
5. F23 остаётся текстовым исследованием без norm highlight.
6. Configurable result выходит за/попадает в границу с правильной оценкой.
7. Карточки ВСЭ показывают зелёный/красный/нейтральный текст и цвет.
8. UNKNOWN не становится зелёным и не меняет итог врача.
9. Старый saved evaluation snapshot не меняется после правки каталога.
10. Storybook показывает fixed, configurable, deviation, unknown, not applicable,
    loading, error и narrow states.

Все тесты используют fixtures/MSW; реальные внешние write-вызовы ВетИС не
выполняются.

## 10. Docker, subagents и Git

Агент использует **subagent-driven-development**: отдельные задачи для AppHeader,
Reports/Arrivals UX, catalog registry/backend и examination evaluation; затем
review/integration task с проверкой общего diff.

После реализации:

```powershell
cd C:\electronic_lab_dev\frontend
npm.cmd run format:check
npm.cmd run lint
npm.cmd run typecheck
npm.cmd run test
npm.cmd run build-storybook
npm.cmd run build
npm.cmd run test:e2e

cd C:\electronic_lab_dev
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build backend frontend vetis-worker
docker compose -f docker-compose.yml -f docker-compose.dev.yml ps
```

Не выполнять `docker compose down -v`, destructive reset/seed и не удалять
пользователей, лаборатории, партии, ВСД, ВСЭ, пробы, отчёты или PostgreSQL
volume.

ТЗ добавить вместе с кодом в feature-ветку. После тестов проверить diff,
отправить feature-ветку, выполнить `git pull --ff-only` для `main`, объединить
без force-push и отправить обновлённый `main`. При защищённой ветке создать PR.

## 11. Критерии готовности

- шапка компактна и показывает правильные initials/область пользователя;
- hub отчётов не содержит лишней ссылки на поступления;
- статус обновления понятен пользователю и не раскрывает технический шум;
- справочник содержит только настраиваемые нормы;
- фиксированные правила оценки работают без фиктивных строк каталога;
- бактериоскопия отсутствует в справочнике, но работает в форме ВСЭ;
- карточки исследований получают корректную зелёную/красную/нейтральную оценку;
- обязательность и медицинский итог не подменяются подсветкой;
- tests, Storybook, контейнеры и merge в `main` выполнены.
