# Журнал ВСЭ, учёт проб, мясной контекст и операционные услуги Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILLS: Use `superpowers:subagent-driven-development` to implement this plan task-by-task and `superpowers:systematic-debugging` for every defect investigation. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Привести «Журнал ВСЭ» и «Учёт проб» к согласованному интерфейсу, оставить в рабочей шапке только мясной MVP и исправить учёт двух услуг сверки в операционном отчёте для новых и уже погашенных эВСД.

**Architecture:** Журнал получает отдельную серверную read-модель карточек ВСЭ вместо ошибочного использования списка поступлений. API учёта проб возвращает готовые человекочитаемые проекции, а не заставляет фронтенд сопоставлять внутренние UUID. Мясной контекст фиксируется в общей шапке как непереключаемый контекст MVP. Факты двух услуг сверки формируются сервером в момент подтверждённого гашения, а операционный отчёт продолжает считать сохранённые факты, не клиентские заявления и не тарифные строки.

**Tech Stack:** FastAPI, SQLAlchemy, PostgreSQL/Alembic, Pydantic/OpenAPI, React, TypeScript, TanStack Query, React Router, общие компоненты приложения и Storybook, Vitest, Playwright, Docker Compose.

**Spec:** `journal.html`, `DESIGN.md`, `UX-CONTRACT.md`, `STORYBOOK.md`, `Функциональные требования/v2.0/05-samples.md`, `Функциональные требования/v2.0/09-reports.md`, `Функциональные требования/v2.0/sources/foundation-v1.9/02-product-design-records.md`, `docs/TZ_development/plans/2026-11-06-05-samples.md`, `docs/TZ_development/plans/2026-11-06-08-reporting.md`, SC-071–079 и настоящая спецификация.

## Global Constraints

- Перед изменением интерфейса полностью прочитать `AGENTS.md`, `DESIGN.md`, `UX-CONTRACT.md`, `STORYBOOK.md`, затем текущую реализацию и похожие страницы.
- Эталон внешнего вида журнала — корневой `journal.html`. Нельзя переносить из него демонстрационные данные, локальный JavaScript или SVG-копии; требуется воспроизвести композицию через реальные React-компоненты и API.
- Серверная пагинация, поиск и фильтры обязательны. Нельзя фильтровать только 20 строк текущей страницы в браузере и выдавать это за фильтрацию журнала.
- Русский язык обязателен. В пользовательских таблицах не показывать внутренние `party_id`, `actor_id`, `collected_by`, `product_species_id`, ревизии и иные служебные UUID. UUID самого эВСД и номер внешнего эВСД являются предметными реквизитами и могут отображаться с понятной подписью.
- Человекочитаемые значения разрешаются на сервере одним запросом/ограниченным числом запросов без N+1 и без вызовов ВетИС из экранов.
- Не менять правила доступа: VET/HEAD могут регистрировать утилизацию, ANALYST видит учёт проб только для чтения, ADMIN не получает отчётный доступ.
- Не возвращать молоко в бизнес-область MVP. Молочные HTML-макеты и исторические данные не удалять, но production-интерфейс не должен предлагать молоко и не должен сохранять/восстанавливать молочный рабочий контекст.
- Операционный отчёт считает одну фактически завершённую услугу как одну единицу независимо от цены, количества мест и тарифного множителя. Ярмарочная цена 0 ₽ не означает отсутствие выполненной услуги.
- Полный возврат (`RETURN_ALL` / состояние `RETURNED`) сам по себе не создаёт две услуги. Автоматическое формирование обеих услуг относится к успешно погашенному полностью или частично эВСД (`ACCEPT_ALL`/`PARTIAL`, состояние `CONFIRMED`).
- Никаких изменений интеграции гашения и никаких живых SOAP-вызовов ВетИС в рамках этой задачи.
- Не менять пользовательские несвязанные изменения в рабочем дереве. ТЗ и реализацию вести в одной feature-ветке, затем слить в `main` через отдельный merge-коммит и отправить в удалённый репозиторий.

## Подтверждённые причины дефектов

1. `ExaminationJournalPage.tsx` при отсутствии `status` выбирает `WAITING`. Более того, журнал использует `GET /api/v1/arrivals`, где `result=WAITING` означает очередь ожидаемых поступлений, а не `Examination.status == WAITING`; затем строки без `examination_id` отбрасываются на клиенте. Это неверная read-модель журнала.
2. Текущий журнал не получает из API итог ВСЭ, сохранённого специалиста и дату карточки, поэтому не может честно повторить поля и фильтры `journal.html`.
3. `BalanceView`, `CollectionView` и `DisposalView` возвращают внутренние идентификаторы без готовых имён. Фронтенд прямо показывает `product_species_id`, `party_id`, `collected_by`, `actor_id`; история утилизаций пытается угадать название продукции по одной странице активных отборов, поэтому на другой странице или после утилизации снова показывает UUID.
4. В общей React-шапке `ProductSwitcher` всегда строит варианты `meat` и `milk`; сохранённый контекст приложения также способен восстановить `milk`, хотя действующий MVP ограничен `productType=1`.
5. `ReconciliationForm.tsx` всегда формирует `services: []`. Backend сохраняет этот пустой список, хотя `_price_check_services()` одновременно рассчитывает обе услуги. `operational_query()` корректно считает только `services[].performed == true` и поэтому возвращает нули. Существующие unit-тесты создают факты вручную и не ловят разрыв реального сквозного сценария.

## Целевое поведение

### 1. Журнал ВСЭ

- Маршрут остаётся `/labs/:labId/examinations`.
- При открытии маршрута без `status` активна вкладка **«Завершённые»** и запрашивается `status=COMPLETED`. Вкладка **«Ожидание результатов»** остаётся доступной только после явного выбора пользователя.
- Состояние вкладки и все фильтры хранятся в URL. Назад/вперёд браузера восстанавливают экран; смена вкладки или фильтра сбрасывает страницу на 1.
- Внешний вид, размеры рабочей области, карточки, интервалы, фильтры, пагинация, пустое состояние и адаптивность повторяют `journal.html` в рамках общих токенов приложения.
- Заголовок: «Журнал ВСЭ мяса и мясопродуктов».
- Состав фильтров:
  - «Поиск» с placeholder `Хозяйство или UUID ВСД`;
  - «Итог ВСЭ»: «Все итоги», «Пригодно», «Непригодно»; для WAITING фильтр сбрасывается и недоступен, потому что итог ещё отсутствует;
  - «Автор»: реальные специалисты, имеющие карточки в доступной лаборатории; значение — стабильный ID, подпись — сохранённое ФИО;
  - «Сортировка»: «Сначала новые» / «Сначала старые»;
  - «Период обращения» с режимами «Дата», «Дата и время», «Диапазон», кнопками «Сбросить» и «Применить».
- Карточка строки показывает:
  - «Дата и время обращения» — `Examination.created_at`, формат `ДД.ММ.ГГГГ ЧЧ:ММ` в `Europe/Moscow`;
  - «Хозяйство» — сохранённое человекочитаемое имя отправителя/владельца из партийного snapshot/read-модели;
  - «UUID ВСД» — `IncomingDocument.evsd_uuid`;
  - «Автор» — `Examination.specialist_name`, то есть выбранный специалист Госветслужбы, а не технический `created_by`;
  - для COMPLETED — текстовый итог «Пригодно»/«Непригодно» с согласованным статусным тоном;
  - для WAITING — «Ожидание результатов»;
  - иконку просмотра с доступным именем и ссылкой на реальный `/labs/:labId/examinations/:examinationId`.
- Не вводить отсутствующий в модели результат «Условно-пригодно» только потому, что он есть в старом демонстрационном HTML.
- Удалённые карточки не показывать. Доступ и область лаборатории проверять сервером.

### 2. Серверная read-модель журнала

Добавить отдельный scoped endpoint, например:

```text
GET /api/v1/examinations
  ?laboratory_id=<uuid>
  &status=WAITING|COMPLETED
  &q=<text>
  &outcome=FIT|UNFIT
  &specialist_id=<uuid>
  &occurred_from=<offset datetime>
  &occurred_to=<offset datetime, exclusive>
  &sort=asc|desc
  &page=<n>
```

Не переиспользовать `result` списка поступлений. Ответ страницы должен содержать компактный `ExaminationJournalItem` с уже готовыми полями `examination_id`, `status`, `created_at`, `first_completed_at`, `outcome`, `specialist_id`, `specialist_name`, `evsd_uuid`, `consignor_name` и ревизией только если она действительно нужна клиенту. Отдельный scoped endpoint авторов либо метаданные списка должны возвращать варианты фильтра «Автор» без чтения всех пользователей и без N+1.

Правила запросов:

- поиск без учёта регистра по хозяйству и UUID эВСД;
- период полуоткрытый `[from, to)`; календарная дата пользователя переводится из `Europe/Moscow` в точные границы;
- COMPLETED сортируется по `first_completed_at`, WAITING — по `created_at`, затем стабильный tie-breaker `id`;
- фильтры применяются до `count`, `offset`, `limit`;
- размер страницы 20;
- неизвестные/несовместимые параметры дают 422, чужая лаборатория не раскрывается.

### 3. Учёт проб

Страница `/labs/:labId/reports/samples` должна стать полноценным рабочим экраном в стиле системы, без декоративной самодеятельности:

- ширина, фон, типографика и отступы из `DESIGN.md` и общих токенов;
- хлебные крошки «Отчёты → Учёт проб», заголовок и короткое пояснение;
- последовательные секции:
  1. «Остатки проб»;
  2. «Доступные отборы»;
  3. «История утилизации» с фильтром периода внутри своей секции;
- использовать существующие `DataTable`, `StatusView`, `Button`, `FormSection` или расширить их общий API; не создавать локальные копии таблиц, кнопок, пагинации и состояний;
- таблицы оформлены как белые рабочие панели с границей/мягкой тенью, в согласованном ритме; на узком экране нет горизонтального выхода страницы, данные остаются читаемыми;
- отдельные loading, empty, error, forbidden и retry-состояния для каждого независимого набора данных;
- период истории влияет только на историю утилизаций и не меняет текущий остаток;
- ссылка на 5-ВЕТ сохраняет действующие права и не показывается VET;
- действие «Утилизировать остаток» остаётся только у VET/HEAD; диалог тоже показывает название продукции, а не UUID.

Поля интерфейса:

| Блок | Колонки/данные |
| --- | --- |
| Остатки проб | «Вид продукции», «Остаток, кг», действие для разрешённых ролей. Внутреннюю ревизию не показывать. |
| Доступные отборы | «Вид продукции», «Дата отбора», «Вес, кг», «UUID ВСД», «Отобрал». |
| История утилизации | «Дата утилизации», «Вид продукции», «Вес, кг», «Номер исходящего эВСД», «Провёл». |

Форматировать даты как `ДД.ММ.ГГГГ`, время при наличии как `ДД.ММ.ГГГГ ЧЧ:ММ`, массу без лишних конечных нулей и с русской десятичной запятой. Длинные названия сокращать только визуально, с доступным полным значением/подсказкой.

### 4. Человекочитаемый API учёта проб

Расширить read DTO без изменения write-контракта утилизации:

- `BalanceView`: добавить обязательное `product_name`; `product_species_id` и `revision` остаются техническими полями для действия, но не выводятся пользователю;
- `CollectionView`: добавить `product_name`, `evsd_uuid`, `collected_by_name`;
- `DisposalView`: добавить `product_name`, `actor_name`.

Источники:

- название вида продукции — сохранённая `classification_snapshot.product.name` соответствующего отбора; для balance сервер выбирает детерминированное непустое имя активной группы, а при противоречащих именах не подменяет ID случайным названием: тест фиксирует выбранное правило и диагностическое событие;
- UUID ВСД — join `SampleCollection.party_id -> Party -> IncomingDocument.evsd_uuid`;
- ФИО отбора/утилизации — join с `User.full_name` по `collected_by`/`actor_id`;
- история утилизаций получает своё название и ФИО независимо от текущей страницы активных отборов. Запрещён клиентский `speciesLabel()` с fallback на UUID.

Если связанная учетная запись позднее заблокирована, ФИО всё равно показывается. Если историческая связь действительно повреждена, интерфейс показывает «Данные не найдены», а не сырой UUID.

### 5. Только мясо в шапке

- В production work-mode показывать один статичный контекст с иконкой мяса и текстом **«Мясо и мясопродукты»**.
- Элемент не является кнопкой: нет `aria-haspopup`, `aria-expanded`, `role=listbox`, стрелки, выпадающего меню, обработки ArrowDown/Escape и варианта молока.
- Визуальная геометрия шапки остаётся согласованной с `components/shell/AppHeader.js` / `app-header.css`.
- При загрузке production-приложения активный `productType` принудительно нормализуется в `meat`; ранее сохранённый `milk` игнорируется/очищается и не влияет на маршруты или запросы.
- Не удалять молочные HTML-макеты и не мигрировать их данные. Они перестают быть доступной опцией рабочей системы, но остаются историческими дизайн-материалами.
- Общему компоненту шапки добавить документированный single-product вариант и Storybook-состояния: обычная ширина, длинное название, узкий экран. Один и тот же вариант использовать в приложении и Storybook.

### 6. Операционные услуги

Сервер, а не браузер, является владельцем факта оказания услуг.

- Убрать `services: []` как клиентский источник истины. Клиент не должен иметь возможности увеличить или уменьшить отчёт произвольным payload.
- При успешном сохранении полного валидного результата сверки можно рассчитать тарифный snapshot, но окончательный факт выполненных услуг закрепляется атомарно с успешным `confirm_receipt`:
  - `ACCEPT_ALL` и `PARTIAL` / итоговое состояние `CONFIRMED`: сохранить ровно по одному `{code: PRODUCT_IDENTIFICATION, performed: true}` и `{code: TRANSPORT_INSPECTION, performed: true}`;
  - `RETURN_ALL` / `RETURNED`: не добавлять эти два факта автоматически;
  - OPEN/неполная сверка: фактов нет.
- Повторный poll/replay подтверждения не создаёт дубликаты и не меняет уже замороженный результат.
- `operational_query()` продолжает считать сохранённые boolean-факты: одна сверка — максимум +1 в каждый показатель, независимо от количества/цены. Внутренняя транзакция исключается только из `processed_parties`, но её выполненные услуги считаются. Ярмарка даёт услуги при цене 0 ₽.
- Период определяется `Reconciliation.completed_at` успешного внешнего результата, не датой создания карточки ВСЭ.

Добавить миграцию `0021_...py` для существующих данных:

- для строк `reconciliations.state = 'CONFIRMED'` с `completed_at IS NOT NULL` детерминированно восстановить оба факта `performed=true`, если их нет;
- не дублировать уже существующие факты и не затирать другие валидные записи;
- `RETURNED` не обогащать автоматически;
- downgrade должен быть безопасным для схемы; фактические исторические данные не удалять молча;
- миграция обязана иметь тест на повторный запуск/идемпотентность логики backfill.

## Review Focus

- Plain URL журнала открывает COMPLETED; явный `?status=WAITING` открывает ожидание.
- Поиск/фильтр на второй странице ищет по всему набору, а не по текущим 20 строкам.
- Дата/время и границы календарного дня корректны в `Europe/Moscow`.
- Фильтр автора использует выбранного специалиста ВСЭ, не автора технического запроса.
- В учёте проб нет внутренних UUID даже после утилизации, на второй странице и при заблокированном пользователе.
- Период истории не меняет остатки.
- ANALYST не видит действие утилизации; VET не видит 5-ВЕТ; ADMIN получает прежний запрет.
- В шапке нет кликабельного переключателя, caret и milk option; старое значение `milk` не восстанавливается.
- Реальная сверка из production-формы после гашения даёт +1 идентификацию и +1 осмотр транспорта.
- PARTIAL считается так же, как ACCEPT_ALL; RETURN_ALL не получает услуги автоматически.
- INTERNAL: processed +0, services +1/+1. FAIR: стоимость может быть 0 ₽, services +1/+1.
- Повторная доставка результата ВетИС не удваивает показатели.
- Backfill исправляет существующие CONFIRMED записи, поэтому отчёт меняется сразу после миграции, а не только для будущих партий.
