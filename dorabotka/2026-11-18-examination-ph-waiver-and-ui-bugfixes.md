# Валидация исследований, бесплатная ВСЭ и исправления формы/карточки ВСЭ — Implementation Plan

> **Для ИИ-агента:** перед работой обязательно применить `superpowers:systematic-debugging` и заново подтвердить причины на актуальном `main`. Реализацию вести через `superpowers:subagent-driven-development`: отдельный implementer на каждый логический этап, затем reviewer соответствия настоящему ТЗ и reviewer качества кода; после всех этапов — независимый whole-branch review. Для интерфейсной части использовать `frontend-design`, `AGENTS.md`, `DESIGN.md`, `UX-CONTRACT.md`, `STORYBOOK.md` и существующие общие компоненты. Все пункты ниже вести как чек-лист `- [ ]`.

**Цель:** перестать блокировать сохранение pH из-за выхода за норму; дать ветврачу возможность сделать бесплатной только создаваемую/редактируемую ВСЭ без изменения стоимости уже выполненной сверки; привести поля, списки, компоновку и destructive icon-button к согласованному интерфейсу; восстановить интервалы на странице сохранённой карточки.

**Подтверждённое решение владельца:** если отметка «Ярмарка» устанавливается в карточке ВСЭ, обнуляется **только стоимость услуг ВСЭ**. Сохранённая стоимость сверки данных не пересчитывается и не изменяется. Существующая отметка, установленная на этапе сверки, продолжает действовать по уже утверждённому правилу партии и делает ВСЭ бесплатной.

**Стек:** FastAPI, Pydantic, SQLAlchemy, Alembic, PostgreSQL, React 19, TypeScript, React Hook Form, TanStack Query, CSS, Vitest/Testing Library/MSW, Storybook, Playwright, pytest, Docker Compose.

**Источники:** `AGENTS.md`, `DESIGN.md`, `UX-CONTRACT.md`, `STORYBOOK.md`, `electronic-vse-journal.html`, `vse-view.html`, текущие ФТ/Product Foundation/TZ_development, настоящее ТЗ.

## 1. Подтверждённые причины

### 1.1. pH ошибочно является блокирующим ограничением

Ограничение продублировано и потому воспроизводится независимо на двух уровнях:

- `frontend/src/features/examinations/indicators.ts`: у `VSE-F25` заданы `min: 0`, `max: 14`;
- `frontend/src/features/examinations/formValues.ts`: `researchErrors()` превращает `min/max` в блокирующую ошибку формы;
- `backend/src/modules/examinations/validation.py`: `validate_researches()` отдельно отклоняет pH вне диапазона 0–14;
- текущие тесты прямо закрепляют отклонение `14.5`;
- `docs/TZ_development/plans/inputs.md` описывает старое блокирующее правило.

Это противоречит решению владельца: справочник норм должен оценивать введённое значение как «Норма» или «Отклонение», но выход за норму сам по себе не препятствует сохранению медицинского факта.

### 1.2. В карточке ВСЭ нет собственного признака бесплатности

Сейчас `backend/src/modules/examinations/commands.py::pricing_request_for()` передаёт в pricing engine только `reconciliation.fair`. `PricingPreviewRequest` принимает лишь исследования, а `ExaminationWrite` не принимает признак бесплатности ВСЭ. На фронте `SnapshotPricingTable` выводит disabled/readonly checkbox из server snapshot. Поэтому пользователь не может изменить его в карточке ВСЭ.

Нельзя просто сделать существующий checkbox визуально кликабельным: без отдельного серверного факта preview и финальное сохранение будут расходиться, а изменение `reconciliation.fair` задним числом испортит аудит и стоимость сверки.

### 1.3. Непоследовательные элементы формы

- `OutcomeFields.tsx` использует обычный `<textarea>` для причины и выводит лишнюю подсказку для `UNFIT`.
- `ResearchFields.tsx` использует нативные `<select>` для результатов исследований и наименований болезней, хотя в проекте уже есть доступный `SelectDropdown` с канонической стрелкой и клавиатурным управлением.
- Дата отбора и checkbox отправки проб находятся в двух половинах grid, но checkbox не выровнен по линии контрола даты.
- Readonly-секции в `frontend/src/pages/ExaminationViewPage.tsx` возвращаются фрагментом, а `gap: 18px` задан только `.vse-exam-form`; поэтому сохранённые секции визуально слипаются.
- Кнопка удаления использует глобальный solid `danger`. Изменять этот вариант нельзя: он нужен подтверждающим destructive-кнопкам. Для спокойной icon-only кнопки нужен отдельный мягкий вариант.

## 2. pH: значение сохраняется, норма только оценивает

### 2.1. Целевое правило

- [ ] Для `VSE-F25` значение `14.5`, `14,5` и любое другое синтаксически корректное неотрицательное десятичное значение не блокирует preview и сохранение ВСЭ.
- [ ] Запятая нормализуется так же, как сейчас, и на API отправляется каноническая decimal-строка с точкой.
- [ ] Пустое, нечисловое, бесконечное значение, экспоненциальная запись, превышение разрешённой точности/длины хранения остаются структурной ошибкой ввода.
- [ ] Не ослаблять правила массы пробы, количества, микроскопии и других полей побочным изменением общего decimal parser.
- [ ] Каталожная норма продолжает сравниваться сервером с введённым pH. Значение вне настроенного правила получает `evaluation.status = "DEVIATION"`, карточка подсвечивается и сохраняется.
- [ ] `DEVIATION` не меняет выбранный пользователем итог ВСЭ автоматически и не делает поле невалидным.

### 2.2. Изменения

- [ ] Удалить `min/max` только из определения pH в `indicators.ts` либо прекратить использовать эти свойства как бизнес-норму для pH. Не удалять типизированные ограничения у других полей, если они являются именно структурными ограничениями.
- [ ] Удалить серверную проверку `0 <= pH <= 14` из `validation.py`. Оставить проверку kind/формата/дубликатов/обязательности.
- [ ] Не переносить границы норм из справочника в Pydantic/форму: справочник участвует в evaluation, не в reject.
- [ ] Обновить противоречащие актуальному решению ФТ/Product Foundation/TZ_development, как минимум `docs/TZ_development/plans/inputs.md`: явно разделить «структурно допустимое значение» и «соответствие норме».
- [ ] Обновить тест, который сейчас ожидает отклонение `14.5`: он должен ожидать успешный payload и серверную оценку `DEVIATION` при соответствующей норме.

### 2.3. Приёмка pH

- [ ] pH `7,4` сохраняется и отображается в русском формате.
- [ ] pH `14,5` проходит клиентскую и серверную валидацию, preview возвращает строку исследования и «Отклонение», сохранение завершается успешно.
- [ ] После перезагрузки сохранённой карточки исходное значение не потеряно и не заменено границей нормы.
- [ ] `abc` и пустое значение выполненного pH дают понятную ошибку поля и не отправляются как медицинский факт.

## 3. Отдельная бесплатность ВСЭ

### 3.1. Предметная модель

Ввести отдельный сохраняемый признак карточки, например `vse_fair` / API `vseFair` (окончательное имя выбрать одно и использовать последовательно). Не переиспользовать и не мутировать `reconciliation.fair`.

Эффективное правило расчёта ВСЭ:

```text
effective_vse_fair = reconciliation.fair OR examination.vse_fair
```

- `reconciliation.fair = true`: сверка уже бесплатна, и ВСЭ остаётся бесплатной по существующему правилу партии;
- `reconciliation.fair = false`, `examination.vse_fair = true`: бесплатны только услуги ВСЭ;
- оба `false`: обычный расчёт ВСЭ;
- изменение `examination.vse_fair` никогда не меняет строки/total/fair frozen snapshot сверки.

### 3.2. База и аудит

- [ ] Добавить Alembic-миграцию от актуальной головы (на момент написания последняя видимая — `0024`; номер не хардкодить без проверки).
- [ ] Добавить в `examinations` boolean `vse_fair`, `NOT NULL`, server default `false`; после backfill при принятом в проекте стиле убрать временный server default или оставить осознанно.
- [ ] Существующие карточки получают `false`; их frozen pricing snapshot и суммы не пересчитываются.
- [ ] При create/edit сохранять выбранный признак атомарно с карточкой, пробой, pricing snapshot и audit event.
- [ ] В TechnicalEvent/audit payload фиксировать старое/новое значение `vse_fair` и источник эффективной бесплатности (`RECONCILIATION`, `EXAMINATION`, `NONE`). Не записывать только безымянный `fair=true`.
- [ ] Same-day edit может изменить `vse_fair` и пересчитать только snapshot ВСЭ. После окончания разрешённого дня действуют текущие ограничения редактирования.

### 3.3. API и единый серверный расчёт

- [ ] Добавить `vseFair: boolean` в `ExaminationWrite` и `PricingPreviewRequest`.
- [ ] Вернуть в form/read model достаточно данных для честного состояния UI: сохранённый `vseFair`, `reconciliationFair` и/или типизированный `fairSource`. Не заставлять фронт угадывать источник по `total == 0`.
- [ ] `preview_pricing()` и финальный `save_examination()` должны вызывать один и тот же `evaluate_and_price` с одним правилом `effective_vse_fair`.
- [ ] Preview не создаёт карточку, sample, command record или audit event.
- [ ] Финальный серверный расчёт не доверяет preview total клиента и всегда пересчитывает snapshot в транзакции.
- [ ] Сохранить существующую защиту от изменения тарифов/ревизии и stale preview.
- [ ] Обновить OpenAPI и `frontend/src/shared/api/schema.d.ts` штатной генерацией, не ручным рассинхронизированным патчем.

### 3.4. Поведение checkbox в форме

В live-форме создания/редактирования внутри блока «Расчёт стоимости услуг»:

- [ ] Checkbox «Ярмарка» является controlled полем React Hook Form, а не представлением `snapshot.fair`.
- [ ] Если `reconciliationFair=false`, checkbox доступен. Включение устанавливает `vseFair=true`, выключение — `false`.
- [ ] Подпись рядом: **«ВСЭ по этой карточке проводится без оплаты. Стоимость сверки данных не изменится.»**
- [ ] Если `reconciliationFair=true`, checkbox отмечен и недоступен для снятия, потому что бесплатность уже закреплена на этапе сверки. Подпись: **«Бесплатность установлена при сверке данных и распространяется на ВСЭ.»**
- [ ] Disabled в унаследованном состоянии — не единственный носитель смысла: пояснение доступно визуально и программам чтения с экрана.
- [ ] В режиме обычной доступной отметки checkbox работает с клавиатуры, имеет видимый focus и hit area не меньше 40×40 px с учётом label.
- [ ] Toggle немедленно запускает новый server preview. При включении сервер возвращает `0,00 ₽`; при выключении восстанавливает реальную сумму, если бесплатность не унаследована от сверки.
- [ ] Во время recalculating старую сумму можно оставить видимой только с явным текстом «Пересчитываем стоимость…»; сохранить карточку до успешного ответа, соответствующего текущим `researches + vseFair`, нельзя.
- [ ] Stale/отменённый ответ для предыдущего положения checkbox не заменяет новый результат.
- [ ] В create payload и edit payload отправляется то же значение, для которого получен последний успешный preview.

### 3.6. Приёмка бесплатности

- [ ] Сверка 280 ₽, затем в ВСЭ включена «Ярмарка»: сверка остаётся 280 ₽, ВСЭ сохраняется с total 0 ₽.

1. - [ ] **Task A — characterization и pH:** RED-тесты текущей блокировки, исправление frontend/backend, документация.
2. - [ ] **Task B — доменная бесплатность ВСЭ:** миграция, модель, схемы, pricing rule, audit, backend tests.

4. - [ ] **Task D — поля и dropdown:** reason input, removal note, sample row, shared dropdown migration, accessibility/tests/stories.
5. - [ ] **Task E — readonly view и danger-soft:** section stack, tokens, Button variant, view tests/stories.
6. - [ ] После каждого implementer — отдельный spec reviewer, затем quality reviewer; исправления возвращать тому же implementer и повторять review до approve.
7. - [ ] Whole-branch reviewer проверяет бизнес-инвариант: VSE-only waiver не меняет reconciliation snapshot.
