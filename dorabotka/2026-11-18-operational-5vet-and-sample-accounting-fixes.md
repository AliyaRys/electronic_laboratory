Для всех интерфейсных решений использовать `frontend-design`, `DESIGN.md`, `UX-CONTRACT.md`, `STORYBOOK.md` и существующие общие компоненты. После выполнения всех задач провести независимый whole-branch review. Каждый пункт плана вести как чек-лист `- [ ]`.

**Цель:** убрать дублирующий учёт проб из операционного отчёта, заменить метрику партий на честное количество сохранённых карточек ВСЭ, разрешить формирование и сохранение 5-вет за любой выбранный календарный диапазон и упростить отчёт «Учёт проб» до остатков и истории утилизаций.

**Архитектура:** операционный отчёт продолжает получать серверные агрегаты за период, но его контракт больше не содержит текущие остатки проб. Метрика `saved_examinations` считается непосредственно по сохранённым локальным карточкам ВСЭ. 5-вет переходит с пары `year/half` на инклюзивный календарный диапазон `date_from/date_to` во всём сквозном контракте: UI → API → подписанный preview → idempotency/уникальность → БД → список/просмотр → PDF/XLSX. «Учёт проб» сохраняет серверные остатки и неизменяемую историю, но перестаёт загружать и показывать отдельный список доступных отборов.

**Стек:** FastAPI, Pydantic, SQLAlchemy, PostgreSQL/Alembic, React 19, TypeScript, React Router, TanStack Query, общие UI-компоненты, Vitest/Testing Library/MSW, pytest, Storybook, Playwright, Docker Compose.

**Источники:** `AGENTS.md`, `DESIGN.md`, `UX-CONTRACT.md`, `STORYBOOK.md`, актуальные ФТ и product foundation, `frontend/src/features/arrivals/ReconciliationDateFilter.tsx`, `components/admin/samples/SampleAccounting.js`, настоящее ТЗ.

## 1. Подтверждённые причины

### 1.1. Операционный отчёт

Сейчас `frontend/src/pages/OperationalReportPage.tsx`:

- выводит breadcrumb `← Отчёты`;
- подписывает `processed_parties` как обработанные партии;
- использует сокращённые подписи двух услуг со служебными кодами;
- выводит `current_sample_balances` отдельной секцией.

`backend/src/modules/reporting/queries.py` считает `processed_parties` по завершённым сверкам и отдельно вызывает `balance_list`. Поэтому простая замена текста создала бы ложную метрику: количество сохранённых ВСЭ необходимо считать новым запросом к `Examination`.

`OperationalView` в `backend/src/modules/reporting/schemas.py` также содержит `processed_parties` и `current_sample_balances`, то есть лишний блок является частью API, а не только JSX.

### 1.2. 5-вет ограничен полугодием во всех слоях

Ограничение не является только элементом формы:

- `ReportPreviewParams`, `ReportSnapshotView`, `ReportSummary` содержат `year` и `half`;
- `period_bounds`, `sources_for_period` и `_ensure_completed` работают с завершённым полугодием;
- `ReportSnapshot` хранит `year/half`, имеет `half_valid` и уникальность по полугодию;
- подпись preview, idempotency context, проверка дубликата, сортировка и payload зависят от `year/half`;
- список, карточка, диалог удаления, PDF/XLSX и имена файлов показывают полугодие;
- UI содержит выбор года/полугодия и ошибку `REPORT_PERIOD_UNFINISHED`.

Следовательно, требование владельца «любой выбранный диапазон дат» должно быть реализовано сквозным изменением контракта и миграцией, а не подстановкой дат только во frontend.

### 1.3. «Учёт проб» выполняет лишнюю загрузку

`SampleAccountingPage.tsx` одновременно запрашивает balances, collections и disposals. Блок «Доступные отборы» — это отдельный `fetchCollections`, отдельный query key, URL-параметр `collections` и отдельная пагинация. После удаления блока страницу необходимо перестать отправлять этот запрос.

Утилизация остатка сейчас помещена в `row.menu` общего `DataTable`, хотя действие одно. `DataTableRow` уже поддерживает `actions: ReactNode`; прямую кнопку следует реализовать через этот публичный вариант либо оформить как общий именованный icon-action, не создавая локальное меню.

### 2.2. Семантика «Сохранённых ВСЭ»

`saved_examinations` — количество реально существующих записей `Examination` данной лаборатории, созданных в выбранном периоде.

- Использовать `Examination.created_at` как момент первого сохранения карточки.
- Интерпретировать UI-даты по календарю `Europe/Moscow` и считать полуоткрытый интервал `[date_from 00:00, date_to + 1 день 00:00)`.
- Включать карточки `WAITING` и `COMPLETED`: обе являются сохранёнными ВСЭ.
- Не включать tombstone/удалённые карточки, записи другой лаборатории и записи вне периода.
- Не исключать карточку из-за признака внутренней транзакции партии: метрика относится к сохранённым ВСЭ, а не к виду поступления.
- Не удваивать карточку из-за joins с исследованиями, пробами или услугами; использовать прямой `count(Examination.id)`.

Метрики `product_identifications` и `transport_inspections` сохранить по действующей серверной логике завершённых услуг сверки и выбранного периода. Не подменять их количеством карточек ВСЭ.

## 3. 5-вет за произвольный диапазон дат

Требование настоящего ТЗ заменяет прежнее ограничение «одно завершённое полугодие». Тип отчёта остаётся `5VET_SECTION_III`, но пользователь может сформировать его за любой валидный календарный диапазон.

### 3.1. Контракт периода

Во всех новых/изменённых контрактах использовать:

```json
{
  "date_from": "2026-11-01",
  "date_to": "2026-11-18"
}
```

- `date_from` и `date_to` — календарные даты ISO `YYYY-MM-DD`, обе обязательны.
- UI и сервер считают обе границы включительно.
- Для SQL границы переводятся в `Europe/Moscow`: `[date_from 00:00, date_to + 1 день 00:00)`.
- Валидировать `date_from <= date_to`.
- Не вводить искусственный предел длины диапазона и не требовать, чтобы период был завершённым полугодием.
- Разрешать текущий и будущий календарный диапазон; если в нём нет завершённых источников, использовать существующую честную ошибку `REPORT_NO_DATA`, а не `REPORT_PERIOD_UNFINISHED`.
- В 5-вет по-прежнему включать только завершённые карточки ВСЭ по `first_completed_at`; WAITING не становится источником официального отчёта.

### 3.2. Backend и подписанный preview

- [ ] Заменить `year/half` на `date_from/date_to` в `ReportPreviewParams`, `ReportSnapshotView`, `ReportSummary` и связанных DTO.
- [ ] Заменить `period_bounds(year, half)` для этого workflow на функцию границ произвольного диапазона. Старый helper удалить, если после миграции он не используется.
- [ ] Удалить `_ensure_completed` и код `REPORT_PERIOD_UNFINISHED` из workflow 5-вет, OpenAPI и пользовательских mapper-ов ошибок.
- [ ] `list_report_sources` должен выбирать завершённые ВСЭ по новым границам, сохраняя лабораторный scope, текущую классификацию и прежние правила расчёта.
- [ ] Поднять версию нового подписанного payload до `2`. В payload и строку MAC включить точные `date_from/date_to`; `year/half` не включать.
- [ ] Изменение любой даты на странице инвалидирует preview и введённые коды тем же безопасным способом, что нынешнее изменение года/полугодия.
- [ ] Idempotency namespace/context и проверка дубликата должны использовать `report_type + laboratory_id + date_from + date_to`.
- [ ] Два отчёта с полностью одинаковыми границами для одной лаборатории и типа запрещены с `REPORT_PERIOD_EXISTS`. Перекрывающиеся, но не идентичные диапазоны разрешены.
- [ ] Сохранение использует только проверенный подписанный preview; клиент не отправляет отдельно изменяемые даты в save-команде и не пересчитывает матрицу.

### 3.3. Миграция БД

Создать следующую миграцию после актуальной `0022_journal_service_facts.py`, например `0023_report_date_ranges.py`.

- [ ] Добавить `date_from DATE` и `date_to DATE` сначала nullable.
- [ ] Backfill существующих записей без потери данных:
  - `half=1` → `YYYY-01-01` … `YYYY-06-30`;
  - `half=2` → `YYYY-07-01` … `YYYY-12-31`.
- [ ] После backfill сделать оба поля `NOT NULL`.
- [ ] Заменить `half_valid` на check `date_from <= date_to`.
- [ ] Заменить `uq_report_snapshot_period` на unique `(report_type, laboratory_id, date_from, date_to)`.
- [ ] Удалить legacy-колонки `year` и `half` после успешного backfill; ORM и новый код не должны зависеть от них.
- [ ] Предусмотреть корректный downgrade: восстановить `year/half` можно только для диапазонов, точно совпадающих с полугодием. Если произвольный диапазон нельзя представить старой схемой без потери смысла, downgrade должен завершаться явной ошибкой до разрушительных DDL, а не молча округлять даты.

- [ ] Валидировать обратный диапазон до запроса и показать русское inline-сообщение; существующие валидные пустые границы сохраняют значение «вся история».

### 4.4. Прямая кнопка утилизации

Для ролей `VET` и `HEAD` в строке остатка вместо меню `⋯` с одним пунктом показать одну icon-only кнопку.

- Иконка: существующая `admin-dispose` (символ утилизации/переработки), **не** `admin-delete` и не мусорная корзина.
- Accessible name и tooltip: **«Утилизировать остаток»**.
- Кнопка `type="button"`; клик открывает существующий `DisposalDialog` для этой строки и не инициирует навигацию.
- Использовать `DataTableRow.actions` или добавить общий именованный `DataTableIconAction` в `shared/ui`; не вставлять SVG и не создавать screen-local action menu.
- Внешний вид — компактная иконка действия в action column, не красная кнопка удаления. Опасность действия подтверждается существующим диалогом, а не иконкой корзины.
- Для `ANALYST` кнопку не рендерить вообще. Если в строке нет доступных действий, не показывать пустое меню `⋯`.
- Сохранить текущую optimistic/conflict-safe механику: fresh balance после 409, `If-Match`, idempotency и повторное подтверждение не менять.

### 4.5. Компоновка и состояния

## 7. Критерии приёмки владельцем

- Операционный отчёт не содержит остатков проб и breadcrumb; показывает три карточки с точными согласованными названиями.
- «Сохранённых ВСЭ» совпадает с числом сохранённых карточек данной лаборатории за выбранные даты, включая WAITING и COMPLETED.
- На странице создания 5-вет нет текста/переключателей полугодия; произвольный диапазон выбирается знакомой кнопкой и popover как в «Поступлениях».
- Можно сформировать, сохранить, открыть и экспортировать 5-вет за текущий произвольный диапазон; старые отчёты за полугодия не потеряны.
- «Учёт проб» содержит только остатки и историю утилизаций; список доступных отборов и служебные примечания отсутствуют.
- «Применить» выглядит как общая primary-кнопка.
- Утилизация запускается одной понятной icon-only кнопкой с символом `admin-dispose`, а не через меню и не через корзину.
- На 390 px и при 200% zoom нет page-level horizontal scroll, обрезанных controls и недоступных действий.
- Изменения, настоящее ТЗ и тесты находятся в истории `main`; контейнеры работают на новом merge commit.
