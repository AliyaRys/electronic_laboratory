# Сверка данных, доступность гашения и нейтральные исследования ВСЭ — Implementation Plan

> **Для ИИ-агента:** до изменения кода обязательно применить `superpowers:systematic-debugging` и повторно подтвердить описанные ниже причины на актуальном `main`. Реализацию вести через `superpowers:subagent-driven-development`: отдельный implementer на каждую задачу, затем отдельный reviewer соответствия ТЗ и отдельный reviewer качества; после всех задач — whole-branch review. Для интерфейса использовать `frontend-design`, а также полностью прочитать `AGENTS.md`, `DESIGN.md`, `UX-CONTRACT.md`, `STORYBOOK.md`, найти существующую реализацию и ближайший эталон. Все шаги вести чекбоксами `- [ ]`.

**Цель:** исправить поведение сверки и доступность гашения, привести локальные элементы сверки к каноническому дизайну, убрать лишние служебные пояснения со страниц ВСЭ и вывести из справочника норм исследования, для которых единая норма предметно неприменима.

**Архитектура:** полнота сверки, денежный расчёт и допустимость гашения остаются серверными. Отметка основного сопроводительного документа становится единственным пользовательским вводом вместо скрытых legacy-полей CHK-F25–27. Исследования без универсальной нормы продолжают сохраняться и тарифицироваться, но получают серверный режим `NONE` и остаются визуально нейтральными. Интерфейс не показывает технические статусы и не добавляет новые подсказки без согласования владельца.

**Технологии:** FastAPI, Pydantic, SQLAlchemy, PostgreSQL, React 19, TypeScript, React Hook Form, TanStack Query, CSS, Vitest/Testing Library/MSW, Storybook, Playwright, pytest, Docker Compose.

**Спецификация:** `AGENTS.md`, `DESIGN.md`, `UX-CONTRACT.md`, `STORYBOOK.md`, ФТ, Product Foundation, `docs/TZ_development`, настоящее ТЗ.

## Глобальные ограничения

- Начать от актуального `main` в отдельной ветке `feature/reconciliation-examination-norms-bugfixes`.
- Настоящее ТЗ добавить в feature-ветку первым отдельным коммитом.
- Не выполнять реальное гашение и не отправлять SOAP write-запросы в ВетИС в рамках автоматических или ручных проверок этой задачи.
- Не изменять вручную сохранённую сверку, входящий эВСД или справочники в рабочей БД для маскировки дефекта. Исправление должно корректно обработать уже существующие данные.
- Не скрывать серверные ошибки CSS-правилами. Сначала исправлять первопричину; допустимые ошибки привязывать к тому полю, которое пользователь действительно может изменить.
- Денежные значения не рассчитывать в браузере. Preview и итоговое сохранение используют одну серверную функцию ценообразования.
- Не добавлять новые пояснения, badges, diagnostics, audit-карточки или служебные подписи в пользовательский интерфейс без отдельного согласования владельца.
- Не менять серверную предметную логику, не указанную в настоящем ТЗ. В частности, сохранить проверку неотрицательного числового результата микроскопии и неизменяемость сохранённых снимков завершённых ВСЭ.
- Микроскопию не удалять из перечня исследований и из справочника стоимости. Убирается только настраиваемая **норма** и визуальная оценка нормы.
- Исторические ВСЭ с ранее сохранённым результатом `OTHER` пробы варки должны оставаться читаемыми. Новые карточки не должны позволять выбрать или отправить этот вариант.
- Для уже существующих компонентов использовать текущий API и общий CSS. Не копировать реализацию select, кнопок, карточек и SVG в страницу или story.
- Сохранить несвязанные изменения рабочего дерева, включая пользовательский `.gitignore`, и не включать их в коммиты задачи.

## Подтверждённые причины дефектов

### 1. «Тип транзакции» использует другой CSS

`frontend/src/features/arrivals/ReceiptDecision.tsx` выводит `#transaction-type` обычным `<select>` внутри `.app-field`. Эталонный `#inspection-joint` находится в `ReconciliationForm.tsx`; его высота, стрелка, правый внутренний отступ, focus и disabled заданы только селектором `.vse-rec-observation select` в `reconciliation.css`. Поэтому одинаковые нативные controls выглядят по-разному.

### 2. Полный возврат показывает противоречивый акт

Backend верно вычисляет `act.required=false` для `RETURN_ALL`, но `ActPreview.tsx` меняет только заголовок и всё равно выводит таблицу `act.items`. В результате интерфейс одновременно сообщает, что акт не формируется, и показывает «Расхождения, включаемые в акт». Столбец «Факт» — введённое фактическое значение обычного поля; у сопроводительного документа такого ввода больше нет, поэтому пользователь видит бессмысленный прочерк.

### 3. Обратный пересчёт «Ярмарки» возвращается к старому снимку

Live preview в актуальном коде существует, но после первого переключения `previewPayload` снова становится `null`, если draft совпал с сохранёнными полями. Тогда UI показывает `initial.pricing`, а не делает обратный серверный preview. Это особенно ломает уже существующие несогласованные строки.

В рабочей БД подтверждён реальный пример:

- указанный владельцем UUID `a2b833f5-a2e1-4783-8783-6ec1251dfb20` — UUID эВСД;
- локальная партия: `b5c63991-efef-484d-b648-16d6e123e33e`;
- сохранённая сверка: revision `9`, `decision=RETURN_ALL`, `fair=false`;
- старый `pricing_snapshot.fair=true`, `total=0.00`.

При неполном повторном сохранении `save_reconciliation()` сохраняет новое `row.fair`, но оставляет прежний pricing snapshot. Поэтому публичный read model способен вернуть одновременно `fair=false` и нулевой снимок с `pricing.fair=true`.

### 4. Сохранённая сверка ошибочно считается неполной

У этой же партии основной документ отмечен:

```text
documentChecks.abc25742ec853fee =
  { matches: false, reason: "так исторически сложилось" }
```

Однако `validation.py` считает legacy-поля CHK-F25–27 закрытыми только при `primary_document_check.matches == true`. При `matches=false` сервер дополнительно требует три скрытые отметки, хотя фронтенд больше не показывает старые карточки. Read model возвращает:

```text
complete=false
CHK-F25: сравнение не отмечено
CHK-F26: сравнение не отмечено
CHK-F27: сравнение не отмечено
```

Это и блокирует «Подготовить гашение». Отметка основного документа должна считаться выполненной независимо от результата «Соответствует / Не соответствует»; при несоответствии отдельно требуется только причина.

### 5. Микроскопия ошибочно считается настраиваемой нормой

`VSE-F24` не имеет явного `evaluation_mode` в `mandatory.py`, поэтому наследует `CONFIGURABLE`. Из-за этого она попадает в «Нормы исследований», требует `MethodRule` и получает зелёную/красную оценку. Предметное решение владельца: единой нормы для микроскопии нет, результат остаётся числовым фактом.

### 6. «Иное (указать)» пробы варки закреплено в двух реестрах

Вариант присутствует в backend `_COOKING_OPTIONS` как «Иное (указать)» и во frontend `COOKING_OPTIONS` как wire value `OTHER`. Поэтому он одновременно появляется в справочнике норм, форме ВСЭ и дополнительном поле пояснения.

## Review Focus

- Быстрое переключение `Ярмарка: false → true → false`: поздний нулевой ответ не должен перезаписать последний обычный расчёт.
- Основной документ с `matches=false` и непустой причиной: сверка полная, скрытые CHK-F25–27 не требуются, акт не обещается при полном возврате.
- Прямой API-запрос preview гашения для действительно неполной сверки: честный `RECONCILIATION_INCOMPLETE`, ноль XML/outbox/SOAP.
- Микроскопия без MethodRule: форма сохраняется, тариф применяется, карточка нейтральна и в справочнике норм строки нет.
- Новая проба варки не принимает `OTHER`, но историческая сохранённая ВСЭ с этим значением остаётся читаемой.

## Порядок выполнения через subagent-driven-development

1. Task 1 — transaction select и полный возврат.
2. Task 2 — двусторонний pricing preview и инвариант snapshot.
3. Task 3 — полнота основного документа и receipt gate.
4. Task 4 — очистка страницы ВСЭ.
5. Task 5 — микроскопия `NONE`.
6. Task 6 — проба варки без `OTHER`.
7. Task 7 — общая проверка и выпуск.

На каждую Task:

- fresh implementer читает только task brief и обязательные ссылки;
- implementer сначала пишет RED-тест, затем минимальную реализацию;
- отдельный reviewer проверяет соответствие ТЗ и качество;
- незакрытые Critical/Important замечания не переносятся на следующую Task;
- контроллер ведёт ledger с commit range и результатами проверок.

## Итоговые критерии приёмки

- «Тип транзакции» визуально и функционально совпадает с эталонным select совместной перевозки.
- Выбор полного возврата не создаёт лишнее сообщение и не показывает противоречивый блок акта.
- Снятие «Ярмарки» немедленно возвращает обычную серверную стоимость, без сохранения формы.
- `fair` и `pricing.fair` никогда не расходятся в публичном ответе.
- Отметка несоответствия основного документа с причиной закрывает проверку документа; CHK-F25–27 не блокируют гашение.
- Существующая сверка эВСД `a2b833f5-a2e1-4783-8783-6ec1251dfb20` после обновления кода становится полной без ручного исправления БД.
- Со страницы создания ВСЭ удалены ссылка и обе лишние категории пояснений.
- Микроскопия отсутствует в «Нормах исследований», но остаётся вводимой и тарифицируемой без оценки нормы.
- У пробы варки отсутствует «Иное (указать)» в справочнике и новой карточке; история остаётся читаемой.
