# 02. Поступления и приёмка

Полный состав полей CHK-F01–44 дан в 10. Поддерживаются все три решения; вариант не выбирается автоматически. Исходные и фактические значения хранятся раздельно. Никаких индивидуальных маркировок туш.

**Контур O-12/O-13:** входящие эВСД читаются из тестового профиля ветеринарных управлений. Все три решения ниже должны быть полностью реализованы вплоть до реального submit/poll. Однако ИИ-агенты, автоматические тесты и приёмка не отправляют их в Меркурий и не расходуют ограниченные тестовые эВСД. Write capability по умолчанию выключена и включается оператором только для штатного действия уполномоченного пользователя по решению владельца.

| Условие | Полное гашение | Частичное гашение | Полный возврат |
| --- | --- | --- | --- |
| Нет блокирующих расхождений | Вся доставленная партия принимается | Реальный положительный принятый и возвращаемый объём | Вся прибывшая партия возвращается |
| Допустимое расхождение требует акта | После факта/причины, с актом | После факта/причины и разделения, с актом | Без акта этой ветки |
| Недопустимое исправление участника/классификации/производителя/даты выработки/вида транспорта/хранения | Запрещено | Запрещено | Только если допускает внешний контракт |
| Неблагоприятное состояние отделения/совместной перевозки | Само не блокирует | Само не блокирует | Само не блокирует |
| Неприменимый статус эВСД | Запрещено | Запрещено | Запрещено |

При сочетании расхождений действует более строгое ограничение. Доступность повторно проверяется при отправке. XML-пути, версия сервиса и справочники устанавливаются по INPUT-01, а не по демонстрационной реализации.

### FT-ARR-01. Получение и обновление входящих эВСД

**Основание:** PDR-001/004/020; SC-001.

**Требование:** Планировщик каждые 15 минут получает из тестового профиля ВУ все страницы входящих оформленных транспортных эВСД Агропромышленного парка; ручное обновление запускает тот же процесс. После scoped-запроса локально создаются поступления только для `certifiedConsignment/batch/productType=1`; иной или отсутствующий тип не приравнивается к мясу. Повторное получение того же внешнего UUID обновляет его внешнюю версию без дубликата партии. Полученный XML и checksum версии сохраняются как защищённый источник; нормализованные поля обновляются, но местные факты не затираются. Если изменился снимок, по которому начата/завершена сверка, она помечается устаревшей и требует повторной проверки. Отсутствие результата запроса не означает отсутствие поступлений.

**Приёмка:** Два разрешённых read-обновления одного эВСД не дают две строки или две ВСЭ; изменение внешней версии обновляет показанные поля и инвалидирует использованную сверку, неизменная версия остаётся идемпотентной. Планировщик выдерживает интервал 15 минут и полный проход страниц; `productType!=1` не появляется в мясной очереди; транспортный spy подтверждает ноль write-вызовов.

### FT-ARR-02. Очереди и сохранение сверки

**Основание:** PDR-004/005/014; R-03.

**Требование:** «Ожидаемые», «В работе», «Принятые» отражают этапы из 00. Начатая сверка сохраняет выбранные отметки и введённые факты для продолжения. Полный возврат доступен через фильтр результата без возможности создавать ВСЭ. Ожидание и возврат после удаления видны с отдельным статусом. Незавершённая форма ВСЭ не создаёт сохранённой карточки; начатая сверка сохраняется независимо от отмены черновиков ВСЭ (O-09).

**Приёмка:** Обновление страницы после сохранения не теряет факты; удалённая ВСЭ возвращает партию в работу без повторного гашения.

### FT-ARR-03. Порядок и обязательность сверки

**Основание:** PDR-005; SC-015–018.

**Требование:** Порядок: документ → участники → транспорт → продукция → сопроводительные документы → прежняя ВСЭ при наличии → результаты → стоимость. Каждое сравниваемое поле требует явной отметки; значение по умолчанию не считается проверкой. Информационные поля не требуют фиктивной отметки.

**Приёмка:** Пропуск одного обязательного сравнения запрещает завершение и указывает конкретное поле.

### FT-ARR-04. Участники и классификация

**Основание:** PDR-005/008; CHK-F05–08/15–19.

**Требование:** Участники — предприятие и владелец для отправителя и получателя. Уровни `productType`, `product`, `subProduct`, `productItem` и производитель поступают из Меркурия. Для каждого вложенного объекта сохраняются его собственные GUID/UUID и source `name`; интерфейс показывает это `name`, не общий локальный справочник и не идентификатор. Уровни не подменяют друг друга. Адрес не выделяется отдельно; строка предприятия может его содержать. Недопустимое изменение блокирует принятие по матрице. Исходные значения не затираются фактическими.

**Приёмка:** Другой получатель блокирует полное/частичное принятие даже при допустимом расхождении веса.

### FT-ARR-05. Транспорт и сопроводительные документы

**Основание:** PDR-005/006; CHK-F09–14/25–27.

**Требование:** Проверяются вид транспорта, ТС, прицеп или «Без прицепа», хранение, состояние отделения и совместная перевозка; тип, номер, дата транспортного документа. Неблагоприятный осмотр не выбирает возврат и не создаёт акт сам по себе. Серия и отдельное поле связанных документов не вводятся.

**Приёмка:** «Есть загрязнения или повреждения» сохраняется как результат осмотра; врач сохраняет право выбрать допустимое решение.

### FT-ARR-06. Раздельные количественные факты

**Основание:** PDR-004/006; SC-011/012/026.

**Требование:** Документальное, доставленное, принятое и реально возвращаемое количества/вес различаются. Для частичного принятия принятое + возвращаемое = доставленное в одной единице; обе части положительны. Для полного принятия принято всё доставленное, для полного возврата принято 0. Вес/количество не вычисляются равным делением туш.

**Приёмка:** Документ 120 кг, доставлено 100 кг, принято 100 кг: возврата 20 кг нет. При 120 доставленных и 100 принятых возвращается реально имеющиеся 20 кг.

### FT-ARR-07. Допуск веса и акт

**Основание:** PDR-006; SC-024–026; CHK-F21.

**Требование:** При положительном документальном весе отклонение = (доставленный фактический вес − документальный) / документальный × 100%. Границы ±5% включены; акт по весу нужен за их пределами при полном/частичном принятии. Другие основания акта действуют независимо. Нулевой/невалидный документальный вес не допускает деление и требует проверки источника.

**Приёмка:** При 100 кг значения 95 и 105 не требуют акта только по весу; 94,999 и 105,001 требуют. Недостача не создаёт обратный груз.

### FT-ARR-08. Расхождения и содержание акта

**Основание:** PDR-005/006; CHK-F42–44; SC-022/023.

**Требование:** Допустимые расхождения названия продукции, количества, веса сверх допуска, срока годности, ТС/прицепа и транспортного документа требуют фактического значения и причины по каталогу. До отправки показываются поле, исходное значение, факт, причина и плашка акта. Акт добавляется к полному/частичному гашению без отдельного значения «с актом». Полный возврат не формирует акт этой ветки.

**Приёмка:** Смена решения с принятия на полный возврат не оставляет обещание автоматически сформировать акт; данные расхождения остаются в сверке.

### FT-ARR-09. Выбор решения и проверка состава

**Основание:** PDR-006; SC-019–027.

**Требование:** Три значения видны в заданном порядке, недопустимые выключены с объяснением. Решение выбирает врач. После изменения фактов ранее выбранный недопустимый вариант не отправляется: требуется новый допустимый выбор. Неприбытие/нулевая доставка не считаются успешной положительной приёмкой или возвращённым отсутствующим грузом.

**Приёмка:** Нельзя отправить частичное гашение с нулевым принятием/возвратом или полное гашение после появления блокирующего расхождения.

### FT-ARR-10. Причина возврата

**Основание:** PDR-006/020; CHK-F35; SC-099.

**Требование:** Частичное гашение и полный возврат требуют справочного кода Меркурия; OTHER_REASON требует текста. Полный список кодов дан в 10. Текст и длины проверяются по внешнему профилю; значение из старого чек-листа 240 символов не заменяет подтверждённое ограничение INPUT-01. Возвратный эВСД создаётся через API и связывается с реальным возвращённым составом.

**Приёмка:** Без причины возврат не отправляется; внешний номер появляется только после подтверждения.

### FT-ARR-11. Прежняя ВСЭ и повторная ВСЭ

**Основание:** PDR-007; SC-028–032.

**Требование:** Блок прежней ВСЭ и выбор необходимости повторной показываются только при соответствующих сведениях эВСД. При «Требуется» обязательны свободные основание и № акта; тип акта не придумывается. При отсутствии прежней ВСЭ местная ВСЭ нужна без фиктивного решения о повторной.

**Приёмка:** С прежней ВСЭ без основания/№ акта нельзя завершить выбор повторной; без прежней ВСЭ скрытые поля не блокируют.

### FT-ARR-12. Переход после подтверждённой приёмки

**Основание:** PDR-006/007/013; SC-029/032/098.

**Требование:** Положительное подтверждение гашения открывает местную ВСЭ при её необходимости. Без повторной при прежней ВСЭ доступны сохранённая сверка и заключение по пригодному достаточному основанию. Неполнота прежнего основания не заполняется местным вымышленным номером; документ недоступен с причиной. Полный возврат не создаёт местную ВСЭ.

**Приёмка:** Таймаут Меркурия не открывает создание/печать; подтверждение ручного гашения позволяет продолжить тот же маршрут.

### FT-ARR-13. Транзакция и ярмарка

**Основание:** PDR-004/012; SC-013/014/058/059.

**Требование:** Обязателен выбор «По партии будет произведена транзакция: Да/Нет»; при Да обязателен тип «Внутренняя/Внешняя». При Нет тип не сохраняется как активное значение. «Ярмарка» необязательна, по умолчанию не отмечена. Оба признака сохраняются при сверке и доступны производным данным; сами транзакцию не выполняют.

**Приёмка:** Внутренняя партия проходит обычную приёмку и ВСЭ; ярмарка даёт 0 ₽ без гипотетического платного итога.

### FT-ARR-14. Подтверждение и неизвестный внешний исход

**Основание:** PDR-006/020; SC-027/098–101.

**Требование:** Состояния отправки, подтверждения, отказа и неизвестного исхода различаются в предметной модели и реализации external transport. При ошибке ввод сверки сохраняется. Двойное нажатие и повтор после таймаута не выполняют необратимую команду без проверки внешнего состояния. Ручное действие в Меркурии не подтверждается одним нажатием «выполнено» или введённым номером: нужна проверка факта и связи с эВСД. Отсутствие живого write-теста фиксируется как `not-run by O-13`, а не устраняется расходованием созданного ветеринарами эВСД; это не разрешает оставить submit нереализованным.

**Формирование XML:** `docInspection` следует документарной сверке, `vetInspection` независимо отражает проведённый осмотр (`CORRESPONDS/MISMATCH/UNSUPERVISED`), `decision` следует выбору пользователя. При допустимом несоответствии и `ACCEPT_ALL/PARTIALLY` обязателен `discrepancyReport`; при `RETURN_ALL` он не передаётся. `returnedDelivery` передаётся только для `PARTIALLY/RETURN_ALL`. Для электронного ВСД передаётся его UUID; принятый/возвращаемый состав строится из фактов сверки и повторно проверяется по закреплённому source checksum.

**Включение:** реализация содержит полный внешний submit и enabled-state UI. В установке `VETIS_WRITE_ENABLED` по умолчанию false; агент, тест, seed и миграция его не включают. После решения владельца оператор включает server capability, а уполномоченный пользователь явно подтверждает конкретное гашение. Дополнительное внешнее поштучное разрешение на UUID не требуется.

**Приёмка:** Обезличенные fixtures покрывают все шесть сочетаний соответствие/несоответствие × полное/частичное принятие/полный возврат, включая три результата ветосмотра. Проверяется production-код формирования, submit boundary, polling и reconcile через подменённый transport; после смоделированной потери ответа повторный submit отсутствует. Автоматизированная проверка требует ноль живых write-вызовов, но подтверждает наличие рабочего enabled-state. При отказе не показывается зелёный локальный успех.

### FT-ARR-15. Неизменность подтверждённой приёмки

**Основание:** PDR-004/006/020; R-03.

**Требование:** После подтверждения исходный принятый состав и аналитические признаки не меняются обычным редактированием ВСЭ. Исправление внешнего факта требует проверки интеграционного сценария, а не перезаписи полей карточки. Удаление местной ВСЭ не отменяет сверку/гашение.

**Приёмка:** Открытая старая сверка не перезаписывает уже подтверждённое решение; пересозданная ВСЭ получает те же принятые количества.
