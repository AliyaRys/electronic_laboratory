## 3. Альтернативы структуры и выбранный подход

Рассмотрены три структуры спецификации:

1. **По процессам лаборатории — выбранная.** Сохраняет сквозной смысл приёмки, исследования, решений и повторного осмотра; отдельные модули читаются с общими инвариантами. Удобна для трассировки PDR → ФТ → ADR → ТЗ.
2. **По экранам макета.** Удобна для первоначального перечня полей, но повторяет права/расчёты на каждом экране и наследует противоречия прототипов. Макеты использованы как вспомогательное свидетельство состава.
3. **По будущим техническим сервисам.** Преждевременно выбирает архитектуру и смешивает поведение со способом реализации. Технические границы будут предметом ADR.

Выбранный комплект делит систему на предметные части с понятной ответственностью. Не требуется один огромный план реализации всего комплекта: после ADR его можно разбить на последовательные проверяемые поставки, сохранив общий контракт.

## 4. Задание следующему агенту по ADR

**Вход:** весь комплект ФТ, его `sources/`, актуальные AGENTS.md и UI-контракты при работе над интерфейсом, результаты доступных INPUT/OPS. **Выход:** набор architecture design records с идентификаторами, контекстом, рассмотренными альтернативами, выбранным решением, последствиями, проверками и ссылками на конкретные ФТ. Слово «предложено» у R не терять при цитировании.

| Архитектурный вопрос | Что обязательно сохранить |
|---|---|
| Предметные данные и идентичность | Один входящий эВСД — одна партия; одна существующая местная ВСЭ; отдельные внешнее основание/осмотры/документы; FT-ARR-01/05/14, FT-VSE-01–03, FT-REP-02 |
| Доступ и аутентификация | Две роли, пять независимых прав, лаборатория/продукция, актуальность допуска; FT-ACC-01–15 |
| Сохранение и конкуренция | Нет дублей, атомарные операции, конфликт устаревшего сохранения, ручной уникальный номер без годового сброса; FT-VSE-02, FT-COM-05/06 |
| Интеграция Меркурия | Личный инициатор; реальное подтверждение; ручной обход при неудаче; сопоставление внешнего факта; FT-ARR-16–18, FT-DOC-05/06 |
| Расчёты/методика | Разные единицы первичного/повторного показателя, закреплённые основания в актуальной записи; FT-VSE-11, FT-CAL-01–11 |

Стек, БД, протоколы нашего API, разбиение на модули/сервисы, размещение, технический маркер актуальности, хранение секретов и механизм получения внешних результатов — решения ADR. Наличие минимальной технической проверки дубля не разрешает добавить автоматическое восстановление отправок или кабинет разбора ошибок.

## 5. Готовность к следующим этапам

- **Для обзора требований:** весь комплект написан, источники и предлагаемые детали различимы, критерии приёмки перечислены.
- **Для архитектурной проработки:** можно проектировать границы и альтернативы с явными INPUT; решения, зависящие от внешних данных, не объявлять окончательно проверенными до их получения.
- **Для финального ТЗ:** владелец проверил ФТ/R; получены применимые методики, цены, внешний профиль и печатные реквизиты; ADR привязан к требованиям.
- **Для официального запуска:** пройдена сквозная приёмка на реальной конфигурации, INPUT-01–04 и OPS-01 закрыты; организация подтвердила переход. Успешная сборка UI и этот документ сами по себе этого не доказывают.

Изменение принятого PDR оформляется адресно. Не требуется заново выбирать наличие архива, способ бумажной подписи, простую модель доступа, ручной остаток или каталог ошибок: эти решения уже приняты.
